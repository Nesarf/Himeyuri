板子这一侧：HMYR 在一个微控制器上跑
====================================================================

  2026-10-27 起。目标板是 Nucleo-F411RE（STM32F411RE，Cortex-M4F 96 MHz，
  Flash 512 KB，SRAM 128 KB）。这一页记的是「这条路走到哪儿了」，
  以及每一步用什么命令复现。

一、现在到哪一步
--------------------------------------------------------------------

    [成] 工具链进来：MSYS2 的 ucrt64 双栈

         pacman -S mingw-w64-ucrt-x86_64-arm-none-eabi-gcc make
         → arm-none-eabi-gcc 16.1.0、GNU Make 4.4.1

    [成] 编译：vm/hmyr.c 一行没改就编得过（除了那处 main，见第三节）

         text 161211 · data 8 · bss 3164（-Os，Cortex-M4）
         → 板子 Flash 512 KB，占三成

    [成] 在模拟器上跑通：QEMU 的 mps2-an385（Cortex-M3）

         examples/zone-ledger.hmoca 的完整输出（与板子上逐字一致）：
           行=4 总长=15
           各段=5,3,4,3
           关之前 held=5
           关之后 报告.live=1 zone=managed

         这个示例同时用上 arena、owned、managed 三区 —— 也就是说
         区模型在真 ARM 上是对的，不只是「打印了个数」。

    [成] 2026-10-28 烧上真板子并跑通

         同一份映像、同一个程序，串口（ST-Link 的 VCP，COM5，115200）
         读到四行输出与退出码 0。烧写用 OpenOCD：

           openocd -f interface/stlink.cfg -f target/stm32f4x.cfg \
             -c "program build/hmyr-board.elf verify reset exit"
           → device id 0x10006431 · flash size 512 KiB · Verified OK

         hello.hmoca 的判据也在真板上验过：串口读到 0x35（"5"），
         前面那一个 0xFF 是复位时线路上的伪字节，不是程序输出。

    [未成] 更小的栈：现在用的是 link.ld 里 8 KB 的栈（_estack 下方留的），
           而桌面上量到三区示例在 64 KB 栈下也跑得动 —— 板子上到底要多少，
           还没有逐档压过。

二、两个文件各自管什么
--------------------------------------------------------------------

    port/startup_cm4_gnu.s    向量表 + Reset_Handler（.data 拷贝、.bss 清零、bl main）
    port/link.ld              STM32：Flash 0x08000000 / RAM 0x20000000 / 栈顶 0x2001C000
    port/link-mps2.ld         MPS2：Flash 0x00000000 / RAM 0x20000000 / 栈顶 0x20100000
    port/arm-port.c           平台口：把「读字节码」与「写出口」换成内存里的两段
    port/board-main.c         板侧入口：装平台口、跑、把出口交给串口
    port/uart.c               Nucleo 的 USART2
    port/uart-mps2.c          MPS2 的 CMSDK UART
    port/Makefile             四根旋钮：CPU / UART / LDSCRIPT / PROGRAM

  两份串口、两份链接脚本、不是「一份带开关的」：三者都是「换芯片时要改的数」，
  而一个文件里放两套地址，最容易出的错是改了这边忘了那边。

三、为板子改的那一处
--------------------------------------------------------------------

    vm/hmyr.c 的 main 现在包在 #ifndef HMYR_BOARD 里。

    一条 #ifndef 就够，因为「这台机器与它跑在哪无关」这件事在 hmyr_运行 以下
    已经成立 —— 只有「从哪儿拿字节码、往哪儿写出口」是平台的事，而那两件
    本来就在 port/ 里。

四、怎么复现（三条命令）
--------------------------------------------------------------------

    在模拟器上跑（Cortex-M3）：

      cd port && make elf PROGRAM=examples/zone-ledger.hmoca \
        UART=uart-mps2.c LDSCRIPT=link-mps2.ld CPU=cortex-m3
      qemu-system-arm -M mps2-an385 -kernel build/hmyr-board.elf \
        -nographic -monitor none -serial stdio

    给板子编（Cortex-M4）：

      cd port && make elf PROGRAM=examples/zone-ledger.hmoca

    诊断用的心跳：编的时候加 -DHMYR_HEARTBEAT，程序会在输出之前先吐一个叹号。
    它把「没跑起来」与「跑了没话说」分开，而那是最费时间的一步。

五、三个已经踩过的坑
--------------------------------------------------------------------

    一、main 重复。vm/hmyr.c 有 main，board-main.c 也有 —— 链接器说 multiple
       definition。见第三节。

    二、objcopy 的符号名由「它看到的路径」决定。传 build/program.hmoks 会得到
       _binary_build_program_hmoks_start，而 board-main.c 等的是
       _binary_program_hmoks_start。差一个目录名就链不上，而弱声明的症状是
       「字节码是空的」—— 看上去像程序自己没跑。

    三、核不同。用 -mcpu=cortex-m4 编给 Cortex-M3 的 MPS2，M4 的 DSP 指令在 M3 上
       是未定义指令，症状是 lockup（R15 = 0，R14 = 0xfffffff9）。所以 CPU 是一根
       旋钮，不是一句优化选项。

六、下一步
--------------------------------------------------------------------

    ・真板子上验串口：烧一个只吐叹号的映像，看 ST-Link 的虚拟串口有没有反应。
      有反应，就说明 port/uart.c 那三个数（基址、引脚复用、BRR）都填对了。
    ・把 ST-Link 的烧写接进 Makefile（st-flash 或 openocd，看本机装哪个）。
    ・然后才是「更大的程序」：现在的三区示例只用了 bss 的一部分，
      而 bss 48128 字节已经是板子 SRAM 的三分之一 —— 下一次要量的是
      跑自举层那一格需要多少。

七、烧写与编译器：三个坑，都不是代码
--------------------------------------------------------------------

    第一个：驱动没装。板子插上之后 Windows 认出了设备，但 problem code 是 28
    （CM_PROB_FAILED_INSTALL），于是 pyocd 报 "No available debug probes
    connected"。而 Keil 的安装目录里自带那一套：

      D:\Keil_v5\ARM\STLink\USBDriver\stlink_dbg_winusb.inf   ← ST-Link Debug
      D:\Keil_v5\ARM\STLink\USBDriver\stlink_VCP.inf          ← 虚拟串口

    用 pnputil 装上（不需要 dpinst，它在这台机器上报了一个错误码）：

      pnputil /add-driver stlink_dbg_winusb.inf /install
      pnputil /add-driver stlink_VCP.inf /install

    装完之后 pyocd 能认到探针（STM32 STLink，唯一 ID 0666FF485282494867205545），
    虚拟串口也出现了（COM5）。

    第二个：pyocd 与这块探针不合。驱动装好、探针认得、串口也在，
    但 pyocd 仍然报 STLink error (5): No device connected；
    connect_mode=attach / pre-reset 与 frequency=1MHz / 100kHz 四种组合都一样。

    而同一个探针在 OpenOCD 下一次就通了：

      STLINK V2J28M18 (API v2) VID:PID 0483:374B
      Target voltage: 3.260887
      [stm32f4x.cpu] Cortex-M4 r0p1 processor detected

    所以「烧不了」这件事在换了后端之后就没了。现在 Makefile 的 flash 目标
    用 pyocd；真要烧的时候用 OpenOCD 那一行（第 4 节的命令），或者把
    PROBE 换成 openocd（这一条还没写进 Makefile）。

    第三个（2026-10-30 才发现，原来是「三个坑」）：PATH 里缺 ucrt64/bin 时，
    arm 编译器静默退出。症状是 make elf 报 "Error 1"，一行诊断都没有；
    单独跑那一条 gcc 也是返回 1、没有输出。原因在 cc1.exe —— 它要
    ucrt64/bin 里的几个 DLL，而 DLL 找不到的时候 Windows 不打印任何东西，
    退出码 1 于是成了唯一的线索。

      export PATH=/d/msys64/ucrt64/bin:$PATH

    这一条值得写下来，因为它长得像「代码编不过」，而实际上代码一个字没动。
    同一类症状在 mingw32 那一侧也见过：32 位 gcc 的 cc1 同样是静默退出。

八、读串口时的两个讲究
--------------------------------------------------------------------

    一、复位与读取要同时进行。程序跑得比人快：main 返回之后才吐字节，
       而那时候串口工具往往还没打开。所以要先开串口、再复位，
       在 3 到 4 秒的窗口里收字节。

    二、收到的第一个字节常常是 0xFF。它不是程序输出，是复位时线路上的
       伪字节（起始位被当成数据）。判据要看 0x35 而不是看「有没有东西」。

    QEMU 的 stm32f4 模型里 USART 的 TXE 不置起，所以那条路只能验到
    「程序跑完」，验不到「串口通」—— 串口这件事只有真板子能验。

九、天花板：一个数字，和一处说不通的地方
--------------------------------------------------------------------

    量法在 tools/heap-census.mjs：编字节码、在桌面那台 C 机器上带 HMYR_MEM=1 跑、
    读它打印的堆峰值，再与板子的 128 KB 比。

      板子：SRAM 131072 字节 · 栈 8192 · 静态段 48128

      程序                    字节码      堆峰值      合计需要      判据
      hello.hmoca               70 B      92144     148464 B    差 17392
      arith.hmoca              485 B     103983     160303 B    差 29231
      zone-ledger.hmoca        985 B     131745     188065 B    差 56993
      twice.hmoca              202 B      97524     153844 B    差 22772
      view-window.hmoca        772 B    1237359    1293679 B    差 1162607

    按这张表，连 hello 都装不下 —— 而 hello 在板子上是真的跑通了（串口读到 0x35）。
    两件事同时为真，说明这张表量的不是板子上的那一件事。

    2026-10-28 验到底之后，结论与一开始猜的不一样，而两次猜错都记在这里。

    第一次猜「诊断自己在分配」。理由看着很顺：HMYR_MEM 要记下每次分配才能打印，
    而那份记录住在堆上。但把「不带诊断的峰值」量出来之后（HMYR_HEAP_ONLY=1，
    它只读那个一直在记的数），同一个 zone-ledger 在桌面上是 131635 字节，
    而带诊断是 131745 —— 只差 110 字节。诊断几乎不占地方，这条猜测不成立。

    第二次才找到成因：字长。桌面是 x64，指针与 size_t 都是 8 字节；
    板子是 Cortex-M4，两者都是 4 字节。而 VM 的堆上一大半是「值的容器」——
    值槽、元组项、记录字段 —— 它们在 64 位上每一项都从 8 字节起算。
    同一个 zone-ledger：桌面 64 位 131635 字节。

    第三次：字长只解释了一半。装 MSYS2 的 mingw32 工具链编出 32 位的宿主
    （PE32，Intel i386），同一个程序在新宿上是 75343 字节 —— 从 131635 掉到 75343，
    少了 43%，方向对。而板子上是 39322，比 32 位桌面还少 48%。
    两个都是 4 字节指针，所以「字长」不是唯一的差别。

    剩下的那一半，2026-10-28 用直方图找到了落点。

    做法：给 vm/hmyr.c 加一层分配直方图（按 8 字节一档，24 档，只在
    HMYR_MALLOC_HIST=1 时统计），并把它暴露成三条接口给裸机那一侧读
    （hmyr_分配档 / hmyr_分配档数 / hmyr_开直方）—— 板子上没有 stderr，
    所以诊断要能「被读走」而不是「被打出来」。board-main.c 在 heap= 之后
    多打一行 hist=。

    同一个 zone-ledger，两边各读一次：

      板子      0:55  8:72  16:22  24:3   32:3   48:2  56:51  112:4  184:12
      桌面 32 位 0:26  8:19  16:30  24:54  32:23  40:1  48:1  56:50  64:2  72:1  88:1  112:4  184:15

    读法：24 到 31 字节那一档，桌面分配了 54 次，板子上只有 3 次；
    而 0 到 15 字节那一带，板子比桌面多出约 80 次。总次数差不多（两边都是三百多次），
    所以不是「多分配了」，是「同一批分配在两边落进了不同的档」——
    桌面把某样东西当作 24 到 31 字节来要，板子上只要 0 到 15 字节。

    下一层：按调用点分桶。做法比预想的便宜 —— 不需要返回地址，也不需要 backtrace：
    把 hm_malloc / hm_calloc 包成宏，让 __LINE__ 作为参数传进去。它是编译期常数，
    传一次是一个立即数；关掉统计时编出来的代码与原来那次调用没有区别。
    board-main.c 在 hist= 之后多打一行 lines=，桌面上那条由 HMYR_MALLOC_HIST 打。

    同一个 zone-ledger，两边的 lines 各读一次（板子的行号与桌面不同，
    因为 -DHMYR_BOARD 让整个文件的 #if 分支变了，所以只能比次数，不能比行号）：

      板子      heap=39322  hist= 0:55 8:72 16:22 24:3 32:3 48:2 56:51 112:4 184:12
                lines= 1419:1 1280:46 1426:1 1427:1 1430:1 352:3 1063:1 801:95 4470:37 1088:13
      桌面 32 位 heap=75155  hist= 上面那张（24:54 / 32:23）
                lines= 4593:1 1419:1 1280:46 1426:1 1427:1 1430:1 352:3 1938:117 1893:1 1894:1 4470:37 4489:17

    能对上的站点有四个：1280（46 次）、352（3 次）、4470（37 次），以及 1419/1426/1427/1430
    那几个各一次的。对不上的那个是 GC：桌面上是 1938 行的 gc_分配 117 次，
    板子上是 801 行的同一个函数 95 次。

    而 1938 行那一句是 hm_malloc(sizeof(Gc块) + 字节) —— 也就是说，
    24 到 31 字节那一档就是 GC 块：16 字节的头加 8 到 15 字节的载荷。

    所以「差一半」的成因现在是这一句：那一档是 GC 块，而板子上的 GC 分配
    比桌面少 22 次（95 对 117）。而 24 到 31 那一档差 51 次（3 对 54）——
    两个数不一样，说明「少 22 个 GC 块」解释不了「少 51 个小块」。

    到此为止，而停在这里的理由要写清：再往下要回答「板子为什么少分配 GC 块」，
    而那要先确定「哪些载荷在板子上根本不产生」。那需要给 gc_分配 的每个调用者
    也编号（它有三个主要调用者：字符串、元组、记录），并再烧一次。
    那一步是可做的，但它是「继续调试」而不是「回答能跑多大的程序」——
    而这一节要回答的是后者，它已经有答案了：39322 字节，装得下。

    第三次：按种类分开。gc_分配 本来就有种类这个参数（0 值槽、1 字符串、
    2 索引项、3 索引），所以不用再编一套编号。桌面 32 位那一台给出：

      kinds: 0:1/56B  1:95/930B  2:8/9216B  3:13/260B

    种类 1 是 95 个、930 字节的字符串载荷 —— 平均 9.8 字节。而 GC 块的头是
    16 字节（一个指针、一个 size_t、一个 uint32 的标记、一个 uint8 的种类，
    对齐到 4）。所以每一个字符串块都该是 16 + 8 到 15 字节，也就是全都落在
    24 到 31 那一档。桌子那一台确实是 54 个落在那档（95 个字符串块里的一部分
    加上别的种类），而板子上那一档只有 3 个。

    这里有一个说不通的地方，写下来而不是绕过去：95 个字符串块，而 24 到 31
    那一档只有 3 个。两种可能，都没有验：
      一、板子上的 sizeof(Gc块) 不是 16（-mthumb 下 uint8 的对齐可能不同）。
         若是 8，那 95 个字符串块会落进 16 到 23 那一档 —— 而板子上那一档是 22 个，
         仍然对不上 95。
      二、板子上的 hist 与 kinds 不是同一批分配（比如 kinds 记的是全部 117 个，
         而 hist 只记了其中一部分）—— 而两个计数器都在 hm_malloc 里，按说不会。

    第四次：种类 × 档。桌面 32 位那一台给出：

      kindband 0: 72:1
      kindband 1: 16:29 24:53 32:9 40:1 48:1 64:2
      kindband 2: 184:8
      kindband 3: 32:13

    这张表把「95 个字符串块」拆开了：24 到 31 那一档的 53 个几乎全是字符串
    （加上值槽那一个，正好是整张 hist 里的 54）。所以那一档的成因现在没有疑问：
    它是字符串 GC 块，头 16 字节加载荷 8 到 15 字节。

    而板子上这一张表取不到，具体是这样：接口声明补齐之后 kinds= 那一行打出来了，
    但内容是空的（kinds= 后面直接换行），也就是 hmyr_种次 依次返回 0，
    而同一个二进制里 lines= 明明报着 841:95（95 个 GC 块）。
    kindband 那几行同样一行也没出来。

    顺着「kinds 为什么是空的」查下去，答案一次说清了三处说不通的地方：

      vm/hmyr.c 里 gc_分配 有两个定义：
        #if defined(__arm__) ...  →  { (void)字节; (void)种类; return NULL; }
        #else                     →  真的分配一个 GC 块
      也就是说板子上不编 GC 堆，gc_分配 是个桩。

    而字符串走的是这一条：

      static uint16_t *串存(size_t 码元数) {
        if (g_gc开) return gc_串分配(码元数);   // 桌面走这里：带 16 字节的块头
        else { malloc(码元数 * 2) ... }         // 板子走这里：裸载荷，没有头
      }

    于是三处都说通了：
      一、kinds= 是空的 —— 板子上 gc_分配 一次也不真的分配，g_种次 自然是零。
      二、板子上 lines= 里那个 841:95 不是「95 个 GC 块」，是 841 行的 malloc ——
         而 841 行正是上面那个 else 分支。两边都是 95 次，因为都是同一批字符串，
         只是桌面给它加了 16 字节的头、板子没有。
      三、24 到 31 那一档板子上只有 3 个：那 95 个字符串在板子上是 2 字节每码元的
         裸载荷（平均 9.8 字节），落在 8 到 23 那几档；而桌面是 16 加 9.8，落在
         24 到 31。差的那一半不是「板子少分配」，是「板子没有块头」。

    这就是成因。而它顺带回答了更大的一层：板子比 32 位宿主少一半，主要不是字长，
    是没有 GC 堆 —— 没有块头（每一块 16 字节），也没有值槽、索引项、索引
    各自的登记。95 个字符串上的块头是 1520 字节，而总差约 35833；剩下的是
    「GC 不编」这件事本身省下来的。

    所以这一整条线到这里是完整的：
      板子上没有 GC：gc_分配 是桩，字符串与数组直接 malloc。
      24 到 31 那一档是「字符串加 GC 块头」，而板子上没有那个头，所以那一档几乎空。
      39322 字节是这么来的，而它装得下这四台之外的第五台 —— 那块板子。

    所以这一节停在两个明确的句子上：
      一、24 到 31 那一档是字符串 GC 块 —— 有证据：两边都读到 hist，桌面还读到 kindband。
      二、板子上那一档只有 3 个 —— 事实；而为什么只有 3 个，还没有证据。
    第二句要的东西已经写清：板子上也要能读到 kindband 那一行，而它现在读不到。

    所以那张表现在说明的是：64 位的上界、32 位宿主的中界、板子在它下面，
    而「板子比 32 位宿主还少一半」这件事已经从「一团雾」变成「24 到 31 字节那一档」。

    三条各自的地位，改过之后是这样：

      一、带边界的 _sbrk 是真的改进了：越界从此是分配失败，而不是悄悄踩栈。
         这一条留在 port/arm-port.c 里，与量得准不准无关。
      二、heap-census 那张表要读成「64 位的上界」。它还没有改成读 HMYR_HEAP_ONLY，
         所以表里是带诊断的数 —— 而那个数只比真数多 110 字节，不影响结论走向。
      三、32 位宿主是一个参照，不是答案：75343 对板子的 39322，两个都是 4 字节指针，
         差的那一半还没找到成因。它证明的是「字长有用」，不是「字长够了」。
      四、view-window 那一行是另一件事：它的堆峰值 1.2 MB（64 位），
         因为 read_bytes 把 11 KB 读成字节元组，而每个元素在堆上是一个值。
         板子上跑不了它，而那与 128 KB 无关 —— 是「字节元组」这个表示
         在微控制器上太贵。

    一、复位与读取要同时进行。程序跑得比人快：main 返回之后才吐字节，
       而那时候串口工具往往还没打开。所以要先开串口、再复位，
       在 3 到 4 秒的窗口里收字节。

    二、收到的第一个字节常常是 0xFF。它不是程序输出，是复位时线路上的
       伪字节（起始位被当成数据）。判据要看 0x35 而不是看「有没有东西」。

    QEMU 的 stm32f4 模型里 USART 的 TXE 不置起，所以那条路只能验到
    「程序跑完」，验不到「串口通」—— 串口这件事只有真板子能验。

十、板子上的那条规矩：一个区，别在循环里建
--------------------------------------------------------------------

    既然板子上没有 GC（第九节），那「分配」在板上就是单向的：拿了不还。
    语言里唯一能一次还清的是 arena，而它的用法在板上有一个硬边界。
    这一节记的就是那条边界，连同我是怎么撞到它的。

    第一版示例：50 轮，每轮建一个区、轮末关掉，每轮里分 8 块。
    桌面上跑得很好（轮=50 累计=497 最宽=13）。板子上没有任何输出 ——
    串口读到的是四百多个零字节，而那不是输出，是线路噪声。
    连上调试器看 PC，它停在 arm-port.c 的 exit 里 —— 那是 hm_malloc 失败之后
    走的死循环。也就是说：内存耗尽了。

    而装载器早就说过这件事：HMYR-載-016，「an arena is built inside a loop:
    every round allocates a new one, so the total grows with the number of rounds」。
    第一条判据是它，而我没听 —— 那份示例正是它的反例。
    桌面上看不出来，因为关掉的区会被回收器收走；板子上关掉只是标成关，
    那块内存还在。

    第二版：循环外面建一个区，里面分 200 块，最后关一次。桌面上跑通。
    板子上又是零字节 —— 200 块加上块头超过了板上能拿到的量。

    第三版：同一个形状，20 块。板子上跑出来了，与桌面逐行相同：

      块数=20
      总长=111
      最宽=11
      关之前 held=20
      关之后 报告.live=1 zone=managed
      heap=58084

    所以板子上的规矩，写清楚是两句：
      一、arena 在板上是能用的，但它的容量就是板上能拿到的那么多（这一份 20 块、
         总长 111 字节、堆峰值 58084）—— 它不是无限的，而超了之后的表现是
         「串口什么也没有」，而不是一条说得清的错。
      二、别在循环里建区。HMYR-載-016 说的就是这条，而它在板上比在桌面上严重得多：
         桌面上那是浪费，板子上那是跑到一半就没了。

    示例在 examples/arena-on-board.hmoca。

十一、边界表：这块板子装得下多少

      块数    heap 峰值    装得下
      20       37434       是
      30       56730       是
      40       69370       是
      45       75690       是
      50       失败        不（堆已用 81768，它想再要 4096）

      一、这一份程序在板上能到 45 块，heap 峰值 75690 字节。

    那是一条小改动，但它会让这张表从「沉默」变成「说清」，所以它值得做 ——
    只是不在这一页，而进了下一轮。

[改] 2026-10-28 当天晚些时候：那条「沉默」已经被改成一句可读的话了。

  做的事：Hmyr平台 加了第三个回调 错误。有它的时候，要命的事走它
  （板侧那份 板子错 逐字节交给串口）；没有的时候退回 fprintf(stderr)，
  所以桌面上的行为一个字节没变。

  而 hm_malloc 那十几处原有的 fprintf + exit 全部换成 分配失败()，
  它报的是当时的堆峰值而不是这一次要了多少。理由：失败点在十几个地方，
  逐个传「要多少」会把改动散到十几个函数里；而「堆到哪儿了」是同一件事，
  且它更能说明「这个程序超出了这块板子多少」。

  同一份 50 块的映像，现在串口上读到的是这一行（44 个字节）：

    hmyr: out of memory, heap peak 90308 bytes

  而 20 块那一版照旧：块数=20 … heap=58084，逐行与原来相同。

  于是这一页那张表的两格「没有输出」从今天起应该读作「有一行文字」——
  而它仍然不是一条错误编号：这一层没有编号体系，它是一台机器在停下之前
  最后说出的一句话。

十二、自举层能不能装进那块板子：量了一次，答案是不能
--------------------------------------------------------------------

    这一节要回答的是一个具体的问题：Nucleo-F411RE 那块板子上，能不能跑自举层
    （self/ 里那几份），也就是「这块板子上跑的是 HMYR 自己」这件事能不能成立。
    做法是先量，不是先写。

    一、最小的一份由哪几份构成

      self/run.hmoca 的 import 是五份：lex、chain、stmt、body、eval。
      run 自己是启动器（读 argv、读文件、调进去），所以「读一份 .hmoca 并求值」
      真正要的是那五份。六份（加 run）是「连启动器一起」。

    二、它们编出来多大（实测，不是估的）

      node bin/hmyr.mjs --compile self/pack.hmoca <输出> self/lex.hmoca \\
        self/chain.hmoca self/stmt.hmoca self/body.hmoca self/eval.hmoca

        五份  →  71212 字节（279 个块）
        六份  →  90131 字节（353 个块）

      而 Flash 是 512 KB，所以字节码本身装得下 —— 装不下的话会是另一件事。
      真正的问题在 RAM：那台机器要把整份字节码读进来，建函数表与字符串池。

    三、读进来要多少 RAM（实测）

      把 five.hmoks 直接当 program.hmoks 烧上去（跳过编那一步），读串口：

        hmyr: out of memory, heap peak 91712 bytes

      也就是说：读到一半就耗尽了。而 91712 不是峰值，是失败点 ——
      真实需要量比它更大。

    四、与已知的几个数比

      20 块的 arena 示例      heap 58084   装得下
      30 块                   heap 75332   装得下
      40 块                   没有输出      装不下
      五份自举层              读到 91712   耗尽

      所以「读一份五份构成的自举层」要的 RAM，比这台机器上任何跑通过的程序都多。

    五、结论

      不能。 以现在这个读法（整份字节码读进 RAM、建完整的函数表与字符串池），
      五份自举层在这块板子上装不进来 —— 而且不是差一点，是差得比「30 块到 40 块」
      那一步还多。

      若要做成，可走的路只有一条：不整份驻留。让那台机器从 Flash 里按需读
      指令（函数表只放偏移与长度，字符串池按需解），于是 RAM 里只有「当前帧」。
      那是一次真正的改动：vm/hmyr.c 的读法要从「读进内存」变成「贴着 Flash 读」，
      而板子上 Flash 是可直接寻址的（0x08000000），所以那条路在硬件上成立。

      不做的事：换一块更大的板子。那会让「装得下」变成一个外部条件，
      而这一节要问的是「这台机器能不能」，答案是它现在的读法不能。

    这一节的用法：下次有人问「板子上能跑 HMYR 自己吗」，答案是
    「字节码装得下（71212 字节对 512 KB），而读法装不下（91712 就耗尽）」。

十三、以后可能加的两块存储：把这条路先画出来
--------------------------------------------------------------------

    2026-10-28 记：以后可能会给这块板子加两块 SPI 存储 ——
    W25Q256JVEIQ（32 MB，QSPI NOR Flash）与 MX35LF1GE4A（128 MB，SPI NAND Flash）。
    而现在按「只有 Nucleo-F411RE」来做：这一节不改任何代码，它写的是一条以后的路，
    以及那条路与第十二节那个结论的关系。

    为什么它值得现在就写：第十二节量出来的结论是「读法装不下」——
    五份自举层的字节码 71212 字节，而读进来要的 RAM 超过这块板子能给的
    （读到 heap 峰值 91712 就耗尽）。那一节给的唯一出路是「不整份驻留，
    贴着 Flash 读」。而 F411RE 自己的 Flash 是 512 KB，装得下字节码 ——
    也就是说那条路今天就在硬件上成立，不必等任何新零件。

    那么两块存储带来的是什么：不是「能不能」，而是「能放多少」。

      W25Q256JVEIQ   32 MB   QSPI NOR   —— 够放几十份字节码，且 NOR 可直接寻址执行
      MX35LF1GE4A    128 MB  SPI NAND   —— 更大，但 NAND 要坏块管理与页读，
                                           不能像 NOR 那样当地址空间用

    而 F411RE 的 SPI1 到 SPI5 都还空着，所以接上去在引脚上不冲突。
    这一页不写接线与驱动 —— 那些等零件真的到了再写，而那时要先回答三个问题：
    一、那块存储是从 SPI 还是从 QSPI（F411 只有 SPI，QSPI 要软件模拟或用 F446）。
    二、字节码放在外部存储上时，读它的是 hmyr_运行 的哪一层（现在那一层假设整份在内存里）。
    三、写一份字节码进去的工具在哪一侧（现在 write_bytes 写的是宿主文件系统）。

    所以这一节现在的状态是：画在那里，不施工。而它画在那里的理由不是「以后可能有用」，
    是「第十二节的那条出路，与这两块零件是同一件事的两半」——
    一半是读法（软件），一半是存储（硬件）。

[改] 2026-10-28 晚些时候：这一节多了一层量测，而它把问题指到了具体一个函数上。

    加了 HMYR_LOAD_ONLY=1（装载完就停、只报装载本身），于是「装完再跑」那个
    合起来的数被拆成两半。同一个 five.hmoks（71212 字节）在 32 位桌面上：

      只装载        1075474 字节
      装载加跑      1124904 字节
      于是「跑」      49430 字节

    也就是说：装载占 96%。瓶颈不在执行，在 load_program —— 它把整份字节码
    解成 Func 数组、每函数一个 Ins 数组（每条指令一个结构体）、以及一个名字池。
    而板子上失败在 91712，那是在这个解码过程的中途。

    所以第十二节那条出路现在可以说得更准：要改的不是「跑起来怎么省」，
    是「读进来怎么省」。而具体是别把 Ins 数组解出来 —— 指令留在字节流里，
    执行时按偏移解一条。名字池同理：只记偏移，用时才解码。

    不做的事：把 Ins 结构体压小。那能省一半，而省一半不够 —— 32 位桌面要 1.07 MB，
    板子 128 KB，差八倍。压结构体是修边角，不整份驻留是换形状。

[改] 2026-10-28 深夜：这一刀落下去了 —— 装载不再建 Ins 数组。

    做法：Func 里 code 那个数组换成 code_at（每条指令在字节码里的偏移），
    装载时只记偏移、用 读一条(&r, NULL) 扫过；执行时按偏移现场解一条。
    指令序号不变，所以字节码格式与两台机器之间的通用性都没动。

    量出来的（32 位桌面，同一份 five.hmoks 71212 字节）：

                    改之前      改之后
      只装载        1075474  →  186350   降 82.7%
      装载加跑      1124904  →  236412   降 79.0%

    板子上（把 five.hmoks 直接当 program.hmoks 烧）：

      改之前  hmyr: out of memory, heap peak 91712 bytes
      改之后  hmyr: out of memory, heap peak 67420 bytes

    而这两个数不能直接比：它们都是失败点（当时已经用掉的量），不是峰值。
    能说的是可用上界在 67420 与 75332 之间 —— 后者是 arena 30 块那一版的峰值，
    而它跑通了。所以现在差的是「还差一点」，不是「差八倍」了。

    剩下的大头是名字池：每个名字一份 UTF-16 副本，而装载时 pool_add 一份都不省。
    下一刀在那儿 —— 池也只记偏移，用到时解码。而 code_at 那张表（每条四字节）
    是这一刀付出的代价，它与「不建 Ins 数组」是同一件事的两面。

    一并删掉的东西：GC 不再需要标指令里的常量值（那些值不在这台机器的堆上了）。
    代价写在 gc 那一处：非空的元组常量会每次执行 CONST 都解一次，从而每执行一次
    泄漏一份 —— 而现有语料里没有那种常量，所以先这样。

[改] 2026-10-29：code_at 从四字节压成两字节（段内偏移），而它揭示了一件更要紧的事。

    做法：Func 加 code_base（这个函数的指令流在整份字节码里的起点），
    code_at 存段内偏移（uint16）。越界会在装载时报出来并停下 ——
    悄悄截断会让执行跳到错的指令上，那种错查起来最费时间。

                    改之前      改之后
      只装载        186350  →  163548   降 22802（约 22.8 KB，与预估的 28 KB 接近）
      装载加跑      236412  →  213610   降 22802

    而板子上：

      改之前  hmyr: out of memory, heap peak 67420 bytes
      改之后  hmyr: out of memory, heap peak 66938 bytes

    只降了 482 字节。这个「只降 482」是个有用的负数证据：

    板子上的失败点在 code_at 分配之前。桌面省下的 22.8 KB 在板子上没有出现，
    因为板子还没走到那一张表就停了 —— 它在更早的某一步耗尽。
    而更早的几步是：函数表那个 calloc、每个函数名字的 rd_str 副本、
    效果表的两张 calloc、以及名字池。

    所以现在两条数的关系要说清：
      桌面装载全量      163548 字节
      板子可用上界      66938 到 75332 之间（后者是 arena 30 块的峰值，跑通了）
    差约 2.3 倍。也就是说从 1075474 压到 163548（降 85%）之后，还差两倍多。

    下一刀落在那四样里最大的那一样上，而这件事要在板子上量而不是在桌面上：
    桌面省了 22.8 KB 而板子只降 482，说明两个平台的瓶颈不是同一个地方。
    做法：给装载的每一步加一个 HMYR_LOAD_TRACE=1 的标记（几步各报一次堆峰值），
    板子上也能读 —— 那比在桌面上猜便宜。

[改] 2026-10-29：装载分步跟踪建好了，而板子给出第一个数据点。

    机制：vm/hmyr.c 里有 hmyr_开装载跟踪()，开一次之后在装载的几步各报一次
    「到这一步为止的堆峰值」。它是一条接口而不是环境变量 —— 板子上 getenv 返回 0。
    board-main.c 在 HMYR_LOAD_TRACE 编译期开关下打开它，于是串口上直接读得到：

      loadstep 函数表=5364
      hmyr: out of memory, heap peak 66936 bytes

    这一对数字说的是：函数表那一步只花了 5364 字节，而接下来「读每个函数」
    （名字、效果表、code_at）累积到 66936 才耗尽 —— 也就是说那 149 个函数
    读下来要六十多 KB，平均每个四百字节出头。

    这与 code_at 压两字节时「桌面省 22802、板子只省 482」是同一个结论的两种说法：
    板子卡在「读函数们」那一段，而 code_at 只是那一段里的一部分。

    下一个落点因此很清楚：不是再压某一张表，是把 code_at 本身换掉。
    可选的做法里最省的一种是分段表 —— 每 64 条指令记一个绝对偏移，
    段内执行时顺着字节流扫最多 64 条。表从三十 KB 降到半 KB 以下，
    代价是每条指令要多扫几十字节。那是一次执行循环的改动，与这次同一个形状。

    不做的事：把名字池也改成偏移。名字池在桌面上的份额不大（rd_str 那一处
    三千次分配、按档估算约二十 KB），而板子上先耗尽的是别处 —— 先动大头。

[改] 2026-10-30：分段表落下去了，而它把「两次失败点互不相容」解开了。

    做法（vm/hmyr.c 的三处）：

      Func          code_at（每条指令两字节）  →  seg_at（每 64 条一个四字节）
      装载          每条记一次偏移              →  每 64 条记一次
      执行          查表即得                   →  查表 + 一条「下一条的起点」缓存

    代码段宽是 64：跳转时从段头顺着字节流扫过最多 63 条，顺序执行则命中缓存。
    缓存放在帧里而不是机器里 —— 同一个函数递归时每一帧各有自己的位置。

    桌面上的数（同一台机器、同一个编译器，为了能比，把上一版另外编了一份）：

      上一版   load=183664
      这一版   load=162538
      省       21126

    而板子上第一次读出来的，是一个更难看的数（串口原文，行首那个问号是线路噪声）：

      ?loadstep ?????????=5960
      hmyr: out of memory, heap peak 53796 bytes

    那九个问号是「函数表」三个字在串口上变成的 —— 源码那一行是 UTF-8，
    而替换发生在别处，还没查到；数字不受影响，所以先记在这里。

    53796 比上一轮那个 66936 更早。一个省了二十多 KB 的改动，在板子上反而更早
    撞墙 —— 这句话本身说明「堆峰值」这个判据不足以回答「板子上还剩多少」。

    于是失败那一行多了两个数：这次要多少（want）、一共分了多少块（blocks）。
    板子第二次读：

      hmyr: out of memory, want 0 live 53796 peak 53796 blocks 3431 bytes

    三个数在这一行里各自说了一件事。

    一  统计学不是真实占用。live 与 peak 都是「请求量之和」，而真实堆里每一块
        还有四字节的头与分配器的元数据。3431 块，每块按十二字节算是四十一 KB ——
        那一截从来不在 live 里。两块板子上的失败点（53796 与 66936）因此不矛盾：
        它们是两次撞墙时的请求量，真实占用两边都已经到顶。

    二  want 0 是堆真的满了。请求零字节也失败，说明失败已经与请求大小无关 ——
        剩下的不是「某一次要得太多」，而是「一块都分不出来」。

    三  所以下一个落点是块数，不是字节数。三千四百多块里，三千次是 rd_str 的
        名字副本（上一轮直方图里那一句 1324:3013 就是它）。名字池改成「记偏移、
        用到时再解码」之后，块数会从三千四降到几百 —— 光省下的块头就是四十 KB
        这个量级，而这一轮的分段表只省了二十一 KB 的载荷。

    一处自己写错的话，在这里更正：上一轮记的「四处裸 calloc 不在 hm_malloc 那条路上」
    是错的。vm/hmyr.c 的 494 到 497 行把 malloc、calloc、realloc、free 四个名字
    全都换成了带统计的版本，所以装载里没有裸分配。那一轮看到的「差 145 KB」
    与这一轮看到的是同一件事的两面：差在块头与元数据，不在有没有记账。

十四、装进去了：名字池不再复制，五份自举层在这块板子上跑完了
--------------------------------------------------------------------

    上一节最后那句「下一个落点是块数」在这一节变成了结果。

    做法（vm/hmyr.c）：名字池只记两样东西 —— 这个名字在字节流里的起点（偏移）
    与它的码元数。取值用一条读两字节的算式（名码），要 uint16_t* 的旧接口
    用 池取到 解到栈上，而记录字面量的字段名那种要长期持有的用 名复制。
    函数名与效果名同样改成偏移（Func.name_off / effect_offs）。

    桌面上的装载，四个数连成一条线（同一台机器、同一个编译器）：

      一开始（每条指令一个 Ins 结构体）   1075474
      Ins 不建了（指令留在字节流里）        186350
      code_at 压成两字节                    163548
      分段表 + 名字池零拷贝                 124432

    而板子上的两轮读数，才是这一节要记的东西。

    第一轮：装载走完了，卡在第一次压栈。

      ?loadstep 函数表=5960

      loadstep 全局名=50450

    三个 loadstep 全都打出来了 —— 这是第一次「装载整份跑完」。块数从 3431
    降到 1251。而失败落在装载之后：want 14336，行号 393（那是 hm_realloc
    收到空指针时的分支，真正的调用点是 push 里第一次扩栈）。
    Value 是五十六字节，256 个就是 14336 —— 桌面上的初始栈容量，在板子上
    正好是它剩下的全部。

    第二轮：把初始容量按平台分开（桌面上仍是 256，板子上 64），再烧：

      7

    lines 那一行里，1489 是 名复制 那一处（九百零四次），而 1648 到 1662

    一  块数才是板子上的那个变量。三千四降到一千二，省下的是每块十二字节的

    二  字节数的账要一路记下来。1075474 到 124432 不是一次做成的，中间三个数
        各自对应一次改动，而每一次都在板子上量过。

    三  板子上最后一个瓶颈不在装载里，在执行期的第一次扩栈。装载成功不等于
        程序跑得起来 —— 那一行 want 14336 与失败点只差一步，而它属于另一件事。

    第三步：装载时连值都不构造（2026-10-30 晚些时候）。

    loadstep 那一行，读出来的是：

      loadstep 函数们=50450 blocks 1248

十五、两份新读数：一个真程序的逐字节比对，与六份的那一句 hard fault
--------------------------------------------------------------------

    这一节的两件事都是「让板子上的东西可以被核对」，不是「多跑一个程序」。

    一、真程序：串口字节与桌面 stdout 逐字节相同

    示例 examples/board-run.hmoca 只用语言自己这一侧的东西：循环求和、
    元组索引、字符串拼接与长度。它不碰文件系统，也不碰托管区 —— 板子上没有 GC。

    桌面两处都跑过（默认路径与 C 机器），四行输出：

      和=55
      首项=3 三项之和=15
      名=ヒメユリ 长=4
      串=ABCDE

    板子串口上读到的原始字节（十六进制，前两段完整，后两段照抄）：

      ff e5 92 8c 3d 35 35 0a
      e9 a6 96 e9 a1 b9 3d 33 20 e4 b8 89 e9 a1 b9 e4 b9 8b e5 92 8c 3d 31 35 0a
      e5 90 8d 3d e3 83 92 e3 83 a1 e3 83 a6 e3 83 aa 20 e9 95 bf 3d 34 0a
      e4 b8 b2 3d 41 42 43 44 45 0a

    头一个字节 ff 是线路噪声（每次接上串口都会有），其余逐字节就是那四行。
    之后是退出码字符 0，再之后才是板侧自己的 heap、hist、lines 那几行。

    二、上一节写的那句「替换发生在别处，还没查到」是错的

    问号不在固件里，在读的那一端：SerialPort 的默认编码是 ASCII，非 ASCII 字节
    在 ReadExisting() 那一步就已经变成问号，再按 UTF-8 编回来当然是 0x3f。
    改成按字节读之后，loadstep 的中文与程序输出的中文一次全对。

    把这一条记下来的理由：上一节把结论指向固件，而固件一直是对的。
    错的是「谁在看」，不是「谁在写」。

    三、六份自举层：装载成功，执行时栈溢出

    run.hmoks（六份，88139 字节）烧上去，串口读到的：

      ?loadstep 函数表=8040 blocks 1
      loadstep 函数们=43792 blocks 606
      loadstep 全局名=43792 blocks 606
      hmyr: hard fault (stack past its reserve, or a bad access)

    装载走完了：峰值 43792、606 块（五份是 40996 与 450，六份只多一点）。
    而执行时栈溢出 —— 调试器读到的寄存器是 pc 0x00000000、msp 0x1ffff828，
    而 SRAM 从 0x20000000 起，MSP 落在它下面。run.hmoca 的 main 会调用求值器，
    而求值器是递归的。

    四、为了让这句话说得出来，补了两条

    一  执行期的失败也走平台口。run_bytecode 里那两处 fprintf(stderr) 在板子上
        是空路，于是「步数超了」「取不到字段」这类错误一个字节都不出。
    二  启动文件的向量表补上 HardFault_Handler，它写一行然后停住。在那之前，
        栈溢出与「程序根本没跑」在串口上长得一模一样。

    两条都在桌面上零影响：报错出去 没有平台口时退回 fprintf(stderr)。

    五、所以六份的结论是一句关于两支账的话

      装载要堆      六份 43792 字节，装得下
      执行要栈      求值器的递归深度，八 KB 不够

    而这两支账在同一片一百二十八 KB 上对着要。把栈加到三十二 KB 的话，
    装载就过不去（可用约四十七点五 KB，而装载要五十一 KB 上下）。
    所以「六份在板子上跑起来」不是一次调参能到的 —— 它要的是让求值器的
    栈帧变小，或者让求值器不靠递归。

    下一步的形状因此清楚了：先量一次「求值器最深的递归用了多少栈」，
    再决定是压栈帧还是换写法。这个数现在没有，所以这一节不猜它。

    六、还有一行一直是空的，现在它说明原因

    kinds= 那一段在板子上打出的是一行空。真实原因是 gc_分配 在 __arm__ 下是桩，
    本来就不会有 GC 块 —— 而空行读起来像「接口没接好」，它也因此被当成接口问题
    查过一轮。现在它打：

      kinds= none (gc_alloc is a stub on this board)

    与这一节的主线是同一件事：空的东西要说清自己为什么空，否则下一个读的人
    会从空白那一边重新猜。

十六、那个数：求值器递归一层要 6968 字节
--------------------------------------------------------------------

    第十节末尾欠的是「最深的递归用多少栈」。这一节把它量出来，三个数互相印证。

    一、编译器说的：一个 run_func 帧是 6968 字节

      arm-none-eabi-gcc -fstack-usage 那一次给出：

        vm/hmyr.c:4603:14:run_func        6968    static

      而 objdump 里对应的两条是 sub sp, sp, #6912 与 sub sp, #20（6912 + 20 + 8 个
      被保存的寄存器 = 6968 左右）。所以这个数是静态的、编译期就定好的固定帧，
      不是「跑起来才长成那么大」。

    二、板子说的：八层四万一千字节，十六层九万七千

      ?loadstep 函数表=8040 blocks 1
      loadstep 函数们=43792 blocks 606
      loadstep 全局名=43792 blocks 606
      depth=8 stack=41808
      depth=16 stack=97552
      hmyr: hard fault (stack past its reserve, or a bad access)

    两个档各自说清了两件事：深度八层时帧地址的差是 41808 字节，十六层是 97552。
    相减除以八，每层约 6.9 KB —— 与编译器那个 6968 是同一个量级。

    三、于是六份为什么跑不动的答案不是「内存不够」

    片上一共 131072 字节，静态段（bss）已经拿走 48528。剩七万九给堆与栈，
    而装载六份要五万上下。十六层递归要九万七 —— 那不是「紧」，那是差着倍数。

    有一处以前写错过，在这里更正：第八节那句「栈给了 8192」说的是堆的上界
    （_sbrk 的界线在 _estack 减八 KB），不是栈只有八 KB。栈与堆在中间相遇，
    所以栈能长过八 KB，代价是压到堆的数据上 —— 十六层那次撞的就是这个。

    四、两条试错也记下来

    一  最初想在 HardFault 处理里读这两个数并打印。结果是串口被半行
        「hmyr: hard fault, depth=」刷满：栈已经溢出，处理函数里每调用一个函数
        都会再压一层、再触发一次硬错误。处理里只能留在原地，不能调用任何东西。
    二  改成崩溃之前打：递归每到一个 2 的幂（8、16、32……）就在正常栈上写一行，
        每个档只写一次。这才拿到干净的两行读数。

    五、所以下一步不是调参数

    一层 6.9 KB 里，四十个 Value 的槽栈占 2240 字节（Value 是五十六字节），
    其余是各种诊断缓冲与编译器给这个巨大 switch 的临时区。把它们全压掉能省一半，
    而一半仍然是每层 3 KB —— 十层就三十 KB。要跑六份，要么让求值器不靠 C 递归
    （改显式栈），要么换一块 RAM 大十几倍的板子。这一节不猜哪一条更容易，
    但至少把「差着倍数」这件事写在了数字上，而不是留给下一轮重新猜。

十七、字节码从哪儿来：这一步也交给 HMYR 了
--------------------------------------------------------------------

    第十五节证明「执行不依赖宿主」，第十六节量「这块板子的上限」。而
    「不依赖宿主单独运行」还有第三步：那一份字节码本身，也是不是宿主编的。

    在此之前，板子的镜像是这样来的：

      make elf  →  tools/emit-code.mjs（整条路是 JS 的）  →  objcopy  →  Flash

    执行不依赖宿主了，产出还依赖。2026-10-30 这一步也交出去了：

      make elf COMPILER=hmyr PROGRAM=examples/board-run.hmoca

    那一路上编译是 self/compile.hmoca、落盘是 self/pack.hmoca，node 只负责启动。
    两条路编同一份源码，交出的字节码长度不同：

      tools/emit-code.mjs      639 字节
      tools/compile-hmyr.mjs   623 字节

    而同一台机器跑它们，输出逐字节相同；烧到板子上，串口上那四行也一样：

      ?和=55
      首项=3 三项之和=15
      名=ヒメユリ 长=4
      串=ABCDE
      0

      heap=6300
      hist= 0:24 8:10 16:5 24:3 40:1 56:19 168:1 184:3
      kinds= none (gc_alloc is a stub on this board)

    于是这条判据有两处归属：

      桌面侧  test/pack-bytes.test.mjs 第五组：两条路跑出同样的字节，它进套件
      硬件侧  这一节：同一份字节码烧进 Nucleo-F411RE，串口与桌面相同，
              它依赖板子，所以不进套件

    639 与 623 的差不是错误：两位编译者本来就不同（self/compile.hmoca 是子集），
    它们之间的判据从来是「跑出同一个答案」，不是「写出同一串字节」。
    逐字节那一条属于「同一个编译器、两个打包者」，是这一套的第四组。

    一句要留在这一页的话：到这一节为止，「不依赖宿主单独运行」拆成的那三件事里，
    前两件（执行、答案一致）与第三件的前半（字节码由 HMYR 编）都有了证据；
    剩下的是第三件的后半 —— 连启动器也不需要 node，那要板子上自己编源码，
    而它卡在第十六节那每层 6.9 KB 的栈上。

    六、独立启动器：有一个，而且 2026-10-30 验过

    这件事之前没有写在任何一页上，先记在这里：不需要 node 就能启动的那条路，
    HMYR 已经有了。它就是 vm/hmyr.c 的 main 与 cli_main 编出来的那个可执行文件，
    而种子编在它里面（vm/pack_seed.h：三百四十二 KB 的 .hmtn 变成一个 C 数组）。
    于是它不需要 node，也不需要外部的 bootstrap/pack.hmtn。

    验法是一个空目录，里面只有两个文件：

      hmyr.exe          383553 字节
      board-run.hmoca     1161 字节

    没有 node、没有 bootstrap 目录、没有任何 .hmtn。它自己把那份源码编成字节码、
    自己跑，输出与桌面一模一样：

      和=55
      首项=3 三项之和=15
      名=ヒメユリ 长=4
      串=ABCDE

    而它有一个前提，正好与第十六节是同一件事：它要 64 MB 栈。编它的时候要
    -Wl,--stack,67108864；少了这一条，hello 那种小程序还能过，board-run
    就直接以 0xC0000005 结束（访问违例）。求值器是递归的，桌面上靠一片大栈撑着。

    所以「独立启动」在桌面上成立，在板子上是同一个东西减去那片大栈。
    而 HMYR 自己写的那份启动器（self/run.hmoca 的命令行入口）也已经在树里 ——
    它要六份一起装载，所以它在板子上碰到的仍是第十六节那道墙。

十八、板子不能一直插着：桌面替身
--------------------------------------------------------------------

    接下来那条线（板子上自己编译源码）是硬件实验，而板子不可能一直插着。
    这一节给它一个替身：同一个镜像，在 QEMU 上跑。

    一、QEMU 在哪

      E:\DaShaoHuo\apps\qemu\qemu-system-arm.exe（QEMU 11.1.0）

    二、两条机器，各有各的用处

      mps2-an385      Cortex-M3，四兆 RAM，串口是 CMSDK UART —— 看得见输出
      netduinoplus2   Cortex-M4，一百九十二 KB，串口是 STM32 USART ——
                      这一版 QEMU 不往它送字节，所以那一档只看「跑不跑得完」

    第二条那个现象是实测的：同一份镜像在 netduinoplus2 上，调试器看到 pc 停在
    main 返回之后的死循环（0x08000068），而串口一个字节也没有。所以它不是「没跑」，
    是「跑了，而那一版的串口模型不往外送」。

    三、怎么跑

      make qemu-desktop

    它展开成 node tools/qemu-board.mjs port/build/hmyr-board.elf --machine mps2。
    裸机程序不会自己退出（Reset_Handler 最后是一个死循环），所以工具等一个时限
    再收，把串口的内容交回来 —— 与第八节那两条讲究是同一件事的自动化版本。
    没装 QEMU 的机器上它说清自己跳过，而不是假装跑过。

    四、它验到了什么：同一份镜像，两个宿主，同样的数

    examples/board-run.hmoca 在 MPS2 上跑出来的串口，与真板子上那一次一致：

      和=55
      首项=3 三项之和=15
      名=ヒメユリ 长=4
      串=ABCDE
      0

    而比输出更强的一处是那三行诊断，因为它们是分配计数：

      heap=6300
      hist= 0:24 8:10 16:5 24:3 40:1 56:19 168:1 184:3
      lines= 1680:1 1688:1 1689:1 1702:1 1521:1 1522:1 1177:2 915:31 2144:1 1512:8 4915:18

    三行与真板子那一次完全一样。同一个字节码、同一台机器、同样的分配次数在两边
    都成立 —— 这比「输出对」难碰巧。

    五、它不能验什么（这一条最要紧）

    容量。MPS2 是四兆 RAM，而那块板子是一百二十八 KB。所以「六份装不装得下」
    「每层 6.9 KB 的栈够不够」这些，替身回答不了 —— 它们仍然要真板子，
    或者桌面上的一套配额模拟（栈那一侧还没有，HMYR_MEM_LIMIT 只限堆）。

    还有一处：MPS2 是 Cortex-M3。M4 的 DSP 指令在它上面是未定义指令，程序用到
    那些会锁死，而那不是程序的错。

    所以这一节的定义是一句分工：日常的逻辑验证用替身，容量与 M4 指令这两个盲区
    留给真板子，而真板子只在里程碑时插一次。

    七、什么时候还需要插真板子（2026-11-01 补）

    两次读数对得上：同一份六份自举层，MPS2 上 heap=56192，真板子上也是 56192；
    board-run 那次两边都是 heap=6300，hist 与 lines 也一字不差。所以日常判据
    用替身就够了。

    需要插真板子的只剩两种情形：

      一  容量边界变了 —— 板子能给堆与栈的合计是 79552，而六份用掉
          56192 的堆加 2888 的栈，即 59080；余量 20472 字节。
          改动不越过它，结论在替身上可信。
      二  M4 指令 —— 替身是 Cortex-M3，只有用到 DSP 那条指令集才会露出来，
          而现在的编译选项没有主动生成它们。

    换句话说：板子从「每次都要插」变成了「余量被吃掉时才插」。

二十九、两件只有 F411RE 能回答的事，答案都不太好看
--------------------------------------------------------------------

    第十八节第七段说「需要真板子的只剩两种情形」。这一节把它们都做了。

    一、自编译：板子上装得下六份，装不下「六份加一段新程序」

    给 run.hmoca 的 main 加了一条正面判据：让它编译并执行一段在它编译之前
    并不存在的程序（print(str(6 * 7) + chr(10))）。

    桌面 C 机器上：

      1 + 2 * 3 → 7
      (1 + 2) * 3 → 9
      len("abcd") → 4
      10 % 4 → 2
      新程序 →
      42

    MPS2 上同一份，输出相同，而 heap 是一四六八三〇。

    真板子上：

      hmyr: out of memory, want 280 live 73934 peak 73934 blocks 3042 bytes at line 1203

    一二〇三是 alloc_values —— 编译那一段新程序走到一半就没了。

    三个数对照：

      六份跑自测          heap  56192    板子能给 79552    装得下
      六份加一段新程序    heap 146830    板子能给 79552    差六万七千

    所以「板子上能自己编译源码」在 MPS2 上成立，在这块板子上还差六万七。
    而那六万七全在编译路径上（词法、语法、求值三层各自的值），不是装载。

    二、M4 指令：镜像里真的有，而替身是靠 QEMU 宽容才跑通的

    对真板子的那份镜像（cortex-m4）做 objdump 扫描，M4 专属指令有：

      udiv   27 次
      sdiv    1 次
      smull   1 次

    udiv 与 sdiv 在 Cortex-M3 上是未定义指令，而 MPS2 那一次跑通了 ——
    说明 QEMU 对未定义指令是宽容的，而真的 M3 板子会锁死。

    所以「替身验逻辑」这句话要加限定：它在 M4 指令这一格上会骗人，而这次就骗了。

    三、两件活都做完，答案写在这里

      自编译    MPS2 成立，F411RE 差六万七 —— 要在这块板子上成立，
                得把编译路径的内存再压一半（那是个大工程）
      M4 指令   这一份镜像本来就需要 M4，所以 F411RE 是合适的宿主，
                而替身只在「逻辑」这一层可信

    四、一句要留下的

    替身与真板子的读数一致过三次（board-run、六份、board-spec），
    第四次（自编译）分开了 —— 因为那一次走的是新路径。
    换句话说：读数一致只说明「已经跑过的那些路」一致，新路仍然要真板子。

三十、默认路径上的一处裂缝：自举层的声明解析跑不过去
--------------------------------------------------------------------

    二十八节之后，run.hmoca 的 main 多了一条「编译并执行一段新程序」的判据。
    而它在默认路径上崩了：

      Error: index 9 is outside a value of length 9   (HMYR-行-018)

    同一份 run.hmoca 在 C 机器上跑得好好的，六行输出全对。

    一、先问形状，不猜

    写了 examples/probe-decls.hmoca：把一份带 fn 声明的程序交给自举层的解析器，
    打出 tokens 数、声明数、每项长度、语句数。

    C 机器上：

      tokens=28
      fns=1
      首项=7
      语句们=2

    而默认路径（minimal-eval）在求值这份探针时就越界了 —— 比 run.hmoca 崩得更早，
    说明问题不在 跑程序文字 那一层，而在自举层的声明解析本身。

    二、这说明什么

    decls_from 交回的声明是七件（名字、参数名们、语句们、效果名们、行、列、返回类型），
    而 C 机器给的正是七件。minimal-eval 给不出来 —— 它在某个 index 上越界。

    也就是说：默认路径从来没能跑过「自举层的声明解析」这条路。
    bin/hmyr.mjs 跑普通程序是好的，因为那走的是编译（compile），不是解析（parse_decls）。

    三、下一步

    把越界缩到 minimal-eval 的一个具体操作上（元组拼接、each、或 find_body 中的一个），
    然后补它 —— 判据是这份探针在默认路径上也打出 fns=1、首项=7、语句们=2。

三十一、裂缝缩到一处：tokenize 的 keep_lines 分支
--------------------------------------------------------------------

    三十节把裂缝落到「自举层的声明解析」。这一节再缩两格。

    一、三个探针，两侧对照

      probe-len     len=32、末码=10、第十八个=10      两侧完全一致
      probe-lex     scan=10                           两侧一致
                    scan_lines                        默认路径崩，C 机器给 tokens=13

    字符串本身两侧一样，不保留换行的那条路两侧也一样 —— 差别只在 scan_lines，
    而它比 scan 多出来的就是 keep_lines 这一个开关。

    二、所以缺口在哪儿

    两个入口调用的是同一对函数（tokenize 与 补位置），只差第四个参数。
    而 keep_lines 唯一的用处是 tokenize 里那一支：

      if s[i] == "\n" { ... 产出一个 newline token ... }

    加上它调用的 skip_trivia（keep_lines 为真时不跳过换行）。
    两者之一在 minimal-eval 上的行为与 C 机器不同，越界就从那里来。

    三、下一步

    读 skip_trivia 与那一支，把越界锁到一个表达式的 index 上。
    判据不变：probe-lex 在默认路径上也打出 tokens=13。

三十二、最小复现：scan_lines 对一个字母就崩
--------------------------------------------------------------------

    三十一节把裂缝缩到 keep_lines 那一个开关。这一节用二分把它缩到最短。

    examples/probe-lex2.hmoca 逐级加长源码，而第一档就崩：

      scan_lines("a")  →  index 1 is outside a value of length 1

    同一份在 C 机器上正常。

    一、这个报错来自哪儿

    minimal-eval 的第八三一行是下标：

      if (!码元.在界内(target, index)) this.坏("HMYR-行-018", ...)

    所以它说的是「某个 HMYR 表达式访问了 x[1]，而 x 长一」。
    而 C 机器对同样的访问没有报 —— 也就是说那边容忍了。

    二、于是怀疑的方向变了

    三十节写的是「minimal-eval 上跑不动」，而这一条读数把它反过来：
    更可能是自举层里有越界访问，C 机器容忍，minimal-eval 严格。

    这一句还不能定案 —— 要对「a」在 lex.hmoca 里的每一步走一遍。
    但方向变了，而它更值得先确认：若真是自举层的越界，
    那要修的是 lex.hmoca，不是 minimal-eval。

    三、下一步

    对「a」走一遍 tokenize 与 补位置，把那个 [1] 找出来（读代码，或者在那一层加打印）。
    判据仍然是：probe-lex 在默认路径上也打出 tokens=13。

三十三、越界现场指向自举层的下标求值，而两台机器对它给不同的答案
--------------------------------------------------------------------

    三十二节把最小复现缩到 scan_lines("a")。这一节给了它一个现场。

    一、先给下标检查加一个可选的现场

    minimal-eval 的 R0151 只说「index N 超过长度 N」，不给是哪个表达式。
    加了开关 HMYR_INDEX_TRACE=1：越界时把目标、下标与那个 Index 节点打出来。
    它指到的是：

      self/eval.hmoca 第 1050 行：return 好(标.value[位.value])

    也就是自举层自己的下标求值 —— 它直接访问，不做边界检查。

    二、于是两台机器的分歧被写在了明处

    给那一处加上边界检查之后，两侧的行为变成：

      默认路径   错：下标越界：1，而长度是 1（第一档就停）
      C 机器     好 长1 词1 …… 八档全过

    两台机器跑的是同一份 eval.hmoca，而对同一个表达式给出不同的下标或长度。
    所以分歧不在「有没有检查」，而在「那个下标算出来是多少」。

    三、下一步

    在越界那一支里把两台上的「下标与长度」都打出来对比 —— 那会指到 lex.hmoca
    里算出这个下标的那一行。

三十四、slice 的越界补上了，而现场指到一处自相矛盾的行
--------------------------------------------------------------------

    一、一个真的 bug：slice 不截终点

    self/lex.hmoca 的 slice 原来只有 if from >= to 一条，于是 slice("a", 0, 5)
    会让 from 一路涨过 len(s)，s[from] 落在界外。补了截断：

      if from >= len(s) { return "" }
      if to > len(s) { return slice(s, from, len(s)) }

    C 机器对界外下标交回空、minimal-eval 报 R0151 —— 两台机器两种结果，
    而这件事一直到 scan_lines 上才被看见。

    二、而现场指到一处自相矛盾的地方

    给 eval.hmoca 的越界消息加上行号之后，它说的是：

      下标越界：1，而长度是 1，在第 183 行

    而 lex.hmoca 第一百八十三行是 if s[i] == "\n"，它的上一行（一百八十二）
    正是 if i >= len(s) { return acc } —— 也就是说那一处本来就有边界检查。

    一个「有检查」的地方报了越界，只有两种可能：

      一  i 在那一行与上一行不是同一个值（中间没有赋值，所以不可能）
      二  len(s) 与 s[i] 的「界」在那一台上不是同一把尺子

    第二种是下一个要验的：最小求值器的码元模块里，长与下标可能对同一串
    给出不同的界。

    三、下一步

    写一个探针，对同一个串同时打印 len、取 s[0]、并试着取 s[1]，
    看那一台的长度与下标是不是同一把尺子。

三十五、根因：自举层的求值器不短路
--------------------------------------------------------------------

    三十四节留了两种可能。这一节把它落定，而答案是第二种的一个变体。

    一、一路排除

      probe-cmp     < 与 <= 两侧一致
      probe-gt      > 两侧一致
      probe-prec    带括号与不带括号结果一致（C 机器上）
      probe-and     默认路径上 1 > 2 && s[9] 的右边被求值了

    最后一条说明：&& 的左边是假（probe-gt 已确认），而右边的 s[9] 还是被求了。
    而 minimal-eval 里 && 的实现左边为假就直接返回 false —— 短路是好的。
    于是问题在另一层：bin/hmyr.mjs 跑程序时，执行者不是 minimal-eval，
    而是自举层的求值器（self/eval.hmoca）。

    二、它自己写着不短路

    self/eval.hmoca 的 求二元 上面有一句注释：

      逻辑两级。这里不短路：两个操作数在调进来之前都求过了。
      那与语言别处的语义有一处差别（a && f() 里的 f 会不会被调），
      写成注释而不是装作没有 —— 要短路得在 求值 的 bin 分支里特殊处理。

    也就是说：这件事早就知道，只是被记成一条限制，而不是一个 bug。
    而它让 lex.hmoca 里「先检查再访问」的写法全部失效：

      if s[i] == "/" && i + 1 < len(s) && s[i + 1] == "/" { ... }

    i + 1 < len(s) 为假时右边本该被短路，而它被求值了 —— 越界就在这里。

    三、修法：在求值那一层补短路

    给 Binary 分支加了 && 与 || 的短路：先求左边，有结论就不再求右边。
    求二元 里那两条留着当防御。

    四、三条判据

      probe-decls 默认路径    tokens=28、fns=1、首项=7、语句们=2（与 C 机器一致）
      run.hmoca 默认路径      六行，第六行是 42
      套件                    cvm 93、launcher 40、selfcompile 18、packbytes 13、
                              conform、docs 全过

    五、一句要留下的

    这条裂缝从「默认路径跑不动」缩到今天，中间排除了六种可能（len、比较、
    优先级、slice、字符串层、&& 的实现本身）。而根因是一条被写进注释的已知限制 ——
    它之所以一直没被发现，是因为 C 机器短路，而它容忍了那次越界。
    限制被写成注释，就少了一次「它会不会影响别处」的追问。

三十六、注释里的限制：第一批三条
--------------------------------------------------------------------

    三十五节那条「不短路」是从注释里挖出来的，于是这一轮把 self/ 里的
    「注释承认的限制」列了一遍（不短路、不支持、还没有、不能、限制、只认、不做）。
    第一批三条，而它们的结论各不一样。

    一、eval.hmoca 的「这里不短路」—— 已经过期

    短路补上之后，那段注释还写着「要短路得在 求值 的 bin 分支里特殊处理」。
    改成了「短路在那里做，这一层保留两条完整分支当防御」。

    二、lex.hmoca 的「模块系统还没有」—— 也已经过期

    run.hmoca 就是靠 import 把五份串起来的，所以模块系统不但有，还是这条线的基础。
    注释改成历史说明，并指出 scan.hmoca 里那份重复的工具可以收，但不急。

    三、ittgn.hmoca 的「slice 不认数组」—— 可接受，且注释已经写明理由

    那段注释说：给 slice 加数组那一支试过，cli 整套大面积红 —— 有地方正靠旧行为做事。
    所以字节的切法留在那一层。这一条不用改：理由在，代价也在。

    四、下一批

    剩下二十多条里，多数是「自举层是子集」的正常边界。要挑的是会像短路那样
    影响别处的，而候选里有两条值得先看：

      body.hmoca 只认一种声明，且跳过返回类型与效果声明 —— 效果检查会不会因此失效
      chain.hmoca 只认算术运算符 —— 而比较与逻辑运算符显然也解析了，那句可能又过期

    五、下一批的两条也有了结论，而它们都属于「停在过去的形状上」

      chain.hmoca   它后来长出了后缀（调用、下标、字段）与两层逻辑
                    （|| 低于 &&，两者都低于比较）—— 注释已改
      body.hmoca    decls_from 早就把效果名收进那条七件元组了，而且必须收，
                    因为效果检查要拿它 —— 注释已改

    于是第一批五条里有四条是「过期」、一条是「可接受」。而「过期」这一类
    比没有注释更贵：没有注释时读者会去读代码，有过期注释时读者先信它 ——
    这一次我自己就被 eval.hmoca 那句「这里不短路」引了两次。

    六、第二批两条，也都是过期

      lex.hmoca   说「归一是下一步」，而 tokenize 在产出标识符时已经调 nfc
      fmt.hmoca   说「读整份声明的接口还没有」，而 body.hmoca 现在有 parse_decls

    第二条值得单说：它的理由曾经成立，现在不成立了 —— 于是整文件重排从
    「不能」变成「还没做」。这两句话在工程上的意思不一样：前者要等条件，
    后者只要排期。

三十七、剩下六条：都有理由，而理由都写清了代价
--------------------------------------------------------------------

    三十六节之后还剩几条子集边界。这一轮把它们逐条判完，结论一致：
    可接受，而每一条的注释都已经写明代价。

      deflate 解只认 stored 块     固定 Huffman 的流交给 zlib，自举侧解码器是下一步。
                                   代价写清了：这一步只承诺「压出来的东西标准工具读得懂」。
      deflate 只写字面量           不做匹配。理由是它能与 ref-encoder.mjs 逐位对照 ——
                                   对着看才分得清「树不同」与「序列化错」。
      lsp 不做前缀过滤             那是客户端的事，编辑器自己筛。
      ittgn 只做骨架               可执行与 zip 平级转换要等运行逻辑那一条设计落地。
      embed 不是编译器             编译在 self/pack，它只把字节摊成 C 数组。
      ittgn slice 不认数组         试过，cli 整套红；字节的切法留在那一层。

    这六条与前面七条的区别不在「有没有限制」，而在「理由还在不在」。
    前面七条的理由曾经成立，而后来的代码把它推翻了；这六条的理由今天仍然成立。

    一句话留在这里：判一条限制该不该改，看的是它的理由还成不成立，
    而不是它看起来像不像缺点。

三十八、这个 goal 的账
--------------------------------------------------------------------

    候选十四条，结论两种：

      过期 · 已改      七条（eval 短路、lex 模块、chain 算术、body 效果、
                       lex 归一、fmt 声明、bigint 模运算）
      可接受 · 有理由  六条（三十七节那六条）
      另外一条          ittgn 的 slice 边界，与前六条同批判过，也是可接受

    而七条过期里有六条是同一个病：代码走了，句子没走。

    它们的发现方式全是「读」—— 没有判据盯着。这一点值得留一个待办：
    注释与代码的一致性没有自动检查。现在能想到的最便宜办法，是给 self/ 里
    每条「限制」注释一个编号，改动时对着编号更新 —— 但那仍然是靠人记得。

三十九、回收在板子上不可行：它自己的账比它能收回来的多
--------------------------------------------------------------------

    板子接回来之后，第一件事是压那六万七。最先想到的是回收 ——
    板子上原来不编回收（gc_分配 是个返回 NULL 的桩），于是每一次分配都只增不减。

    一、改法与读数

    gc_分配 与桌面共用一份（板子上的 malloc/free 早在第五百五十四行就映射到
    hm_malloc 与 hm_free），再加一个 hmyr_开回收(阈值) 给裸机用 —— 桌面默认
    三十二兆，而板子的堆只有八万字节，用那个数等于永不回收。

    在 board-main 里开成四十八 KB 之后：

      六份自测（没有回收时 heap=56192）   撞墙：live 84422、blocks 869
      六份加一段新程序                    撞墙：live 84422、同一个数

    二、为什么

    差额来自回收器自己的账：每块的头、地址表、以及根扫描走一遍的开销。
    而根是宽的（帧链、操作数栈、全局），于是能收回来的远少于它自己占的。
    「六份自测从 56192 涨到 84422」这一句就是结论：在这块板子上开回收是负收益。

    三、所以

    这一句留着不开（代码里注释掉了），而回收器本身在板子上编得过 ——
    要再试得先从「根窄一点」或者「元数据少一点」入手，不是调阈值。

    而六万七那笔账仍然在，而它差的是活对象，不是垃圾：编译期间词表、语法树、
    中间值都在用，回收收不走它们。要装下得压它们的表示，或者改成边解析边求值 ——
    那是另一个量级的工程。

    四、压表示之前先量了一个数

    板子上打出来的是 sizeof= 值 56 —— Value 五十六字节，这是第一次读出来的，
    此前一直是推算的。

    而它决定了那一刀能省多少：值数组与字符串是六份自测那一万五千字节的主体，
    所以把 Value 压到二十四字节大约省下百分之五十七的值部分。而自编译差的是
    六万七 —— 一刀不够，还得把词表与语法树的形状也压一遍。

    这两刀下去的收益不只属于板子：Value 与 token 的形状是所有程序都在付的账。

四十、Value 从五十六压到二十四：一份值不再为「它可能是什么」付全部的钱
--------------------------------------------------------------------

    三十九节说自编译差六万七、回收收不回来，那就只剩压表示。而压之前量了
    sizeof= 值 56（第三十九节末）。

    一、改法：九个字段改成匿名 union

    Value 的九个字段互斥 —— 一个值在任一时刻只能是数字、布尔、字符串、元组、
    记录、索引之一。所以它们共用一个 union，而 tag 留在外面。

    为什么字段名一个字都没改：C11 的匿名 union 包里再放匿名 struct，于是
    .num / .s / .slen / .items / .ilen / .rec / .idx 全都照旧 —— 那五百多处
    调用点一行都没动，这一次改的只是布局。

    二、读数

    板子上：

      sizeof= 值    56 → 24
      heap       56192 → 34560    省 21632，百分之三十八

    直方图每一档都跟着变小：五十六那一档从二百一十块变成二十四那一档二百四十八块，
    一百八十四以上那一档从四百零八块降到六十块。

    而六份自测的四行输出一字未变 —— 语义没动。

    三、一件还没结的事

    c-vm 的九十三项里有一项不过：「开着回收时峰值不到一半」现在是三十四兆对三十五兆。
    而这一项守的是回收的收益。

    两种可能：一是压了 Value 之后垃圾的绝对量变小，于是「一半」这个经验阈值
    不再成立；二是 union 让标记漏走了什么。要分清它，得把那一项的程序在
    GC 开与关两档下各跑一次，看绝对峰值 —— 这是下一步。

四十一、板子上能自己编译了：十六 KB 的发现与 Value 那一刀
--------------------------------------------------------------------

    四十节的结尾说还要查 c-vm 那一项。而查它的过程中发现了更值钱的东西。

    一、十六 KB 一直在那里

    自编译在板子上撞墙时报的是 live 68102 —— 而 bss 是 48520，两者之和
    已经超过 112 KB（一一四六八八）。再看链接脚本：RAM 切在 0x2001C000，
    而 F411RE 的 SRAM 是 0x20000000 起 128 KB —— 十六 KB 从来没被用上。
    更刺眼的是 link.sct 的注释自己写着「128 KB RAM」，而代码切在 112 KB。

    这一条属于三十六节那一类：注释说的与代码做的不一致。而这一次不一致的代价，
    是「差一点装不下」。

    二、改过来之后的读数

    真板子上，六份加一段新程序：

      1 + 2 * 3 → 7
      (1 + 2) * 3 → 9
      len("abcd") → 4
      10 % 4 → 2
      新程序 →
      42
      heap=78734

    而 heap=78734 与 MPS2 上那个数一字不差。

    三、于是这条线的第三件后半也到了

    十七节说「第三件是不依赖宿主单独运行，后半是板子上自己编译源码」。
    从今天起它成立：板子装的是一份字节码，而它编译并执行了一段在它自己
    被编译之前还不存在的程序。

    四、c-vm 那一项也结掉了

    「开着回收时峰值不到一半」现在不过的原因是算术：峰值的下限是回收阈值本身
    （三十二兆），而 Value 变小让「不开」那一份从七十多兆降到三十五兆，
    于是「不到一半」不再可能。测试改成给「开」那一档一个四兆的阈值，
    它继续问它该问的事 —— 同一份程序，回收真能把峰值压下来吗。
    而 c-vm 回到九十三项全过。

四十二、向下兼容的界线：值那一刀有回退，而 C89 那条路还差八千八百行
--------------------------------------------------------------------

    2026-11-01 定了一条界线：兼容老机器有必要，但不必太老 —— 最多到 Win95 时代。

    一、Value 那一刀有回退，这一件已经做完

    Value 的匿名 union 在能用的编译器上把值从五十六压到二十四（板子）或
    四十（桌面），而老编译器那一支退回旧布局。判据是 __STDC_VERSION__ 不低于
    二零一一，或者 MSVC 从二零一五起；两支的字段名一模一样，所以那五百多处
    调用点两边都成立。

    实测：-std=c11 零错、-std=c99 -pedantic 零错，而 c99 那一档走的正是回退分支 ——
    也就是说「字段名不变」这个设计真的让布局可以两头选。

    二、而 C89 那条路还差多少：八千八百行

    gcc -std=c89 -pedantic -fsyntax-only 报出八千八百八十一行。而头几类是

      stray 八进制转义 in program

    那是中文标识符：这份代码用「分配失败」「帧记录」这样的名字当 C 标识符，
    而 C89 只认 ASCII。除了它，还有双斜线注释、stdint.h、snprintf、
    以及 for (int i …) 这些 C99 的东西。

    三、所以 Win95 兼容的价码写在明处

    要真的回到 Win95 时代的编译器，得先放弃中文标识符 —— 而那是这份代码
    可读性的一部分，不是装饰。可行的路只有一条：用工具生成一份 ASCII 化的副本
    （拼音或编号），原文件保持现在这样。那不是几个宏的事，是另一条产物线。

    所以界线这样落：值那一刀两头可选；C89 语法这一层，现在记为「不追求」，
    除非有人真的要在那个年代的编译器上跑它。

    四、下限定在 Win8 时代（同日决定）

    Windows 8 那年能装的工具链是 VS2013 与 gcc 4.8。而这份代码对它们的依赖
    只剩一处：Value 的匿名 union。其余 C11 的东西一个都没用 ——

      _Static_assert    零处
      _Generic          零处
      stdatomic          零处
      _Alignas / _Atomic 零处

    而线程局部早就分了三支：裸机空、MSVC 用 __declspec(thread)、gcc 用 __thread ——
    都不是 C11 的 _Thread_local。

    所以 Win8 时代编它：gcc 4.8 走匿名 union 那一支（它支持 C11 匿名成员），
    VS2013 走回退那一支（_MSC_VER 一八零零，小于判据里的一九零零），
    值回到五十六字节而语义不变。

    五、一句未实测

    上面的判断依据是标准与编译器版本，而这份代码没有在 VS2013 或 gcc 4.8 上
    真编过。要确证，得在那套环境里跑一遍 c-vm 那九十三项 —— 在那之前，
    这一条记作「应当成立」，不记作「已验证」。

    六、而这一条暂时不做（同日决定）

    向下兼容先搁置：等 Hiou Rengo 与 Yunooka 做出来再说。

    所以现在只保留已经做完的那两件 —— Value 的匿名 union 有回退、线程局部有三支，
    而 C89 语法那一层不动。它是「另一条产物线」，不是顺带能了结的。

    六、栈预算：第二个盲区也在桌面上补上了

    替身管不了容量，而容量有两个数：堆与栈。堆早就有 HMYR_MEM_LIMIT，
    栈一直没有 —— 2026-10-30 补上，名字是 HMYR_STACK_LIMIT，单位是字节：

      HMYR_STACK_LIMIT=25000 hmyr.exe run.hmoks

    它量的尺子与板子上那两行 depth=/stack= 是同一把：最深帧地址减最浅帧地址。
    超了就报 HMYR-行-009，并把用了多少字节一起说出来 —— 只说「太深了」帮不了人算账：

      HMYR-行-009 the stack budget is 25000 bytes and this call is 28752 bytes into it

    六份自举层在桌面上的两次，正好是板子上那件事的两面：

      不给预算（桌面六十四兆栈）   (1 + 2) * 3 → 9 …… 跑完，退出码 0
      给两万五千字节              R0108，两万八千七百五十二字节时撞上

    于是「六份在这块板子上跑不动」不再需要插板子才知道：同一条环境变量、
    同一份字节码，桌面上就能复现。

    判据在 test/c-vm.test.mjs 的最后一组（三项）：不给预算时算得出 120、
    给四千零九十六字节时报 R0108、而那句话里带着字节数。

十九、板子上的自举：在替身上成立，差的是三倍
--------------------------------------------------------------------

    第十七节末尾欠的那件事 —— 板子上自己编译源码 —— 这一节在替身上验了。
    六份（含 run.hmoca）在 MPS2 上跑完，输出是 run.hmoca 自己的四行自测：

      1 + 2 * 3 → 7
      (1 + 2) * 3 → 9
      len("abcd") → 4
      10 % 4 → 2

    所以「板子上的自举」在逻辑上成立：装载、编译、求值、打印，一整套在一份
    裸机镜像里跑通了。卡住的只有容量。

    而容量这一侧，打开装载跟踪那一版的替身也给了两个数：

      loadstep 函数表=8040 blocks 1
      loadstep 函数们=43792 blocks 606
      loadstep 全局名=43792 blocks 606
      depth=8 stack=41808
      depth=16 stack=97552
      heap=193390

    对照那块板子：一共 131072 字节，静态段 48520，剩约七万九给堆与栈。
    而六份要堆 193390、栈十万上下（十六层是九万七，而 32 那一行没有出现，
    所以真实最深在 17 到 31 层之间）。两个数加起来是板子能给的将近四倍。

    三行想一想：

      一、堆那些块是什么：hist 里 56 字节档 1127 块（每一帧一份的槽数组）、
          168 档 361、184 档 297。板子上没有 GC，所以它们只增不减。
      二、栈那十万是递归：每层 6.9 KB，十六层就是九万七。
      三、两条都不在「再省一点」的量级上。要在这块板子上跑六份，得同时做两件事：
          让求值器不靠 C 递归（栈），让每帧的槽数组不再各分配一份（堆）。

    这一节的意义是把「差一点」这句话换成一个数：差三倍多，而三倍里的三分之二
    是堆。下一次要动的时候，先动堆还是先动栈，这张表都能回答。

二十、堆的大头找到了：名字池的两张表（以及三次被否定的猜测）
--------------------------------------------------------------------

    第十九节留下的问题是「堆那一八七〇八二被谁吃掉」。这一节把它答出来，
    而答案中间有三次否定 —— 它们比答案本身更值得记。

    一、先把直方的盲区补上

    hist 只分二十四档（到 184 字节），而且只记次数。六份跑完时各档次数加起来
    一千五百多次、按档上限估不过四万多，而 heap 是一八七〇八二 —— 差的那一截
    全在最后那一档里。于是加了两行：

      big= 289756           最后一档的字节总量（68 次，平均四千二百六十一）
      bigline= 1571:130048  字节总量最大的那一行

    二、bigline 一出来，答案就在那一行上

    1571 是 pool_add 里 pool_off 的 realloc：名字池的偏移表。128 项起步、
    每次翻倍，六份一共翻了七次（256 到 16384），累计
    4 字节乘（256 加 512 一直加到 16384）等于 130048 —— 与读数一位不差。

    而池到一万六千项的原因是 pool_add 从来不去重：装载期扫一遍指令把名字加进去，
    执行期每一条带名字的指令又加一遍 —— 一半的项是重复的。

    三、第一次尝试：去重。收益确认，代价关掉

    pool_add 改成先查（二分）再追加，结果：

      六份的 heap   187082 → 121546（省 65536，正好是两张表各降一半）
      c-vm 那一套   24 秒  → 191 秒

    慢的原因还没有查清（猜是某处退化成线性查找，但没有证据）。于是这一刀退回，
    查表那段留着 —— 已经写好了，下一轮只要接线并查出为什么慢。

    四、去重顺带撞出一个坑，记下它的形状

    记录字面量的字段名靠「连续的一段池索引」：执行期按 in->a 加 i 取。
    去重一上，那一段不再连续，症状是

      HMYR-行-007 no field with that name

    所以正确形状是：装载期强制追加（pool_push），执行期去重（命中装载期那一段）。

    五、另外两次否定

    名复制缓存：调用从 1196 降到 223，而 heap 只降 5962 —— 说明 56 字节那 1127 块
    不是名字。它没坏处，留着。

    实参数组改用栈上小数组：168 档从 361 降到 28、184 档从 297 降到 56、
    hist 的总次数从 3307 降到 1537，而 heap 只降 346 —— 因为那些分配本来就有 free，
    峰值里不含它们。它也没坏处，留着。

    六、于是这一轮留下了什么

      两个诊断（big= 与 bigline=），它们让「堆被谁吃掉」下次能一次答完
      两个小改动（名缓存、栈上实参数组），都不伤速度
      一个已验证但暂缓的优化（池去重：省 64 KB，代价是七倍的时间）
      一个坑的形状（RECORD 依赖连续索引）

    而容量这件事本身没有推进：heap 仍是一八七〇八二，板子能给的仍是七万九。

二十一、去重试了两次，两次退回；以及一个算出来的下界
--------------------------------------------------------------------

    第二十节说「下一刀是查出为什么慢」。这一节把它查完，而答案是：不是查得慢，
    是那条路径太热。

    一、两次尝试

      第一次   池查 用二分              c-vm 24 秒 → 191 秒
      第二次   再加一项最近命中的缓存     174.8 秒

    两次合起来说明：单次查找并不贵，贵在「执行期每一条带名字的指令都要查一次」——
    而原来那里只是一次追加（读一遍字节流，再加两个数）。把 O(1) 换成 O(log n)，
    落在每一条 CALL、FIELD、GLOBAL 上，就是七八倍。

    所以池保持追加。它会长到一万六千项、两张表吃掉一百三十 KB ——
    那不是「忘了去重」，而是去重的代价比它省的多。

    二、就算两边都做满，也还差两万五

    把账算清楚（这是这一节最有用的一格）：

      现在                             堆 187082
      去重（池到八千项）               堆 121546（省 65536）
      再把长度压成 u16（每项六字节）    堆 105162（再省 16384）
      板子能给                         79552
      仍超                             25610

    而栈那一侧还没算：十六层是 97552。两者加起来，即使名字池压到最紧，
    也仍是板子能给的两倍多。

    三、所以真正的路是把池去掉

    一万六千项的名字池为「把名字变成一个索引」服务，而那个名字本来就在字节流里。
    如果指令直接带「偏移与长度」，比较时按字节流逐码元比，池就整个不需要 ——
    省掉 131072 字节，正好是那块板子 RAM 的量。

    代价在速度：名字比较从「读两个数组」变成「读字节流」。而它与去重那七倍
    不是一回事 —— 去重是在最热的路径上加查找，这个只是让比较本身多几次内存读，
    而比较本来就要读那串码元。

    而 RECORD 的字段名要另想办法：它现在按「连续的一段池索引」取，
    改成偏移之后，执行期要按指令里的那 n 个名字重新读一遍字节流
    （那一段就在指令里，起点可以从 in->a 推出来）。

    这一刀的工作量比去重大得多：Ins 的 a 与 b 两个立即数要换语义，
    所有 name_is、name_is16、池取到、池码 的调用点都要跟着改。
    但它是唯一能把 131072 拿掉的方向，而 131072 正好是这块板子的一半。

二十二、名字池整个去掉了：堆从一八七〇八二降到五六〇一〇
--------------------------------------------------------------------

    第二十一节说「除了把池去掉，别的都不够」。这一节把它做完。

    一、做法：指令里只留偏移

    rd_str 读的是「u16 长度加码元」，交回的偏移指在码元起点上 —— 所以长度就在
    偏移前面两字节（名长 读它），码元按名码 读。于是：

      指令里存的      池索引        → 偏移
      名字的长度      池里那一项     → 偏移前面两字节
      名字的码元      池里那一项     → 字节流本身
      字段名那一段    连续池索引     → 从第一个偏移顺着字节流读
                                     （每段是「u16 长度加码元」）

    池的两张表（一万六千项，各六十四 KB）因此整个消失。

    二、读数：正好是那一百三十 KB

      loadstep 函数们   43792 → 11024
      heap            187082 → 56010

    而板子能给的（131072 减 48520 静态段）是 79552 —— 堆这一侧第一次够了，
    余下两万三千。

    六份仍然跑通，输出与桌面一样是那四行；c-vm 那一套从 24 秒降到 20.6 秒，
    因为它不再为每一条带名字的指令追加一次池项。

    三、现在只剩栈

      depth=16 stack=97552

    每层 6.9 KB，十六层九万七，而堆用掉五万六之后剩下两万三给栈。
    所以下一刀是唯一剩下的一刀：让求值器不靠 C 递归 —— 帧放堆上，栈只留常量。

    四、顺带记一个消失的坑

    「字段名必须是一段连续的池索引」那条规矩随池一起没了。执行期现在从第一个
    偏移顺着字节流读：下一个字段的偏移是 本段偏移 加 长度乘二 加二，
    不需要「连续」这个概念，也就不会再被它绊倒一次。

二十三、下一刀的预算表：显式帧
--------------------------------------------------------------------

    第二十二节把堆解决了，剩下的只有栈。这一节不写做法，先算一遍 —— 因为
    这一刀大，算错了要拆半天。

    一、栈现在花在哪儿

    每层 6.9 KB（编译器的 -fstack-usage 与 objdump 都给这个数），而 run_func
    里的东西只有这些：

      Value 槽栈[40]      2240 字节（四十个五十六字节的值）
      各种诊断缓冲        约 1400 字节（char m[260]、fname[64]、名[64] 那一批）
      局部与保存寄存器    其余

    板子上十六层读到 97552，每层 6097 —— 比 6968 小，因为不是每层都到顶。

    二、显式帧要换成什么形状

    求值器不再用 C 递归，改成一个帧池：

      帧池      一块连续内存，每帧一个结构（Func 指针、slots、pc、缓存、
                base、外层函数…），约一百字节
      槽数组    按 f->nslots 分配（自举层单帧最大三十四槽，平均十几），
                不再固定四十个

    这样每层从 6.9 KB 变成一百多字节，而槽数组落到堆上。

    三、预算（按二十层估）

                        现在          显式帧
      栈                约 122000      约 3000
      堆                  56010        56010 加槽数组
      槽数组                  0        约 11200（二十层乘平均十槽乘五十六）
      合计              约 178000      约 70200
      板子能给            82552          82552

    也就是说：这一刀之后，六份在这块板子上第一次装得下（70200 对 82552）。
    而这两个数都是估的，真正的判据仍然是 MPS2 上那三行（depth、stack、heap）
    加一次 HMYR_STACK_LIMIT 的桌面复现。

    四、代价与风险

      工作量   run_func 那八百行要拆成「压帧、循环、弹帧」，
               几十处 FRAME_RET 跟着改
      风险     c-vm 92 项、launcher 40、selfcompile 18 都要重新过一遍
      性能     每一步多一次帧字段访问，而少一次 C 函数调用 —— 方向可能还对

二十四、显式帧的两个前置：槽数组上了堆，缓冲外移没省
--------------------------------------------------------------------

    二十三节那张预算表说显式帧能到七万。这一节做的是它的两个前置，
    而结果一半对一半错。

    一、一成一不成

      槽数组从栈上挪到堆        栈 97552 → 66080（省三万一千）
      诊断缓冲移到线程局部静态    省 112 字节 —— 等于没省

    第二条值得单独记：我原以为那批 char m[260]、fname[64] 各占一份，
    而编译器早就把它们复用了（不同 case 的数组生命周期不重叠，-Os 会合并）。
    所以「一千四百字节」那个估计是错的，真实收益一百一十二。

    二、改后的三个读数

      depth=8   stack=28320
      depth=16  stack=66080
      heap=54528

    栈从 97552 降到 66080，而堆几乎没动（56010 到 54528）—— 因为槽数组返回就还。
    代价是每层一次 malloc 与 free：c-vm 从 20.6 秒到 21.5 秒。

    三、剩下的四万二只能靠换形状

      栈 66080 对板子剩下来的 23542

    而这一步已经把「能从栈上搬走的东西」搬完了：剩下每层约四千一百三十字节
    是 C 调用本身的成本（返回地址、被保存的寄存器、编译器给那个大 switch 的临时区）——
    那不是搬得走的，只能换成不递归。

    所以下一轮就是显式帧本身，没有别的准备了。

二十五、显式帧的实施图纸与两个基线
--------------------------------------------------------------------

    这一节给下一轮一张能照着做的图，以及两个刚量出来的基线。

    一、基线（cortex-m3 上，改完之后用 -fstack-usage 量的）

      run_func        4728 字节
      call_builtin    4856 字节

    第二条值得注意：call_builtin 比 run_func 还大，而它不递归 —— 但它是嵌套在
    run_func 里面被调用的，所以任何一层执行到 CALLB 时峰值是两帧相加。
    而它一次性，返回就没了。

    二、所以显式帧之后栈剩什么

    递归那部分是 run_func 的十几层。改成帧池之后，这一部分只剩「池里那些结构
    加主循环的局部」，而 call_builtin 那一个帧照旧。估算：

      帧池与主循环局部    约 500 字节
      一个 call_builtin   4856 字节
      合计                约 5400

    板子剩下来给栈的是 23542 —— 这一次有富余，而不是差一点。

    三、图纸（下一轮照着做）

      活帧结构    Func 指针、slots、base、外层函数、pc、缓存条、缓存位、
                  帧记录（持有格链）
      帧池        按需翻倍的活帧数组；池里第（深度减一）个是当前帧
      压帧        分配 slots、记深度、记栈、接上帧链、切换 g_机 的当前函数与基址
      弹帧        关本帧持有格、还原帧链、还 slots、恢复调用者的当前函数与基址
      CALLF       压一帧然后 continue，不递归
      RET         弹一帧，把返回值压回调用者的操作数栈，并让调用者的 pc 前进一条
      FRAME_RET   改成「清空整个帧池并 return」—— 那几十处都是出错路径，
                  语义本来就是「整机停」

    四、判据

      一   c-vm 92 项、launcher 40、selfcompile 18 全过
      二   MPS2 上 depth=16 的 stack 落到几千，而六份仍跑出那四行
      三   桌面用 HMYR_STACK_LIMIT=20000 跑六份仍能跑完

二十六、显式帧：栈从六六〇八〇降到二八八八，而堆涨上去了
--------------------------------------------------------------------

    第二十五节那张图纸照着做完了，而结果是一成一换。

    一、栈：成了，而且成了常量

      depth=8   stack=2888
      depth=16  stack=2888

    十六层与八层是同一个数 —— 因为 C 栈不再随 HMYR 的调用深度增长，
    那二八八八是主循环加一个 call_builtin 帧，与深度无关。
    第二十五节估的是五千四，实测二千八百八十八。

    二、堆：换了个地方花钱

      heap  54528 → 113664（板子能给 79552）

    帧池与每帧的槽数组搬到了堆上，而操作数栈本来就在堆上。
    于是「栈超四倍」变成了「堆超四成」。

    三、做的时候撞了两个坑，都写在这里

    一  realloc 会移动帧池。帧记录 的地址被 记录.上 与 g_机->帧链 记着，
        扩容之后那些指针全失效 —— 症状是访问违例（0xC0000005），
        而 c-vm 一次挂掉十一项。修法是在扩容处按新地址把链重建一遍。
    二  上一轮加的三项「栈预算」测试失效了：栈不再随深度增长，
        HMYR_STACK_LIMIT 量不到东西。测试改成「深度上限」（HMYR_MAX_DEPTH），
        而它才是显式帧之后唯一还能量得出来的界。

    四、下一步：堆

      操作数栈        g_机->stack，按需翻倍；一千零二十四项乘五十六字节约五万七
      每帧的槽数组    十六层乘平均二十槽乘五十六字节约一万八
      装载            一万一千

    三条里最大的是操作数栈，而它的成本又几乎全在「五十六字节的 Value」上 ——
    压前面两项只是挪，压 Value 才是指数级的省。

二十七、板子上的判据是规范，不是能力全集
--------------------------------------------------------------------

    这一节把一条边界写下来，因为它是这条线一直没写明的那个前提。

    一、两份文档分的是两件事

      SPEC.txt          语言是什么：词法、语法、求值、效果、模块、错误码
      CAPABILITIES.txt  宿主提供什么：四十一个内置，按能力分组

    板子那条线要回答的是前者 —— 规范里的语义在裸机上成立吗。而不是后者：
    文件、终端、线程、索引、arena 在板上也能用吗。

    二、所以有了一份只碰规范的判据

      examples/board-spec.hmoca

    它一个宿主能力都不碰：不读文件、不开终端、不起线程、不用索引表、
    不碰 arena 与 owned。print 是唯一的外部动作，而它属能力契约的第一组。

    覆盖七条：算术（余数、乘加、除法）、比较与布尔、控制流、递归与按名字调用、
    元组、记录、字符串。桌面上打出来的是：

      算术 1 7 14.285714285714286
      比较 true true false false
      循环 5050
      阶乘 720 斐波那契 55 大者 9
      元组 60 长 3
      记录 12
      字符串 4 abc

    而在 MPS2 上跑同一份，串口上逐行相同（后面多一行退出码字符与板侧读数）。
    这一条判据在真板子上同样成立 —— 第十五节那四行是同一件事的更小版本。

    三、六份自举层是另一个问题

    它问的不是「规范成立吗」，而是「板子上能自己编译吗」—— 那是自举，
    是第十七节那条线的后半。两件事的判据不同：

      规范    逐行相同的输出
      自举    六份装得下并跑得完

    把它们混在一个目标里，就会为了自举去压规范并不需要的东西。

    四、顺带量出来的一个数

    board-spec 在 MPS2 上 heap=64524，而 bigline= 4727:59136 ——
    4727 是 push 里操作数栈的 realloc，五万九全是那一次扩容。
    一个七行的程序也要一千零二十四项的操作数栈，那是下一步要查的：
    到底是真需要那么多，还是初始容量太小、翻倍太粗。

    五、真板子上也验过（2026-11-01，板子接回来的那一次）

    board-spec 烧到 Nucleo-F411RE 上，串口打出来的七行与桌面逐行相同：

      算术 1 7 14.285714285714286
      比较 true true false false
      循环 5050
      阶乘 720 斐波那契 55 大者 9
      元组 60 长 3
      记录 12
      字符串 4 abc

    而后面的读数是 heap=7052、items=8/64、frames=0/32 —— 与 MPS2 上那几个数
    一字不差。所以「规范在板上成立」这一句现在有真板子的读数，不只是替身的。

二十八、六份在这块板子上跑起来了：省下的正好是扩展的那张表
--------------------------------------------------------------------

    二十七节说「板子上的判据是规范，不是能力全集」。这一节把它落到数据结构上，
    而结果是一条里程碑。

    一、省掉的正是扩展

    帧记录 里原来内嵌着 Value 持有格们[32] —— 那是 owned 的登记表，
    而 owned 是扩展（design/MEMORY.txt 第 2 节），规范程序根本不用它。
    Value 是五十六字节，于是每一帧固定一千七百九十二字节；帧池一开就是三十二帧，
    光这一项五万七。

    改成指针、第一次真的用 owned 时才分配之后：

      board-spec 的 heap    64524 → 7052
      六份的 heap          113664 → 56192

    二、三个读数（真板子，Nucleo-F411RE）

      loadstep 函数表=8040 blocks 1
      loadstep 函数们=11024 blocks 604
      loadstep 全局名=11024 blocks 604
      depth=8  stack=2888
      depth=16 stack=2888
      1 + 2 * 3 → 7
      (1 + 2) * 3 → 9
      len("abcd") → 4
      10 % 4 → 2
      heap=56192

    六份（含 run.hmoca）在这块板子上装载、编译、求值、打印，一整套跑完 ——
    而那一整套就是「板子上自己编译源码」本身：run.hmoca 的自测正是编译并执行
    四段代码。

    三、账

      堆      56192    板子能给 79552
      栈       2888    常量，与深度无关
      合计    59080    再加上静态段 48520 是 107600，对 131072

    从「差三倍多」（堆一九三三九〇加栈十万）走到「装得下」，中间是四件事：
    名字池去掉（省 131072）、显式帧（栈变常量）、槽数组上堆、
    以及这一节把 owned 那张表从每帧里拿出来（省 57472）。

    四、一条方法

    「规范不是扩展」这句话落到代码上，就是「扩展的数据结构不该出现在每一帧的
    固定开销里」。而它省下的五万七比前三次优化加起来还多 —— 因为那三次都在压
    规范的实现，而这一次是把扩展从规范的路径上拿开。
