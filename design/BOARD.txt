板子这一侧：HMYR 在一个微控制器上跑
====================================================================

  2026-10-27 起。目标板是 Nucleo-F411RE（STM32F411RE，Cortex-M4F 96 MHz，
  Flash 512 KB，SRAM 128 KB）。这一页记的是「这条路走到哪儿了」，
  以及每一步用什么命令复现。

一、现在到哪一步
--------------------------------------------------------------------

    [成] 工具链进来：MSYS2 的 ucrt64 双栈

         pacman -S mingw-w64-ucrt-x86_64-arm-none-eabi-gcc make
         → arm-none-eabi-gcc 16.1.0、GNU Make 4.4.1

    [成] 编译：vm/hmyr.c 一行没改就编得过（除了那处 main，见第三节）

         text 161211 · data 8 · bss 3164（-Os，Cortex-M4）
         → 板子 Flash 512 KB，占三成

    [成] 在模拟器上跑通：QEMU 的 mps2-an385（Cortex-M3）

         examples/zone-ledger.hmoca 的完整输出（与板子上逐字一致）：
           行=4 总长=15
           各段=5,3,4,3
           关之前 held=5
           关之后 报告.live=1 zone=managed

         这个示例同时用上 arena、owned、managed 三区 —— 也就是说
         区模型在真 ARM 上是对的，不只是「打印了个数」。

    [成] 2026-10-28 烧上真板子并跑通

         同一份映像、同一个程序，串口（ST-Link 的 VCP，COM5，115200）
         读到四行输出与退出码 0。烧写用 OpenOCD：

           openocd -f interface/stlink.cfg -f target/stm32f4x.cfg \
             -c "program build/hmyr-board.elf verify reset exit"
           → device id 0x10006431 · flash size 512 KiB · Verified OK

         hello.hmoca 的判据也在真板上验过：串口读到 0x35（"5"），
         前面那一个 0xFF 是复位时线路上的伪字节，不是程序输出。

    [未成] 更小的栈：现在用的是 link.ld 里 8 KB 的栈（_estack 下方留的），
           而桌面上量到三区示例在 64 KB 栈下也跑得动 —— 板子上到底要多少，
           还没有逐档压过。

二、两个文件各自管什么
--------------------------------------------------------------------

    port/startup_cm4_gnu.s    向量表 + Reset_Handler（.data 拷贝、.bss 清零、bl main）
    port/link.ld              STM32：Flash 0x08000000 / RAM 0x20000000 / 栈顶 0x2001C000
    port/link-mps2.ld         MPS2：Flash 0x00000000 / RAM 0x20000000 / 栈顶 0x20100000
    port/arm-port.c           平台口：把「读字节码」与「写出口」换成内存里的两段
    port/board-main.c         板侧入口：装平台口、跑、把出口交给串口
    port/uart.c               Nucleo 的 USART2
    port/uart-mps2.c          MPS2 的 CMSDK UART
    port/Makefile             四根旋钮：CPU / UART / LDSCRIPT / PROGRAM

  两份串口、两份链接脚本、不是「一份带开关的」：三者都是「换芯片时要改的数」，
  而一个文件里放两套地址，最容易出的错是改了这边忘了那边。

三、为板子改的那一处
--------------------------------------------------------------------

    vm/hmyr.c 的 main 现在包在 #ifndef HMYR_BOARD 里。

    一条 #ifndef 就够，因为「这台机器与它跑在哪无关」这件事在 hmyr_运行 以下
    已经成立 —— 只有「从哪儿拿字节码、往哪儿写出口」是平台的事，而那两件
    本来就在 port/ 里。

四、怎么复现（三条命令）
--------------------------------------------------------------------

    在模拟器上跑（Cortex-M3）：

      cd port && make elf PROGRAM=examples/zone-ledger.hmoca \
        UART=uart-mps2.c LDSCRIPT=link-mps2.ld CPU=cortex-m3
      qemu-system-arm -M mps2-an385 -kernel build/hmyr-board.elf \
        -nographic -monitor none -serial stdio

    给板子编（Cortex-M4）：

      cd port && make elf PROGRAM=examples/zone-ledger.hmoca

    诊断用的心跳：编的时候加 -DHMYR_HEARTBEAT，程序会在输出之前先吐一个叹号。
    它把「没跑起来」与「跑了没话说」分开，而那是最费时间的一步。

五、三个已经踩过的坑
--------------------------------------------------------------------

    一、main 重复。vm/hmyr.c 有 main，board-main.c 也有 —— 链接器说 multiple
       definition。见第三节。

    二、objcopy 的符号名由「它看到的路径」决定。传 build/program.hmoks 会得到
       _binary_build_program_hmoks_start，而 board-main.c 等的是
       _binary_program_hmoks_start。差一个目录名就链不上，而弱声明的症状是
       「字节码是空的」—— 看上去像程序自己没跑。

    三、核不同。用 -mcpu=cortex-m4 编给 Cortex-M3 的 MPS2，M4 的 DSP 指令在 M3 上
       是未定义指令，症状是 lockup（R15 = 0，R14 = 0xfffffff9）。所以 CPU 是一根
       旋钮，不是一句优化选项。

六、下一步
--------------------------------------------------------------------

    ・真板子上验串口：烧一个只吐叹号的映像，看 ST-Link 的虚拟串口有没有反应。
      有反应，就说明 port/uart.c 那三个数（基址、引脚复用、BRR）都填对了。
    ・把 ST-Link 的烧写接进 Makefile（st-flash 或 openocd，看本机装哪个）。
    ・然后才是「更大的程序」：现在的三区示例只用了 bss 的一部分，
      而 bss 48128 字节已经是板子 SRAM 的三分之一 —— 下一次要量的是
      跑自举层那一格需要多少。

七、烧写：两个坑，都不是代码
--------------------------------------------------------------------

    第一个：驱动没装。板子插上之后 Windows 认出了设备，但 problem code 是 28
    （CM_PROB_FAILED_INSTALL），于是 pyocd 报 "No available debug probes
    connected"。而 Keil 的安装目录里自带那一套：

      D:\Keil_v5\ARM\STLink\USBDriver\stlink_dbg_winusb.inf   ← ST-Link Debug
      D:\Keil_v5\ARM\STLink\USBDriver\stlink_VCP.inf          ← 虚拟串口

    用 pnputil 装上（不需要 dpinst，它在这台机器上报了一个错误码）：

      pnputil /add-driver stlink_dbg_winusb.inf /install
      pnputil /add-driver stlink_VCP.inf /install

    装完之后 pyocd 能认到探针（STM32 STLink，唯一 ID 0666FF485282494867205545），
    虚拟串口也出现了（COM5）。

    第二个：pyocd 与这块探针不合。驱动装好、探针认得、串口也在，
    但 pyocd 仍然报 STLink error (5): No device connected；
    connect_mode=attach / pre-reset 与 frequency=1MHz / 100kHz 四种组合都一样。

    而同一个探针在 OpenOCD 下一次就通了：

      STLINK V2J28M18 (API v2) VID:PID 0483:374B
      Target voltage: 3.260887
      [stm32f4x.cpu] Cortex-M4 r0p1 processor detected

    所以「烧不了」这件事在换了后端之后就没了。现在 Makefile 的 flash 目标
    用 pyocd；真要烧的时候用 OpenOCD 那一行（第 4 节的命令），或者把
    PROBE 换成 openocd（这一条还没写进 Makefile）。

八、读串口时的两个讲究
--------------------------------------------------------------------

    一、复位与读取要同时进行。程序跑得比人快：main 返回之后才吐字节，
       而那时候串口工具往往还没打开。所以要先开串口、再复位，
       在 3 到 4 秒的窗口里收字节。

    二、收到的第一个字节常常是 0xFF。它不是程序输出，是复位时线路上的
       伪字节（起始位被当成数据）。判据要看 0x35 而不是看「有没有东西」。

    QEMU 的 stm32f4 模型里 USART 的 TXE 不置起，所以那条路只能验到
    「程序跑完」，验不到「串口通」—— 串口这件事只有真板子能验。

九、天花板：一个数字，和一处说不通的地方
--------------------------------------------------------------------

    量法在 tools/heap-census.mjs：编字节码、在桌面那台 C 机器上带 HMYR_MEM=1 跑、
    读它打印的堆峰值，再与板子的 128 KB 比。

      板子：SRAM 131072 字节 · 栈 8192 · 静态段 48128

      程序                    字节码      堆峰值      合计需要      判据
      hello.hmoca               70 B      92144     148464 B    差 17392
      arith.hmoca              485 B     103983     160303 B    差 29231
      zone-ledger.hmoca        985 B     131745     188065 B    差 56993
      twice.hmoca              202 B      97524     153844 B    差 22772
      view-window.hmoca        772 B    1237359    1293679 B    差 1162607

    按这张表，连 hello 都装不下 —— 而 hello 在板子上是真的跑通了（串口读到 0x35）。
    两件事同时为真，说明这张表量的不是板子上的那一件事。

    2026-10-28 验到底之后，结论与一开始猜的不一样，而两次猜错都记在这里。

    第一次猜「诊断自己在分配」。理由看着很顺：HMYR_MEM 要记下每次分配才能打印，
    而那份记录住在堆上。但把「不带诊断的峰值」量出来之后（HMYR_HEAP_ONLY=1，
    它只读那个一直在记的数），同一个 zone-ledger 在桌面上是 131635 字节，
    而带诊断是 131745 —— 只差 110 字节。诊断几乎不占地方，这条猜测不成立。

    第二次才找到成因：字长。桌面是 x64，指针与 size_t 都是 8 字节；
    板子是 Cortex-M4，两者都是 4 字节。而 VM 的堆上一大半是「值的容器」——
    值槽、元组项、记录字段 —— 它们在 64 位上每一项都从 8 字节起算。
    同一个 zone-ledger：桌面 64 位 131635 字节。

    第三次：字长只解释了一半。装 MSYS2 的 mingw32 工具链编出 32 位的宿主
    （PE32，Intel i386），同一个程序在新宿上是 75343 字节 —— 从 131635 掉到 75343，
    少了 43%，方向对。而板子上是 39322，比 32 位桌面还少 48%。
    两个都是 4 字节指针，所以「字长」不是唯一的差别。

    剩下的那一半，2026-10-28 用直方图找到了落点。

    做法：给 vm/hmyr.c 加一层分配直方图（按 8 字节一档，24 档，只在
    HMYR_MALLOC_HIST=1 时统计），并把它暴露成三条接口给裸机那一侧读
    （hmyr_分配档 / hmyr_分配档数 / hmyr_开直方）—— 板子上没有 stderr，
    所以诊断要能「被读走」而不是「被打出来」。board-main.c 在 heap= 之后
    多打一行 hist=。

    同一个 zone-ledger，两边各读一次：

      板子      0:55  8:72  16:22  24:3   32:3   48:2  56:51  112:4  184:12
      桌面 32 位 0:26  8:19  16:30  24:54  32:23  40:1  48:1  56:50  64:2  72:1  88:1  112:4  184:15

    读法：24 到 31 字节那一档，桌面分配了 54 次，板子上只有 3 次；
    而 0 到 15 字节那一带，板子比桌面多出约 80 次。总次数差不多（两边都是三百多次），
    所以不是「多分配了」，是「同一批分配在两边落进了不同的档」——
    桌面把某样东西当作 24 到 31 字节来要，板子上只要 0 到 15 字节。

    下一层：按调用点分桶。做法比预想的便宜 —— 不需要返回地址，也不需要 backtrace：
    把 hm_malloc / hm_calloc 包成宏，让 __LINE__ 作为参数传进去。它是编译期常数，
    传一次是一个立即数；关掉统计时编出来的代码与原来那次调用没有区别。
    board-main.c 在 hist= 之后多打一行 lines=，桌面上那条由 HMYR_MALLOC_HIST 打。

    同一个 zone-ledger，两边的 lines 各读一次（板子的行号与桌面不同，
    因为 -DHMYR_BOARD 让整个文件的 #if 分支变了，所以只能比次数，不能比行号）：

      板子      heap=39322  hist= 0:55 8:72 16:22 24:3 32:3 48:2 56:51 112:4 184:12
                lines= 1419:1 1280:46 1426:1 1427:1 1430:1 352:3 1063:1 801:95 4470:37 1088:13
      桌面 32 位 heap=75155  hist= 上面那张（24:54 / 32:23）
                lines= 4593:1 1419:1 1280:46 1426:1 1427:1 1430:1 352:3 1938:117 1893:1 1894:1 4470:37 4489:17

    能对上的站点有四个：1280（46 次）、352（3 次）、4470（37 次），以及 1419/1426/1427/1430
    那几个各一次的。对不上的那个是 GC：桌面上是 1938 行的 gc_分配 117 次，
    板子上是 801 行的同一个函数 95 次。

    而 1938 行那一句是 hm_malloc(sizeof(Gc块) + 字节) —— 也就是说，
    24 到 31 字节那一档就是 GC 块：16 字节的头加 8 到 15 字节的载荷。

    所以「差一半」的成因现在是这一句：那一档是 GC 块，而板子上的 GC 分配
    比桌面少 22 次（95 对 117）。而 24 到 31 那一档差 51 次（3 对 54）——
    两个数不一样，说明「少 22 个 GC 块」解释不了「少 51 个小块」。

    到此为止，而停在这里的理由要写清：再往下要回答「板子为什么少分配 GC 块」，
    而那要先确定「哪些载荷在板子上根本不产生」。那需要给 gc_分配 的每个调用者
    也编号（它有三个主要调用者：字符串、元组、记录），并再烧一次。
    那一步是可做的，但它是「继续调试」而不是「回答能跑多大的程序」——
    而这一节要回答的是后者，它已经有答案了：39322 字节，装得下。

    第三次：按种类分开。gc_分配 本来就有种类这个参数（0 值槽、1 字符串、
    2 索引项、3 索引），所以不用再编一套编号。桌面 32 位那一台给出：

      kinds: 0:1/56B  1:95/930B  2:8/9216B  3:13/260B

    种类 1 是 95 个、930 字节的字符串载荷 —— 平均 9.8 字节。而 GC 块的头是
    16 字节（一个指针、一个 size_t、一个 uint32 的标记、一个 uint8 的种类，
    对齐到 4）。所以每一个字符串块都该是 16 + 8 到 15 字节，也就是全都落在
    24 到 31 那一档。桌子那一台确实是 54 个落在那档（95 个字符串块里的一部分
    加上别的种类），而板子上那一档只有 3 个。

    这里有一个说不通的地方，写下来而不是绕过去：95 个字符串块，而 24 到 31
    那一档只有 3 个。两种可能，都没有验：
      一、板子上的 sizeof(Gc块) 不是 16（-mthumb 下 uint8 的对齐可能不同）。
         若是 8，那 95 个字符串块会落进 16 到 23 那一档 —— 而板子上那一档是 22 个，
         仍然对不上 95。
      二、板子上的 hist 与 kinds 不是同一批分配（比如 kinds 记的是全部 117 个，
         而 hist 只记了其中一部分）—— 而两个计数器都在 hm_malloc 里，按说不会。

    第四次：种类 × 档。桌面 32 位那一台给出：

      kindband 0: 72:1
      kindband 1: 16:29 24:53 32:9 40:1 48:1 64:2
      kindband 2: 184:8
      kindband 3: 32:13

    这张表把「95 个字符串块」拆开了：24 到 31 那一档的 53 个几乎全是字符串
    （加上值槽那一个，正好是整张 hist 里的 54）。所以那一档的成因现在没有疑问：
    它是字符串 GC 块，头 16 字节加载荷 8 到 15 字节。

    而板子上这一张表取不到，具体是这样：接口声明补齐之后 kinds= 那一行打出来了，
    但内容是空的（kinds= 后面直接换行），也就是 hmyr_种次 依次返回 0，
    而同一个二进制里 lines= 明明报着 841:95（95 个 GC 块）。
    kindband 那几行同样一行也没出来。

    顺着「kinds 为什么是空的」查下去，答案一次说清了三处说不通的地方：

      vm/hmyr.c 里 gc_分配 有两个定义：
        #if defined(__arm__) ...  →  { (void)字节; (void)种类; return NULL; }
        #else                     →  真的分配一个 GC 块
      也就是说板子上不编 GC 堆，gc_分配 是个桩。

    而字符串走的是这一条：

      static uint16_t *串存(size_t 码元数) {
        if (g_gc开) return gc_串分配(码元数);   // 桌面走这里：带 16 字节的块头
        else { malloc(码元数 * 2) ... }         // 板子走这里：裸载荷，没有头
      }

    于是三处都说通了：
      一、kinds= 是空的 —— 板子上 gc_分配 一次也不真的分配，g_种次 自然是零。
      二、板子上 lines= 里那个 841:95 不是「95 个 GC 块」，是 841 行的 malloc ——
         而 841 行正是上面那个 else 分支。两边都是 95 次，因为都是同一批字符串，
         只是桌面给它加了 16 字节的头、板子没有。
      三、24 到 31 那一档板子上只有 3 个：那 95 个字符串在板子上是 2 字节每码元的
         裸载荷（平均 9.8 字节），落在 8 到 23 那几档；而桌面是 16 加 9.8，落在
         24 到 31。差的那一半不是「板子少分配」，是「板子没有块头」。

    这就是成因。而它顺带回答了更大的一层：板子比 32 位宿主少一半，主要不是字长，
    是没有 GC 堆 —— 没有块头（每一块 16 字节），也没有值槽、索引项、索引
    各自的登记。95 个字符串上的块头是 1520 字节，而总差约 35833；剩下的是
    「GC 不编」这件事本身省下来的。

    所以这一整条线到这里是完整的：
      板子上没有 GC：gc_分配 是桩，字符串与数组直接 malloc。
      24 到 31 那一档是「字符串加 GC 块头」，而板子上没有那个头，所以那一档几乎空。
      39322 字节是这么来的，而它装得下这四台之外的第五台 —— 那块板子。

    所以这一节停在两个明确的句子上：
      一、24 到 31 那一档是字符串 GC 块 —— 有证据：两边都读到 hist，桌面还读到 kindband。
      二、板子上那一档只有 3 个 —— 事实；而为什么只有 3 个，还没有证据。
    第二句要的东西已经写清：板子上也要能读到 kindband 那一行，而它现在读不到。

    所以那张表现在说明的是：64 位的上界、32 位宿主的中界、板子在它下面，
    而「板子比 32 位宿主还少一半」这件事已经从「一团雾」变成「24 到 31 字节那一档」。

    三条各自的地位，改过之后是这样：

      一、带边界的 _sbrk 是真的改进了：越界从此是分配失败，而不是悄悄踩栈。
         这一条留在 port/arm-port.c 里，与量得准不准无关。
      二、heap-census 那张表要读成「64 位的上界」。它还没有改成读 HMYR_HEAP_ONLY，
         所以表里是带诊断的数 —— 而那个数只比真数多 110 字节，不影响结论走向。
      三、32 位宿主是一个参照，不是答案：75343 对板子的 39322，两个都是 4 字节指针，
         差的那一半还没找到成因。它证明的是「字长有用」，不是「字长够了」。
      四、view-window 那一行是另一件事：它的堆峰值 1.2 MB（64 位），
         因为 read_bytes 把 11 KB 读成字节元组，而每个元素在堆上是一个值。
         板子上跑不了它，而那与 128 KB 无关 —— 是「字节元组」这个表示
         在微控制器上太贵。

    一、复位与读取要同时进行。程序跑得比人快：main 返回之后才吐字节，
       而那时候串口工具往往还没打开。所以要先开串口、再复位，
       在 3 到 4 秒的窗口里收字节。

    二、收到的第一个字节常常是 0xFF。它不是程序输出，是复位时线路上的
       伪字节（起始位被当成数据）。判据要看 0x35 而不是看「有没有东西」。

    QEMU 的 stm32f4 模型里 USART 的 TXE 不置起，所以那条路只能验到
    「程序跑完」，验不到「串口通」—— 串口这件事只有真板子能验。

十、板子上的那条规矩：一个区，别在循环里建
--------------------------------------------------------------------

    既然板子上没有 GC（第九节），那「分配」在板上就是单向的：拿了不还。
    语言里唯一能一次还清的是 arena，而它的用法在板上有一个硬边界。
    这一节记的就是那条边界，连同我是怎么撞到它的。

    第一版示例：50 轮，每轮建一个区、轮末关掉，每轮里分 8 块。
    桌面上跑得很好（轮=50 累计=497 最宽=13）。板子上没有任何输出 ——
    串口读到的是四百多个零字节，而那不是输出，是线路噪声。
    连上调试器看 PC，它停在 arm-port.c 的 exit 里 —— 那是 hm_malloc 失败之后
    走的死循环。也就是说：内存耗尽了。

    而装载器早就说过这件事：HMYR-W0310，「an arena is built inside a loop:
    every round allocates a new one, so the total grows with the number of rounds」。
    第一条判据是它，而我没听 —— 那份示例正是它的反例。
    桌面上看不出来，因为关掉的区会被回收器收走；板子上关掉只是标成关，
    那块内存还在。

    第二版：循环外面建一个区，里面分 200 块，最后关一次。桌面上跑通。
    板子上又是零字节 —— 200 块加上块头超过了板上能拿到的量。

    第三版：同一个形状，20 块。板子上跑出来了，与桌面逐行相同：

      块数=20
      总长=111
      最宽=11
      关之前 held=20
      关之后 报告.live=1 zone=managed
      heap=58084

    所以板子上的规矩，写清楚是两句：
      一、arena 在板上是能用的，但它的容量就是板上能拿到的那么多（这一份 20 块、
         总长 111 字节、堆峰值 58084）—— 它不是无限的，而超了之后的表现是
         「串口什么也没有」，而不是一条说得清的错。
      二、别在循环里建区。HMYR-W0310 说的就是这条，而它在板上比在桌面上严重得多：
         桌面上那是浪费，板子上那是跑到一半就没了。

    示例在 examples/arena-on-board.hmoca。

十一、边界表：这块板子装得下多少
--------------------------------------------------------------------

    量法：examples/arena-on-board.hmoca，只改一个数（块数），烧上去，读串口。
    板子在 board-main.c 里本来就会打 heap= 那一行，所以每一档只要一次烧写。

      块数    heap 峰值    装得下
      20       58084       是
      30       75332       是
      40       没有输出     不
      50       没有输出     不

    「没有输出」是这样的：串口收到几百个零字节，而那不是程序的输出，是线路噪声。
    连调试器看 PC，它停在 arm-port.c 的 exit 里 —— hm_malloc 失败之后走的那条路。
    所以「装不下」的表现不是一条错误，是沉默；这一点在第十节已经说过一次，
    而这张表让它在数字上可查。

    由此得到两个可用的数：

      一、这一份程序在板上能到 30 块，heap 峰值 75332 字节。
      二、板子的 SRAM 是 131072，栈给了 8192，剩下的不是全部可用 ——
         静态段（bss）实测 48128。三者加起来 75332 + 8192 + 48128 = 131652，
         略超 131072，而它居然跑通了。这说明那个加法不严格成立：
         bss 与堆在同一片 RAM 里，而 bss 里有一部分是那块 4 KB 的出口缓冲，
         另外 VM 的静态数组也不全是常驻。要精确算得看链接脚本给的 end 与 _estack，
         而那两处正是 _sbrk 的界线 —— 见 port/arm-port.c。

    不做的事：把「装不下」变成一条可读的错。那需要在板侧给 hm_malloc 的失败
    加一条串口消息（现在它 fprintf(stderr) 然后 exit，而板子上 stderr 是空的）。
    那是一条小改动，但它会让这张表从「沉默」变成「说清」，所以它值得做 ——
    只是不在这一页，而进了下一轮。

[改] 2026-10-28 当天晚些时候：那条「沉默」已经被改成一句可读的话了。

  做的事：Hmyr平台 加了第三个回调 错误。有它的时候，要命的事走它
  （板侧那份 板子错 逐字节交给串口）；没有的时候退回 fprintf(stderr)，
  所以桌面上的行为一个字节没变。

  而 hm_malloc 那十几处原有的 fprintf + exit 全部换成 分配失败()，
  它报的是当时的堆峰值而不是这一次要了多少。理由：失败点在十几个地方，
  逐个传「要多少」会把改动散到十几个函数里；而「堆到哪儿了」是同一件事，
  且它更能说明「这个程序超出了这块板子多少」。

  同一份 50 块的映像，现在串口上读到的是这一行（44 个字节）：

    hmyr: out of memory, heap peak 90308 bytes

  而 20 块那一版照旧：块数=20 … heap=58084，逐行与原来相同。

  于是这一页那张表的两格「没有输出」从今天起应该读作「有一行文字」——
  而它仍然不是一条错误编号：这一层没有编号体系，它是一台机器在停下之前
  最后说出的一句话。

十二、自举层能不能装进那块板子：量了一次，答案是不能
--------------------------------------------------------------------

    这一节要回答的是一个具体的问题：Nucleo-F411RE 那块板子上，能不能跑自举层
    （self/ 里那几份），也就是「这块板子上跑的是 HMYR 自己」这件事能不能成立。
    做法是先量，不是先写。

    一、最小的一份由哪几份构成

      self/run.hmoca 的 import 是五份：lex、chain、stmt、body、eval。
      run 自己是启动器（读 argv、读文件、调进去），所以「读一份 .hmoca 并求值」
      真正要的是那五份。六份（加 run）是「连启动器一起」。

    二、它们编出来多大（实测，不是估的）

      node bin/hmyr.mjs --compile self/pack.hmoca <输出> self/lex.hmoca \\
        self/chain.hmoca self/stmt.hmoca self/body.hmoca self/eval.hmoca

        五份  →  71212 字节（279 个块）
        六份  →  90131 字节（353 个块）

      而 Flash 是 512 KB，所以字节码本身装得下 —— 装不下的话会是另一件事。
      真正的问题在 RAM：那台机器要把整份字节码读进来，建函数表与字符串池。

    三、读进来要多少 RAM（实测）

      把 five.hmoks 直接当 program.hmoks 烧上去（跳过编那一步），读串口：

        hmyr: out of memory, heap peak 91712 bytes

      也就是说：读到一半就耗尽了。而 91712 不是峰值，是失败点 ——
      真实需要量比它更大。

    四、与已知的几个数比

      20 块的 arena 示例      heap 58084   装得下
      30 块                   heap 75332   装得下
      40 块                   没有输出      装不下
      五份自举层              读到 91712   耗尽

      所以「读一份五份构成的自举层」要的 RAM，比这台机器上任何跑通过的程序都多。

    五、结论

      不能。 以现在这个读法（整份字节码读进 RAM、建完整的函数表与字符串池），
      五份自举层在这块板子上装不进来 —— 而且不是差一点，是差得比「30 块到 40 块」
      那一步还多。

      若要做成，可走的路只有一条：不整份驻留。让那台机器从 Flash 里按需读
      指令（函数表只放偏移与长度，字符串池按需解），于是 RAM 里只有「当前帧」。
      那是一次真正的改动：vm/hmyr.c 的读法要从「读进内存」变成「贴着 Flash 读」，
      而板子上 Flash 是可直接寻址的（0x08000000），所以那条路在硬件上成立。

      不做的事：换一块更大的板子。那会让「装得下」变成一个外部条件，
      而这一节要问的是「这台机器能不能」，答案是它现在的读法不能。

    这一节的用法：下次有人问「板子上能跑 HMYR 自己吗」，答案是
    「字节码装得下（71212 字节对 512 KB），而读法装不下（91712 就耗尽）」。

十三、以后可能加的两块存储：把这条路先画出来
--------------------------------------------------------------------

    2026-10-28 记：以后可能会给这块板子加两块 SPI 存储 ——
    W25Q256JVEIQ（32 MB，QSPI NOR Flash）与 MX35LF1GE4A（128 MB，SPI NAND Flash）。
    而现在按「只有 Nucleo-F411RE」来做：这一节不改任何代码，它写的是一条以后的路，
    以及那条路与第十二节那个结论的关系。

    为什么它值得现在就写：第十二节量出来的结论是「读法装不下」——
    五份自举层的字节码 71212 字节，而读进来要的 RAM 超过这块板子能给的
    （读到 heap 峰值 91712 就耗尽）。那一节给的唯一出路是「不整份驻留，
    贴着 Flash 读」。而 F411RE 自己的 Flash 是 512 KB，装得下字节码 ——
    也就是说那条路今天就在硬件上成立，不必等任何新零件。

    那么两块存储带来的是什么：不是「能不能」，而是「能放多少」。

      W25Q256JVEIQ   32 MB   QSPI NOR   —— 够放几十份字节码，且 NOR 可直接寻址执行
      MX35LF1GE4A    128 MB  SPI NAND   —— 更大，但 NAND 要坏块管理与页读，
                                           不能像 NOR 那样当地址空间用

    而 F411RE 的 SPI1 到 SPI5 都还空着，所以接上去在引脚上不冲突。
    这一页不写接线与驱动 —— 那些等零件真的到了再写，而那时要先回答三个问题：
    一、那块存储是从 SPI 还是从 QSPI（F411 只有 SPI，QSPI 要软件模拟或用 F446）。
    二、字节码放在外部存储上时，读它的是 hmyr_运行 的哪一层（现在那一层假设整份在内存里）。
    三、写一份字节码进去的工具在哪一侧（现在 write_bytes 写的是宿主文件系统）。

    所以这一节现在的状态是：画在那里，不施工。而它画在那里的理由不是「以后可能有用」，
    是「第十二节的那条出路，与这两块零件是同一件事的两半」——
    一半是读法（软件），一半是存储（硬件）。
