Himeyuri 的终端与文本工具：理念、出处与本项目的改动
====================================================================

理念
====================================================================

  集百家之长，成一己之胜。

这条理念的落实方式是一条纪律，而不是一句口号：

  每一项能力都要写明它学自哪里、以及我们改了什么。

说不出来处的能力，要么是没想清楚，要么是把轮子又造了一遍。这与 Himeyuri
在其他地方的做法一致：声明带出处，取舍写在明处，界外的事写下来而不是留白。


已经定下的分工
====================================================================

  ・可见字符进源码，控制序列留给运行时与工具。
    于是源码永远是可 diff、可签名、可搜索的纯文本，而屏幕上的效果照样有。

  ・字符分类与文本原语由宿主提供：len · slice · is_letter · is_mark · nfc · to_upper · to_lower。
    语言自己不带副本——副本会与它抄的那份标准渐渐分叉。
    这一条的例外是 C 那台（vm/hmyr.c）：它没有宿主可问，于是带着从 data/ucd 生成的副本
    （字母、记号、大小写、归一化四张表）。哪一天两份副本真的分叉了，分叉会把数字说出来——
    第一次量出来的结果是 Unicode 17.0 与 16.0 之间的五十六个码点，记在 design/C-VM.txt；
    2026-10 语料升到 17.0 之后，那个数归零。

  ・规范输出是 ASCII 记号；Unicode 记号在读取时接受并归一（接受宽、输出严）。
    否则同一份程序会有两种写法，格式器也就无从统一。


首批来源与我们的改动
====================================================================

  ・终端控制序列（学自 ANSI X3.64 与 ECMA-48）：不写进源码，由 term 模块在运行时产生。
  ・备用屏与光标（学自 ncurses 的 smcup 与 rmcup）：以结构化调用给出，term.enter 与 term.leave。
  ・双缓冲与差异刷新（学自字符界面的老办法）：只输出变化的格子；帧内容可注入、可断言。
  ・行编辑与历史（学自 readline 与 linenoise）：已做（shell.hmyr，方向键、Home/End、退格与 Del 都认）；
     全角标点与中文输入的组合：都做了（字宽 · 显示列 · 按字移动 · 列到位 · ime.hmyr 的预编辑）。
     顺序是：先让位置算得准，再让组合中的文字不进缓冲区——而后者是这条线真正的难点。
  ・文本原语（学自 POSIX 与 Unicode 属性表）：交给宿主；语言侧不复制属性表。
  ・标识符规则（学自 Unicode 的 ID_Start 思路）：L 类字母、M 类组合记号与下划线；标识符做 NFC 归一。
     混用多种文字的标识符会被报出 HMYR-W0001（这一条宿主词法里早就有了）。
  ・字符动画（学自终端艺术与 TUI 传统）：帧是数据，不是字节，于是动画也能进套件。

  ・按节拍驱动（学自 plaaosert 的 credits_public，即 Frums - Credits EX 的终端动画）：它按 beat 推进
     而不是按帧率推进，画面因此不随机器快慢而漂移。我们的改动：同样一拍一幕，但帧的内容是数据，
     所以每一帧都能被套件断言；它直接写 stdout，动画没法被自动验。
     注意：那个仓库没有许可声明，所以只学思路，不搬代码。
  ・场景栈与叠印（学自同一个仓库的 SceneManager）：它的 active_scene 是列表，每个活动场景各自请求
     下一帧，于是字幕可以叠在背景动画上。我们的改动：场景用名字分派（这门语言还没有一等函数），
     等函数值进语言之后可以收窄成一张表。
  ・字符定义与逻辑分离（学自同一个仓库的 string_defs.py）：字符长什么样是数据，怎么画是逻辑。
     我们的改动：字形放在 glyphs.hmyr、画法放在 term.hmyr，并让定义用点号写，好在编辑器里看得出形状。
  ・输入可注入（这是我们的改动，那个仓库没有）：它的键盘库直接嵌在程序里，于是输入只能靠手按；
     我们让真实终端与套件走同一个队列，于是「按键就停」能被自动验。

原来是「还没做」、现在已做的六条
====================================================================

  ・源码里出现控制字符或 Emoji 时报错，不沉默；全角标点与数学符号走别名归一。
      （已做：HMYR-E0006 与 lexer 里的 ALIASES 表）
  ・term 的尺寸、清屏、光标定位、颜色、帧延时。
      （已做：term.hmyr 与六个 term 内置，外加 sleep_ms）
  ・输出可注入：套件里用一个字符串缓冲，于是每一帧的内容都能被断言。
      （已做：套件换掉 rt.write）
  ・shell 与文本工具里的 shell。
      （已做：行编辑与历史、内建认法、执行层、会话层，各带套件）
  ・按差异输出：只重写变了的行（term.hmyr 的 画一帧差异；两帧一样时什么都不写）。
     一条与之俱来的限制：差异用光标定位，所以要求终端宽度不小于画布宽度。
  ・行编辑按「字」而不是码位：退格与删除都把基字与组合符号一起处理，
     不会留下孤零零的重音符。

还欠着的（写在这里，免得又变成「以为做了」）
====================================================================

  ・全角标点与中文输入法的处理：做了底座，还差组合过程。
      已做：字宽（零宽的组合符号、二宽的全角与 CJK、一宽其余）与显示列——
            于是「光标该去第几列」可算，而那正是折行与光标定位共同需要的。
      又做：光标按「字」移动（左一字／右一字），于是按左右键不会停在
            组合符号中间——那一步在屏幕上看起来像「按了没动」。
      再算上：列与位之间的换算（列到位／折行位），于是「第几列」能找到对应的码位下标，
            而折行与光标定位共用这一处换算。它加了一层而没有改「位」的语义——
            那是刻意的：一次只动一处，于是现有的每一条验收都不受影响。
      再往前一步：按列插入（在列插入）与光标所在列（光标列），于是编辑器能用列说话，
            而缓冲区里仍存码位——两层之间由 列到位 接起来。
      现在做了：输入法的预编辑（ime.hmyr）。状态是 (缓冲, 位, 预编辑)，
            而那条规矩是——组合中的文字不进缓冲区。理由写在文件头上：
            输入法会反复改写它（n → ni → 你），若中间态进了缓冲区，
            用户按左键、按退格就会碰到那些从不该存在的东西。
            组合中按退格删的是预编辑；取消什么也不留；定下时只进最后那一个。
      仍留着的：shell 的状态还是 (缓冲, 位)，而位是码位下标。按列插入与光标列都做好了，
            所以「用列说话」的路已经通了；而把状态本身改成列，是一条会牵动每一处编辑键的改动——
            在它真需要之前不做，是刻意的：一次只动一处。
            而 shell 的状态仍是码位形状——那是刻意的，因为它还够用）。
  ・文本工具那一半：格式化器早就有了（src/format.mjs，M6），另加一层空白规范化（whitespace.hmyr）。
     还欠的是语言服务器（LSP）——而它要 AST 反射，那是下一件。

这份文件是草稿，随实现更新；每加一项能力，就在上面的表里补一行。

发布流程：曾判定不搬，现在可以搬了
====================================================================

package / manifest / verify / release 四件仍是 JS。判据来自 test/ 那四套，
而它们全都要求清单里每个文件带 sha256、整份带 digest —— 于是问题落在 SHA-256 的代价上。

第一版的判断是「卡在没有位运算符」，还量了数：self/sha256.hmyr 对 src/eval.mjs
（约 30 KB）跑了三十分钟没有出结果，进程常驻 1.5 GB。

那个判断错了一半。把位运算做成内建（位与 / 位或 / 位异或 / 位非 / 位右移 / 位加 /
位循环右移 / 位循环左移，落到与 数组 / 设 相同的七个位置）之后，同样的测量仍然是
十五分钟超时。真正的大头是填充那一步：

    出 = 出 + (字节,)

三十 KB 就是三万次元组重建，平方级。换成块化加折平拼接（每 1024 字节封一块）之后：

    src/eval.mjs（约 30 KB）   4.14 秒，哈希与 node 的 createHash 一致

同一句教训出现过三次：deflate 的编码器、deflate 的解码器、现在是 SHA-256 的填充。
「往一个元组上一个个追加」在这门语言里永远是平方级，写法要换成块化加折平。位运算内建
也有用（它让消息扩展那一层回到常数时间），但它不是这一处的主因。

四件工具因此可以搬了：按 30 KB / 4 秒估，这份仓库的清单在十几分钟量级，可以接受；
真要更快，下一步是让 sha256 只对要进清单的那部分文件算，而不是把整棵源码树过一遍。
在那之前，这一层保持 JS —— 不搬的理由从「搬不动」改成「还没搬」。


发布流程：还差两层，以及为什么这一版停在这里
====================================================================

读过 tools/verify.mjs 之后，前置条件从一层变成三层。按被卡住的顺序：

  一、位运算            已补。八个内建落在七处，30 KB 的哈希从三十分钟以上降到 4.14 秒。
  二、列目录 read_dir    未补。manifest 要遍历 runtime/、tools/、design/，而语言里没有列目录。
                        src/capabilities.mjs 里有个 io.file.directories，它对应 ensureDir（建目录），
                        不是列目录 —— 名字像，用起来不是那件事。
  三、JSON 解析与生成     未补。verify 要读清单里的 [{file, sha256}]，还要把整份清单重新序列化
                        成与原文逐字节相同的形式（键序、两空格缩进），再比 digest。后半件比解析
                        更难：它要求复刻一个特定实现的输出字节。

三样各自独立，也都不是「打包逻辑」的一部分。四件工具里 manifest / verify / release 三件都
要 JSON，package 要 manifest —— 于是没有一层能先落地。

这一版的结论因此是：第一件不搬，理由是上面三层，一层一层写在这里，而不是一句「还早」。
要搬的话，顺序是 read_dir（一轮）、JSON（两轮）、然后才是四件工具。


发布流程：verify 搬了第一版，digest 还差接线
====================================================================

上一节说 JSON 未补，那句话说错了一半。json.hmyr 一直有解析器（test/json.test.mjs 在测它），
真正缺的是生成与「串到 UTF-8 字节」这两步。这一轮补上了：生成（紧凑与两空格缩进）与
node 的 JSON.stringify 逐字节一致；从文本 按 UTF-8 编码，与 Buffer.from 的字节一致，
覆盖基本多文种平面，超出这一层的码点明写在文件头。

于是 verify 能搬第一版了。self/verify.hmyr 逐行扫清单，不做整份解析：

    真清单（21568 字节，两百零一项）  64 秒
    对得上 200 项，不对 0 项，缺 0 项

它验的是每一项的哈希。整份的 digest 还没验 —— 那一步要「删掉 digest 字段、重新生成、
转成字节、再算哈希」，四件东西（解析、生成、从文本、sha256）现在都在了，差的是把它们
串起来。那是下一轮的事，不是缺能力。

read_dir 仍然没补，而 verify 不需要它：清单自己带着每一条的路径。

为什么不解析整份：json.hmyr 的解析器用元组追加写，二十一 KB 的清单会让它平方级超时。
逐行扫的代价写在文件头 —— 它丢掉了结构，tools 与 design 两个前缀只能靠「这一行落在
哪一段里」推出来。

途中抓到四个错，全在「解释器能跑、字节码那台不能」的分界上：

  一、main 少声明 process 效果。verify 与 self/sha256.hmyr 各一处，解释器不查这个。
  二、self/sha256.hmyr 的 位长 用 let 声明却在循环里赋值。解释器不查可写性，
      字节码那台报 R0150 —— 而 sha256 那九项测试一直是绿的。
  三、跑字节码 调 合并程序 时没交入口那一份，于是被 import 的自测 main 抢走了入口。
      症状是「跑 verify，输出的是 sha256 的哈希」，安静得可怕。
  四、逐行扫一开始判的是「这一行含不含某个键」。清单里有一个套件就叫 sha256，
      它的 name 行写着 "name": "sha256"，于是那一行被当成哈希行，读出来的哈希是
      字面量 sha256 —— 而标签还是上一项的路径。改成判键名，不判内容。
