文件类型：扩展名、目录名与改名办法
====================================================================

  这一页定两件事：哪些文件按扩展名分派、哪些按目录区分。
  判据只有一条 —— 读它的程序要不要先知道它是什么。
  要，就给扩展名；不要，就给目录名。

一、扩展名
--------------------------------------------------------------------

    hmoca    源码              ひめおちゃ      流动的、会被人改的
    hmoks    字节码            ひめおかし      固定的、拿去就跑
    hmtn     种子              ひめたね        自举的根
    hmnkk    一般文本          ひめにっき      给人读的
    hmoug    配置文本          ひめおうぎ      被工具读的
    hmknst   错误码与用例      ひめけんさつ    三张表：码、用例、人话
    hmkit    套件清单          ひめきっと      哪一套跑哪些文件
    hmkgr    乐曲与场景        ひめかぐら      数据与程序同体
    hmbnso   说明书与集成文    ひめぶんしょ    SPEC、README、发布说明

  另有一个容器型（hm-ittgn-krgn-m），判据与上面九个都不同，见第三节 ——
  上面九行按「文件怎么被读」分，它按「整包怎么被装、被跑、被转换」分。

  为什么源码只有一个（hmoca）而不是「常规」「特殊」两个：
  运行档位不是文件类型，是这一个文件对运行时的要求。它该写在文件头，
  随内容走 —— 因为同一份源码可能两种情形都跑。扩展名只有一位，
  让它说「这是什么」，不说「它想怎么跑」。

  文件名不能表达的东西不要塞进文件名：塞进去的样子，是同一份源码
  为了两个运行档位要存成两个名字。

二、名字（目录或集合），不是扩展名
--------------------------------------------------------------------

    hmkoudi  鏡台    对照实现        src/ 里那六个只做对照的模块
    hmszrbk  硯箱    工具链          写字的家伙
    hmzsnt   厨子棚  语料与外部表    摆着等被取的

  这三个改了不会让任何工具换读法 —— 它们让读代码的人知道这一格是什么。
  镜子照的是自己：对照实现不参与跑程序，它的存在只为「两台机器同一个答案」
  这一句。所以它不该被算进产品目录，也不该被删。

  硯箱与厨子棚都是容器，差别在装什么：前者是「我要动手时取的」（工具），
  后者是「摆着等被取的」（语料、编码表、色彩档）。

三、容器型：.hm-ittgn-krgn-m
--------------------------------------------------------------------

    hm-ittgn-krgn-m   容器    ひめ いつつぎぬ からぎぬ も

  一个很灵活的 .exe：自己带着运行逻辑，所以能直接跑；同时是一种特殊的压缩包，
  能被装进别的包，也能装别的包。名字取自十二単 —— 一件能穿的和服，摊开是十二层布。

  形状：

    单文件，允许 GB 级，不设数据量上限
    内部至多 12 层嵌套
    层里放 HMYR 原生扩展名（hmoca · hmoks · hmnkk …）与 HMYR 支持的外部格式
    扩展名只在最外层出现一次

  三条要紧的规矩：

    一、深度各自算。每个容器数自己那 12 层，不从外面累加 ——
       否则一叠套娃，外层两层加内层十层就超了限，而它们本来互不相干。

    二、容器里不出现 hmsnp 与 hmhsr。那两个是容器逻辑的一部分，不是成员。
       写成成员的样子是「转换一次多一份副本」，往返两次就是四份。

    三、不进 SDK 与 OS 的发布包。理由是分发：单个文件过大会撞上传限制。
       它只在该在的地方生成 —— 用户装好之后在自己机器上即时编译。
       最基础的制作依赖是完整 HMYR 库，不需要 SDK，也不需要 OS。

  它填的是仓库里一条已有的欠账：package.hmoca 的文件头写着「几 MB 的语料是几百万个值，
  读进来先撞内存」，所以 runtime/ucd 那 45 MB 不进包。语料与外部档案该去的地方，
  就是它在用户机器上编出来的这一个容器。

四、转换产物里的两个入口
--------------------------------------------------------------------

    hmsnp    さんぽ    稳定    资源吃得少、结果稳、速度固定
    hmhsr    はしれ    弹性    吃满硬件、动态调度、速度可变

  档位由后缀定，不由文件内容猜 —— 与「源码还是字节码」那条同一条规矩：
  判据要能被一眼核出来。判断只写一处：JS 侧在 tools/file-kind.mjs 的 档位，
  C 侧在 vm/hmyr.c 的 步限从环境。

  两档落在两个已经存在的数上，不是新编的：

      steady    步限五百万（C 那台一直以来的默认）、GC 开、线程池一个槽
      elastic   步限两亿（启动器主路径一直以来的默认）、GC 关、线程池用编译期那个数

  所以「内容相同」与「行为不同」可以同时成立：决定行为的是名字，而名字在文件名上。
  一份普通的 .hmoca 没有档位，仍然落在两亿 —— 多了两档不改变普通文件的跑法。

  这三项在两侧都生效，而池这一项两侧各数各的：
  C 那台数它的线程槽（vm/hmyr.c 的 线程起），JS 那侧数它自己的线程表
  （src/minimal-eval.mjs 的 thr_spawn）；两处都按后缀定的档位取上限。
  2026-10-26 之前最小求值器的 thr_spawn 是桩（恒返回 -1），于是「线程」在默认跑法里只是一个名字；现在它起自己的工人，两侧都有判据。

  两档不是性能开关，是同一条语义的两种资源策略。它与 design/MEMORY.txt 的三区模型
  不是同一件事：三区是内存管理模型，两档是资源预设。混着说会让「两档做完了」听起来像「三区也做完了」。

  容器里那份运行逻辑可以按环境自选余地，所以容器是一个文件；而通用压缩包没有运行逻辑、
  自选这件事无人可做，于是转换时两个都编出来，放在包的根目录：

    容器 → 压缩包     释放运行逻辑，编成 xxx.hmsnp 与 xxx.hmhsr，落在根目录
    压缩包 → 容器     把根目录那一对吸回去，成为运行逻辑，不再是成员

  判据：同一份内容、两个入口、零份副本。两个入口都从自己所在的目录读成员。
  不写这一条，往返一次就会变成两份内容。

  所以「转换」不是退化：压成通用格式之后内容仍旧能跑，只是跑的人要自己挑档。

五、还没对应物的一个
--------------------------------------------------------------------

  hmoug（配置文本）现在没有文件可管：仓库里被工具读的文本还住在 .mjs 里
  （conformance 那三张表就是）。它是为产品配置留的，等第一个产品落地再用。

六、不该改的
--------------------------------------------------------------------

    data/*.txt             UCD 语料，有主
    deps/*.icc             ICC 色彩档，国际标准
    deps/encodings/*       编码表，同理
    manifest.json          发布清单，选 JSON 正是为了让外人能验
    *.sig                  ssh-keygen 的产物
    vm/pack_seed.h         给 gcc 读的 C 头
    port/*.c .s .ld .sct   工具链的格式

  这些要么有国际标准的主人，要么要交给编译器与外部工具读。
  改了名，认它的人就找不到了。

七、改名的三步走
--------------------------------------------------------------------

  一、工具同时认两套（那一步的旧名是 .hmyr 与 .hmyrb）。凡是有扩展名判断的地方
      —— vm/hmyr.c、bin/hmyr.mjs、src/loader.mjs、src/code-file.mjs、check-docs
      的扫描规则 —— 先加新的、留着旧的。

  二、批量改名。git mv 一次做完，旧扩展名一个不留。

  三、删掉旧的判断，跑一次全量。

  反过来做（先改名后改工具）会留下半个仓库两种后缀，而那种状态最难查：
  工具认一半，剩下那一半安静地不被扫到。

  第二步的实际经过（2026-10-26）：八十七个文件改名，一百九十九个文件的引用重写。
  走过的弯，一条一条记在这里，因为每一条都是「不会报错」的那一类：

    一、判断不只在 JS 与 C 里。self/manifest.hmoca 与 self/package.hmoca 里各有
       两处「以尾(名, 后缀)」，决定 runtime/ 下哪些文件该进清单、该进包。
       第一遍只看了 .mjs 与 vm/hmyr.c，于是这两处漏了 —— 而漏了的样子是
       清单与包都少几项，退出码仍是零。

    二、产物名要与种子的改名成对改（这一段里写的 .hmyrb 都是旧名）。C 那台会把「以 .hmyrb 结尾的临时路径」
       改写成 .seed.hmyrb；临时路径先移到 .hmoks 而这一对没跟上，种子文件
       与编译产物就会同名。

    三、名字派生的东西要跟着看。objcopy 从输入文件名造符号，于是
       program.hmyrb 变成 program.hmoks 之后，符号成了 _binary_program_hmoks_start，
       而 port/board-main.c 还声明着旧名 —— 弱声明静静落空，arm 报
       「字节码不在映像里」，那读起来像链接脚本的问题。

    四、字节码里带着 import 路径。四份 runtime/ 产物必须重生成，否则每个产物
       都会去找已经不存在的 .hmyr。

    五、最后一处藏在打包器的一个正则里：tools/package.mjs 收文件那一行写着
       /\.(mjs|hmyr|txt|md)$/。包照样打得出来、退出码照样零、清单照样说「全对」，
       只是 runtime/ 下的 .hmoca 与 .hmoks 被那一行滤掉了。
       症状是 package 那一套报「缺 2 项」，而缺的正好是仅有的两份 .hmoca。

  这五条的共同点：改名最危险的地方不是报错，是「少了几样东西而没人喊」。
  所以第二步之后要跑的不只是编译，还有清单与包 —— 它们数的是「东西在不在」。

这一页自己的验收
--------------------------------------------------------------------

  每个扩展名一行判据；每个「名字」说清它不让工具改什么。
  改名走完之后，tools/src-roles.mjs 与 tools/builtin-gap.mjs 这类量具
  不该有任何一处还写着旧扩展名 —— grep 一次就能核。
