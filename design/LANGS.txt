三台机器与三层就位：语言分层的判据
====================================================================

为什么这一份不是「把 JS 换成 Rust」的计划
--------------------------------------------------------------------

  用户的方向是三层分工：中重量级语言为核心建设参考，轻量级语言辅助优化，
  专门类语言介入针对性开发。方向是对的，而「降低 JavaScript 使用率」这句话
  落到这个仓库上会指向一个错的行动 —— 因为使用率按什么算，决定了该动哪里。

  按文件数算，三百四十六个 .mjs 里二百二十三个在 test/；按行数算，四万八
  千一百三十二行里二万七千五百一十八行在 test/。无论哪个口径，第一大的那块
  都是测试脚手架，而测试脚手架本来就该留在轻量级语言里。

  也就是说：若以使用率本身为目标，最省力的一步是重写测试，而它换不来任何
  架构收益。所以这一份不打算把使用率当目标。它要给的是另一条口径。

  这一份改过两次判断，两次都是同一个病：拿自举的账去算分层的账。第一次说
  「前端只有一台机器」，第二次说「第二台前端踩在 JS 求值器上」—— 两次都在
  找一个不在这一层存在的缺口。第三版把它们分开，而分开之后这一层的结论很短：
  三层都就位了。

量出来的账（2026-11-17，工具实测）
--------------------------------------------------------------------

  口径写在这里，因为头一版这张表栽在口径上：它只数了六个目录，却写成「全仓库」，
  因此每一个数都偏小，而偏小的原因还藏在一句 -ErrorAction SilentlyContinue 里
  （读失败的文件被静默跳过）。现在这一份只数参与构建与验收的十三个目录 ——
  src、tools、test、self、lib、kpb、bench、conformance、vm、port、deps、bin、
  bootstrap —— 不含 examples、probes、data、runtime、dist、build 与 .git；
  行数是文件全文按换行切开的段数。同一条口径写在 tools/check-langs.mjs 里，
  判据与本表共用它，所以两边不会各自漂。

      src/          41          10,620      宿主参考实现
      tools/        71           8,768      工具链与发行

    HMYR 自己写的代码（21,087 行）是 C 那份的两倍半以上，而 JS 那四万八千里
    真正属于「这门语言的核心语义」的是一万零六百二十行。而这台工程的重心不在
    JavaScript 里，它在 test/ 里；test/ 却不是重心。

  现存的四份语言里，只有 Python 那七百四十七行是随时可以换掉的：它是 deps/
  下的窗口探测与 PNG，跑在开发机上，不进任何发行产物。

  这张表本身就是判据的输入：套件 langs 读上面四行总量，与盘上对账 —— 文件数
  精确，行数给一成，另加三条主张（test/ 的行数多于 src/、HMYR 自己的行数是
  C 的两倍以上、Python 只在 deps/）。所以改这张表不是改文档，是改一条判据的
  期望值：文件数变一个就得改，因为文件数是结构；行数不必天天跟，因为行数每天
  都在动，而一条天天要改文档的判据最后会被改成「见代码」。

三台机器，而不是一台主机
--------------------------------------------------------------------

  这个仓库里同时有三台能跑 HMYR 的机器，而它们的边界不一样：

    机器一   src/*.mjs        源码 → 词法 → 语法 → 求值／编码。全在 JS。
    机器二   vm/hmyr.c        字节码 → 结果。不经过 JavaScript。
    机器三   self/*.hmoca     源码 → 词法 → 语法 → 求值 → 编译 → 打包，
                              全部由 HMYR 自己写。跑在 src/eval.mjs 上。

  三台不是冗余，是这条工程最值钱的东西：两台机器对同一份输入给同一个答案，
  才使得「规格」与「实现」是两个词。判据已经有一批，而且不是一条：
  test/self.test.mjs（扫描器对反射器）、test/self-lex.test.mjs（词法逐 token）、
  test/self-body.test.mjs（函数体）、test/adapter*.test.mjs（宿主与自举对同一份
  源码算同一个数，分表达式、语句、函数表三层）。

三层分工，每层在这个仓库里的落点
--------------------------------------------------------------------

  一、中重量级 —— 核心语义的参考实现

    这一层管「同一份源码，两个独立实现，同一个答案」。语言里属于它的：
    词法、语法、作用域与闭包、字节码编码、求值。

    落点是 vm/hmyr.c，它已经在，而且已经能跑自举层：design/BOARD.txt 第 713 行
    记着「五份自举层在这块板子上跑完了」，design/FULLSELF.txt 第四十一件记着
    「第四台机器把自举层跑起来了」。所以这一格不缺东西。

  二、轻量级 —— 脚手架与胶水

    这一层管「让判据跑起来」，不管「答案是什么」。属于它的：test/ 的二万七千行、
    tools/ 里的一次性普查脚本、bench/、发行脚本的粘合。

    限制只有一条：核心语义路径上不许出现它。判据不是「JS 有多少行」，而是
    「src/ 里每加一个 .mjs 之前，有没有问过它属于哪一层」。

  三、专门类 —— 链接期与裸机

    这一层管「换一种语言能直接换到别的东西」。属于它的：port/ 的 .ld 链接脚本、
    .sct 分散加载、.s 汇编、deps/ 那 23 个 .icc，以及隔壁 Yunooka 的 NASM。
    HMYR 自己也在这一格里长出来：它是给 KID 那层用的领域语言。

结论：这一层不缺缺口，缺的那一段不属于这一层（第三版）
--------------------------------------------------------------------

  把三层的账分开算之后，答案是短的：三层都就位了。

    ・中重量级有 vm/hmyr.c（6,780 行），且已能跑自举层。
    ・轻量级是 tools/ 与 test/，位置对。
    ・专门类是 port/ 与隔壁的 NASM，位置也对。
    ・机器三（self/ 那六十三份 .hmoca）也在，而且里面有 self/vm.hmoca。

  头两版都在这份文档里找了一个不在这里的缺口，因为把两件事混在一本账上：

    ・分层问的是「同一层有没有两支独立的实现、它们能不能对上」。
    ・自举问的是「这个仓库里还剩下多少不是 HMYR 写的行」。

  自举那本账在 design/FULLSELF.txt，它有自己的四段路线，而第三段写着：
  「字节码机：先让 HMYR 写的 VM 跑通 test/bytecode.test.mjs，再接 C 那台的位置。
  这一段最长。」——那一段确实还差着，而它不属于这一份。

  它差到哪一格，可以量：self/vm.hmoca 八百一十六行，能装载 .hmoks、能执行、
  能认二十二个内置，而它自己的判据是「把这 22 个正好够把 examples/hello.hmoca
  从源码跑到 5」（test/vm-boot.test.mjs）。FULLSELF 第三段要的是下一格：
  test/bytecode.test.mjs。两格之间差多少，是自举那本账要量的，不是这一本。

  所以这一份到此为止。它结清的是一句更短的话：分层已就位；想去补缺口，先看清
  缺口在哪一本账上，否则会去补一个不缺的东西 —— 这一份自己就是这样错了两次。

门禁
--------------------------------------------------------------------

  一条可检查的规矩，替代一个不可检查的比例：

    ・src/ 下新增的 .mjs 必须有理由，理由里要写它属于哪一层。属于核心语义的
      不得以 .mjs 新建 —— 已有的不强制迁，新开的不许再添。
    ・test/ 与 tools/ 不限语言，但 tools/ 里凡进入发行产物的那几份
      （release、package、verify、manifest 一路）按核心对待。

  这一条现在是一条判据：套件 langs 跑 tools/check-langs.mjs，它读本文件第九节
  那张清单，与 src/ 的实际文件对账 —— 盘上有而清单里没有是「新文件没登记」，
  清单里有而盘上没有是「清单过时」，两向都红。所以往核心语义里加一行 JS，
  代价是先在这张表上写一个词，而那个词要说清它属于哪一层。

已定：C++（用户 2026-11-17 点下）
--------------------------------------------------------------------

  决定的理由不在四个候选的内部比较里，而在它上面那条链上。用户的原话是：
  「hmyr 还需要一个完整的 ynok 基础库以自建，所以可以考虑选择 C++」。

  这句话说的是一条依赖。HMYR 要自建（design/SELF.txt 那条路），先要有一个
  在裸机上跑得起来的基础库；而 Yunooka 那边这一格叫「必须住在基础库里的
  东西」—— design/LAYERS.txt 与 design/NAMES.txt 两份清单，加 PLAN 的
  system-software 那一条，列的是 Ichiwatashi、Nanodesu、Torikago、
  Volcano-Separator、Oak-Barrels、KID 六件。那个库现在一行都没有。

  所以 C++ 要买的是那块地 —— 一个与 vm/hmyr.c、与 port/、与将来那个基础库
  共用一个世界的宿主。它买不到 SPEC 里「不做未定义行为」那条的保证，所以
  代价那一栏仍然成立。

  而用户在同一天把时间线也说了：「速度方面暂时不着急，等到 ynok 完善后还要
  再建一次 hmyr 的」。这一句把 C++ 的位置又说清了一层 —— 它不是给第一代补
  一块地，它是第二代 hmyr 的基座：

    ・第一代（现在这棵树）：src 的 JS 参考实现加 vm/hmyr.c 加 self 的自举那一族，
      目标是 FULLSELF 那本账里的一百。它还差一格没走完 —— HMYR 写的字节码机
      接 C 那台的位置 —— 而那一格今天不急：判据已经在跑（bytecode 的三台里
      就有它），而「慢三个数量级」这件事在这一代里改不动。
    ・第二代：ynok 完善之后，在一个已经有 C++ 基础库的裸机环境里重造一遍。
      那一遍从头就不必问「脚本语言能不能当宿主」这个问题。

  于是「提高 C++ 使用率」这句话在这个仓库里的意思不是「把 src 改写一遍」，
  是「下一次建造从 C++ 起」。前者要动四万多行，后者要动的是还没写的那一部分 ——
  而后者才是集百家之长那句真正指向的路。

另外三个为什么没选
--------------------------------------------------------------------

  ・Rust：与 design/MEMORY.txt 那条「全所有权，安全最强，但学习曲线把下限
    压死」直接相接，也是这门语言读过并部分采纳的那一套。它没有运行时，与
    C 那份机器二也能直通 FFI。没选的理由不是它不好，是它的好处落在「与规格
    自洽」上，而这一格要买的是「与地基同侧」—— 两件事不冲突，只是先后。
  ・C#：与 SPEC 借来清单里「C# / Java：丰富类型系统、泛型、大标准库、LSP 与
    调试器」直接对应，工程性与调试体验最好。它进不了裸机那一侧，而这一格
    的第一件东西恰恰要在裸机上跑。
  ・Java：与 C# 同一档，差别在这台机器上更小。

  记下这三条不是礼貌。下一次要动工具链那一侧（格式化器、LSP、反射），C# 那
  条会更值钱；下一次要给一门新方言做前端，Rust 那条会更值钱。这条决定只对
  「给自举那一层换一块地」这一格成立。

这一份怎么被检查
--------------------------------------------------------------------

  三条主张，两条已经落到判据上，第三条被移出了这一份的范围：

    ・台数的账：成了。套件 langs（tools/check-langs.mjs）读第二节四行总量与
      盘上对账 —— 文件数精确、行数给一成、三条主张用不等式。
    ・门禁那一条：成了。同一个套件读第九节那张表，与 src/ 实际文件两向对账。
    ・缺口那一条：不在这份文档里。第三版把它交还给 design/FULLSELF.txt 的
      第三段 —— 那一段有它自己的判据（test/bytecode.test.mjs），而这一份
      只管分层。把两本账混起来写，正是前两版错的原因。

  三版改下来只留一句该记住的：一份判断写错之后，要改的往往不是它指向的行动，
  而是它引用的那个事实 —— 以及它没有分清的那本账。
