三台机器与一块地：语言分层的判据
====================================================================

为什么这一份不是「把 JS 换成 Rust」的计划
--------------------------------------------------------------------

  用户的方向是三层分工：中重量级语言为核心建设参考，轻量级语言辅助优化，
  专门类语言介入针对性开发。方向是对的，而「降低 JavaScript 使用率」这句话
  落到这个仓库上会指向一个错的行动 —— 因为使用率按什么算，决定了该动哪里。

  按文件数算，三百四十六个 .mjs 里二百二十三个在 test/；按行数算，四万八
  千一百三十二行里二万七千五百一十八行在 test/。无论哪个口径，第一大的那块
  都是测试脚手架，而测试脚手架本来就该留在轻量级语言里。

  也就是说：若以使用率本身为目标，最省力的一步是重写测试，而它换不来任何
  架构收益。所以这一份不打算把使用率当目标。它要给的是另一条口径，以及
  这条口径下的具体缺口。

  第二版改了一处判断，改法记在第五节末尾：这一份的头一版把「第二台前端」
  当成了缺口，而取证之后发现前端有两台，缺的是跑第二台的那块地。判断改了，
  判据没改 —— 它们本来就指向这件事。

  现存的四份语言里，只有 Python 那七百四十七行是随时可以换掉的：它是 deps/

  这张表本身就是判据的输入：套件 langs 读上面四行总量，与盘上对账 —— 文件数

  C 的两倍以上、Python 只在 deps/）。所以改这张表不是改文档，是改一条判据的
  期望值：文件数变一个就得改，因为文件数是结构；行数不必天天跟，因为行数每天
  都在动，而一条天天要改文档的判据最后会被改成「见代码」。

三台机器，而不是一台主机
--------------------------------------------------------------------

  这个仓库里同时有三台能跑 HMYR 的机器，而它们的边界不一样：

    机器一   src/*.mjs        源码 → 词法 → 语法 → 求值／编码。全在 JS。
    机器二   vm/hmyr.c        字节码 → 结果。不经过 JavaScript。
    机器三   self/*.hmoca     源码 → 词法 → 语法 → 求值 → 编译 → 打包，
                              全部由 HMYR 自己写。跑在 src/eval.mjs 上。

  三台不是冗余，是这条工程最值钱的东西：两台机器对同一份输入给同一个答案，
  才使得「规格」与「实现」是两个词。判据已经有一批，而且不是一条：
  test/self.test.mjs（扫描器对反射器）、test/self-lex.test.mjs（词法逐 token）、
  test/self-body.test.mjs（函数体）、test/adapter*.test.mjs（宿主与自举对同一份
  源码算同一个数，分表达式、语句、函数表三层）。

三层分工，每层在这个仓库里的落点
--------------------------------------------------------------------

  一、中重量级 —— 核心语义的参考实现

    这一层管「同一份源码，两个独立实现，同一个答案」。语言里属于它的：
    词法、语法、作用域与闭包、字节码编码、求值。判据是交叉验证，不是行数。

    现状：词汇与语法这一级已经有两份、也已经对上了。缺的东西见下一节。

    选哪个语言属于这一层：Rust、C#、Java、C++ 各有代价，见本文末。

  二、轻量级 —— 脚手架与胶水

    这一层管「让判据跑起来」，不管「答案是什么」。属于它的：test/ 的
    二万七千行、tools/ 里的一次性普查脚本（census、gap、dump 那类）、
    bench/、发行脚本的粘合。

    限制只有一条：核心语义路径上不许出现它。判据不是「JS 有多少行」，
    而是「src/ 里每加一个 .mjs 之前，有没有问过它属于哪一层」。

  三、专门类 —— 链接期与裸机

    这一层管「换一种语言能直接换到别的东西」。属于它的：port/ 的 .ld 链接
    脚本、.sct 分散加载、.s 汇编、deps/ 那 23 个 .icc，以及隔壁 Yunooka 的
    NASM。它们是「这件事只有这种语言做得到」，不是「顺手用这个」。

    HMYR 自己也在这一格里长出来：它是给 KID 那层用的领域语言。

缺口：第二台前端跑在第一台的求值器上（第二版改过）
--------------------------------------------------------------------

  头一版这一节写的是「前端只有一台机器」，理由是「源码到 AST 只有 JS 一份」。
  那是对的判断配了错的事实：取证之后，self/ 里六十三份 .hmoca 之中有
  lex.hmoca、parse.hmoca、stmt.hmoca、body.hmoca、scan.hmoca —— 前端早就
  有第二份，而且是 HMYR 自己写的，并且有判据盯着它与 JS 那份一致。

  真正卡住的地方只有一处，而它写在 self/host.mjs 自己的第二行注释里：

    The scanner is written in Himeyuri and runs on the evaluator; this file is
    only the bridge.

  那座桥做的事是：读文件（宿主只给 {file} 这一项能力）、切成一百行一块、
  对每一块调用 scan()。而它 import 的是 Runtime，来自 src/eval.mjs ——
  也就是说，能读源码的那台机器，脚下踩的是 JS 的求值器。

  所以缺口不是「再写一份前端」，是「给已经有的那份换一块地」。这也正是用户
  那句话的形状：hmyr 还需要一个完整的 ynok 基础库以自建 —— 基础库不是前端，
  是那块地。

  顺带记一处判据认错：头一版把 test/crosscheck.test.mjs 当成了「两台 VM 比
  字节码」的那条。它不是 —— 它比的是三处报数工具之间的恒等式（种子字节数、
  自举的 builtin 列、工具账本的加和）。认错的代价是把一条已经不缺的东西写成
  了缺的东西，而修法不在代码里，在这一节。

顺序：下一步是宿主，不是前端
--------------------------------------------------------------------

  词法与语法已经搬完（self/lex.hmoca 与 self/parse.hmoca，各有判据对着 JS 那份）。
  求值器也搬了（self/eval.hmoca 与 eval-*.hmoca 那一族）。所以再写一份 C++ 的
  词法与语法，是把已经做完的事做第二遍。

  下一步是让那套 HMYR 前端不靠 src/eval.mjs 也能跑。三条可能的路，代价
  不同而判据是同一批：

    一、把它挂到 vm/hmyr.c 上。那台机器已经会跑字节码、也已经带着内置种子；
        缺的是「把源码交给它、它去调 HMYR 写的 scan()」这条链 —— 而那正是
        self/host.mjs 今天用 JS 做的那件事。
    二、先写 C++ 的基础库（分配器、字符串、文件读写），让自举那一层有一个
        比 JS 求值器更小的宿主。
    三、继续用 JS 当宿主，只是不再叫它「高级宿主」—— 代价最小，而它换的是
        说法，不是那一步。

  一条与二之间不是先后关系，是同一件事的两端：一条是「接到现有的机器上」，
  二条是「造一个新机器」。一条更短，而它先要回答一个问题：vm/hmyr.c 认的
  是字节码，而 self/ 那一族要的是求值器的运行时（闭包、作用域链、异常）——
  那些在 vm/hmyr.c 里有没有？没有的话，二就不是绕路，是唯一的路。

  这个问题的答案是下一步第一件要取证的，不是可以推断的。

门禁
--------------------------------------------------------------------

  一条可检查的规矩，替代一个不可检查的比例：

    ・src/ 下新增的 .mjs 必须有理由，理由里要写它属于哪一层。属于核心语义的
      不得以 .mjs 新建 —— 已有的不强制迁，新开的不许再添。
    ・test/ 与 tools/ 不限语言，但 tools/ 里凡进入发行产物的那几份
      （release、package、verify、manifest 一路）按核心对待。

  这一条现在是一条判据：套件 langs 跑 tools/check-langs.mjs，它读本文件第九节
  那张清单，与 src/ 的实际文件对账 —— 盘上有而清单里没有是「新文件没登记」，
  清单里有而盘上没有是「清单过时」，两向都红。所以往核心语义里加一行 JS，
  代价是先在这张表上写一个词，而那个词要说清它属于哪一层。

已定：C++（用户 2026-11-17 点下）
--------------------------------------------------------------------

  决定的理由不在四个候选的内部比较里，而在它上面那条链上。用户的原话是：
  「hmyr 还需要一个完整的 ynok 基础库以自建，所以可以考虑选择 C++」。

  这句话说的是一条依赖。HMYR 要自建（design/SELF.txt 那条路），先要有一个
  在裸机上跑得起来的基础库；而 Yunooka 那边这一格叫「必须住在基础库里的
  东西」—— design/LAYERS.txt 与 design/NAMES.txt 两份清单，加 PLAN 的
  system-software 那一条，列的是 Ichiwatashi、Nanodesu、Torikago、
  Volcano-Separator、Oak-Barrels、KID 六件。那个库现在一行都没有。

  于是这一格不该做成「第二份前端」。按第五节的取证，前端已经有两份了；C++
  要买的是那块地 —— 一个与 vm/hmyr.c、与 port/、与将来那个基础库共用一个
  世界的宿主，让 self/ 那一族不必踩在 src/eval.mjs 上。

  它买不到 SPEC 里「不做未定义行为」那条的保证，所以代价那一栏仍然成立。

另外三个为什么没选
--------------------------------------------------------------------

  ・Rust：与 design/MEMORY.txt 那条「全所有权，安全最强，但学习曲线把下限
    压死」直接相接，也是这门语言读过并部分采纳的那一套。它没有运行时，与
    C 那份机器二也能直通 FFI。没选的理由不是它不好，是它的好处落在「与规格
    自洽」上，而这一格要买的是「与地基同侧」—— 两件事不冲突，只是先后。
  ・C#：与 SPEC 借来清单里「C# / Java：丰富类型系统、泛型、大标准库、LSP 与
    调试器」直接对应，工程性与调试体验最好。它进不了裸机那一侧，而这一格
    的第一件东西恰恰要在裸机上跑。
  ・Java：与 C# 同一档，差别在这台机器上更小。

  记下这三条不是礼貌。下一次要动工具链那一侧（格式化器、LSP、反射），C# 那
  条会更值钱；下一次要给一门新方言做前端，Rust 那条会更值钱。这条决定只对
  「给自举那一层换一块地」这一格成立。

这一份怎么被检查
--------------------------------------------------------------------

  三条主张各有落点，没有一条是只在文档里出现的借用：

    ・台数的账：成了。套件 langs（tools/check-langs.mjs）读第二节四行总量与
      盘上对账 —— 文件数精确、行数给一成、三条主张用不等式。
    ・门禁那一条：成了。同一个套件读第九节那张表，与 src/ 实际文件两向对账。
    ・缺口那一条：它现在指向的不是一条新判据，而是一个问题 ——
      vm/hmyr.c 认不认 self/ 那一族要的运行时。那一问的答案落在下一步的取证
      里，不是落在这一份文档里。

  第二版把第五节从头改过，因为取证推翻了头一版的事实。这一步值得单独记一句：
  一份判断写错之后，改的地方往往不是它指向的行动，而是它引用的那个事实。
