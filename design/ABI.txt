HMYR 调 C：ABI 那一页
====================================================================

  这一页是 design/FFI.txt 第六节推过来的那一页。那一页只回答「一块内存怎么给 C」，
  而这一页回答「一个函数怎么找、参数怎么传、返回值怎么收」。

  为什么这两页要分开：FFI 那一页管的是「借一块内存看」，而这一页管的是「叫一个
  外部函数」。前者不许重入、不许写，后者必然跨边界、必然要定类型映射。混在一起
  会让两边的约束互相污染。

一、谁在做
--------------------------------------------------------------------

  调用从 HMYR 发起，而接收端是 C 的一个函数指针。中间那个人是 C 机器（vm/hmyr.c），
  因为只有它手里有 dlopen 与 dlsym。

  所以这一页的读者是两方：写 HMYR 程序的人（他要写调用），与改 C 机器的人
  （他要实现那扇门）。而这一页的内容对两边都必须是同一句话。

二、谁和谁
--------------------------------------------------------------------

  HMYR 这一侧：一个内置函数 call_c(库, 函数, 参数们)。
  库是库文件的名字（字符串），函数是符号名（字符串），参数们是元组。

  C 这一侧：拿到那三个东西之后，dlopen 那个库、dlsym 那个符号，然后把参数们
  按第三节的规矩摊成 C 的调用。

  三样东西都是字符串加元组，没有指针从 HMYR 那一侧传出去 —— 这是这一页的
  第一条硬规则：HMYR 里的值永远不直接当 C 的指针用。

三、怎么说话
--------------------------------------------------------------------

  类型映射只有四条，而每条都要能说清「往」与「回」：

    Int 与 Bool    与 C 的 int / bool 同宽（Int 是 f64，所以往那边是截成 int，
                   回来时再扩成 f64 —— 截断有损，所以往回传整型要显式写明）
    String         与 C 的 const char * 互相借，不复制；生命周期是这次调用
   元组            摊成 C 的可变参数列表，元素只能是前面两种
   返回值          只有 Int、Bool、String 三类；别的形状要调用方自己拆

  而「怎么说话」的取舍与 FFI 那一页同一条：字符串不复制，所以调用期间它有效，
  调用之后不再保证。理由也一样 —— 复制会让「谁分配」的问题冒出来，而这一侧
  不该拥有那块内存。

四、最小的可执行形状
--------------------------------------------------------------------

  call_c("libc.so.6", "abs", (-7,))  →  7

  这一个例子里有整条路的每一段：找库、找符号、摊参数、收返回值。而它的判据是
  「与 C 那边算出来的同一个数」—— 也就是在 HMYR 里读到 7，而在 C 里 abs(-7) 也是 7。

  第二个例子是字符串：call_c("libc.so.6", "strlen", ("abc",))  →  3
  它验证的是「借而不复制」那一条：字符串在调用期间有效，回来之后 HMYR 那一侧
  仍然拥有它。

五、谁开口（失败的形状）
--------------------------------------------------------------------

  三处会失败，而每处都有自己的话：

    库打不开        HMYR-器-013（器那一层，因为它是「把外部东西装进来」）
    符号找不到      HMYR-器-014
    参数类型对不上  HMYR-器-015

  三处都失败得早：在真调用之前就把话说清，而不是让 C 那边拿到一个坏指针。

  而这一页不做的事也要说清：不做「调用之后的清理」（C 那边的资源归 C 那边），
  不做「跨调用的状态保持」（每次调用都是独立的），也不做「异常穿过边界」
  （C 那边崩了，HMYR 这边只知道这次调用失败）。

六、仍然不做的
--------------------------------------------------------------------

  ? 结构体与回调。它们要的是「把 HMYR 的函数交给 C 去调」，而那是反过来的门 ——
    属于 design/EMBED.txt 那一页（被别人调用）。
  ? 类型推断。参数的类型由调用方写明，不从上下文猜 —— 猜错的样子是
    「C 那边拿到一个坏指针」，而那种错在 HMYR 这边看不见。
  ? 跨平台。dlopen 与 LoadLibrary 在 Windows 与 Linux 上不是一回事，而这一页
    先写 dlopen 那一种。另一个平台要另写一段，而不是在这一段里加分支。

  这三件不做的理由与 FFI 那一页同一条：一页只回答一件事，而边界要能说清。
