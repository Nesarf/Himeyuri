Unicode 数据：库的一部分，不是附带的下载
====================================================================

为什么要带这份数据
--------------------------------------------------------------------

  这门语言说「字符串的长度按 UTF-16 码元算」，那是它的语义，一句话就写完了。
  而「这个码元属于哪一类、叫什么名字、属于哪一块、哪一套文字」是数据，
  跟着 Unicode 版本走的大表。

  以前那件事是借宿主的：求值器直接调 normalize 与一条属性正则。那就是借这张表，
  只是从源码里看不出来。2026-10-25 起它进了能力层的 unicode 组（借在明处）；
  而这一份把它作为库的一部分带起来 —— 数据在 data/ucd/，生成器在 tools/ucd.mjs。

数据里有什么
--------------------------------------------------------------------

  Unicode 17.0.0（2026-10 升级），十三份 .txt 合计八点八六兆；三个子目录另行存放。分三块：

    UCD 主体     UnicodeData.txt（四万零五百七十五行字符记录）、Blocks、Scripts、
                 PropList、DerivedCoreProperties、CaseFolding、SpecialCasing、
                 NormalizationTest、LineBreak、EastAsianWidth、NamesList、
                 CompositionExclusions、DerivedAge
    断行与辅助   auxiliary 下的字素、词、句、行四套属性与四套一致性测试
    Unihan       八个文件、三十九点八九兆：读音、变体、笔画、字典索引、IRG 来源

生成器产出什么
--------------------------------------------------------------------

    runtime/ucd/summary.json   规模与抽查（字符行数、块数、脚本数、类别分布）
    runtime/ucd/blocks.hmoca    一个 HMYR 函数：码点 → 块名（三百三十八个块）

  第二份才是这一格的要点：它是给 .hmoca 看的，不是给 JS 看的。
  一张只能被宿主读的表，等于没有这张表。

  验收在 test/ucd.test.mjs（二十二项）：生成器跑得动、摘要的抽查说得对
  （U+0041 在 Basic Latin、U+3042 在 Hiragana、U+4E2D 在 CJK Unified Ideographs 且脚本 Han）、
  生成的表能读进并能求值、原始数据真的在仓库里且超过五十兆。

归一化表：同一份语料，第三样产出
--------------------------------------------------------------------

  tools/ucd-nfc.mjs 从同一批语料生成 C 那台的 NFC 要的三样，产出 vm/ucd-nfc.h：

    UnicodeData 第五段（只收规范的，<compat> 不算）  分解，递归到底，2081 条
    UnicodeData 第三段                              组合类，非零的 934 个
    直接分解正好两个、第一个类为零、且没被排除         组合对，961 个

  韩文不进表：初、中、终三个字母拼一个音节是算术，一万多个音节写进表里
  只会是同一条算式抄一万遍。所以那一段在 vm/hmyr.c 里。

  分解用「全分解」而不是直接分解：查一次就到底，C 那边不必递归。
  最长的一道是四个码点（藏文的几个元音记号），生成器遇到更长的会自己停下。

  验收在 test/c-vm.test.mjs 第十一节：一万五千多行样本，两台机器逐行一致；
  其中一万三千五百多个单码点与 conformance/unicode-nfc.txt（一百一十一万行）一字不差；
  961 个组合对各自拼成第三个码点；组合类不同的两个记号按两种先后排给出同一个结果；
  韩文字母拼得成音节。这份测试语料是宿主生成的，所以它同时也是「宿主与语料差不多」
  这件事的旁证 —— 归一化这一块，16.0 与 17.0 之间没有那条大小写才有的缝；
  而升级之后（17.0 对 17.0），连大小写那一条也归零了。

大小写表：同一份语料，另一种产出
--------------------------------------------------------------------

  tools/ucd-case.mjs 从同一批语料生成 C 那台要的两张映射表与两组属性区间，
  产出 vm/ucd-case.h：

    UnicodeData.txt 的第十二、十三段      简单映射
    SpecialCasing.txt 里无条件的那几条    完整映射（一个字母摊成两个单元的那种）
    DerivedCoreProperties.txt             Cased 与 Case_Ignorable 两个属性

  带条件的 SpecialCasing 条目没有进来：tr / az / lt 是地区规则，而这门语言没有地区。
  词尾那一条（同一个字母在词里与在词尾形状不同）是位置的事，写在 C 里按位置现算。

  为什么这一张表非要搬过去：C 那台没有宿主可问。不搬，to_upper 就只对英文成立，
  而「同一种语言、两台机器」是这门语言最要紧的承诺之一。

  这条缝的来历与归宿（2026-10）：
    语料原先是 Unicode 16.0，而这台机器上的 Node 是 17.0，于是有 56 个码点是
    「宿主认得、语料里还没有」的。C 那台按语料走，对那些码点一个字也不动；
    JS 那台问宿主，于是会动。test/c-vm.test.mjs 第十节把它数出来，读三遍：
    C 那台、JS 那台、语料自己。

    17.0 的出处经代理查过（不是凭印象）：17.0.0 于 2025-09-09 发布；UCD 的 ReadMe
    日期是 2025-08-15；版本文档自述「17.0 新增 4803 个字符」。
    出处：https://www.unicode.org/versions/Unicode17.0.0/
          https://www.unicode.org/Public/17.0.0/ucd/ReadMe.txt

    2026-10 这一次把语料升到了 17.0：经代理取 Public/17.0.0/ucd/ 的十三份 .txt，
    覆盖 data/ucd/，重跑 tools/ucd.mjs 与 ucd-c / ucd-case / ucd-nfc 三支生成器。
    结果：UnicodeData 从四万零一百一十六行变成四万零五百七十五行；大写映射 1580 条、
    小写映射 1488 条；字母 684 段、记号 327 段；分解 2081 条、组合类 968 条。
    那条缝从 56 归零 —— test/c-vm.test.mjs 第十节现在说「宿主比语料多认得的那些（0 个）」，
    而测试一个字没改，只是数出来的东西变了。

    三个子目录（Unihan、emoji、auxiliary）没有动：它们不在四条生成链上，
    仍是 16.0 的语料。要升它们，得先有谁在用它。


三个坑，都是跑出来的
--------------------------------------------------------------------

  一、边界不能写十六进制。自举那一层的数字字面量走 to_int，而它只认十进制，
      于是 0x41 在读目标程序时报「不是整数字面量」。表里现在写十进制，
      十六进制放在行尾注释里 —— 注释给人看，代码给自举那一层看。

  二、条件不能写复合。自举那一层的 parser 读不进两个与号，也读不进 and：
      两个比较写在一起，它会在 if 那一行报语法错。嵌套两层它就读得动，
      于是三百三十八个块各写成两层 if。

  三、断言会抓到自己。查「代码里没有复合条件」时，第一版只剥了注释，
      于是抓到了注释里那句「为什么不用 &&」；剥了注释之后又抓到了几个块名
      （「Greek and Coptic」这种）。再剥掉字符串字面量才对。

  还有一件没解决：用启动器（也就是自举那一层的解释器）跑这张表会撞步限。
  解释器的解释器跑三百多个嵌套 if 太贵了，而这不是表的错。所以验收走最小求值器
  直接读 conformance/ucd-blocks.hmoca；自举那条路要更大的步限，还没调。

内存：这一套吃多少，为什么（2026 实测）
--------------------------------------------------------------------

  跑全量时内存涨得厉害，量下来前三名是这样（单套峰值，maxRSS）：

    test/ucd.test.mjs       375 兆
    test/corpus.test.mjs    289 兆
    test/c-vm.test.mjs      260 兆

  原因分两类，都是同一个形状：把几十兆的语料整份读进来再切成行。

  corpus 与 c-vm 是在测试里切的。一份十七点八兆的语料切成一百一十多万个短字符串，
  光对象头就要几百兆，而这两套只用得到其中几个行号或几百个样本。
  改成按行号取、逐行扫过之后：

    corpus   289 → 163 兆
    c-vm     260 → 142 兆

  ucd 那套的大头在生成器（tools/ucd.mjs）自己：UnicodeData 的区间要展开成
  二十九万条对象（不展开的话 CJK 那十万多个码点会被当成未分配，那才是错的），
  模块顶上还建一张同内容的 Map，于是 import 就付掉几十兆。而 主() 里又解析了一遍 ——
  同一张表在内存里存两份。改成复用顶上的 字符表，再把写全码点表时的批次
  从两万行降到两千行，峰值 375 → 263 兆。

  剩下那 263 兆是这套工具的真实成本：二十九万条展开记录加一张 Map，
  加一百一十一万次逐码点拼字符串（要写出四十四兆的表）。要再往下降，
  得把「区间展开成逐条记录」换成「区间加例外、查的时候二分」——
  那是生成器换数据结构，不是打磨，等真有必要再说。
