平台记录：这一门语言在哪些机器上跑过，以及各自的差异

2026-11-05：在 Windows 原生跑过一次全量
--------------------------------------------------------------------

从 pwsh 那一面（不是 WSL）跑 node tools/check-all.mjs，输出重定向到日志：

  WSL（bash）      231 套全过，330 秒
  Windows（pwsh）  231 套全过，383 秒

没有一套因为路径分隔符、盘符或行尾而失败。两处差异，都不是缺陷：

  一、重定向的编码。日志里读到 閫氳繃 而程序打的是 通过。程序发的是 UTF-8，
      而 PowerShell 的 *> 重定向按控制台编码写 —— 于是文件是 GBK，而读它的人按 UTF-8 看。
      问题在重定向那一层，不在程序：同一个日志用 GBK 读回来就是对的。
      跨两条路比较日志的人要知道这件事，否则 diff 看起来像损坏。

  二、速度与慢榜。383 秒对 330 秒，而慢的五套也不同：Windows 上是 inflate 154、
      vmboot 134、sign 109、selfvmcompile 96、curve 94；WSL 上最慢的 curve 约 83。
      那是进程启动的成本 —— 这一份清单要起几百个 node 进程 —— 是平台的形状，不是测试的。

一条这一轮没有确立的事：C 那台机器没有在 Windows 上原生编过再跑。vm/hmyr.c 那条路
在普通全量里走的是 WSL 的工具链，所以上面那 231 套只在那一层的意义上覆盖它。

2026-11-05：C 那台机器在 Windows 上原生编过、跑过
--------------------------------------------------------------------

上一节留下的那条空白补上了。编译器是 Strawberry Perl 自带的那一份：

  C:/Strawberry/c/bin/gcc.exe -O2 -o hmyr.exe vm/hmyr.c

一条命令，没有警告也没有错误，产出 409246 字节。种子头文件 vm/pack_seed.h 本来就在。

跑的是两份编出来的字节码，与另外几台对答案：

  examples/hello.hmoca        输出 5，退出码 5 —— 与自举层、字节码机一致
  examples/zone-ledger.hmoca  输出前四行与自举层逐字节相同，退出码 0 —— 三台都是 0

一处输出惯例的差别，不是算错：

  自举层把 main 的返回值也打出来（所以 zone-ledger 多一行 0），C 机器只在非零时
  用它当退出码、不打。hello 那种返回值本身就是输出的例子看不出这件事，而
  zone-ledger 这种「干完活再报一个状态」的例子一眼就看见了。

一条仍然没有确立的事：MinGW 下 int 与 long 的宽度、文本模式的换行这些常见坑，
这一轮一个都没有撞到 —— 不是因为确认过它们不存在，而是因为这两份程序走的路
没有碰到它们（没有读文件、没有写二进制、没有字符级 I/O）。

2026-11-05 续：文件 I/O 在 Windows 的 C 机器上失败，而同一份字节码在 WSL 上成功
--------------------------------------------------------------------

这一轮专门造了一份读写文件的探针（写一行、读回来、数字节），编成同一份 .hmoks，
在三处各跑一次：

  自举层（WSL）              往返一致，20 字节
  C 机器（WSL，gcc -lm）      往返一致，20 字节
  C 机器（Windows，gcc）      HMYR-內-012 cannot write that file，退出码 1

同一份字节码、同一份源码，两个平台两个结果 —— 那是这一整段里第一个跨平台的失败。

往下查了两层，两层都是干净的：

  · TEMP 目录本身没问题。Windows 上 TEMP=E:\DaShaoHuo\cache\tmp，目录存在，
    PowerShell 往里写文件成功。
  · temp_path 在两边都给真路径 —— 自举层给 E:\DaShaoHuo\cache\tmp\hmyr-x.txt，
    自举层在 WSL 给 /tmp/hmyr-x.txt。那是各自平台该有的答案。

而 C 机器的 temp_path 在 Windows 上给的是 E:\DaShaoHuo\cache\tmp/hmyr-x.txt ——
反斜杠与正斜杠混着。它在 PowerShell 里能开，而在 C 的 fopen 里不成立，所以嫌疑落在
两条上：混用的分隔符，或者 utf16_to_utf8 之后按 ANSI 代码页交给 fopen 的路径编码。

一条顺带记下的编译差异：WSL 的 gcc 要 -lm（不然 undefined reference to floor），
Strawberry 那一份不用 —— 那是 libm 在 MinGW 里并进 libc 的关系，不是程序的差别。

2026-11-05 收口：那个 fopen 失败不是 fopen，是 temp_path 建错了对象
--------------------------------------------------------------------

上一条留下两条嫌疑（混分隔符、路径编码），而两条都不是。根因在别处，且更简单：

  vm/hmyr.c 的 temp_path 在最后建目录时，建的是「全」（完整文件路径），
  而不是「dir」（临时目录本身）。

    拼接(dir, "/hmyr-") + 名  →  全
    _mkdir(全)                     ← 把 hmyr-xxx.txt 建成了一个目录

于是 Windows 上 temp_path("x.txt") 造出一个叫 hmyr-x.txt 的目录，下一步
write_text 去开那个名字就撞上目录，报 HMYR-內-012 cannot write that file。

为什么它只在 Windows 上露出来：WSL 那一路先被自举层跑过，同名文件已经在了，
mkdir 失败之后什么也没改 —— 于是那边的下一次写是成功的。换句话说，WSL 那次成功
不是因为这边对，而是因为顺序恰好绕开了。

两处改动：

  vm/hmyr.c    _mkdir(dir) / mkdir(dir, 0777) —— 建临时目录本身
  手动清理      删掉旧行为留下的目录（hmyr-x.txt、hmyr-hmyr-io-probe.txt）

验证（同一份 io.hmoks，三处各跑一次）：

  WSL 的 C 机器（重编）      往返一致，20 字节
  Windows 的 C 机器（重编）  往返一致，20 字节
  自举层（WSL）              往返一致，20 字节

两条被排除的嫌疑也记在这里，因为它们看起来都像真原因：混分隔符不是问题
（单独写一份 E:\...\tmp/mix-probe.txt 成功），路径编码也不是（temp_path 交回的
四十个字符逐个查过，全是可打印 ASCII）。

2026-11-06：arm 那一套在 Windows 上红了很久，而红的那一条把后面五条藏了
--------------------------------------------------------------------

今天跑全量，232 套里一套没通过：arm。它报的是

  make[1]: mkdir: No such file or directory
  make[1]: 三个星号 [Makefile:108: build/hmyr.o] Error 127
  （那一行原文是以三个星号开头的，这里按文档的规矩不照抄）

根因在套件自己那一行。test/arm.test.mjs 拿绝对路径找到 make（这台机器是
D:\msys64\usr\bin\make.exe），找到了就直接 spawn，而 msys 的 bin 并不因此就在
子进程的 PATH 上。port/Makefile 的配方写的是 @mkdir -p $(BUILD) —— POSIX 写法，
make 去 PATH 上找 mkdir，找不到，于是 127（Error 127 的意思是「命令没找到」，
不是「命令失败」）。mkdir.exe、sh.exe、rm.exe 都躺在 D:\msys64\usr\bin\ 里。

修法一行：spawnSync 时把 path.dirname(make) 前置进 PATH —— 找到谁，就带着它的邻居。
Makefile 本来就是按 MSYS2 写的（CROSS 默认值 /d/msys64/ucrt64/bin/arm-none-eabi-），
它只在那个环境里成立，所以缺的只是把环境给它。

值得记的是第二件事，也是这一条真正的收获：那一条红把后面五条判据一起藏了。
第一节「一之三」的写法是

  ok("make h723 链得出来", ...);
  if (fs.existsSync(映)) { 向量表、入口、栈顶、Flash、RAM 五项 }

而映像不存在时那五项连跑都不跑。于是那一套报的是 26 passed, 1 failed ——
红线之外还有五条，从来没有在 Windows 上过过。修好之后它是 32 passed, 0 failed。

一条红的失败往往不止它自己。一段被 if 包住的判据，前提不成立时是静默的，
而静默在总数里看不出来：27 与 32 都是「只有一条不通过」，区别在那一套当时
到底验了几件事。所以看「几项通过」这个数时，要知道它是被前提缩过的。
