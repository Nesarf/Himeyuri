并发模型（设计稿 2）

  对应 SPEC.txt 的 [悬] 2。本文给出倾向、理由、反例与验收；定稿后并入规格。
  与 design/MEMORY.txt（MEMORY.txt）（三区模型）咬合最紧——任务边界就是区边界。

====================================================================
1. 这一页要解决什么
====================================================================

并发要同时满足两头：

  ・脚本（软）：await 一下就好；不用想线程与锁
  ・实时（硬）：不许阻塞、不许暂停、不许分配；回调必须跑完就返回
  ・多用途（游戏、音频、CAD、工具）：容错（一个任务崩了不该带走全局）、可复现（出错要能重放）

答案不是「一个万能模型」，而是四句话说清的结构：

====================================================================
2. 倾向：结构化并发 + 进程式隔离 + 消息传递
====================================================================

— 2.1 任务成树（结构化并发）

  ・[定] 任务只能作为子任务创建，父任务不得先于子任务结束。
  没有「游离任务」（detached）这个概念——想让它活得更久，就得显式移交给一个活得更久的父。
  ・[定] 取消是结构的：取消父任务即取消整棵子树。
  ・理由：游离任务是并发 bug 的头号来源（谁负责、谁清理、何时结束，全说不清）。
  Kotlin 的 coroutines、Java 的 structured task scope 都把这一点作为核心，说明它不是口味问题。

— 2.1.5 取消的两种形态，分界在「谁能被语言调度」

  2026-10-27 定。这一条一直挂着，因为「协作式还是强制式」听起来像二选一，
  而实际情形是两种都存在，分界在调度器归谁。

  ・[定] 任务树内的取消是结构的：取消父即取消整棵子树（2.1 已定，实现见 task.hmoca）。
  ・[定] 语言自己调度的任务用协作式：取消在取消点上被检查，任务自己决定什么时候让出。
    理由是它跑在语言自己的轮转里（sched.hmoca 那一层），而协作式让「取消发生在一条
    语句的中间」这件事不存在 —— 于是清理是可写的。
  ・[定] 借宿主能力起来的任务用强制式：thr_spawn / thr_cancel 那一层。语言停不掉一个
    卡在宿主调用里的 worker，只能要求宿主终止它。这条路本来就不承诺清理，
    所以强制在这里是诚实的 —— 它不假装有序。

  分界一句话：被语言调度的用协作，被宿主调度的用强制。

  为什么两种都要写明，而不是选一个：取消在两种情形下的语义本来就不同。
  用协作式去描述宿主那一层，会让「清理一定会跑」变成一句谎；用强制式去描述
  语言这一层，会让「任务之间不共享可变内存」这条规矩随时可能被撕开。

— 2.1.6 效果在并发下的传播：两层，今天只有一层

  2026-10-27 定。这一条原来是一个 [议]，而把它拆开之后发现它问的是两件事，
  一件今天就能答，另一件今天连对象都没有。

  ・[定] 派生处：派生者必须自己声明 thread 效果。thr_spawn 带那个效果，
    所以没声明的函数调它会被 HMYR-內-001 拒 —— 「派生这件事被声明过」是语言今天的保证。
  ・[悬] 任务那一层：任务能碰的效果不许超出派生者的范围。今天做不到，而原因不是
    没写分析器：任务是一段源码字符串（thr_spawn 收的是源码与入口名），它的 effects
    在那段字符串里，语言在派生的时候看不见它 —— 于是没有「任务的效果集」可比。

  这一句不是拖延：两种做法都试过，都不成立。
    一、派生时解析那段源码，取入口的 effects 再比。宿主那一层做得到（它本来就有解析器），
        自举层也做得到；而它换来的是一句「你交给我一段源码，我先替你解析」——
        而那正是把「任务」当成一个要编译的输入，不是当成值。
    二、让 thr_spawn 收一个函数值。那最干净，可这门语言没有一等函数值 ——
        而那不是并发这一页的事。

  所以这一条的落点是：等任务成为一等值的那一天。在那之前，把「今天能保证什么」
  写清比把「明天应该怎样」写长更有用。

— 2.2 任务即隔离单位（进程式）

  ・[定] 任务之间不共享可变内存；通信靠消息（值传递）或显式的共享类型。
  ・[定] 失败不默认连坐：子任务失败时，父任务三选一——
  ① 传播（默认）② 由监督者按策略重启 ③ 用 Result 接住。
  ・理由：「让它崩，然后有人管」在多用途软件里是常态需求；但默认必须是可预测的，所以传播是默认，重启要显式。

— 2.3 区不跨任务（与内存模型的分界）

  ・区属任务：arena 属于创建它的任务；任务结束时恰好关闭一次：[定]
  ・不许偷渡：把 arena 内的引用传给别的任务 → 编译错误：[定]
  ・显式移交：transfer 可把所有权交给另一个任务；移交后原方不可再用：[定]
  ・共享是类型：要跨任务共享，必须使用共享类型（atomic[T]、sync[T]、channel[T]）：[定]
  ・托管可跨任务：managed 值可自由传递（不移动回收，指针稳定）：[定]

— 2.4 实时档位不许暂停

  ・[定] @realtime 里不许 await、不许创建任务、不许阻塞、不许分配（与 MEMORY.txt §3 同一条）。
  ・[定] 效果不得放大：子任务声明的效果必须是父任务效果的子集。
  于是「一个只声明了 file 的任务，无法偷偷起一个联网的子任务」——这条与「不许偷偷联网」同源。

====================================================================
3. 可复现：确定性调度
====================================================================

  ・[议] 提供确定性调度器：给定种子，任务的交错顺序可复现；测试与回放用它，生产用它做故障复现。
  ・[议] 单线程调度模式：所有任务跑在一个线程上（脚本档位默认），仍然遵守上面全部规则。
  ・理由：并发 bug 最贵的地方不是「有 bug」，是「复现不出来」。把可复现做成语言能力，成本远低于事后查。

====================================================================
4. 反例（必须编译失败，或必须被工具拒绝）
====================================================================

— 4.1 游离任务

fn handler() {
  spawn_detached { write_log() }      // 反例：父任务结束后它还在跑
}

— 4.2 区跨任务偷渡

fn feed(a: Arena, ch: Channel[Bytes]) {
  let b = a.alloc(16)
  ch.send(b)                          // 反例：另一个任务将持有本任务的 arena 内存
}

— 4.3 隐式共享可变

var counter = 0
parallel { counter += 1 }             // 反例：跨任务共享可变状态，必须改为 atomic[int]

— 4.4 实时里暂停

@realtime fn on_audio(out: borrowed mut Buffer) {
  let data = fetch_config().await     // 反例：回调里等待
}

— 4.5 效果放大

fn only_files() effects(file) {
  spawn { http_get("...") }           // 反例：子任务的效果超出父任务
}

— 4.6 「看起来能过」的坑（工具必须警告）

fn warmup() {
  spawn { heavy_precompute() }        // 每帧 spawn 一次，且从不等待
}

语法合法、也不违反结构（若父等它），但每帧一次就是性能陷阱——工具要警告，而不是沉默。

====================================================================
5. 验收方式
====================================================================

  ・结构化并发：5 个反例程序必须编译失败（符合性套件的负例）
  ・区不跨任务：同上（4.2）；另加一个 transfer 的正例，移交后原方使用必须失败
  ・无数据竞争：在确定性调度器下跑测试套件 + 共享类型上的竞态检测；只对共享类型负责，这一点如实写明
  ・实时不暂停：4.4 必须编译失败；另用一个计数钩子断言回调内分配 0 次、暂停 0 次
  ・效果不放大：4.5 必须编译失败
  ・可复现：同一个种子跑两次，任务交错轨迹逐项一致
  ・监督有效：杀掉一个子任务，监督者按策略重启，父任务状态保持自洽（Elixir 式用例）

====================================================================
6. 与其他设计的关系
====================================================================

  ・内存模型：区属任务；任务结束即 arena 关闭（清理点唯一）
  ・效果声明：任务边界处只许收窄，不许放大
  ・实时档位：不许暂停、不许分配、不许起任务
  ・错误处理：失败默认传播；Result 是「接住」的方式；panic 只在非实时档位
  ・契约：「这个任务不会阻塞」这类断言交给编译器核对

7. 待定
====================================================================

  ・共享类型的最小集合：[议]：先给 atomic[T]、channel[T]、sync[T] 三个，其余等用起来再加
  ・监督策略的表达：[议]：restart: never：transient：permanent + 退避参数，照 Elixir 的直觉
  ・与 OS 线程的关系：[议]：任务由运行时调度到线程上，1:N；实时任务可绑定到专属线程
  ・跨机器：[悬]：先不做；要做得与「不移动」和消息传递一起重新推演
  ・确定性调度的粒度：[悬]：目前只承诺「同一实现同一版本同一种子」可复现，不承诺跨版本

====================================================================
补记：同步求值器与真并行（2026 年间实测）
====================================================================

  这一句必须写下来，因为它会反复被想起来：

  在 Node 这样的单线程宿主上，同步的求值器做不到真并行。
  道理很直：并行要等异步的完成事件，而同步等待会把事件循环堵死，
  于是那个完成事件永远不来——与 sleep_ms 忙等导致的死锁是同一个病。

  实测过一次：用 Atomics.wait 在求值器里同步等子进程的 close 事件，
  子进程起来了、也跑完了，而 close 事件一次都没送到。

  所以「语言层加一个并行的内置」这条路，在求值器还是同步的时候不成立。
  两条真正的出路：

    一、让语言有异步（await 一类）。那与本文第 1 节的第一头（脚本要软）一致，
       但它是语言层的大件，不是加个内置。
    二、借外部能力并行：把「同时起几个」交给一个本来就支持并行的进程
       （例如 PowerShell 的 Start-Job），而语言侧只是同步地调用它、等它回来。
       这与颜色那条桥、native 那个窗口同一个做法——借能力，不复制实现。

  眼下走第二条。它的边界也写在明处：
    ・并行发生在那个外部进程里，语言看不见它怎么调度；
    ・所以「哪个任务在哪个核上」不归语言管，这是第 2 节末尾那句话的同一个意思；
    ・而语言能保证的仍然是那三条：不阻塞宿主、可取消、失败不连坐。
