标准库：第一份，与它逼出来的三处修补
====================================================================

  lib/strings.hmoca        二十二个函数：大小写、修剪、前后缀、查找、替换、重复、填充、十六进制
  lib/numbers.hmoca        十四个函数：绝对值、符号、最小最大、夹住、奇偶、整除、幂、阶乘、
                          最大公约数、最小公倍数、平方根、百分比
  conformance/lib-strings.hmoca  二十二条断言，跑在自举层上
  conformance/lib-numbers.hmoca  二十三条断言，同样跑在自举层上

  断言写成「不通过就交回它的编号」，于是失败能说出是哪一条，而不是只说「假」。
  启动器上跑这一份，退出码就是那一条的编号；全过是零。

它为什么长那样
--------------------------------------------------------------------

  四条规矩，每一条都来自语言此刻的缺口，而不是风格：

  一、没有 ord。内置只有 chr（码点 → 字符），没有反方向。于是大小写转换只能
      一条一条地比字符本身 —— 那是五十二行 if。这不是库的品味，是缺口的形状。

  二、没有复合条件。自举那一层的 parser 读不进两个与号，也读不进 and，
      于是「甲或乙」写成先判断甲、返回，再判断乙、返回。

  三、没有 break。循环靠一个标志收尾，标志用 var 才能改。

  四、没有整数除法。除号给双精度，于是「除以十六取整」写成先减余数再除 ——
      那一步精确，因为减完之后正好能被整除。

  这四条写在文件头。它们决定了下面每一行的形状，换个写法就会在自举那条路上读不进。

为了让它跑通，补了三处
--------------------------------------------------------------------

  第一版跑了三次，每一次红在不同地方，而三次都不是库写错了：

  一、布尔字面量。自举的切词器把关键字一律当成标识符（self/lex.hmoca 开头那段写着），
      于是目标程序里写一个 true，求值时报「没有这个名字：true」。
      修在 self/eval.hmoca 的 name 分支：先认 true 与 false，再查名字。

  二、内置太少。自举的求值器原先只转 len 与 str 两个纯函数，而库要用 slice、chr、
      to_int、nfc、is_letter、is_mark。补在 self/eval.hmoca 的 求调用 里 ——
      它们不碰世界，转给语言自己的同名内置就够。

  三、字符串转义。自举的 read_string 原样保留内容，于是目标程序里的 "\t" 拿到的是
      反斜杠加 t 两个字符，而空白判断正是靠那一个字符。症状是「修剪不认制表符」，
      看起来像库里写错了。修在 self/lex.hmoca：认 n、t、r、反斜杠、引号五个，
      别的原样留两个字符，不猜。

  三处都是真的缺口，补上之后自举层能读的东西多了一截 —— 而这一份库就是那件事的第一批用例。

第二份：数值，与它逼出来的小数解析
--------------------------------------------------------------------

  lib/numbers.hmoca       十四个函数：绝对值、符号、最小最大、夹住、奇偶、整除、
                         幂、阶乘、最大公约数、最小公倍数、平方根、百分比
  conformance/lib-numbers.hmoca  二十三条断言

  这一份写第一版就红了：目标程序里写 1.41421356，自举层报「不是整数字面量」。
  成因是自举的求值器把所有数字字面量都交给 to_int，而 to_int 只认整数。
  修在 self/eval.hmoca：带小数点的自己拆成整数部分与小数部分，各自 to_int，
  再算 整数 + 小数 / 十的幂。三个函数（幂十、小数点位置、数到），二十来行。

  这是自举层的第四个缺口，前三个是布尔字面量、内置太少、字符串转义。

  数值库本身有两条约定写在文件头：没有错误值可交回，于是负数开方交回 -1；
  零的零次按惯例给一。两者都不是猜，是写下来的定义。

切分与连接，与它们逼出来的括号配平
--------------------------------------------------------------------

  lib/strings.hmoca 新增三个函数：切分（按分隔切成一段段）、分行、连接（拼回去）。
  conformance/lib-strings.hmoca 扩到三十二条。

  这一格先纠正一处记错：上一份文档写着「元组类型的返回，自举的 parser 写得还不全」。
  量了一次，返回元组没问题 —— 两条路都跑得通。真正的缺口在参数上：
  连接(段们: (String,), 分隔: String) 的第一版跑出来是
  「参数个数不对：连接 要 1 个，给了 2」。

  成因是 self/body.hmoca 里两处只看第一个括号：
  反括号位取到的是元组类型自己的右括号，收名从把类型里的 String 与逗号也当成了参数。

  修法是配平：两个函数各带一个深度，深大于零时既不收名字也不认逗号。
  self/sig.hmoca 里同样的问题也修了（它的 type_at 只认一个标识符，
  现在换成 type_end 加 type_text，括号跟着配平）。

  还有一处让步写在函数头上：返回类型写成 (String,)，因为类型系统不校验元组长度 ——
  段数是运行时才知道的。那一行是说明，不是约束。

第三份：元组
--------------------------------------------------------------------

  lib/tuples.hmoca       十二个函数：插入排序、反转、求和、最小最大、含、子段、接起来，
                        外加字符串元素那一份的串插入、串排序、串含
  conformance/lib-tuples.hmoca  二十五条断言

  元组不可变，所以「排好」是一串新的元组：每次插进一个元素就产生一个新的。
  插入排序在不可变数据上不算快，但它是这里唯一写得短的算法。

  这一份第一版就通过了 —— 因为前一格刚修好「元组类型能进参数表」。
  要是没有那一格，这两条签名（参数是 (Int,) 与 (String,)）会立刻红在同一处。

  两条边界写在断言里：空的元组 最小 交回零（那是定义，不是猜），
  重复的元素排完还是同一个个数。

  类型声明写死元素（Int 或 String），是因为没有泛型参数那一层 ——
  同一条算法为两种元素各写一份。文档里记着这一条是缺口。

第四份：表
--------------------------------------------------------------------

  lib/tables.hmoca       八个函数：键们、有几件、置入、删、取或、合并、空表、是空表
  conformance/lib-tables.hmoca  二十条断言

  这一份能写出来，是因为补了一个内置：field_names（字段名的列表，按造记录时的顺序）。
  没有枚举就写不出通用的置入与删除，而把 field_get 包一层加个默认值，那不是表。

  记录仍然不是哈希表：字段名必须是标识符能写的形状（HMYR-內-014），所以键只能是那种名字。
  这条限制写在文件头上，因为它是这一份能做的事的边界。

  第一版以为记录至少要一个字段，于是 空表 借了一个占位键；record-new 那一套的用例
  证明 record_new(()) 就是空记录，占位键那段删掉了。

  内置的用法是 置入 与 删 都靠「把旧字段搬到新表」：先 键们，再逐条 field_get，
  拼成对，最后 record_new。元组拼接那一条让这件事写得短。

  顺带发现自举层连 record_new、field_get、field_has 都没转发过 —— 库一调就报
  「没有这个函数：record_new」。三处一起补上了。

第五份：帧
--------------------------------------------------------------------

  lib/protocol.hmoca      五个函数：四字节、读四、编帧、解帧、完整
  conformance/lib-protocol.hmoca  十九条断言

  规矩来自 oak-barrels 的协议第 3 节：一帧是 u32 的长度（它数类型字节加载荷）、
  一个类型字节、然后是载荷，整数按小端。跨进程说话第一件要商量的就是「到哪儿停」，
  而长度前缀是唯一不靠内容猜边界的做法。

  这里没有字节类型，所以字节用「0 到 255 的整数元组」表示：每个字节占一个值。
  代价是占地方，好处是不必先给语言加一个字节类型。

  跑的时候撞到两处，都记在这里：

  一、长度字段的含义。第一版把「帧的字节数」当成了长度字段 —— 而它数的是
     类型加一个载荷。七个字节的帧，长度字段写的是三。断言把这件事说清了。

  二、自举层不跟随间接 import。conformance 只 import protocol.hmoca 时，
     它内部那句 import "./tuples.hmoca" 没被处理，于是 子段 不在作用域里，
     报「没有这个函数：子段」。显式 import 两个就通了 —— 那是自举加载器的一个缺口。

     那一处后来修了（2026-10-26）：self/run.hmoca 的 读一棵 把子模块的 import
     也按顶层目录拼，于是它去 conformance/ 找 tuples.hmoca，文件不在就被当成
     「可选引用」跳过。现在 读一棵 用被读文件自己的目录（目录部分 那个函数），
     而 conformance 那一行显式 import 已经删掉 —— 只写 protocol 一个，照样跑通。

效果声明进了自举层
--------------------------------------------------------------------

  自举那一层现在收它：self/body.hmoca 的 效果们 在右括号与 { 之间找 effects( … )，
  函数表的每一项从三件变四件；self/eval.hmoca 装表时存效果、调用时往下核
  （被调的缺什么就报 HMYR-內-001），并在环境里放一个「效果」键 ——
  「当前函数有哪些效果」只能在运行时知道，检查靠的就是它。

  顺带一条边界写在这里：最小求值器对自举层自己关掉了内置的效果检查
  （选项 检查效果: false），因为解释器替目标程序执行，必然碰得到全部效果对象；
  目标程序的效果由 self/eval.hmoca 查。两层各查各的。

  证据：conformance/write-text.hmoca 声明 effects(process, file)，由启动器跑通并写出文件；
  而一个没声明 file 的 main 去调要 file 的函数，会被拒成
  「HMYR-內-001 调 写 要 file 效果，而调用它的函数没有声明」，文件也不会被写出来。

  同一格还补了 read_text 的转发 —— 写通了之后才轮到读，两边都要 file 效果。

目标程序看不到 argv —— 这一处也修了（2026-10-26）
--------------------------------------------------------------------

  整条调用链多带一个参数：命令行入口 → 跑文件入口 → 跑模块们 → 跑程序带函数与参，
  最后 更新(环境, "argv", 参们)。而 eval 的 求调用 里补了一支 argv：查环境，没有就交回空元组。
  目标程序看到的是 目标程序参数(参们, 1, ()) —— 从脚本名之后开始，因为它问的是自己的参数。

  同一处还露出一个更基础的缺口：自举层的 求调用 里根本没有 print 与 print_err。
  于是「能算但说不出」—— 任何带 print 的程序在启动器那条路上都跑不了。
  两支都补了，参数按 str 拼起来，与这门语言 print 的语义一致。

第六份：JSON
--------------------------------------------------------------------

  lib/json.hmoca         十八个函数：解析（串、数、真、假、空、数组、对象）与生成
  conformance/lib-json.hmoca  二十八条断言

  这一份的起点是一条限制，而不是一个选择：语言没有类型反射。
  一个数、一个字符串、一个空元组，在库这一层分辨不出来 —— str 能把它们都写成字，
  写出来之后回不去。所以 JSON 的值一律带一条类标记：

    {数: 1.5}  {串: "ab"}  {真: 1}  {假: 1}  {空: 1}
    {对象: ((键, 值), …)}  {数组: (值, …)}

  对象用对表而不是记录，因为 JSON 的键可以是任意字符串，而记录的字段名必须是
  标识符能写的形状。要记录自己用 record_new 转，那一份不做。

  跑出来的第一处错值得记：-2.5 解析成 -1.5。小数那一层把整数部分与小数部分相加，
  而负数要相减 —— 整数部分是 -2，加上半个就变成 -1.5。断言第 2 条抓住了它。

  生成那边遇到没有标记的值交回空串，而不是猜一个形状：猜错会把一个错误
  变成一句更像真话的错。

还缺什么
--------------------------------------------------------------------

  变长元组的类型。切分那一处的让步就是它：声明几个元素与交回几个元素，
  此刻没有任何一层会核对。JSON 那一份也因此把每个值都包成记录 —— 同一个缺口，
  另一个样子。

  阻塞式的读 —— 这一条已经有了（第十六轮）。入口是 read_line(路径, 起点)，
  交回 {行, 下一起点}，读完交回 -1；另有 read_lines(路径) 给「知道自己要全部」的调用者。
  没有选「打开一个文件句柄」那种形状，因为这门语言没有句柄类型、也没有「用完要关」的机制 ——
  于是每一次调用自己开、自己关、自己 seek：开销大一点，但语义封闭，而调用者可以分段读。
  test/read-lines.test.mjs 盯着它：三行按顺序读出来、CRLF 与 LF 读成一样、空文件是 0 行且没有下一处。

  顺带修掉的一处：C 那台的 fopen 按 ANSI 代码页解释路径，于是「三行.txt」这种名字
  在它那里就是另一个不存在的东西。现在所有开文件都走 _wfopen（先把 UTF-8 转成宽字符），
  中文路径在两台机器上一样读得到。

  类型的检查本身 —— 这一条也有了（第十七轮），而它上线第一件事就是抓错。
  做法是编译期的静态核对，不是运行期的：字节码里没有「返回类型」这个字段，
  而声明与交回的值都在 AST 上，两边都是现成的。能查的是能确定形状的东西 ——
  字面量、元组字面量、记录字面量、调用（查被调者的声明）、算术与比较的结果；
  变量、下标、字段一律放过。静态检查的价值在于「说了就一定对」，
  把猜出来的东西当错误报出去，比不查更坏。

  上线后它点名了二十五处：那些函数写着 -> Int，而体里 return 的是一个记录。
  这门语言有 TypeRef 与 TupleType，但没有「记录类型」这个名字，
  所以那些声明写不对 —— 于是整批改成不声明返回类型。
  而那二十五处一直躺在那儿，没有任何一层说过话。

  test/return-types.test.mjs 盯着它：十六个例子，九个该放过、六个该报出来、
  一个「调用的返回类型也照着核」。tools/emit-code.mjs 现在先核对再编字节，
  有一处不合就不写出文件。

  变长元组的类型 —— 与上面那条一起解决的。subset-parse 原来只认单名类型，
  于是 (Int, String) 这种声明写不进自举层；现在它认元组类型了，
  而核对器会在「元素个数不对」与「第 N 个元素形状不对」两种情况下分别说清楚。
