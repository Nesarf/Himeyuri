Himeyuri 的定位：车间／平台类语言

没有落点的推论不写。

--------------------------------------------------------------------
总目标（先代会话里的口述，2026-11-02 归拢到这里）
--------------------------------------------------------------------

  一门「集百家之长，成一己之特」的独立计算机语言：有着众多计算机语言的优点，
  并在此之上有鲜明的自我特征。本身不依赖任意一种计算机语言，也不会长得像
  某一种计算机语言。有完整且自主的运行逻辑与文件类型，可在绝大部分 2015 年后
  公开的操作系统上运行。有自己的 SDK 与 OS。

  这一句比下面「定位」那一段更硬 —— 它是这一页所有推论的来源。四条硬要求
  逐条落到「哪里查得到」：

--------------------------------------------------------------------
定位
--------------------------------------------------------------------

Himeyuri 不是「一门用来写程序的通用语言」这么简单：它工作的逻辑类型本身就是一个开发平台。
也就是说，人们应该能在 Himeyuri 之上再开发出新的开发平台、新的工具链、乃至新的语言。
软件、工具、工具链、基础依赖这些前面提过的东西，一个都不落下；
能做到某种程度上的「啥都能干」，那是最好的。

「啥都能干」的诚实说法是这句：
四档执行 ＋ 三向接口 ＋ 方言即库。上限靠绑定（谁都能调），下限靠脚本档（谁都能写）。

--------------------------------------------------------------------
推论一：方言即库（新的语言＝新的库，不改核心文法）
--------------------------------------------------------------------

在 Himeyuri 之上长出一门「小语言」，不需要改文法：一组函数、一组记录、一套约定，就是一门方言。
KPB 的谱／混／音色（kpb/piece.hmoca）已经证明了这一条——它看起来像一门小语言，其实就是库。

理由：文法一旦成为扩展点，「同一份源码在别处是什么意思」就说不清了
落点：kpb/ 目录；规格 2.2 的文法保持窄。
里程碑：已经有。

--------------------------------------------------------------------
推论二：宏是核心能力，不是装饰
--------------------------------------------------------------------

要在平台之上再长语言，就必须能在编译期变换代码。规格 4.1 已经定了
「只做卫生宏 ＋ 编译期常量求值，不做任意语法改写」——这条定位确认那个取舍，
并把它从「够用即止」提升为核心能力。

理由：语法改写（reader macro）会让工具（格式化器、LSP、错误定位）全部失去立足点
落点：规格 4.1；已实现（2026-10-25）。语法是一行一条：macro 名(参数们) = 表达式。
展开在 src/expand.mjs，两处接线（src/eval.mjs 的 run 与 src/loader.mjs 的 loadUnit），
验收是 macro 套件（十四项，求值器与加载器各跑一遍）。
卫生是窄的那一条：模板不引入绑定，于是实参树原样嵌入、不被改名，也就不存在
「模板内的绑定捕获实参」。带绑定的模板要块表达式，而字节码那台不认块表达式 ——
这条边界写在 expand.mjs 的文件头，不是留着让人自己推。
里程碑：M6 之后的第一件事 —— 已落地。

--------------------------------------------------------------------
推论三：要能驱动工具
--------------------------------------------------------------------

平台语言的第一职责是指挥别的程序：起进程、读写文件、看时间、读它们吐出来的东西。
这正好用上效果声明：process · file · net · time 四样都在效果词汇表里，
而能力由宿主授予（M5 已经实现：宿主只给 file，脚本就只读不写）。

落点：规格 2.6 的标准库第一圈写着「文件与时间：待加」；现已加 read_text。
里程碑：M6（进程与时间进第一圈，各自带效果）。

--------------------------------------------------------------------
推论四：要能自省与生成
--------------------------------------------------------------------

「在语言之上造语言」需要两样东西：读得懂自己的代码（AST 反射）与写得出代码（打印机）。
而格式化器就是第一个代码生成器——所以规格把格式化器排在 LSP 之前，顺序是对的。

落点：两件都有了。反射在 src/reflect.mjs，打印在 self/fmt.hmoca（能排整个文件）；
验收是 reflect 与 fmtwholehmyr 两套。tools/ 那边仍然是检查器 —— 它做的是「看」，
不是「自省与生成」，所以不在这条推论里。
里程碑：M6（格式化器 → 反射 → LSP）—— 三格都已落地。

--------------------------------------------------------------------
推论五：向外三向接口
--------------------------------------------------------------------

  ・方向：形状：状态
  ・被别的程序调用：子进程 ＋ JSON-RPC：已实现（src/embed.mjs；KID 侧用例 5 项通过）
  ・调用别的程序：进程 ＋ 效果声明：已实现。宿主那侧是 process.exec（能力层的一组），
    自举那侧在 self/eval.hmoca 里按参数个数转发（一到四个），效果名 process ——
    self/ 里那三十几处 effects(process) 就是它的使用者。
  ・编译到别处：WASM，最后原生：已定（规格第六章）

--------------------------------------------------------------------
推论六：包管理要沿用自己的纪律
--------------------------------------------------------------------

平台语言必须有包管理（名字已定：kagaribi，篝火）。
它要能依赖非 Himeyuri 的东西（C 库、系统工具、二进制），因此必须沿用 KID 那套纪律：
声明 · 许可 · 哈希；运行时不许偷偷下载（规格 4.1 的不做清单）。

理由：一个能指挥全机器的平台，若依赖不可追溯，那它指挥出来的东西也不可追溯
落点：D:\CZGD 的 install-czgd.ps1 与 selfcheck.mjs 是同一套做法的先例（校验后再安装，已如此）。
里程碑：M6 之后。

--------------------------------------------------------------------
这一页自己的验收
--------------------------------------------------------------------

每条推论都挂了「落点」与「里程碑」；落点指的是仓库里查得到的地方，
里程碑指的是规格第五章的那张表。两者都要能对上才作数——
这一页本身没有新主张，它只是把定位翻译成了可查的东西。


七、往 vm/hmyr.c 加东西之前要问的三句
--------------------------------------------------------------------

  那个文件有两个受众：桌面的可执行文件，与板子上的映像。同一份源码、
  两个编译命令行、两套可用的库。加一个东西之前问三句：

    一、它要文件系统吗？裸机没有临时目录、没有 mkdir、没有 getenv。
       要，就放进桌面那一块，裸机给 stub。
    二、它是全局状态吗？全局变量的声明可能与写到它的代码不在同一个条件块里 ——
       那一刻裸机上就是「undeclared」。声明与用法要落在同一个条件下。
    三、它的判据在哪一侧被验？arm 那一套不在 cvm 与 cli 的邻域里，
       而它编译的正是同一个文件。

  2026-10-26 这一天，前两句各被踩了一次：容器的 mkdir 与 getenv，
  以及线程池上限那个全局变量。两次都是「桌面绿、板子红」，而红的样子是
  十四项一起不过 —— 那不是一个功能坏了，是整个映像没了。
