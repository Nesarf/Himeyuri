检查体系：怎么跑、为什么这样分、改一处该跑哪几套
====================================================================

全量一次要五到十分钟（四路并行）。每改一行都跑全量，开发节奏就被等船拖住了。
所以要有一份「改哪跑哪」的规则，而规则要落在工具里，不落在记忆里。

这一页里出现的套件数都是各节的当天数，不是今天的数：账记的是「那一天是多少」，
而它会跟着仓库长（这一段的第一次写着一百五十六套，后来是二百三十二，再后来
又多了一套）。今天的数在 README 的 test/ 那一行，或者跑一次
node tools/check-all.mjs --list 数一下。同一个口径适用于 design/OPEN.txt。

一、它现在怎么跑
--------------------------------------------------------------------

    node tools/check-all.mjs                 全量
    node tools/check-all.mjs --only a,b,c    只跑这几套
    node tools/check-all.mjs --skip a,b      跳过这几套
    node tools/check-all.mjs --affects 文件   跑「依赖这个文件」的套件

结构：每套一个子进程，四路并行；少数几套必须串行（写同名临时文件、抢 self/ 的源码），
它们排在最前；失败的会重试一次，因为有些套件在满载下会假红。

输出里超过一秒的套件会带耗时，末尾再列最慢的五套 —— 时间是看得见的才好安排。

二、依赖是怎么算的
--------------------------------------------------------------------

从每个测试文件出发，扫两样东西：

    一、相对 import：从「../src/eval.mjs」这样的写法递归下去。
    二、路径字面量：「self/curve.hmoca」这类字符串。

第二样是关键。很多套件并不 import 被测的 HMYR 源码，而是 spawn 一个 self/*.hmoca 去跑
（curve 套件跑标量乘、package 套件真打一个包）。只看 import 图，这些套件会整个隐形。

判据是保守的：图上有一条路就选中。宁可多跑一套，不可漏掉一套。

三、改一处该跑哪几套
--------------------------------------------------------------------

按「改动落在哪一层」分三档：

    只改一个自足的函数（比如 curve.hmoca 里某个内部函数）
        --only curve
        十几秒。

    改了会被别的程序 import 或 spawn 的 HMYR 源码
        --affects self/curve.hmoca
        选中的十几套，约五分钟。跳掉慢的几套可以压到一分钟内：
        --affects self/curve.hmoca --skip package,packagehmyr,release,releasehmyr

    改了被几乎所有测试 import 的东西（src/eval.mjs、src/bytecode.mjs、loader）
        --affects src/eval.mjs
        几乎全量。这一档不必挑，挑也挑不出来 —— 那就直接全量。

提交之前仍然跑一次全量。这是唯一的硬规矩：小步可以挑着跑，但推出去的那一份要是全绿的。

四、慢在哪
--------------------------------------------------------------------

先分清两个数字，混着读会读错：

    单独跑    node tools/check-all.mjs --only inflate    约 68 秒
    全量里    同一次全量里它占                        约 142 秒

八路并行下每套都在抢 CPU，所以单套在全量里的耗时是单独跑的两倍上下。要与哪一次全量比
就用同一次全量的数，要判断某套自己的速度就用 --only。tools/expected.json 记的是后者。

2026-11-03 量了一次全表（check-all 现在认 HMYR_TIMES，设了就落一份降序表，一行一套）。
同一天量了两次，中间修掉了一处控制流对象：

    209 套    2754.8 秒工作量    墙钟 411.6 秒
    209 套    2173.6 秒工作量    墙钟 353.9 秒

2026-11-04 又量了两次：先是三件新套件（f64bits、vmload、vmrun）进表之后，
后来是第四件（vmboot）进表之后。两次之间只多了 vmboot 那一套（三十一秒）：

    212 套    1680.7 秒工作量    墙钟 298 秒
    213 套    1471.8 秒工作量    墙钟 263 秒

多了一套而工作总量少了二百秒，而这两天里没有任何一次改动是照着「省时间」写的。
所以工作总量这一栏不是量尺，是天气：机器上还跑着什么、页缓存暖不暖、八路怎么分，
都能挪它一成。可比的只有同一轮里的数与同一轮内部的比例 —— 跨轮比要带着这一句。
真要判某套自己的速度，用 --only 单独跑，那是 expected.json 记的那种数。

两次的最慢五套是同一批人，只是名次互换：codeseval 127.0、ittgn 76.5、ucdnfchmyr 74.9、
curve 73.2、signbridge 58.8；以及 codeseval 112.7、ittgn 66.9、curve 65.8、
ucdnfchmyr 64.7、signbridge 53.1。十一月三日那份榜上的 inflate 已经不在了 —— 它单独跑
六十八秒，在全量里曾经占到 146.8 秒，而那正是「别的套件变慢之后 CPU 重新分配」的结果。
所以这张榜只回答「要不要跑全量」，不回答「该改哪一套」；「哪一台机器上花的钱最多」
还是看下面那段按机器归并。

两次都除并行 8 得三百来秒，差的那几十秒是串行那几套与调度。前二十套占六成三
（1378.0 秒），后一百五十套占一成一（229.1 秒）。前十四套是：

    inflate 146.8      codeseval 116.5   sign 103.3        ucdnfchmyr 93.3
    curve 90.6         selfvmcompile 87.3  tree 79.5       ittgn 78.7
    arm 78.1           cvm 63.1         signbridge 62.7  deflate 51.8
    signgen 49.3       verifyhmyr 48.4

「最慢的五套」从这个数起不够用了：它回答「要不要跑全量」，回答不了「下一次该改哪一套」。
后者要的是总工作量的分布，而一套省下的时间还要再除以并行数才落到墙钟上 —— inflate 单独
跑从 133.7 秒到 68 秒，而它在全量里那一格从 141.8 走到 146.8，动的方向甚至是反的：
那是别的套件变快之后 CPU 重新分配的结果，不是它自己慢了。这两个数一定要分清。

按「跑在哪台机器上」把同一批时间重新归一遍，大块才浮出来（括号里是第一次量的数）：

    src/vm.mjs JS 字节码那台    约 284 秒（380）  selfvmcompile、ucdnfchmyr、tree、hmyrcompile
    vm/hmyr.c C 那台            约 262 秒（256）  inflate、deflate、cvm，以及另外几套的一半
    bin/hmyr.mjs 自举解释器     约 182 秒（187）  sign、ittgn
    src/eval.mjs 宿主求值器     约 174 秒（406）  codeseval、selfcov、selfcompile、selfhandoff、selfload

三台 JS 机器合计从九百七十秒降到六百四十秒，占总量三成 —— 而它们解释的是同一份 HMYR。
所以「一处改动、多套受益」的形态在这里，不在「最慢的那五套」里：动一台 JS 解释器的每步
开销，受益的是十几套。这一条与下面那段 curve 的教训是同一个：先看清钱花在哪一层，
再挑改哪一处。

这一节写完的同一天，它就撞上了第一个用例。按机器归并看到 src/eval.mjs 占四百秒之后，
用 node --cpu-prof 跑了一遍 tools/self-coverage.mjs（一行代码都没改），热点是那个求值器
里的一个类：

    Return         src/eval.mjs    59.9%
    evalExpr       src/eval.mjs     7.2%
    execStatement  src/eval.mjs     5.0%

class Return extends Error —— 于是每一个 return 语句都造一个 Error，而 Error 的构造函数
要抓栈，那个栈没有任何代码读过（三个用点：抛出、instanceof 收下、取 .value）。改成不继承
之后，同一台机器上单独跑：selfcov 25.91 秒到 6.58 秒，codeseval 77.48 秒到 62.69 秒。

而全量里受益的不止这两套（最终数）：

    selfcompile   108.8 → 13.6 秒（减 87%）
    selfcov        96.9 → 11.6 秒（减 88%）
    selfload      110.9 → 18.3 秒（减 83%）
    selfhandoff    75.7 → 13.7 秒（减 82%）

selfload 用的是宿主的 loader 与 parser，但它经由 loader 的 runUnit 也走到求值器，所以它
跟着一起快了八成。这一族五套合计从五百一十七秒降到一百七十四秒。总工作量 2754.8 秒到
2173.6 秒，墙钟 411.6 到 353.9 秒。

那之后又试了两处，都不大：execBlock 的 for...of 换成索引循环毫无变化（六十二点三对
六十二点七），而 Scope 的 Map 改成按需分配省了三个百分点（六十点七对六十二点七）。
profile 里 execBlock 占 45.2% 而 Scope 的构造只占 0.9%，说明那笔钱在 V8 内联进 execBlock
的 new Map 上 —— 迭代器早就被优化掉了，空 Map 没有。剩下的四成多是建 Scope 对象本身
与建帧，那是延迟建帧那一档的事，不在这一天里。

这件事的形状要记清楚：那三个受益最大的套件在「最慢五套」榜上并不显眼（selfcompile 第五、
selfload 第四、selfhandoff 第十一），而在「按机器归并」里它们与 codeseval 站在同一列。
挑最慢的几套会挑错，挑最慢的那一层才挑得对。而 codeseval 自己只动了一个百分点 ——
它走的是那七个「只在程序真的跑起来才出现」的构造，return 不是它的瓶颈。

curve 那一行仍然值得单独读，因为它自己就是一条教训。换喂法之前这一行写的是「九次标量乘，
每次一秒多」，而同一套件的实测在 128 到 203 秒之间摆动。先量分解：标量 0 要 3.96 秒、
标量 8 要 3.94 秒、同一个标量跑第二遍还是 3.91 秒，而加载与编译只有 61 毫秒。
于是「十四次各自加载编译是主要开销」这个猜测被推翻了 —— 它错在拿「标量 0
应该几乎不用算」当成一个不用验证的前提。真正的成本全在大整数运算的次数上：
一次标量乘是 255 轮点加与倍点，一次点解压是一轮 255 步的模幂，验签是两次标量乘。

所以这套件的时间不能靠重组调用省下来。去掉两回白算（原来第三节又跑了一遍
2 与 3，而第二节已经有这两个点的结果）换来约 5 秒，是净收益，不是数量级的改善。

窗口法在这一条上也不成立（2026-11-03 查的）：标量乘已经在扩展坐标上跑（X、Y、Z、T
四个分量，只在最后转仿射时求一次逆），所以「改成 Jacobian 省掉 255 次模逆」这个想法
早就在实现里了。剩下的账是：双倍-加是 255 次倍点加 128 次点加，按 dbl-2008-hwcd 的
八次模乘与 add-2008-hwcd-3 的九次算，约三千二百次模乘；四位窗口是 256 次倍点、64 次
点加、再加十来次预计算，约二千七百次 —— 只省一成五。原因是倍点本就占七成，而窗口法
省下来的几乎全是点加。真要快，得动模乘本身，那是大整数表示那一格的事。

这几套的价值在于「真的跑一遍」，所以不裁剪它们的覆盖面，只在你不需要的时候用
--skip 请它们先歇着。

五、这套规则自己的边界
--------------------------------------------------------------------

依赖图是静态扫出来的，扫不到的东西有两种：

    一、运行期拼出来的路径（比如把 "self/" 与一个名字与 ".hmoca" 接起来）。目前没有这样的测试，将来有了
        就得在 SUITES 里手工声明，或者把拼路径改成字面量。
    二、读数据的套件（读 docs、读 tools/suite-list.txt）。它们被 --affects 选中时
        依赖的是「文件在不在」，不是「内容对不对」—— 所以改文档之后仍然要跑 docs。

这一节写在这里，是因为「自动挑套件」最容易出错的地方正是它挑不到的角落。
[改] 2026-10-28：上面第一条那句「目前没有这样的测试，将来有了」已经不成立了。

    tools/hmget.mjs 就是运行期拼路径的：它把 --from 给的那个来源与 <包名>、
    文件名接起来，而那段路径在静态扫的时候完全看不见。而 test/hmget.test.mjs
    覆盖了它 —— 十三节、三十二项。

    于是「将来有了就得在 SUITES 里手工声明」这句话现在有了一个实例，
    而它的做法值得写下来：那个套件在 suite-list.txt 里不声明自己依赖哪些
    具体文件，因为它依赖的是 tools/hmget.mjs 这一个文件；而「拼出来的那些路径
    指向哪儿」由用例自己造（临时目录、临时来源），不靠静态依赖图。

    所以这一条现在的结论是：运行期拼路径的测试不需要在 SUITES 里声明
    它拼出来的东西 —— 它只要声明拼的那个文件。这一点在写 hmget 之前不清楚，
    而现在清楚了，因为有一个真的例子。

[改] 2026-11-02：第三个实例，与上面两个都不同。test/curve.test.mjs 不再自己
    spawn bin/hmyr.mjs，改成把任务表交给 tools/curve-batch.mjs 去跑。那条边也是
    一条命令行参数里的路径，而地图原来的三条规则只收 .hmoca 结尾的字符串 ——
    于是改那个探针，--affects 会答「没有套件」，而曲线套件会红。

    这一种不需要手工声明：套件里写的是字面量 tools/curve-batch.mjs，只是扩展名
    不在原来那三条规则里。加一条收仓库内 .mjs 路径的正则就够，判据在
    test/impact.test.mjs 第五节。

    顺带露出更隐蔽的一条：探针自己 import 了 src/loader.mjs、src/vm.mjs 与
    src/capabilities.mjs，而地图只收「套件脚本自己的 import」—— 改 src/vm.mjs
    同样不会选中 curve。所以那个循环现在把被 spawn 的工具脚本的 src import
    也并进套件的依赖里，判据是同一条。

    同一天还露出第二种形状：test/hmget.test.mjs 把路径拼成
    path.join(ROOT, "tools", "hmget.mjs") —— 两段。于是「整段字符串以 tools/
    开头」那条正则也看不见它。现在两条正则都在，判据同在第五节。

    真拼路径的那一种（字符串相加）仍然扫不到，边界没有变宽。

六、清单是产物，不是事实（2026-11-02）
--------------------------------------------------------------------

工程地图（tools/impact.mjs --map）报的套件数，以及自举那份调度器（self/check.hmoca）
读的那份清单，都来自同一个源头：tools/check-all.mjs 里的 SUITES 表，用
node tools/check-all.mjs --list 导出成 tools/suite-list.txt。

问题在于那份导出件没有人负责重新生成：SUITES 长到一百九十四条，而 suite-list.txt
还停在一百七十七条。少了十七条，而那十七条里有 owned-check、zone-static、realtime、
threads-c-vm —— 正是最近几轮一直在改的那几套。

后果有两处。自举那台调度器只跑一百七十七条，于是「全套通过」这句话的范围比它的
字面小；而工程地图报的「一百七十七个套件」也跟着小。

修法只有一条值得写：清单是产物，产物就要有生成的入口。重新导出一遍，一百七十七条
变一百九十四条，地图那句话跟着变。以后改 SUITES 之后顺手跑一次
node tools/check-all.mjs --list > tools/suite-list.txt 才对。

顺带说清一个口径：地图那一行报的「份 .hmyr」其实是 HMYR 源码的总数（写这一条时
一百零七份，而其中 .hmoca 一百零七份、.hmyr 零份 —— 改名之后源码只叫 .hmoca 了，
而那一行的字还停在旧名上）。数字是对的，字该改，只是它不影响任何判据 ——
记在这里，免得下一个人按那个字去找 .hmyr 文件。

2026-11-02 的账：地图报 111 份 HMYR 源码、205 个套件，与 check-all 的 SUITES 表对得上。
清单那条事故之后，导出件由 node tools/check-all.mjs --list 重生成，两边数字一直同步。
（这几天动过两回：203 到 204 是 impact 那一套，204 到 205 是 mapagree。两回都是
「加了套件、这行数没跟着动」—— 同一件事已经说过两次：清单是产物，产物要有生成的入口。）

这三个数不是照抄那一行 —— 分开数了三遍：

2026-11-06 第二笔：两份文档检查器的宽严不同，第一次不一致是它自己抓到的
--------------------------------------------------------------------

这一轮改文档时，design/PLATFORMS.txt 里照抄了一行 make 的报错，那行以三个星号开头。
docs 那一套（JS 版）判它通过，docshmyr 那一套（HMYR 版）判它含 bold marker —— 两份
检查器对同一份文件给了不同判决，而 docshmyr 正是为抓这种分歧存在的。

分歧在规则本身：

  tools/check-docs.mjs    要求成对：两颗星、中间不含星号的文字、两颗星
  tools/check-docs.hmoca  只要那一行里出现两颗星就算

判断：严的那一边才是纪律的本意。设计稿是纯文本，两颗星出现在里面从来不是为了加粗，
而是照抄别处的输出 —— 我这一次抄的就是 make。而「成对才算」有一个安静的后果：
只写一边的时候看不见。所以 JS 版那一条是放宽，不是 HMYR 版太严。

第二件，同一套的脆弱点：违规时两侧的清单对不上，不是因为判决不同，是因为打印格式
不同 —— HMYR 版在不通过那一行的行尾带上理由（design/PLATFORMS.txt 后面还跟着
bold marker），而两边都用「两个方括号里一个判决」加路径这一种形状去解析，带理由的
行就匹配不到。于是「没有哪一份只在宿主那边」会指着一份其实两边都查过的文件。
后果写清楚：这一套只在零违规的时候才真的在比清单。

两件这一轮都没有改，理由是各自都要动一处真东西：
  第一条改的是正则，改了之后 58 份文档一起受检（design/ 之外还有几份）
  第二条改的是打印格式，两侧都要动，而两侧的格式各有各的用处
两条都该是独立的一件，判据是 docshmyr 那九项一条不改、并且再来一次违规时两侧清单
仍然对得上。

2026-11-06 第三笔：那两件都收了，而第二条的修法换了方向
--------------------------------------------------------------------

上一段写着「两件都该是独立的一件」，而它们当天就收了 —— 收了之后才知道该怎么收，
所以上一段的判断留着，它是当时的判断。

第一条按上一段说的改了：tools/check-docs.mjs 的 bold 规则从「两颗星、中间不含
星号的文字、两颗星」收紧成「出现两颗星就算」，与 tools/check-docs.hmoca 那句
「行里含两颗星」对齐。改之前数过：58 份受检文档里含两颗星的行是 0 行 —— 所以这次
收紧没有让任何一份变红，而它本来也不该有：设计稿是纯文本，两颗星出现在里面从来不是
为了加粗。

第二条的修法换了方向。上一段说「改的是打印格式，两侧都要动」，而真正该动的是解析：
test/docs-hmyr.test.mjs 里那一行正则要求路径之后直接行尾，于是带理由的行（这一侧
写 bold marker，JS 那一侧写 bold marker 加行号）匹配不到，那一份就从清单里整行
消失。改成允许路径之后跟一段空格加任意文字 —— 两侧的格式因此都不用动，而它们各自
的用处（一边报行号、一边不报）都留着。

同一处还有一件必须一起改，否则第一条永远测不出来：那九项的前两项验的是「退出码 0」，

—— 这正好是那一天的真实情形：四项比较全部落空，套件却只在第 1、2 项上说话。
现在它们验的是「退出码是 0 或 1，且末行有那份计数」：零违规由 docs 那一套管，
这一套管的是两侧一致；崩了不会有末行，所以段错误与超时照旧红。

验证分两步，而且是先看它红：在 design/PLATFORMS.txt 末尾加了一行含两颗星的文字，
再跑两套 —— docs 红并指向那一行，docshmyr 九项全过、违规数报 1。有违规的时候
两侧的清单仍然逐份对得上，那正是原来做不到的那一件事。撤掉那一行之后两套都回到
零违规。

2026-11-06 第四笔：有多少判据被前置条件包着，而总数看不见它
--------------------------------------------------------------------

这一节的由来是 arm 那一次：那条不通过把后面五条判据一起藏了，而它们从来没有在
Windows 上过过。所以问的是同一件事的规模 —— 全仓有多少套件，跑过的项数比它
写下的断言少。

量法是两步，工具是 tools/cond-census.mjs：跑一次全量留档，再读那份档。

  一、静态数每个套件脚本里断言函数的调用次数（ok、检查、判 三个名字）
  二、实跑项数是日志里那一行的 passed 加 failed
  三、差额为负的就是候选

数字（232 个套件，其中 228 个的汇总行解析得出来；docs、conform、selfcov、selfload
四个打的是另一种形状）：

  实跑少于静态      22 个
  实跑与静态相等    124 个
  实跑多于静态      82 个（同一条判据在循环里跑了好几次）
  差额合计          71 处

差额不等于「被藏起来的判据」，这一点必须说清，否则这份名单会骗人：

  · 平台分支：arm 里 armclang 那一支在这台机器上本来就不该跑。
  · 环境开关：deflate 那 10 处是 HMYR_HEAVY 控制的重量级用例，默认不跑 ——
    而它是这批里差额最大的一个，所以「差额大」本身不是罪名。
  · 循环里断言的套件反过来：实跑多于静态，82 个属于这一类。

最该先看的不是差额最大的，是差额为负而「跳过」字样为零的那九个：
i18nthree、pipe、readme、crosscheck、f64bits、ucdnfchmyr、ucdcasehmyr、
selftree、distro —— 它们跳过时一句话都没说。

判断：这一件事不设判据。理由是基线与静态数都会漂（加一套、删一条断言都会动），
把会漂的数字钉成判据，红的时候分不清是「新藏了一条」还是「刚加了一条」。
留下的是工具与一条规则：

  一个套件里被条件包住的判据，条件不成立时要打一行跳过，并且带上条数。

现在全仓「跳过」出现 117 次，带条数的少 —— 那是下一步可以做的一件小事，
而不是必须现在做的一件大事。

2026-11-06 第五笔：那九个候选逐个核过，八个别有原因，一个是真的
--------------------------------------------------------------------

第四笔留下的九个「差额为负而跳过字样为零」的套件，今天逐个核了一遍。核法是
读每一处 ok 的前一行：看它是在一个互斥的两支里、在一个守卫分支里，还是在一个
回调里（第三种才可能是真的少跑）。

  i18nthree       20 → 18   Windows 那一支两条，POSIX 那一支两条，跑其中一支
  pipe             9 →  7   一条是「服务端起不来」的守卫；另一条是真的 —— 见下
  readme          16 → 14  「取不到那一行」「替换没生效」两个守卫
  crosscheck      19 → 18  「取不到那份头」的守卫
  f64bits          3 →  2  「临时文件没被改过（否则这一节什么都没验）」的守卫
  ucdnfchmyr       9 →  8  「产物没出来」的守卫
  ucdcasehmyr      9 →  8  同上
  selftree         2 →  1  if/else 两支，只跑一支
  distro          16 → 15  「取不到远端」与「取得到」两支，只跑一支

八个是形状使然：互斥两支永远只跑一支，守卫分支正常就不该跑。判据的总数在
逻辑上就是那么多，而静态计数把两支都数了。

真正的一个在 pipe：那条判据是「hmyr 退出码是 0」，它挂在 子.on("exit") 上；
而管道那一节的 promise 在 sock.on("end") 里就 resolve 了，于是文件末尾的
process.exit 常常赶在 exit 回调前面 —— 那条判据一次都不跑，而总数里只看得出
「少了一项」。这与 arm 那一次同类：一条正向判据被时序挡在门外，静默。

修法：end 那一支不再直接 resolve，改成三秒兜底；exit 那一支跑完那条判据才
resolve。改完 pipe 从 7 项到 8 项，剩下的那 1 项差正是「服务端起不来」的守卫。

所以这一节对第四笔的补充是：普查工具能指出候选，而「候选里哪些是真问题」
只能一处一处读。三种成因里只有第三种（回调里可能不执行）是真问题，前两种
（互斥两支、守卫）是判据本来就该长成那样。工具的说法也照这个改了。

2026-11-06 第六笔：剩下十二个也核完了，第二处同形的问题就在其中
--------------------------------------------------------------------

第四笔列的二十二个候补，第五笔核了九个「跳过字样为零」的，arm 单独记过。
这一次核的是剩下那十二个。

  差额大的五个都是显式开关，不是问题：

    releasehmyr  20 → 10   整个第二节在 if (!process.env.HMYR_HEAVY) 后面，
                           跳过时印出了原因（一分多钟那一条）
    manifesthmyr 17 →  7   同形
    seed         11 →  3   HMYR_HEAVY 两处：三吉字节与四吉字节那两格
    deflate      30 → 20   HMYR_HEAVY 一节，另加六对 try/catch，每对只跑一支
    surface      61 → 53   五处跳过，全是平台或工具缺席

  差额小的六个是守卫或互斥两支，不是问题：

    cli 22 → 21 · readlines 8 → 7 · contracts 40 → 39 · invariants 45 → 44 ·
    zip 29 → 28

  只有 socket 那两条里的第二条不是守卫。「命名管道服务端起得来」是守卫（正常不跑），
  而「管道那条也退出 0」与 pipe 完全同形：end 回调里先 resolve()，那条判据却挂在
  跑(...).then(...) 里，于是文件末尾的 process.exit 常常赶在它前面。修法与 pipe 同：
  判据跑完才 resolve，收尾交给那一支。socket 从 14 项到 15 项。

  所以这一天里同一形状查出两处，都在「网络回调加子进程」这一类套件里 ——
  它们要同时等两个来源，而谁先到没有保证。下一遍若要再查，该从这一类起步：
  test/ 里同时出现 .on( 与 spawn 的那些文件。

  一处关于修法的记性：socket 第一版给 end 那一支加了三秒兜底，而它带 unref()，
  于是事件循环先空掉、定时器不触发、promise 永不 resolve，报的是
  「Detected unsettled top-level await」。兜底定时器不能 unref —— 它存在的意义
  就是当别的东西都不动时动一下。

2026-11-06 第七笔：竞态那一类有了自己的检查器
--------------------------------------------------------------------

第六笔留了一句「下一遍若要再查，该从这一类起步：test/ 里同时出现 .on( 与 spawn
的那些文件」。今天把那一句做成了工具：tools/race-census.mjs。

判据是位置，不是名字。一个 new Promise 块里，若那处「当场 resolve」出现在任何一处
判据之前，就报 —— 因为之后那些判据只能赶文件末尾的 process.exit。

三条例外，每一条都来自一次假阳性，这也是这一份值得写下来的原因：

  一、注释先换成等长空格。第一版没做，工具读到自己注释里的 resolve 与 ok，
      把自己报了出来。
  二、setTimeout(resolve, …) 与 setImmediate(resolve) 不算当场收尾 ——
      pipe 修好之后用的正是三秒兜底。
  三、.on("error", …) 与 .catch(…) 里的东西只在出错时跑，那里的 resolve 与判据
      都不参与正常路径的先后。socket 的假阳性就是 error 那一支的 resolve。

第三条里还藏着一个更细的坑：第一版把注释与字符串都抹成空格，于是 .on("error"
认不出来了 —— error 那五个字母变成了五个空格。注释要抹，字符串不能抹。这一条
写进脚本的注释里了，因为它不是读一遍代码就能看出来的。

所以现在的验收是这样的：造一个已知有问题的样本，它抓到；删掉样本，全仓十二个
new Promise 块 0 处。抓到过、也放得开，才算一个能用的判据。

它跟 cond-census 的分工：那一份数「实跑与静态的差额」，而差额在修好之前与守卫
长得一模一样，所以它只能指候选；这一份直接看形状，能指到行。

它现在也有自己的判据了（test/race-census.test.mjs，五条）：全仓 0 处，加一个必须
抓到的样本与两个必须放过的写法（干净的回调、setTimeout 兜底）。只留前一条是不行的
—— 工具坏掉也会报 0，而那不是假设：这一轮就踩过一次，套件里那段「样本源码」
写在字符串里，被工具当成真代码读进来，报的是那一套自己。

修法是把每个文件读成两份等长文本：注释两份都抹平；字符串只在「找 ok( 与 resolve(」
那一份里抹平，而在「认 .on("error" 与 .catch(」那一份里留着 —— 否则守卫里的
resolve 又会被当成当场收尾。等长是为了两份的下标通用，行号与位置都能对上。

工具另加了 --dir：自检时把样本写进系统临时目录，而不是写进仓库 —— check-all 并行
跑套件，那种文件会被同一轮里别的套件看见。

--------------------------------------------------------------------

impact.mjs 加了多路径 --suites，于是有人会问：mega-index-map 那边是不是也得跟。

量过的差距只有一条：那边的 library_project 收的是 file 一个字符串
（project-map.js 的 op=affects，工具的 schema 里写的就是单值），所以它问不了

2026-11-06 第九笔：探针的答案有了时效判据
--------------------------------------------------------------------

这一件的由来：design/PROBES.txt 里十五份探针都指到了答案落在哪一份设计稿里，而那些
答案是当时的结论。问题修好之后，答案就旧了，而旧答案读起来与新的没有分别 ——
这正是那天「八格没有」那次事故的亲戚。

原以为做不成自动判据，因为 probes 那一套写着「只编不跑，跑起来要么慢、要么要参数」。
那天把十五份挨个跑了一遍：全部跑得动，最慢的一份二十秒，一共七十九秒。
「跑不动」这个理由不成立，于是判据就在眼前：

  把每一份探针今天的输出记进 probes/expected.json（路径里的仓库根归一成 <root>），
  然后 test/probes.test.mjs 真的一份一份跑，与记的比。

红了之后要判断的正是「探针该更新」还是「世界变了」—— 那是留这些探针的意义，
而在此之前，这个问题只能靠人去翻当时的会话。

两处口径写在这里，免得下次重踩：
  · 归一化要用 path.resolve 之后的根（反斜杠）。第一版用的是正斜杠的写法，
    于是 probe-argv 那一行输出里的路径没被替换，换了机器就红。
  · 这一套从零点七秒涨到七十九秒（单跑），而全量并行时是一百九十九秒 —— 它成了
    全量里最慢的一项，比 inflate 还慢三十秒。要省时间可以 --skip probes，但那是
    放弃这一整类判据：探针记的数字还算不算数，别处没有东西在看。
    并行使它慢两点五倍，原因是十五份探针里八份要加载自举层，而全量那四路
    同时在抢 CPU。

2026-11-06 第十笔：差额只能变小，不能变大
--------------------------------------------------------------------

第四笔写着「这一件事不设判据」，理由是基线与静态数都会漂。那个理由只对了一半：
会漂的是绝对数，而有一个量不漂 ——

  每个套件的差额 = 静态断言数 − 实跑项数

加一条判据时两边同时加一，差额不变；修好一处被藏起来的判据时实跑加一，差额变小；
而有人把一组判据包进 if 而没交代时实跑减几，差额变大。那正是 arm、pipe、socket
那三次的形状。

所以判据是「差额不能变大」，基线在 tools/gap-baseline.json：二百二十九个套件，
另四个的日志行不是那种形状（docs、conform、selfcov、selfload）。它只能在那次变化
已经查清之后重写，命令是 cond-census 带 --保存 跑一份全量日志。

test/gap-baseline.test.mjs（六条）验三件：基线完整、差额变大时会报、差额没变时
不许报。第三件与第二件同样要紧 —— 一个什么都报的工具，红几次之后就没人看了。

一处写错又改回来的地方：第一版写「每一格都不为负」，而差额可以是负数（同一条判据
在循环里跑了好几轮）。这个下界没有意义，删掉；后来又想数「负的有几个」并拍了个
阈值四十，那更没有意义 —— 那个数随内容变，而判据只有一条：它有没有变大。

2026-11-06 第十一笔：那一次比对搬进了 check-all
--------------------------------------------------------------------

第十笔的结尾写着「要自动化，得让 check-all 在收尾时自己比一次 —— 那是改核心工具」。
当天下午做完了。

check-all 结束时，若这一次跑的是全量，就自己算一遍每个套件的差额、与
tools/gap-baseline.json 比，变大的列出来并把全量弄红。四条决定：

  · 只在全量时算。--only、--skip、--affects 时没跑的套件都会被算成「少跑了」，
    那种时候比就是在制造噪声 —— 而一个常常误报的判据，红几次之后就没人看了。
  · 只在全绿时算。这一条是加完当天补的：那一轮 deflate 与 tree 在重负载下各跑了
    二十一分钟然后超时，于是少跑了几项，判据报的是「deflate 从 10 涨到 13」——
    看上去像有人藏了判据，其实是机器跑不动。红的套件本来就会被看见，差额那一笔
    等它们绿了再说。补完之后单独重跑那两套：deflate 七十九秒、tree 八十六秒，
    都全过 —— 那二十分钟是负载，不是代码。
  · 它让全量红。差额变大只有两种来路：藏了判据（真问题），或者刚删掉一条判据
    （那时刻意更新基线，而基线的变化会进 commit、可审查）。
  · 四个套件的输出不是「N passed, M failed」那种形状（docs、conform、selfcov、
    selfload），它们没有可算的差额，与普查工具用同一条正则跳过。

还有一处取数错了又改回来：第一版取的是输出里第一个「N passed」匹配，而
checkhmyr 自己会跑三个子套件，那些子套件的数字也在它的输出里 —— 于是它被算成
只跑了三条、差额从 0 涨到 8。判据装好的第一个发现是它自己的错，取末行才对。

于是这条判据从「跑完全量之后手动跑一次 cond-census」变成「跑完全量就有」。
手动的判据等于没有 —— 这一条是这一周里第三次验证的道理（前两次是 probes 的
只编不跑、与 gap-baseline 本身）。

2026-11-06 第十二笔：两个量具，与它们量出来的分布
--------------------------------------------------------------------

vm/hmyr.c 的两个出口，都只在环境变量开着时工作：

  HMYR_OPS      总步数。今天补了一处：失败那一支也会打。原先它在打印之前就
                return 1，于是「跑了二十一分钟然后红了一项」那种情形手里一个数
                都没有，而那正是最需要它的时候。
  HMYR_OPSMAP   按指令的分布，退出时降序打到 stderr。新加的。

为什么加第二个：总步数回答不了「该优化哪一条指令」。tree 那一趟的分布是：

  取      41366157  30.0%      常量   12786225   9.3%
  布尔    10790955   7.8%      假跳留 10757935   7.8%
  加      10628032   7.7%      跳     10249323   7.4%
  假跳     9824417   7.1%      小      8005374   5.8%

  前八条合计 82.8%，而 调函数 5224 次、返回 5225 次 —— 各占不到千分之一。

这一张表推翻了一个猜测：调用与返回极少，所以瓶颈不在帧的构造与销毁，而在槽访问
与栈操作。「取」一条就占三成，它做的事只是从槽里读一个值再压栈。

所以「汇编化」这一类优化该对准前八条，尤其「取」与「常量」（合计 39.3%）——
它们最简单、风险最低，收益可以量。调用路径写不写汇编，从这张表看都不重要。

「每步 220 纳秒」与这张表放在一起看才有一点意思：读一个槽不该要 220 纳秒。那说明
固定开销（解引用机器状态、边界检查、值复制）占了每步的大头，而它与指令的形状无关。
那才是「汇编化」真正能省的东西。

分布是 tree 一趟的（Huffman 表构造，循环密）。别的程序会长得不一样，但步数最大的
那几套大概率同形：都是槽访问加跳转为主。要看别的就跑一次，两个变量一起给：
HMYR_OPSMAP=1，再加步限。

2026-11-06 第十三笔：-O2 换 -O3，快了百分之十九
--------------------------------------------------------------------

第十二笔那张分布表之后要问的是「优化哪一条」。而在动指令之前先量了一个更便宜的东西：
编译器自己还能榨多少。

同一份 vm/hmyr.c，三档旗标，各跑 tree 三次：

  -O2（原来用的）      30.4 秒（30.0 / 30.4 / 30.5）
  -O3                  24.7 秒（23.9 / 24.7 / 24.7）
  -O3 -march=native    崩了：三次里两次十毫秒就退出，一次正常

两档的步数都是 138102538，一模一样 —— 所以 -O3 快的那百分之十九是每步变便宜，不是
走了更少的路。那正是第十二笔说的：固定开销占了每步的大头，而它与指令的形状无关。

三条决定：

  · 桌面编译点换成 -O3。就是 test/、tools/、src/ 里 "-std=c11", "-O2" 那五十七处，
    一次全换（51 份文件）。
  · 不用 -march=native。它会崩，而原因没查 —— 但「会崩」已经足够不碰它。
  · arm 那两处不动：裸机的 -O2 是量过的（Flash 一百六十千字节、RAM 四十五千字节），
    而 -O3 会让映像变大，那是 arm 套件的判据。

验证：tree、deflate、vmboot、inflate 四套先过，随后全量。

顺手记一条口径：这一页前面写的「每步 220 纳秒」是 -O2 编出来的机器的数。换成 -O3
之后它变成约 180 纳秒 —— 而测出来的方式没变，所以那两个数可以直接比。

光这一条不够，还有一次相反的观测要记：换完之后那次全量里，inflate 是 251.9 秒、
tree 163.0 秒、deflate 158.9 秒；而换之前那一次是 inflate 173.6 秒，tree 与 deflate
都不在慢榜（低于 120 秒）。也就是说单跑时 -O3 快百分之十九，而全量并行时它看起来更慢。

那次观测的负载不明 —— 那天连跑了好几轮全量与实验，四路并行里同时有 gcc 与解释器。
所以不能据此说 -O3 更差；但它也不能被忽略，因为全量是最常跑的场景，而 -O3 的代码
更大，icache 压力在四路并行时确实可能翻过来。

要判它只有一条路：在同一条件下各跑一次全量，比同项的耗时。那是两次全量的成本，
今天没做，记在这里当一件开着的事。在那之前，-O3 留着 —— 单跑的百分之十九是真的，
而全量那一面还没被判过。

2026-11-06 第十四笔：一次微优化的负结果
--------------------------------------------------------------------

第十三笔之后手里有「取 占三成步数」这个事实。于是做了一件最小的事：把 OP_LOAD 的
两次比较（a 小于零，或者 a 不小于 nslots）合成一次无符号比较 —— 两种写法等价，
因为负数转成无符号之后必然大过任何 nslots。

量了三次，与改之前的三次比：

  改之前   23945 / 24662 / 24731 ms（中位 24662）
  改之后   23751 / 23977 / 24845 ms（中位 23977）

差百分之二点八，而三次之间的波动本身就有百分之四。所以这个改动在性能上没有位置 ——
-O3 已经看懂了两种写法等价，把同一段代码编了出来。步数两边都是 138102538。

改动留着：一次比较比两次清楚，而注释里写明了为什么等价。但它不是一次优化。

真正的结论在这里：在 -O3 面前，指令层面的微优化（合并比较、展开 push、省一次解引用）
没有位置。剩下的杠杆只有两个：

  · 值的大小。一个 Value 是五十六字节，而每条指令都在搬它 —— push 按值收一份，
    再往栈里存一份。三成的步数是 取，两条指令之内搬两次五十六字节。
  · 步数本身。而第十一笔量过：正常路径的步数已经稳定且合理。

所以下一步若还要动性能，该动的是值的布局，不是指令的写法。而那是大改动：
设计上字段名可以不变（.num / .s / .items 那些），但那仍是五百多处调用点的边界。

2026-11-06 第十五笔：编译缓存试过，回退了
--------------------------------------------------------------------

第十四笔之后有一组数：四套并跑时 tree 从二十四秒涨到一百七十七秒，而它们共同做的
事只有「各编一遍同一个 vm/hmyr.c」。于是做了一件显然的事：给编译加缓存。

做法：src/cc.mjs 加 编C机器(出, 额外旗标)。键是源码字节加旗标，产物缓存在系统
临时目录，返回值形状与 spawnSync 一样，于是调用点只换一个名字；三十七处标准形态
机械替换（三十四份文件），十四处带额外旗标的变体留着。

它在单独跑的时候完全正常：array 从十六秒（其中六秒是编译）变成一点九秒，而单独跑
bytecode、vmload、vmrun、vmboot 四套也全过。

而它在全量里不行。两次全量都是同样四套红，而它们正是「跑 C 机器」的那一类，
分项也几乎一样：

  第一次             bytecode 16 过 7 不通过 · vmload 2 过 5 不通过 ·
                     vmrun 3 过 19 不通过 · vmboot 3 过 4 不通过
  修了原子写之后      同样四套，同样分项

第一次我以为根因是并发写缓存不是原子的 —— 两个进程同时 copyFileSync 到同一个路径，
第三个读到半个 exe。改成写临时名再 rename 之后，单独跑那四套全过，而全量里它们照样红。

所以原子写不是根因。根因没查清，而一个让四套在并发下红的改动不该留着，即使它单独跑
时是好的、即使它能省三百多秒 CPU。所以回退了，缓存目录也清掉了。

留着的是这一段：一处已知的、可量的浪费（五十七处编译、三百四十二秒 CPU），
和一次没成功的尝试。下一次再碰它，该先弄清「为什么这四套在并发下红而单独跑不红」——
而那多半不是缓存本身的问题：回退之后它们在全量里是绿的，同样的并发、同样的四路。

2026-11-06 第十五笔之一：查了两个假设，都不是
--------------------------------------------------------------------

回退之后先验了两件，都是那天能想到的最可疑的。

一、编C机器 把 -lm 放在源文件前面，而原调用放在后面。两种顺序各编一次：

  原顺序（… -o a.exe 源 -lm）   435889 字节
  新顺序（… -lm -o b.exe 源）   435889 字节，字节内容不同

  字节不同是 PE 头里时间戳那一类东西。而行为完全相同：同一份 tree 字节码，两个 exe
  都退出 0、都跑 138102538 步、输出首行都是「输入 4096 字节」。

  所以旗标顺序不是根因。

二、那四套里有没有被替换过的调用点。它们红时的分项与单独跑时一样，而单独跑是绿的 ——
  所以差异不在「换了调用形式」，在「同时还有其他套件也在调它」。而那正是我修了原子写
  之后仍然红的那一面。

剩下的假设只有「并发下某个环节让 exe 不可用」，而它要重现才能观测。重现的办法是重新
应用那个提交、单独跑那四套（已知绿）、再与全量对照，期间把 exe 的字节与行为都记下来。
这一条今天没做 —— 让仓库临时变红需要一个能随手撤掉的环境，而那比手里有的更麻烦。
所以它是这一页最新的一件开着的事。

2026-11-06 第十六笔：两次重现实验都正常，这件事按「不可重现」结案
--------------------------------------------------------------------

第十五笔之一那件开着的事，今天在仓库外面做了两次实验收口 —— 不碰 src/，不碰那四套
套件，也不让仓库变红。办法是把 编C机器 那三十行逻辑抄进临时脚本，让多个进程同时调它，
然后每个进程用「自己编的」与「缓存复制出来的」各跑一份字节码，比退出码与步数。

第一次：八路并行、一种旗标、一份字节码（tree）。八个 worker 全正常，包括缓存产物。

第二次：二十四路并行、三种旗标（-Wall 的有无、-lm 的位置、加 -Wno-unused-function）、
两份字节码（自造的 tree 与仓库里的 runtime/fmt.hmoks —— 后者正是 vmload 读的那一类）、
每个 worker 跑两次。二十四路全正常。

所以：缓存逻辑在「二十四路并发加三种旗标加读仓库产物」这些条件下是可靠的，而它在全量
里确实让四套红过两次，原因没查出来。

这一件按「不可重现」结案。结案的理由不是「找不到就算了」，而是三条：

  · 缓存代码已经回退，仓库是绿的；
  · 三次全量的差异只有「缓存代码在不在」，而两次外部实验在更强的并发下都正常 ——
    说明全量里那个让它们红的条件比「并发」更特殊，而我没有名字给它；
  · 没有名字就写不出判据，写不出判据就验不了修法。

所以它从「查根因」变成「已知不可重现」，而它省的那三百四十二秒 CPU 仍然是一处真实的
浪费 —— 只是下一次该换一条路去拿它：把五十七处编译合并到一次（比如让 check-all 先编
一份、把路径发给各套件），而不是给每一处加缓存。那条路要改的是 check-all 与套件之间的
约定，而它至少有一个明确的好处：不必猜缓存与并发怎么互相干扰。

2026-11-06 第十七笔：那条路也走了一次，同样四套红 —— 而这次没有并发写
--------------------------------------------------------------------

第十六笔的结尾说「下一次该换一条路」。当天就走了那一条，而且把它做完了：

  src/cc.mjs 加 编C机器(出, 额外旗标)，它不缓存 —— 只看环境变量 HMYR_EXE：
  有就复制那一条路径到 出，没有就自己编。
  tools/check-all.mjs 在起任何套件之前先编一份到 %TEMP%/hmyr-shared/hmyr.exe，
  设好 HMYR_EXE；子进程继承环境。
  三十七处标准形态照旧机械替换。

共享的东西只有「一个只读路径、一个写者」—— 全量开始之前就编完了，之后没有任何进程
写它。所以第十五笔里那条「并发写缓存」的可能被彻底排除。

结果：同样四套红，而且这次多红了一套。

  bytecode 16 过 7 不通过 · vmload 2/5 · vmrun 3/19 · vmboot 3/4 · size 3 过 1 不通过

而单独跑一套（不设 HMYR_EXE、自己编）是绿的；经 check-all 跑四套也快（四套十点六秒，
比单独一套十一点九秒还短），说明复制确实生效了。

所以两次尝试的共同点不是「缓存」，也不是「并发写」，而是「exe 不是 gcc 在那一刻刚编
出来的」。这一条把范围缩得很小，而它也是我能给出的最有用的东西：

  · 那四套套件对「exe 是这次刚编出来的」有某种隐含依赖；
  · 而这一点与并发无关 —— 两次尝试的并发模型完全不同，红的却是同样四套。

回退了（git reset 到 ee981df），共用目录也清掉了。

下一次再碰它，起点不该是「怎么让 exe 复用」，而是「查清那四套到底依赖 exe 的什么」。
一个可验的猜测：size 那一套这次也红了，而它量的是大小 —— 那么先看那四套是不是在比对
「exe 的大小或时间戳」。若真是，那这条路从根上就走不通，而五十七次编译属于必须付的钱。

2026-11-07 第十八笔：那四套的共同点是「路径没有 .exe 后缀」，而机制仍不明
--------------------------------------------------------------------

第十七笔留下的问题是「那四套依赖 exe 的什么」。今天查出一件事，它既是线索也是一个陷阱。

  红的四套   vm-load、vm-run、vm-boot、bytecode —— exe 都是 path.join(临, "hmyr")，
             没有后缀
  绿的套件   array（hmyr-array.exe）、bitops、crc、deflate、tree —— 全都带 .exe

四对四，没有一个反例。

而 gcc 的脾气是：gcc -o 一个没有后缀的路径，它自己会加 .exe。所以原来那四套跑
spawnSync(临/hmyr) 时，目录里其实只有 hmyr.exe，而 Node 通过 PATHEXT 找到了它；
换成 copyFileSync 之后，目录里是「无后缀的 hmyr」—— 两者文件名不同。

验了三件，都不是原因：

  · 无后缀的 PE 能不能跑：当时判「能」，而那是假证据 —— 第十九笔更正了它。那个实验的
    目录里 hmyr.exe 也在，所以启动的是 .exe 那一份，不是无后缀的那一份。
  · 那四套有没有 stat exe：0 处。
  · 旗标顺序：两种顺序的产物字节不同而行为相同（第十五笔之一）。

所以线索是「文件名」，机制还没找到。剩下的一个可能是「同一个目录里 hmyr.exe 与 hmyr
同时存在时谁被选中」—— 要验它得重新应用改动，那是第五次尝试。

这一件到此为止。理由不是「找不到就算了」，而是成本已经远超收益：它省的是三百四十二秒
CPU，而四次尝试的代价早就不是三百四十二秒。线索留在这里 —— 下一个碰它的人从「四对四
的后缀分类」起步，比自己从头想快得多。

顺带记一条给所有写这类代码的人：gcc -o 一个没有后缀的路径会自己加 .exe，而
copyFileSync 不会。两者混用的时候文件名会不一样，而「能跑」与「是同一个文件」是两件事。

2026-11-07 第十九笔：那四套的根因找到了 —— spawnSync 在 Windows 上只认 .exe
--------------------------------------------------------------------

第十八笔留下了「四对四的后缀分类」这条线索，而机制没找到。今天用一个不碰仓库的实验
把它测出来了：同一个目录里同时有 hmyr 与 hmyr.exe 时，spawnSync 跑哪一个？

  情形一  只有 hmyr.exe（原来那四套的样子：gcc -o hmyr 之后目录里就是它）
          跑 hmyr → 正常，退出 2，打出 usage
  情形二  只有无后缀的 hmyr（copyFileSync 的样子）
          跑 hmyr → ENOENT，根本没启动
  情形三  两个都在，hmyr 是坏文件
          跑 hmyr → 正常（用的是 .exe 那一份）
  情形四  两个都在，hmyr.exe 是坏文件
          跑 hmyr → UNKNOWN 错误（用的还是 .exe 那一份）

所以机制是：spawnSync 在 Windows 上走 PATHEXT，只认 .exe，从不执行无后缀的那一份。

这一条解释了三件事，一件不缺：

  · 那四套为什么红 —— exe 写成 (临, "hmyr")，而复制只造出无后缀那一份，于是 spawnSync
    报 ENOENT，判据把它记成「跑不起来」；
  · 其余套件为什么绿 —— 它们写的是 (临, "hmyr.exe") 之类，带后缀；
  · 第十八笔那个「无后缀的 PE 也能跑」为什么骗了我 —— 那个测试目录里 hmyr.exe 也在，
    所以启动的是 .exe 那一份，等价于情形三。两次「重现实验都正常」也是同一个原因。

修法一行：复制之后照 gcc 的样子补一份 .exe（src/cc.mjs 的 编C机器）。共享的仍然只有
「一个只读路径、一个写者」—— check-all 在起任何套件之前编好，套件只复制。

验证：bytecode、vmload、vmrun、vmboot 四套先过；随后全量 234 套全过，差额报「没有一个
套件变大」。全量里慢的五套是 probes 197.0 秒、inflate 137.1、vmboot 128.5、examples 123.6、
sign 115.7 —— 与没有共用 exe 那次相比在同一档，因为省下的是编译（几十秒 CPU，摊在四路
并行里），而慢榜量的是「跑」。

这条教训值得单独写：gcc -o 一个没有后缀的路径会自己加 .exe，copyFileSync 不会，而
spawnSync 只认 .exe。三者混用的时候，「文件存在」「是同一个文件」「能被启动」是三件
不同的事，而只验证其中一件就宣布「能跑」会得出错的结论 —— 这一条我错了两次。

2026-11-07 第二十笔：probes 那七十四秒里，四十四秒是同一份装载付了四次
--------------------------------------------------------------------

第十九笔之后给 probes 加了计时，得到「编 0.4 秒 · 跑 74.2 秒（十五份）」。而这一套在
全量里是 197.0 秒，所以它自己只花了一小半，其余是四路并行下等 CPU。

再往前一步：十五份各跑一次、按耗时排序，同时记下每份引入了什么。

  probe-decls2      20.3s   self/run.hmoca
  probe-load2       11.5s   self/run.hmoca
  probe-row         11.4s   self/run.hmoca
  probe-self-load   11.2s   self/run.hmoca
  probe-decls        9.6s   self/lex.hmoca 加 self/body.hmoca
  probe-lex          3.0s   self/lex.hmoca
  probe-lex2         2.6s   self/lex.hmoca
  probe-load         2.3s   self/lex.hmoca
  probe-len          1.4s   self/lex.hmoca
  其余六份           0.3s   什么都没有引入

三件事就此清楚了。

一、装载 self/run.hmoca 的固定开销约十一秒一份。四份付了四次，约四十四秒，占那
    七十四秒的六成。

二、probe-decls2 多出的九秒是它自己的活（只解析公开 的递归回调），不是浪费 ——
    它问的正是「会不会撑到五百层」。

三、没有引入的六份各 0.3 秒，而那 0.3 秒是 node 启动加装载程序本身。

所以「优化 probes」的正确形状不是让每份更快，而是别把同一份装载付四次：一个宿主进程
读那几份，装载只付一次。按这个画像估，七十四秒能到四十秒上下 —— 而那是结构改动
（探针怎么被跑起来），不是一行的事，所以另开一轮。

要留意的是这条画像不只属于 probes：装载 self/run.hmoca 的那十一秒，inflate、vmboot、
examples 也在付。它才是「自举层装载成本」这个数，而这一页此前没有它 —— 有了它，
那几套的耗时才有了可以拆开看的第二项。

2026-11-07 第二十一笔：三套的画像，编都不是大头
--------------------------------------------------------------------

第二十笔给 probes 加了拆分之后，同一天给 vmboot 与 inflate 也加了。三套各单跑一次：

  probes   编 0.4s · 跑 74.2s（十五份，平均 4.9s）
           其中装载 self/run.hmoca 约十一秒一份，四份付了四次 —— 约四十四秒
  vmboot   编 C 机器 5.3s · 跑 60.8s（三次）
           自举链跑 hello 5.5s · 自举链跑 vm-hands 53.7s · 不存在的入口 1.5s
  inflate  编 C 机器 5.5s · 跑 61.3s（压六次 3.1s · 解十四次 58.2s）

三件事就此清楚：

一、编 C 机器在每一套里都是五秒上下，而跑是六十到七十四秒。所以「编」从来不是这几套
    的大头 —— 那与我 2026-11-06 时的猜测相反，而上一轮的共用 exe 省下的正是这五秒。

二、probes 的大头是装载（四十四秒），vmboot 与 inflate 的大头是干活（vm-hands 53.7 秒、
    解 58.2 秒）。两类问题、两种改法：前者把装载合并成一次（一个宿主进程读几份），
    后者要动 HMYR 自己写的那些程序，而它们已有判据（inflate 那一条是「每输出一个字节
    不超过二百六十步」）。

三、全量的数（197.0、128.5、137.1）比单跑的数（74.2、60.8、61.3）大出三成到一倍 ——
    那部分是四路并行下等 CPU，不是它们自己的活。这一条对「该不该优化某一套」很要紧：
    单跑的数才是它的成本，全量的数是它与别的套件一起时的墙钟，而墙钟里有一半是排队。

2026-11-07 第二十二笔：那十一秒不在程序本身 —— 第二十笔的结论要改
--------------------------------------------------------------------

第二十笔写的是「装载 self/run.hmoca 约十一秒一份」。那是相关性：引入 run.hmoca 的四份
各 11 到 20 秒，没引入的六份各 0.3 秒。今天用一个数把它拆开了 —— 把探针编成字节码、
让 C 机器跑，记步数：

  probe-load2    编字节码 15 ms · 跑 51 ms ·          8 步
  probe-row      编字节码  8 ms · 跑 13 ms ·         81 步
  probe-decls2   编字节码 13 ms · 跑 23 ms ·     44,133 步
  probe-lex      编字节码  1 ms · 跑 17 ms ·     22,310 步
  probe-and      编字节码  1 ms · 跑 11 ms ·         18 步

所以在 C 机器上那几份要跑的东西极少（八步、八十一步），而它们在 bin/hmyr.mjs 下各要
十一秒。八步与十一秒放在一起，只能说明一件事：那十一秒不在探针自己身上，而在
bin/hmyr.mjs 这一层 —— 而那一层是「HMYR 写的 VM（runtime/run.hmoks）跑在 src/vm.mjs
上」，两层解释器叠着。

于是第二十笔那句「装载要十一秒」要改成：引入 self/run.hmoca 的探针，在自举层上运行要
十一秒，而原因没有量到。

还有一处不能忽略：这两组数不能直接比。C 机器跑 .hmoks 时未必调 main（八步说明只跑到
了装载），而 bin/hmyr.mjs 会调。所以「步数少」只说明「编译后的指令流里没有那么多步」，
不说明「程序本身快」。

要往前一步，得有「自举层里的步数」—— 而自举层没有那个出口（HMYR_OPS 是 C 机器的）。
给自举层加一个同样的出口是另一件事，而它的收益比这一轮大：inflate、vmboot、examples
都在自举层上跑，而这几套的墙钟此前一条都拆不开。

这一轮到此为止，因为它已经把「该往哪查」从「装载」改成了「自举层」—— 而「自举层没有
仪器」这件事本身就是下一件该做的。

2026-11-07 第二十三笔：自举层没有「步」这个概念，不是漏了仪表
--------------------------------------------------------------------

第二十二笔说「得有自举层里的步数」。今天去加，查出两件事。

一、bin/hmyr.mjs 有两条面：编译面（带 --compile，走 src/vm.mjs 的 跑字节码）与解释面
    （默认，走 src/minimal-eval.mjs 的 最小运行）。我先把 HMYR_OPS 加进了编译面 ——
    而探针走的是解释面，所以那一次打印一次都没出现。

二、解释面那台机器（最小运行时）没有「步」这个量。它有的是「循环闸」：一个一百万轮的
    while 上限（minimal-eval.mjs 第三十九行）。而构造参数里的 stepLimit 赋给了
    this.stepLimit，之后一次都没有被读过 —— 那个属性是死的。

所以第二十二笔那句要改得更准：那一层没有「步」这个概念，不是漏了仪表。它的执行单位是
AST 的一个节点，限制失控靠数 while 的轮次，不做全局计数。

编译面上那个出口留着：带 --compile 时走 跑字节码，那里有 this.步，一行就能报。

解释面要加步数，得动 最小运行时 的求值入口 —— 那是这台机器的核心，不是一行的事，
所以另开一件，不顺手加。

一个自己踩的坑值得单记：第一次改的时候把打印加进了错误的 if 分支，而症状是「代码看着
完全正确、跑起来没有输出」。两次误诊（被 process.exit 吞掉、属性不存在）之后才去读那个
if 的条件。下一次碰到「写了却不见」，第一件事该是确认那段代码在不在执行路径上 ——
而确认它的办法是读条件，不是猜缓冲区。

2026-11-07 第二十四笔：解释面一直在数步，只是属性叫 steps
--------------------------------------------------------------------

第二十三笔写「自举层没有步这个概念」，那是错的。src/minimal-eval.mjs 第 663 行有
this.steps = 0，第 860 行每求值一个节点就加一并与 stepLimit 比 —— 它一直在数，只是
名字是英文的 steps，而我在找中文的「步」。

所以先把结论改回来，再给出量到的数。给 bin/hmyr.mjs 的解释面加上同一个出口（ops=，
与编译面同名同格式）之后，五份探针各跑一次：

  probe-and       457 ms       150,832 步
  probe-lex      4,257 ms    19,014,198 步
  probe-row     14,039 ms    72,240,566 步
  probe-load2   13,097 ms    72,143,173 步
  probe-decls2  23,730 ms   128,325,351 步

三件事：

一、装载 self/run.hmoca 要七千二百万步。probe-load2 与 probe-row 都停在这个数上，
    而它们自己几乎不做事 —— 那七千二百万是装载本身。

二、probe-and（什么都没引入）只有十五万步、四百毫秒。那是「启动加装载程序本身」。

三、probe-decls2 的一亿两千八百万 = 装载的七千二百万加它自己的五千六百万。后者是它
    问的那个问题本身，不是浪费。

还有一个副产品：解释面每步约一百八十纳秒（十三秒除七千二百万），而 C 机器 -O3 编出来的
机器也是每步约一百八十纳秒。AST 解释器与字节码 VM 两台完全不同的机器，每步一样贵 ——
这说明「步」这个单位在两层里是可以放在一起比的，而那正是这一笔想要的性质。

于是 probes 那七十四秒的形状终于是清楚的：四份引入 run.hmoca 的，各付七千二百万步的
装载，合计约二点九亿步，那正是七十四秒里的大头。一个进程只装载一次、依次跑四份，
能省下三份 —— 约三十九秒，与第二十笔按墙钟估的四十秒吻合。

一条教训单独写：第二十三笔的错不在测量，在命名。我按中文的「步」去找，没找到，就下了
「这一层没有这个概念」的结论；而构造器里明明赋着 this.steps。下次去一个新文件里找某个
量，先看构造器赋了哪些字段，再按名字去猜 —— 而且猜的时候要想到它可能是另一种语言的词。

2026-11-07 第二十五笔：一个进程跑多份也省不了，因为装载与那份程序绑在一起
--------------------------------------------------------------------

第二十四笔之后的方向是「一个进程装载一次、依次跑四份」，估省三十九秒。今天先验了那个
方向的前提，而它没通过。

直接调 最小运行 跑那两份探针，在同一个进程里连跑三次：

  probe-load2  第一步  12 步 · 125 ms
  probe-row    第一步  12 步 ·  75 ms
  probe-load2  第三次  12 步 ·  87 ms

十二步 —— 与 bin/hmyr.mjs 下的七千二百万步差六个数量级。

原因是两条路不同。bin/hmyr.mjs 默认走的是「自举层解释」：它把目标程序连同它引入的
self/run.hmoca 一起登记进一个运行时，由自举层去解释目标；而直接调 最小运行 是 JS 自己
解释目标程序，不经过自举层。那七千二百万步数的是自举层那一层的 AST 节点。

所以那七千二百万不是「run.hmoca 的装载」，而是「自举层处理这份程序的成本」，而它与那份
程序绑在一起 —— 每份探针的运行时各自含一份 run.hmoca，所以装载付四次。

要省，只有共享「已经求值过的 self/run.hmoca」——那要动 最小运行时 的模块登记（缓存模块
求值后的状态），不是换一种跑法。

这一件到此为止。它没做成，但它把一个假设测掉了：省三十九秒那条路的前提不成立，而前提
为什么不成立写在上面。而它顺带产出一个更准的说法：那一层付的不是「装载费」，是「再造
一次解释器的钱」。

2026-11-07 第二十六笔：-O3 在并行下也快，那个反向观测是噪声
--------------------------------------------------------------------

第十三笔留下一个开着的问题：-O3 单跑快百分之十九，而换完之后那次全量的 inflate 是
251.9 秒、比换之前的 173.6 更慢。当时写的是「那次的负载不明，所以不是结论」。

今天用两次全量判它。为了让两次只差一个变量，先给编译旗标加了一个开关：HMYR_CC=-O2
切回旧档，缺省 -O3，src/cc.mjs 与 check-all 的共用产物认同一个变量（否则套件复制到的
会是另一档编出来的东西）。然后同一台机器、同一份工作区、同一天，各跑一次全量：

  套件        -O3      -O2      -O3 快多少
  probes     212.7    217.8       2.3%
  vmboot     140.2    159.9      12.3%
  inflate    138.0    164.6      16.2%
  sign       134.7    142.3       5.3%
  examples   126.0    136.4       7.6%

五套全在 -O3 下更快，最快的那一套快一成六。两次的差额判据都报「没有一个套件变大」，
两次都全绿。

所以两件事落定：-O3 在四路并行下也是快的，与单跑一致；第十三笔那个「并行下看起来更慢」
是负载噪声，不是编译档位的问题。那一件收掉，-O3 留着 —— 理由是两次同条件全量，不是
一次单跑。

一条方法上的记录：上一次判错的根源是两次全量的其他条件不同（一次跑在连跑了好几轮
全量与实验之后，机器还热着）。这一次先做出「只差一个变量」的条件，才得到能用的结论。
判据不是「跑两次」，是「两次之间只差你想判的那一个东西」。

2026-11-07 第二十七笔：examples 与 sign 的画像
--------------------------------------------------------------------

按上一笔之后那个顺序，给这两套加了同一种拆分 —— 它们在全量里是百秒以上那一档
（examples 126.0 秒、sign 134.7 秒，-O3 那次），而此前手里只有总数。

  examples  跑 53.0 秒（二十一次，平均 2.5 秒）· 最慢 rational-tour 32.4 秒 ·
            regex-tour 3.9 秒 · json-tour 2.4 秒
  sign      跑 55.9 秒（三次）· manifest.json 28.5 秒 · manifest.json 27.2 秒 ·
            no-such-file 0.2 秒

两件事：

一、examples 的五十三秒里有三十二秒是同一份示例 —— rational-tour。其余二十次合起来
    二十一秒。所以「examples 慢」这句话指向的是「rational-tour 慢」，而那是十份里的
    一份。要动它得先看它算的是什么，而这一笔只负责把问题缩到那一份上。

二、sign 的五十六秒里，两次真验签各二十八秒，而第三次（消息文件不存在）只花 0.2 秒 ——

记下来的意义不在数字，在下一句能问对：下一次有人说「examples 慢」或「sign 慢」，
该问的是「哪一份」与「哪一次」，而这两个问题现在都有答案。

2026-11-07 第二十八笔：sign 那二十八秒是算出来的，不是装载
--------------------------------------------------------------------

第二十七笔写「sign 的五十六秒里两次真验签各二十八秒，而那是装载 self/sign.hmoca 那一树
并跑一次的固定开销」。那句话是猜的。今天量了，而它错了。

编译面有步数出口之后，一次真验签：

  32.7 秒 · 303,938,210 步

三亿步。而 test/sign 里那两次各二十八秒，与它一致。所以那二十八秒里几乎全是验签本身 ——
Ed25519 在 HMYR 里是纯软件实现，三亿步是它的价格，而与装载无关。

顺带两件事：

一、默认步限（五千万）根本不够跑完一次验签。第一次量的时候撞上了，报的是 HMYR-行-003
    「跑得太久」。那正是 test/sign 把 HMYR_STEPS 设成两百亿的原因，而这一条此前只写在
    那个套件里，没写进这一页。

二、「装载与计算长得像」是一个真陷阱。probes 那四份与 sign 那两次都是几十秒、都引入
    self/ 下的东西，而前者是装载（七千二百万步、几乎不做事），后者是计算（三亿步、
    真在算）。分清它们的办法只有一个：量步数 —— 墙钟分不开这两种。

所以那一件不做了：sign 没有「省一次装载」的收益，因为可省的那部分本来就不存在。要让它
更快，只有让 Ed25519 在 HMYR 里算得更快，而那是一件完全不同的事（要动的是那个算法实现，
不是测试怎么调用它）。

2026-11-07 第二十九笔：rational-tour 的四十秒也是算出来的
--------------------------------------------------------------------

第二十七笔把 examples 的五十三秒缩到一份上：rational-tour 占三十二秒。今天量了它：

  40.5 秒 · 198,949,485 步

而它做的是九项有理数运算（它自己打「全对：有理数，九项」）。它引入 lib/rational.hmoca
（一百六十八行），后者引入 self/bigint.hmoca —— 所以那两亿步几乎全在大整数运算里，
平均一项两千二百万步。

与上一笔同一个形状：慢在计算，不在装载。所以 examples 与 sign 这两套，改测试怎么调用
它们没有用 —— 要快只有让大整数与 Ed25519 在 HMYR 里算得更快，而那都是算法层的活。

这一笔没有可做的改动，但它把两件事定下来。

一、examples 那一百二十六秒里，有四十秒是一份真在算的示范。那一份该不该这么重是一个
    内容问题（示范要展示什么），不是性能问题。

二、慢榜上到这一笔为止，六套都拆过了，而它们分成两类：

      装载型   probes（四份各付一次 self/run.hmoca 的七千二百万步）
      计算型   inflate 的解压、vmboot 的 vm-hands、sign 的 Ed25519、
               rational-tour 的大整数

    前一类能靠「少付一次」拿到收益，后一类只能靠算法。这个分类比任何单个数字都有用 ——
    它决定了下一句话该问「怎么少付一次」还是「怎么算得更快」。

2026-11-07 第三十笔：Value 是四十字节，不是五十六
--------------------------------------------------------------------

goal 的第一件事是不改代码的估算，而估算的第一步就撞上一个前提错误。

第十二笔与 OPEN.txt 都写着「Value 是五十六字节」。那是 design/BOARD.txt 第三十九节
记的数，而它是 2026-11-01 改布局之前的值。今天把结构抄进一个小程序量了一次：

  sizeof(Value) = 40
  sizeof(Tag) = 4 · sizeof(Record) = 32 · sizeof(void*) = 8
  offsetof(tag) = 0 · offsetof(num) = 8 · offsetof(rec) = 8

所以桌面上已经是四十字节 —— 匿名 union 那一版（正是 2026-11-01 那次改动）把它从五十六
降到了四十。而源码注释里那句「不再省那三十二字节」说的是老编译器退回旧布局时付的价，
与今天这个数不是一回事。

那还能不能再省？能，而位置很清楚：

  union 里最大的是 Record，按值存，三十二字节。把它改成指针之后，union 就由那个
  「指针加 uint32」的结构决定 —— 十六字节。

  tag 四字节、padding 四字节、union 十六字节，合计二十四字节。四十降到二十四。

代价在 Record 的头部：它要从每个 Value 里搬出去，变成一次堆分配；而它的四个字段
（names、name_lens、vals、n）的读法从 .rec.x 变成 .rec->x —— 那是调用点要改的地方，
而它只在处理记录与元组的那几处，不是五百处。

收益的上界可以算：取 占三成步数、每条搬两次，而每次从四十降到二十四 —— 那是四成的
减少。这个上界还没有除上「一条取 的全部成本里搬运占多少」，而那正是下一次要量的。

2026-11-07 第三十一笔：Value 瘦身的收益不到千分之三 —— 这一件结案
--------------------------------------------------------------------

上一笔量出 Value 今天是四十字节（不是账上写的五十六），而把 Record 改成指针能降到
二十四。这一笔把收益量到底，结论是它不值得做。

做法是一段微基准：两种布局各跑一亿次「读一个槽、写进一个栈」，栈做到一百零四万个值
（四十 MB 与二十四 MB，都超出缓存），各跑三次、记每一次的数。

  40 字节布局   0.052 / 0.053 / 0.056 秒   每次 0.52 到 0.56 纳秒
  24 字节布局   0.052 / 0.054 / 0.052 秒   每次 0.52 到 0.54 纳秒

两种布局一样快，而把栈做到超出缓存也没有差别 —— 因为那循环是顺序写，预取器盖得住。

而一条 取 在真实机器上要一百八十纳秒。所以：

  · 一次「读加写」占那 180 纳秒的百分之零点三；
  · 四十降到二十四能省的，不到千分之三；
  · 缓存那一面也量过，没有差别。

于是这一件按 goal 的条件结案：收益微不足道，理由如上。改布局要动 Record 的四处字段
读法与每个记录头的堆分配，而换来的数在噪声里 —— 那不是一笔值得做的交易。

但这一笔留下一个更值钱的方向。一百八十纳秒里百分之九十九点七不是搬运，那它是什么？
一条 取 只做三件事：边界检查、读槽、压栈。所以剩下的时间在解释器循环本身 —— switch
的分派、g_机 的解引用、以及每条指令进出这一趟的固定成本。

于是第十二笔那张分布表的方向要改：不是「优化最热的那一条指令」，而是「优化每一条指令
都要付的那一份」。前者是挑热的那几条去写汇编，而后者是循环结构的活 —— 而两者之间，
这一笔给出的证据站在后者那边。

2026-11-07 第三十二笔：取 的那一次边界检查值百分之七
--------------------------------------------------------------------

解释器循环的固定成本那件开始做消去法。第一项就是 取 那条指令的槽边界检查：在临时副本
上把它删掉，其余一个字不动，跑 tree 三次。

  基线       22527 / 24391 / 24621 ms   中位 24391 ms   138102538 步
  无槽检查    22619 / 22655 / 23068 ms   中位 22655 ms   138102538 步

中位差 1736 毫秒，百分之七点一，而步数一模一样。所以那一次比较值全量的百分之七。

另一个变体是去掉 push 的栈满检查，它崩了：三次分别 7 毫秒、50 毫秒、79 秒，没有步数 ——
因为栈满检查正是 realloc 的触发器，去掉它程序直接踩坏。它不能这么量，也不该这么改。

那个七个百分点要紧的地方在它的量级。取 占三成步数，所以那 1736 毫秒摊到每条取 上约
四十二纳秒 —— 而一次无符号比较加一次分支只该值一到两纳秒。差了一个数量级，说明那七成
多半不是「比较本身」，而是「比较让编译器少做了一个优化」：它在每条取 的路径上插了一个
可能跳走的分支，而那阻断了别的东西。

所以下一件不是「把检查删掉」—— 那会失去越界诊断，而那正是这个仓库的判据之一。下一件是
「保留检查而让它更便宜」，两条候选：把 f->nslots 提到帧内常量（f 在一帧里不变），或者把
检查与压栈合成一次分支。

消去法还剩两项没做（g_机 的解引用、switch 分派），而它们都是结构性的改动，不是删一行
的事。

2026-11-07 第三十三笔：每步一百二十纳秒是地价，与程序无关
--------------------------------------------------------------------

上一笔量出「取 的边界检查值百分之七」。这一笔换个问法：那 180 纳秒本身，在纯净条件下
是多少？

写一个只有循环与整数的程序（一千万次迭代，两个变量），编成字节码让 C 机器跑。每次迭代
十三步，一千万次共一亿三千万步。

  15267 / 16110 / 16388 ms   一亿三千万步   每步 117 到 126 纳秒

而 tree 那一趟是一亿三千八百万步、中位 24391 毫秒 —— 每步 177 纳秒。

两件事：

一、纯净条件下每步也要一百二十纳秒。那不是缓存压力（这个循环的工作集只有两个变量），
    而是解释器每一条指令都要付的固定成本。一百二十纳秒约三百六十个 CPU 周期，对「读
    一个槽、压栈」来说太多。

二、tree 的 177 比 120 高四成七。那四成七才是「程序更复杂」的部分：更多样的指令、
    更大的工作集。所以「一步一百八十纳秒」这个数里，一百二十是地价，五十七是房子的钱。

那三百六十个周期花在哪？下一个要量的是解码。这台机器不预先建 Ins 数组（Func 里 seg_at
那段注释写着为什么不建：省内存），所以每步都要 读一条 重新解一遍指令，然后 switch 再
分派一次 —— 那至少是「解码加执行」两趟活，而预解码的机器只付一次。

那是比 Value 布局大得多的杠杆，而它的代价也有名字：内存，每个函数一份已解码的 Ins
数组。而那正是当初不预解码的理由。所以下一件事不是「改成预解码」，而是「量出解码占
这 120 纳秒里的多少」—— 若它占大头，那内存换时间的账就该重新算一次。

2026-11-07 第三十四笔：解码占了那 120 纳秒的六成
--------------------------------------------------------------------

上一笔把每步拆成「地价一百二十纳秒」与「程序自身五十七纳秒」。这一笔量地价里最大的一块：
每步重新解码指令。

做法不是消去法 —— 删掉解码会改语义，量出来的东西不算数。改读汇编：gcc -O3 为 读一条
生成了一个特化版本（读一条.constprop.0），说明它没被完全内联，每步要真调它一次。它的体是

  202 行汇编 · 123 条指令
  其中 movq 22 · popq 20 · leaq 12 · call 11 · addq 8 · cmpq 8

十一个 call，那是 rd_u8、rd_u16、rd_u32、rd_str 这些。而二十条 popq 说明寄存器不够用，
参数在栈上来回搬。

一次这样的调用约两百到两百五十个周期，而每步总共约三百六十个周期。所以解码占六成到
七成 —— 它是那一百二十纳秒里最大的一块，而 取 本身只做三件事。

这个数超过了 goal 定的门槛（百分之十），所以按约定它该被做进仓库。而下一步是估算预解码
的价码与上界，两个数都还没有：

  · 内存：每个函数一份已解码的 Ins 数组。tree 那类程序编译后是几万条指令，按 Ins 约
    三十二字节算，是几百 KB 的量级 —— 比「省内存」这个理由当初想的小得多。
  · 收益上界：若解码占六成半而预解码把它压到一成，整体可能快五成。

这两个数决定做不做，而它们都还只是估算 —— 下一件就是把它们量出来。

2026-11-07 第三十五笔：预解码 tree 只要一百零六 KB
--------------------------------------------------------------------

上一笔记下「解码占那一百二十纳秒的六成」，以及两个还没量的数。这一笔量内存那一半。

Ins 的定义是 op（uint8）、a（int64）、b（int64）、val（Value）—— 加起来六十四字节。
而 tree 编译后有多少条指令？

  self/tree.hmoca       16 个函数 · 1,689 条指令 · 每条 64 字节 = 106 KB（字节码 9 KB）
  self/inflate.hmoca    34 个函数 · 2,821 条指令 · 每条 64 字节 = 176 KB（字节码 14 KB）
  examples/hello.hmoca   1 个函数 ·    10 条指令 · 每条 64 字节 =   1 KB（字节码 0 KB）

所以预解码 tree 的全部指令要一百零六 KB，而它的字节码本身是九 KB —— 十一倍。

而那一千六百八十九条指令要被执行一亿三千八百万次（平均每条八万次）。预解码付一次解码
的价钱（一千六百八十九次），省下的是一亿三千八百万次。

一百零六 KB 换掉一亿多次解码，这笔账不用算也知道该做。而它当初没做，理由是省内存 ——
那个理由的价码现在有数了：十一倍的字节码，而 tree 的字节码只有九 KB。

于是 goal 定的门槛过了，这一件该做进仓库。顺序是：先在临时副本上做预解码的原型、量出
它真的快多少，再做进 hmyr.c 并跑全量。而在动手之前还有一处要定：预解码是在装载时一次
做完（简单，但没执行到的函数也占内存），还是第一次执行到那个函数时再做（复杂，
但小程序的代价与今天一样）。tree 一千零六 KB、十六个函数，两种都无所谓；板子上那几套
小程序的字节码只有几 KB，差别也不大 —— 所以先做简单的那一种。

2026-11-07 第三十六笔：预解码做进仓库，tree 快四成三
--------------------------------------------------------------------

上一笔之后这一件做进了 vm/hmyr.c。改动三处，十六行新增：

  · Func 加一个 Ins *已解；
  · 装载时那个为了算 seg_at 本来就要走的循环，把 读一条(&r, NULL) 换成读进 已解[c] ——
    它本来就把每条指令解了一遍，只是把结果丢掉了；
  · 执行循环里加一个判断：有已解就直接取，没有才走现场解码那一条。

所以「多一次解码」并不存在，只是把已经做过的那一遍留下来。原型在临时副本上量的：

  tree  基线中位 21978 ms → 12528 ms   快四成三 · 步数 138102538 一字不差 · 输出同一个

做进仓库之后跑全量：

  七套关键套件全过，而 vmboot 41.6 秒（之前 69.8 到 74.4）、bytecode 21.2（之前
  36.7 到 43.7）、deflate 14.9（之前 18.3 到 33.7）、tree 14.8（之前 40.5 到 48.4）
  全量 234 套全过，差额报「没有一个套件变大」

全量的慢榜也跟着换了一副面孔：

  之前   probes 212.7 · vmboot 140.2 · inflate 138.0 · sign 134.7 · examples 126.0
  现在   probes 180.2 · sign 111.2 · examples 109.3 · inflate 100.3 · curve 96.8

vmboot 直接掉出慢榜 —— 它是「VM 里跑自举层」那一套，而每一层都在跑 C 机器的指令，所以
它受益最大。

一条教训值得写在这里：这一件拖了三天才做，因为我以为「预解码要新加一个循环、要遍历所有
函数、要在装载之后多走一遍」。而实际上装载时早就解过一遍了，只是结果被 NULL 丢掉了。
动手之前先读一遍那段代码，比照着「应该怎么做」去设计省得多 —— 而这三天的代价是每次
全量都多花几分钟。

2026-11-07 第三十七笔：预解码带来的那个 GC 洞补上了
--------------------------------------------------------------------

上一笔把预解码做进仓库，而它留下一个洞：gc_标根 不标 f->已解。

那个洞的形状很具体。gc_标根 里有一段注释写着「指令里的常量值不再需要标：2026-10-28 起
装载不把 Ins 数组建出来」。那段话在那一天是对的，而上一笔让数组又建了出来，于是两件事：

  · 已解 本身是 calloc 分配的，而 calloc 被 #define 成了 hm_calloc —— 它在 GC 堆里，
    又不在任何根上，所以第一次回收就会把它当垃圾收走；
  · 数组里每条指令的 val（字符串与元组）同样在 GC 堆上，同样不被标。

补法是在 gc_标根 里遍历 函数族：标 f->已解 那一块，再逐条标 in->val。

一个必须记下来的地方：补之前它并不崩。用 HMYR_GC=1 与 1 KB 阈值跑 tree，早先三次都对
（138102538 步、输出正确）。那不是安全，是释放的内存还没被重用 —— 读到的是未定义行为。
这种「看起来对」比当场崩更难查，所以值得单独写一笔。

补上之后的证据：HMYR_GC_LOG=1 跑 tree，第一次回收的日志从「放掉 1059920 字节」变成
「放掉 66 字节」，而「标根 函数数 16，已解 16 份」证明那一趟真的走到了。

验证：七套关键套件先过（tree 17.5 秒、vmboot 47.2、bytecode 26.6、deflate 18.7，
以及 vmload、vmrun、c-embed），随后全量 234 套全过，差额报「没有一个套件变大」。慢的
五套与修之前同档（probes 198.2、examples 125.0、sign 120.9、inflate 112.5、
curve 106.1）—— 标记的代价只在回收跑到的时候付，而那本来就不在热路径上。

2026-11-07 第三十八笔：依赖环从一次手算变成一条能重跑的判据
--------------------------------------------------------------------

这一笔起于工程地图上的一个数：文件从 577 涨到 691，边从 688 涨到 1332 —— 边比
文件快四倍。地图不报环，所以先写了检测器：tools/cycles.mjs，扫 .mjs，认四种
import 写法，Tarjan 找强连通分量。

第一趟：343 个文件、664 条边、一个环。两个节点是 src/loader.mjs 与
src/loader-self.mjs。形状记在 design/OPEN.txt 末节：枢纽为了一个 HMYR_LOADER=self
开关静态 import 替身，而替身又要枢纽的三个解析函数。

拆法是搬函数，不是把静态 import 改成动态 —— 后者要让 loadUnit 变成 async，波及
调用方。三个函数（resolveImport、找包根、读包清单）只用能力里的文件与路径两样，
于是整块搬去 src/resolve.mjs。原 loader.mjs 443 行，搬走 171 行；新文件 183 行；
loader.mjs 274 行。

判据怎么立的，比拆法本身更值得记。test/cycles.test.mjs 十四条，抓环那一条拿的是
造出来的样本，不是仓库自己：

  · 两个文件互相 import —— 必须报一个环，且退出码 1；
  · 一棵无环的两文件树 —— 必须报 0，退出码 0；
  · 一个空目录 —— 必须报「0 个文件」，不许报「零环」；
  · 一个不存在的目录 —— 不许静默通过。

第三条与第四条是这一套最该有的：一个什么都没扫到的检测器报零，是最危险的那种绿。

它第一次跑就红了一条，而红得有用：造出来的环里有一行

  import "./丙.mjs";

是副作用式裸导入。检测器的正则只认 from、import() 与 loadUnit 三种写法，这一条
边被漏掉，于是两个环只报出一个。补上第四支之后，仓库自己的边数一条没变（665，
两趟都是），说明仓库里没有裸导入 —— 但尺该有这一支，因为判据要拿造出来的样本
验，不能只拿仓库自己验。

落定：仓库上报 344 个文件、665 条边、0 环；四条导入路径都能加载，且 loader.mjs
交回的 resolveImport 与 resolve.mjs 交回的是同一个函数对象；package、pkgmanifest、
selfmod、selfload 四套先过（14、19、8、27 项）；cycles 这一套 14 项；套件数从 234
到 235，README、tools/check-all.mjs、tools/suite-list.txt 三处同改。

2026-11-07 第三十九笔：跳过行第一次进了全量报告
--------------------------------------------------------------------

第四笔留下的规则是「被条件包住的判据，条件不成立时要打一行跳过，并且带上条数」。
这一笔做的是它的另一半：那些行打了之后，全量里要看得见。

先量。写了一段一次性扫描（不进仓库）：对 suite-list 里每一份套件，找「跳过」行
之后紧跟「} else {」的形状，数那个 else 块里真正执行的 ok( 调用 —— 跳过字符串与
注释。结果 54 处、合计 321 条。

先改本机每趟都跳的七处（releasehmyr 10、manifesthmyr 10、hmyrpack 5、
bootstrap-seed 的 5 与 2 与 5 与 2），因为只有它们对今天的读数是实时的误导。
改完单跑 releasehmyr，那一行打出来了：

  跳过 10 项：真跑一次要先造清单，一分多钟，挂 HMYR_HEAVY 之后

而全量里没有它。查 check-all：子进程的 stdout 被收进「出」这个变量，只在失败时
才印。于是「打了」与「看得见」是两件事，而账上那句话只管了前一件。

改 check-all 的一处：每套的行标与说明之后，把它输出里「跳过 N 项」的那几行印

又写了一遍），读进来一处都解析不出，报「套件 0 个有实跑数字」。日志该由交日志的
那一方写成它声明的编码；用 node 的 execFileSync 捕获再写文件就对了。

剩下的 47 处（遮住 287 条）没改。绝大多数是「这台机器上没有 gcc」与平台分支，
本机不触发。它们仍然沉默，而这是故意的：先让带条数的那几处被看见，再一处一处补。
一次改 54 处、其中 47 处在验证里看不见，比不改更糟。

2026-11-07 第四十笔：普查的第四种成因 —— 样本字符串里的断言名
--------------------------------------------------------------------

第三十九笔让普查跑得起来了（那份日志的编码是那一层的坑）。跑出来的名单里，
「差额为负而跳过字样为零」从九个变成十二个：新进来的是 racecensus（差 6）、
probes（差 1）、gapbaseline（差 1）。

racecensus 最值得看，因为它差六条而一句跳过都没有。读它的源码：整份只有五个
ok( 调用，而静态计数报 11 —— 差的那六条在哪？

在字符串里。这份套件验的是 tools/race-census.mjs 抓不抓得到竞态形状，于是它把
样本源码写成字符串交给工具去扫：第 42 到 84 行那几段里有六处 ok(，而普查的静态
计数用的是 /(ok|检查|判)\(/，字符串里的也数进去了。

所以这不是「沉默地少跑了六条」，是一条都没少跑。静态 11 与实跑 5 的差，全是普查
把测试数据当成了断言。

这补上了第四笔那张表：差额有三种成因（互斥两支、守卫分支、回调里可能不执行），
现在有第四种 —— 样本源码写在字符串里。它与第三种看起来一样（都像「少了」），
而含义相反：第三种是真问题，第四种是工具的分辨率不够。

改的是两处，都在 tools/cond-census.mjs：注释里补第四种，输出里在「最该先看」
那一段之后加两行提示。判据是重跑一次那份日志，两行出现在名单之后、与基线比之前。

probes 与 gapbaseline 那两个 -1 没查 —— 一个够小，另一个（gapbaseline）自己就是
盯差额的套件，它那一处差要先读它自己怎么数。留在列表里，比猜要好。

2026-11-07 第四十一笔：预解码之后的地价是 82 纳秒，其中四成七是每步固定成本
--------------------------------------------------------------------

第三十三笔量过地价：只有一个循环与两个整数的程序，一亿三千万步，每步 117 到
126 纳秒；而 tree 是 177。那一笔说 120 是地价、57 是房子的钱。

预解码做进仓库之后，这两个数都该重测。今天的：

  纯循环（一千万次迭代、两个变量）  130000012 步 · 中位 10781ms · 82.9 ns/步
                                  （五趟 81.6 到 87.3）
  同一份字节码关掉 HMYR_OPS        130000012 步 · 中位 10700ms · 82.3 ns/步

后一行是为了排掉一个嫌疑：HMYR_OPS 那个计数器自己要不要钱。开关两组的中位差
零点二纳秒，而组内波动就有五纳秒 —— 计数器落在噪声里。

所以新的地价是 82，比第三十三笔的 120 少三成一。而 tree 现在是 12528ms 除以
138102538 步 = 90.7 ns/步 —— 房子的钱从 57 纳秒掉到 7.8。

接着换一个问法：这 82 纳秒里，多少是「每一条指令都要付的」，多少是「指令自己
在干活」？

量法是一次消融：给执行循环加一个 HMYR_SPIN 开关，打开时它做完每轮全部固定动作
（从帧池取六个字段、五个判断、switch 分派、pc 推进、写回帧）之后直接 continue，
一个 case 都不执行。同一份字节码、同一份 vm/hmyr.c、同一个步限，两组各三趟：

  正常执行            130000001 步 · 中位 10855ms · 83.5 ns/步
  只付固定成本（空转）  130000001 步 · 中位  5136ms · 39.5 ns/步

所以：固定成本 39.5 纳秒（四成七），指令本体 44.0 纳秒（五成三）。

39.5 纳秒约一百二十个 CPU 周期，而它做的只是「取六个字段、五次判断、一次跳转」。
这是下一步该拆的，而它有名字：

  · 每轮从帧池重取 f、slots、base、pc、缓存条、缓存位 六个字段 —— 理由是 CALLF
    与 RET 会换帧，所以不能只取一次；
  · 每轮五次判断：g_failed、步数超限、pc 越界、g_op计开、g_trace_on；
  · switch 的间接跳转。

后两个判断默认都是假，而一次消融（把它们改成 0 与常量的合取）量到 81.2 对 82.3
—— 也在噪声里。所以它们不是那 39.5 的主要部分，别从那里下手。

一个形状上的旁证：空循环体（只有 i = i + 1）是 79.1、算术循环是 80.7 —— 每步
成本与执行什么几乎无关。而调用循环是 131.0：一次函数调用（含返回）比十二个普通
步骤贵约六百纳秒。它在 opcode 分布里占比不到千分之一，所以那笔钱摊不开，但它是
「调用路径不值得优化」这个旧结论的一个具体数。

两处临时改动都已还原（git checkout vm/hmyr.c），工作区里没有留下消融的痕迹。

2026-11-07 第四十二笔：帧状态只在换帧时重取，地价从 82 降到 64
--------------------------------------------------------------------

第四十一笔把 82 纳秒拆成固定成本 39.5 与指令本体 44.0，并点名了下一步：那
39.5 里「每轮从帧池重取六个字段」是四个候选里唯一还没被排除的。

先量。消融：把六个字段的重取提到循环外。纯循环程序不换帧，所以行为不变 ——
这一条让消融是干净的，不只是快的。

  消融前  130000012 步 · 中位 10700ms · 82.3 ns/步
  消融后  130000012 步 · 中位  8454ms · 65.0 ns/步

十八纳秒一步，而固定成本总共三十九点五 —— 一半是这六次加载。

改法不用在 CALLF 与 RET 里置标志：压帧改 g_活帧深（加一）、弹帧改（减一），
所以深度一变就是换了帧。循环顶部加一个 缓存深，不等就重取那六个字段。

正确性靠两处读出来的事实：CALLF 与 RET 都 continue 回循环顶、不走底部的写回
（5673 与 5685 行），所以换帧之后第一件事就是重取；fr 在压帧的 realloc 之后
会失效，但 realloc 之后深度也变了，同样触发重取。

  改后  130000012 步 · 中位 8380ms · 64.5 ns/步（关 HMYR_OPS；开着是 65.4）

二十一点六的下降，与消融预测的十八到二十一致；差的那一纳秒是深度判断自己的钱。

验证：五套先过（bytecode、cvm、tree、vmrun、vmboot），随后全量 235 套全过，
差额报「没有一个套件变大」。慢五套从 probes 206.0 · sign 126.2 · examples 125.4 ·
curve 111.9 · inflate 110.5 变成 probes 200.6 · examples 125.3 · sign 121.2 ·
curve 108.2 · inflate 105.4 —— 各降三到五秒。

一条要说清的：地价降了两成一，而全量的墙钟只降了百分之三左右。差额在那两处：
一套套件的时间里还有编 C 机器、装载、起子进程，那些都不经过执行循环；而慢的
那几套里 probes 是加载型、sign 是算法型，循环成本只是其中一段。所以「地价降了」
与「全量快了」不是同一个数，两边都要记，别拿一个替另一个。

下一步那 39.5 只剩 21.5（39.5 减 18），而它现在由三样构成：步数计数与步限比较、
pc 越界检查、switch 分派，外加每轮一次的深度比较。三个出口判断的消融已经在第四
十一笔量过（在噪声里），所以下一个该动的是分派本身 —— 而那是结构性改动，要有
一次能看见的测量支撑才值得做。

2026-11-07 第四十三笔：步数计数是每一步一次全局读改写，值十七纳秒
--------------------------------------------------------------------

第四十二笔之后地价是 64.5，固定成本从 39.5 降到 21.5。这一笔动的是那 21.5 里
最不起眼的一行：

  if (++g_机->步数 > g_机->步限) { ... }

每步一次「读全局指针、读字段、加一、写回」。循环里到处是函数调用，编译器不能把
这一份留在寄存器里，所以每步都是一次真的内存读改写。

消融：改成每 64 步同步一次（局部自增，满 64 才写全局并比较步限）。

  消融前  130000012 步 · 中位 8380ms · 64.5 ns/步
  消融后  130000012 步 · 中位 6134ms · 47.2 ns/步

十七纳秒一步 —— 比我预想的大得多（我以为三到五）。

正式改法：循环外一个 步余，每步只自增它；满 64 步把 64 加进 g_机->步数 并比较
一次步限；退出前由 FRAME_RET 与顶层返回把余数补回去，所以 ops= 仍然精确。

  改后  130000012 步 · 中位 6422ms · 49.4 ns/步（关 HMYR_OPS；开着是 47.6）

两处代价要写清：
  · 步限现在最多多跑 63 步才停 —— 步限是防跑飞，不是计数，可以接受；
  · 步数在运行中不再是精确的实时值，只在退出时精确。仓库里读它的地方只有输出
    （ops=）与两处重置，所以没有别的东西依赖它。

验证：tree 单跑报 138102538 步，与改之前一字不差 —— 这是这一改最要紧的一条，
因为「省下时间」与「算错步数」只差一个补写。随后五套过（tree、vmboot、cvm、
bytecode、vmrun），而 tree 的跑那一段从 9.2 秒到不足八秒。

地价这条线现在是：

  预解码前              约 120 ns/步（第三十三笔）
  预解码后              82.9（第四十一笔）
  帧状态只在换帧时取      64.5（第四十二笔）
  步数局部累加          约 48（这一笔）

三笔加起来从一百二十降到四十八，六成。而三笔用的是同一个方法：先量出「哪一段」，
再改「那一段」，改完用同一套测量确认它真的动了。

2026-11-07 第四十四笔：分派换一种编译方式也快不了，这一项到此为止
--------------------------------------------------------------------

第四十三笔之后地价约四十八。固定成本里还剩三样：pc 越界检查（读一次函数字段）、
每轮一次的深度比较、以及 switch 分派本身。

分派先量，而量法不必改代码：编 C 机器那个入口接受额外旗标，于是同一份 vm/hmyr.c
用两种编译方式各编一份，跑同一份字节码：

  默认（-O3，跳表）          130000012 步 · 中位 6193ms · 47.6 ns/步
  -fno-jump-tables（比较链） 130000012 步 · 中位 5946ms · 45.7 ns/步

比较链反而快一点九纳秒 —— 而组内波动就有三纳秒。所以这两个数的差是噪声：分派
的两种实现在这一台机器上分不出高下。

这一条的价值在它的方向：既然跳表与比较链打平，computed goto 能拿到的也只是
「跳表里那一次地址加载」。那是几纳秒的量级，而它要重写八百行 switch 的分派结构。
不做。

所以地价这条线在这里收：一百二十降到四十八，六成 —— 三笔有效改动加一笔负结果。
而剩下的一小半固定成本（pc 越界检查、每轮一次的深度比较）各值一到两纳秒，那是
「再抠两个百分点」，不是「再拿两成」。继续在循环里找，收益已经低于风险。

一条方法上的账：这一笔没有改任何代码，却结束了一个方向。负结果的意义就在这里
—— 它省下的是重写八百行之后才发现没快的那一次。

2026-11-07 第四十五笔：一次验签的钱六成在哈希里，而哈希那个循环换不掉
--------------------------------------------------------------------

账上那句「Ed25519 一次验证三亿零四百万步」今天拆开了，而拆出来的形状与印象不同。

一、各段各值多少（直接用字节码跑，不含装载与编译）：

  一次标量乘（255 位、只有最低位是 1）   27561679 步 · 2354ms
  一次标量乘（全 1）                   57693388 步 · 5449ms
  一次解压                             10906825 步 ·  976ms
  一次真实验签（现场样本）             115339488 步 · 9761ms
  用 C 机器跑 self/sign.hmoca 一次     304428630 步 · 23251ms

最后两个数差出来的那一亿八千九百万步，是「验文件」里除了验签之外的部分。再往下
分一次：SHA-512 一个 37433 字节的文件要 189200625 步 —— 占那三亿零四百万的六成二。

所以一次验签的账是：哈希六成二，椭圆曲线三成八（其中两次标量乘七成四、两次解压
一成九、其余七个百分点）。

二、于是去动哈希。左移32 原来是「循环 n 次，每次 位加(y, y)」，而 位加 是内置的
三十二位加法。看起来那是个纯粹的浪费 —— 三十一次内置调用换一次乘法总能省一点。
改成原生加法加一次条件减，量出来：

  改前  189200625 步（每字节 5054）
  改后  260549537 步（每字节 6960）

慢了百分之三十八。两个原因：原生加号与取模在 HMYR 里并不比内置的位加便宜（后者
在 C 那一侧就是一行截断），而这一版多了一次比较与一次条件减，多出来的分支比省下
的调用更贵。

所以这一处还原了。它是今天第二笔负结果，而它比第一笔更值钱：「内置函数调用一定
比原生算术贵」这个假设是错的 —— 在这台机器上内置的位运算就在 C 里，一行的事。

三、哈希还能怎么动？剩下的热点在元组：每个六十四位字是一个（低半、高半）元组，
每轮造二十来个。要省就得把二十多个函数的签名从「元组进、元组出」改成「两个整数
参数」，那是一次重写，收益估在三四成。

记在这里，不现在做 —— 它要动的是这一片里唯一「没错但可以更快」的代码，而那六成二
换算到 sign 套件上，是它一百三十四秒里的大约二十秒。

四、一条口径更正：账上那句「一次验证三亿零四百万步」说的不是验签本身，而是「跑
整个 self/sign.hmoca 一次」，含读文件与哈希。验签本身是一亿一千五百万步。

2026-11-07 第四十六笔：哈希的热点没找到，而三次猜测都被自己的测量否掉了
--------------------------------------------------------------------

第四十五笔量到 SHA-512 占一次验签的六成二（一亿八千九百万步 / 三万七千四百三十三
字节），于是去动它。三次改动，三次被自己的测量否掉：

一、把 左移32 的循环（每次一个内置 32 位加法）换成原生加法加条件减：
   一亿八千九百万变成两亿六千万，慢三成八。就是上一节那条负结果。

二、把 常量串() 的调用从每一轮提到函数开头（原来每轮构造一次两千五百六十个字符
   的串），并把消息表 w 从元组拼接换成可变数组：
   一亿八千九百二十万变成一亿八千九百四十九万，多了零点一五 —— 也就是没变。

   两个假设一起错：常量串没有每次重建（字面量可能被共享了），而元组拼接也不是
   热点。

三、于是「把二十多个函数的签名从元组改成两个整数」那个重写，前提已经不足。我原先
   以为元组分配是大头，而第二条已经说明拼接不是。

现在手上只有两个数：每块 645736 步、每轮 8072 步。而每轮做的事有名字：取一次常量
（解析十六进制）、四个 σ 与 Σ（各两三次循环右移）、八次 64 位加、八个变量的轮转、
十来个元组构造与索引。8072 除下来，每项量级在一两百步。

要拆这 8072，得能单独调那些私有函数 —— 而它们是私有的。所以下一步不是改哈希，
是给这一片建一个能逐函数计的探针：把 加64、循环右移64、选 各跑一百万次，各自报
步数。有了那张表，再谈重写。

这一笔记在这里，是为了不让下一个动手的人从同一个猜测开始。

2026-11-07 第四十七笔：常量的移位量直接写成乘一个常数，哈希快三倍半
--------------------------------------------------------------------

第四十六笔留下两个数 —— 每块 645736 步、每轮 8072 步 —— 以及一句「下一步不是改
哈希，是给这一片建一个能逐函数计的探针」。

探针建起来了，而且不改仓库：把 self/sha512.hmoca 复制到临时目录，引入路径改成
绝对的，去掉原来的 main，把要量的十几个函数临时加上「公开」，再拼一个按名字分发
的 main。编一次字节码，用同一个 exe 跑十几趟，每趟报 ops。

量出来的表（每项两万次，已减去基线）：

  小σ0 2058 · 大Σ0 1903 · 大Σ1 1799 · 取64 1294 · 小σ1 1057 · 循环右移64 912
  右移64 365 · 左移64 234 · 择 89 · 左移32 73 · 选 64 · 加64 26 · 与64 12 ·
  异或64 12 · 非64 5

四个 σ 与 Σ 每轮各算一次，合计约六千八百步，而一轮总共八千零七十二。所以钱在那
四个函数里，而它们贵在 循环右移64 —— 那里面要用 左移32，而 左移32 是「循环 n 次」
的实现，循环右移 1 位就要走三十一次。

于是把移位量写成常量。原理一句：(x 模 2 的 (32-k) 次方) 乘 2 的 k 次方，与「x 乘
2 的 k 次方再模 2 的 32 次方」同值，而前者小于 2 的 32 次方，双精度精确。所以
循环右移64(a, 28) 就是两行：位右移(lo, 28) 或 (hi 模 2 的 4 次方) 乘 16。

十一个移位量各写一个专用函数（28、34、39、1、8、19、61、14、18、41，另加右移 6 与
右移 7 各一个），四个 σ 与 Σ 改成调用它们。原来的 循环右移64 留着不动 —— 别的
调用方还在用。

量到的：

  SHA-512（37433 字节）    189200625 步 → 53914321 步（每字节 5054 → 1440），省七成二
  用 C 机器跑 sign 一次    304428630 步 → 168218870 步（23.3 秒 → 15.4 秒），省四成五
  哈希在一次验签里的占比    六成二 → 一成八

判据：sha256 套件九项（空、一字节、abc、三个跨块边界的大小）与 sha512 套件八项
（空、三字节、填充边界、双块）都过 —— 这两组都是对 node 的 crypto 比出来的外部
判据，不是自己跟自己比。

一条要写下来的：这一笔之所以能做成，是因为上一笔先建了探针。前三次猜测都错、
第四次对，差别不在想法的好坏，而在有没有一张逐函数的表。

改完之后全量红了三套，而三处都是这一笔的账：

  · deadcode 说 循环右移64 没人调用了 —— 专用版取代了它，而它又拉着 右移64、
    左移64、左移32 三个。四个一起删掉，sha512.hmoca 从 374 行到 340 行。
  · selfmap 说 SELF.txt 里 sha512.hmoca 的行数是旧的（286）。
  · selfbridge 说 runtime/sign.hmoks 比它那条链旧 —— 那份字节码是用 sha512.hmoca
    编出来的，源码动过它就得重编，命令是 node tools/emit-code.mjs self/sign.hmoca
    runtime/sign.hmoks。

三处没有一处是「逻辑错了」，全是被这一笔牵动的旧账；而它们能一句话说清，是因为
每一条报错都精确到名字。

2026-11-07 第四十八笔：执行面换成 C 机器，反而慢了十二秒
--------------------------------------------------------------------

curve 是在慢榜上（全量 95.1 秒，单跑 41.8 秒——全量里那一列含排队）。它本来已经
优化过一次：tools/curve-batch.mjs 一次加载、按任务表依次调用十二回，把十四次装载
压成一次。

但那十二回跑在 src/vm.mjs 上 —— JS 写的字节码机器。而同一份字节码在 C 机器上每步
便宜一个量级（第四十一到四十三笔量的）。于是想把执行面换过去：编一次 .hmoks，
十二个任务各 spawn 一次 C 机器。

量出来：

  原来的路（curve-batch，JS 字节码机器）  41.8 秒
  换成的路（C 机器，十二次 spawn）        53.9 秒

慢了十二秒。判据一条没变（二十八项都过），输的是时间。

原因是两份账互相抵消：C 机器把计算从约八十秒压到约十九秒，而十二次进程启动每次
都要装载那份三万多字节的 .hmoks（读文件、解析、建机器）—— 每次约两秒半，十二次
三十秒。省下的六十秒被启动费吃回去，还倒欠十二秒。

所以正确的改法不是换机器，是「一个进程跑完十二个任务」—— 而那要在 self/curve.hmoca
里加批量模式，或者写一个包装程序。那是另一件事，这一笔只把它写清楚。

已还原。可带走的一句：装载成本与计算成本是两份可以互相抵消的账。同一份字节码，
一台机器每步便宜，而如果每个任务都要重新启动它，省下的可能不够付启动费 —— 这一条
与第四十五笔「内置位运算比原生算术便宜」同一天出现，都是「看起来一定更快」被量翻。

2026-11-07 第四十九笔：examples 那条路也不换，而性能这一线收在这里

examples 是全量里第二慢的（112.9 秒），做法与 probes 同型：每一份起一个 node 去跑
bin/hmyr.mjs，也就是每份都把自举层装载一遍。看起来同样能换成字节码加 C 机器。

但它的判据写得很清楚：「每一份用默认路径跑，退出码为零」。而「默认路径」正是那一
条要验的东西 —— 换成显式编译加 C 机器，验的就不再是默认路径。省时间不能以换掉被
验的对象为代价，所以不改。

于是三条加载型的路都量过，各有各的墙：

  probes    181.3 秒  输出本身就依赖自举层的语义（probe-prec 测的就是它），换 face
                      要连 expected.json 一起改 —— 那是改判据
  examples  112.9 秒  判据是「默认路径」，换 face 就偏离了被验的对象
  curve      95.1 秒  换 C 机器量过，反而慢十二秒（第四十八笔）：装载成本吃掉计算

性能这一线到这里收。这一天的账是：地价从一百二十降到四十八（六成，三笔改动），
SHA-512 快三倍半（一笔，靠探针定位），sign 套件从一百一十一秒掉出慢榜。而剩下三
条慢套件的不动，每一条都有一个说得出的理由，不是「还没做」。

下一次要动它们，该先有一个新的形状 —— 例如 curve 的批量模式（一个进程跑完
十二个任务），那不是换执行面，是换喂法。
