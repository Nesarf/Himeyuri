发布链：现在到哪一步，下一步是什么
====================================================================

这份文件是给「下一次发布」的准备手册，不是设计讨论。设计判断在 TOOLING.txt 与
SIGNING.txt 里；这里只写「按顺序做哪几步，谁来做，还差什么」。

一、一条命令，除签名之外全在 HMYR 里
--------------------------------------------------------------------

    hmyr self/release.hmyr v0.1.0 dist

它做三件事，顺序是硬约束：

    release.hmyr → manifest 的 主   造清单（每个文件一个 sha256，整份一个 digest）
    release.hmyr → package 的 打包  造归档（遍历目录、逐成员写头、中央目录、尾记录）
    release.hmyr → 自己            写说明书（三问：签了什么、没签什么、怎么自己验）

反过来（先打包再造清单）会得到一份「描述已经不存在的字节」的清单，所以顺序不能换。

二、实测的一次
--------------------------------------------------------------------

tag v0.1.0，输出到临时目录：

    清单      1014 行，digest 一份
    归档      270 个文件（含新加的 self/release.hmyr），4377239 字节 → 4408559
    说明书    25 行，三问都在

紧接着用 self/verify.hmyr 复核那份清单：对得上 209 项、不对 0、缺 0，整份 digest
也对得上（重算 22385 个字符）。这一遍走完，除签名之外的每一步都真的跑过一次。

造清单是一分多钟（两百多个文件逐个算 sha256），归档是秒级（CRC 走内建、跑在 C 那台）。
所以「一条命令」在墙钟上是两分钟左右，值得在跑之前说一声。

三、还差什么，差在哪
--------------------------------------------------------------------

签名。这是唯一还没搬的一步，而且它卡在一个测量上，不在工作量上：
Ed25519 的域运算要 32 位乘 32 位得 64 位，而这门语言的数字是双精度
（2 的 53 次方以上就不精确，32 位乘 32 位连低八位都是错的）。三条替代与各自的代价
写在 SIGNING.txt 里，选哪一条取决于这次发布要许什么承诺。

在签名落地之前，说明书里「哪些资产带签名」那一段会老实写着「这一版没有签名」，
而「怎么自己验」那一段走的是另一条路：逐项 sha256 加整份 digest，不需要签名。

四、一次发布的完整步骤（当前版本）
--------------------------------------------------------------------

  一、跑 hmyr self/release.hmyr <tag> dist
  二、用 hmyr self/verify.hmyr dist/manifest.json 复核一遍（它会逐项比对，
      并重算整份 digest）
  三、把 dist/ 里的归档、清单、说明书三样发出去 —— 这一步要网络与凭据，
      所以留在 tools/release.mjs（它跑 gh release create），凭据不进语言运行时
  四、在发布页里贴说明书的内容

第二步与第三步之间的顺序不能反过来：先验再发，发出去的东西才有一份自己的记录。

五、还没做但已经知道要做的事
--------------------------------------------------------------------

  一、签名（见上）。
  二、归档里不含清单本身 —— JS 版把 manifest 收进 zip，HMYR 版暂时把它放在旁边。
      收进去要改 package 的成员列表，不难，但会让「包里的清单」与「包外的清单」
      成为同一份字节的两个副本，得先想清楚哪一份算数。
  三、语料目录（runtime、conformance）不在包里，原因写在 package.hmyr 的文件头：
      这份语言把字节串表示成每字节一个值，几 MB 的语料是几百万个值，读进来先撞内存。
