可变数组

一、为什么要有它

元组是不可变的：+= 复制。这在写编译器时是优点 —— 一份语法树交出去，别人改不动它 ——
而写「按桶分组的候选位置」时是灾难：每压一个字节要改一次桶，改一次是 O(桶数)。

deflate 的找匹配就卡在这里。线性扫描在四万三千字节上跑不完（步数先耗尽），换成按首字
节分桶的链之后能跑完了，但要七十二秒 —— 而 node 里同样的算法只要零点零三秒。差的不是
算法，是「改一个桶的代价」：宿主那边是 O(1) 的 Map，这边是重建整个元组。

所以加一个可变数组，让「桶的 O(1) 更新」在语言里可行。

二、形状

    数组(元组)            复制成可变数组
    设(数组, 下标, 值)     原地改，交回同一个数组
    数组[下标]            读，与元组一样
    len(数组)             与元组一样

- 数组是从元组造出来的，不是字面量：语言里没有 [1, 2, 3] 这种写法。少一种语法，就少一组
  「这到底是元组还是数组」的歧义。
- 设 拒绝元组（HMYR-行-018）。这条是刻意的：元组的不可变是这门语言的一条承诺，让设 能改
  元组就会悄悄破掉它，而破掉的地方在调用方看不见。
- 越界报 HMYR-行-019，与元组下标的 HMYR-行-018 分开 —— 一个是「那个值没有这一位」，
  一个是「你手上这个东西没有这一位」。
- + 从来不就地改：数组 + 数组 得到一个新元组。设 是唯一的原地操作。

三、它落在七个地方，不是六个

宿主解释器、最小的那一份、字节码的内置名、VM 的内置表、自举的 dispatch、C 的 name_is ——
这六处是写代码时数得出来的。第七处是编译期：self/compile.hmoca 的「是内置」名单决定一个
调用发 CALLB 还是 CALLF，漏了它，数组会被编成用户函数调用，运行时才报「没有这个函数」。

C 那边还有一处不显眼：name_is 是拿 ASCII 字节去比名字表的，而中文名字在名字表里是 UTF-16
码元。所以另有一个 name_is16 按码元比，两个新名字走它。

四、验的是什么

test/array.test.mjs 十三项，两条路各一半：自举九项、C 那台四项。覆盖读、写、越界、同一
数组两次改都可见、从元组造的数组改了不影响原元组、以及两台机器给出同一个答案。

五、用它做的事

找匹配换三字节哈希，是加这个数组的理由。做完之后量了三路 —— 同一份 43738 字节的种子、
同一套 --固定 流程、各跑三次取中位数，三份源码除「桶用元组还是数组」与「桶里按几个字节
分组」之外逐字相同：

    首字节桶 · 元组（256）      35.24 秒   方差 0.895
    首字节桶 · 数组（256）       6.87 秒   方差 0.006
    三字节桶 · 数组（4096）      6.02 秒   方差 0.017

结论比原先那句更准：

    元组换数组       35.24 → 6.87，快 5.1 倍 —— 主因
    256 换成 4096 桶  6.87 → 6.02，只快 12%

早先记的「71.9 → 7.5」把两个变量混在一起了：那一版的链自己也是元组
（链 = 链 + (...)，每字节重建整条链），所以那九倍里有一部分来自链，不是桶。这次三路
分开量，才把账算清 —— 而这件事正好说明为什么「改前改后」不能代替对照实验：两处一起改，
你就说不出是哪一处起的作用。

方差那一列也值得看：元组那行 0.895，数组两行 0.006 与 0.017。元组版不仅慢，还更不稳 ——
每字节分配的量级不同，GC 的时机就开始影响结果。

六、第二次用它：inflate 的输出块

deflate 那边换的是「桶」，inflate 这边换的是「当前攒着的那一块输出」。

原来的写法每输出一个字节就 当前 = 当前 + (字节,)。元组的 + 是复制，所以填满一个 1024 字节
的块要搬约 1024 × 1025 ÷ 2，五十二万次元素。每块封好之后又从零开始，所以平方项被块化了、
没有被消掉 —— 64 块乘五十二万，3300 万次。现在的形状是定长 1024 的数组加一个计数：
每字节一次 设，封块时用 截 转一次元组，每块约一千次操作。计数走参数与返回值，不放进记录，
因为记录也不可变 —— 每输出一个字节重建一个两字段的记录，等于把同一个平方项从元组挪到记录上。

账没有我先前算的那么好。654370 字节（十份 bootstrap/pack.hmtn，zlib 的 Z_FIXED）、同一台
C 机器、gcc -O2：

    元组逐字节拼        14.23 秒   1.66 亿步
    可变数组加计数      12.23 秒   1.78 亿步

时间少 14%，而步数多了 7.5%。这两个数里，后一个比前一个更有信息：元组复制不算「步」，
它藏在内置的 + 里面，复制一千个元素仍然记一步。于是「少复制」在步数上看不见，只落在每步
的成本上 —— 86.0 ns 降到 68.7 ns，两成。

我原先记的理由是「四百二十块乘五十二万次等于两亿多次复制，那正是慢一个量级的原因」。
两亿这个数没错，错在它是复制次数而不是步数，而机器计的是步数。两者之间没有换算关系：
每输出一个字节要走 272 步，那个数才是慢的大头，它与输出用什么攒着无关。

这是第一节那个教训的第二次。第一次是把「桶的更新」与「链的重建」混在一起量（第 58 行），
这一次是把「复制次数」当成「步数」。两次的错法不同，根子是同一个：估一个改动值多少之前，
要先看清机器计的是什么。

七、同一条改动在两个系统上差一倍多

第六节那 14% 是 Linux 上的数，也是唯一做过严格对照的地方：用 INFLATE_SRC 把新旧两份源码
喂给同一台 C 机器、同一份样本，只换那一个变量。Windows 上没法这么切，但同一个套件单独跑
的墙钟从 133.7 秒到了 61 秒（两次：63.9 与 58.2，取中位）。而样本同时从 43738 长到
65437 字节 —— 五成更多的输入、一半的时间。

差得这么开，原因落在分配上：元组的 + 每复制一次都要一个新元组，而 Windows 那一侧的分配器
与 GC 压力比 Linux 沉得多。WSL 上同一个十倍样本只从 14.23 秒到 12.23 秒。两个数都对，
但它们回答的不是同一个问题：Linux 那个回答「少复制值多少」，Windows 那个回答「用户等多久」。

要记的形状在这里：全量墙钟是在 Windows 上量的，五个最慢的套件都取自那一侧，而实验做在
Linux 上。拿一个便宜的环境量，再拿它去估另一个环境的账 —— 这是这一页第二次出现同一个动作。
第六节末尾记的是「把复制次数当成步数」，这一条是「把一处的数当成另一处的答案」。两次都
出在一个地方：量到的数没说清它是关于谁的。
