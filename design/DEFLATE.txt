deflate 与 ZIP 的现状

一、两个方向都在 HMYR 里

    self/deflate.hmyr   存储块、固定 Huffman、动态 Huffman 三种编码
    self/inflate.hmyr   存储块、固定 Huffman、动态 Huffman 三种解码，多块流
    self/zip.hmyr       ZIP 容器（stored 与 deflate 两种成员），CRC32 查表

解码侧的输出是块化的：每 1024 字节封一块，复制时按逻辑下标取。逐字节往一个元组上
拼是平方级，四万三千字节会顶到四吉上限；块化之后同样的流用四十兆。

二、压缩率

4 KB 样本（bootstrap/pack.hmyrb 的前 4096 字节），三条路都能被 node 的 zlib 解回原样：

    存储块         4096 加五字节块头
    固定 Huffman   1283
    动态 Huffman   1175

动态比固定小 108 字节。两个数都是量的，不是估的。

解码的代价也量过：整份种子 43682 字节用 1.0 秒、峰值 41 兆；十倍于它 436820 字节用
12.9 秒、峰值 238 兆。两条都随输入线性长。

三、动态编码这件事教会我们的

第一版把码长算成「到根的边数加一」，Kraft 和是 0.516 —— 正好一半。修掉之后是 0.992，
仍不是一。真正的错在另一处：建树时把频率为零的符号也放进了叶子列表，树被压深，
某个码长多算一位，和变成 0.9962。

三处错都指向同一句话：码长集合必须是完整的，即长度倒数的二次幂之和恰好是一。任何
查验的解码器（zlib 就是）会直接拒绝不完整的集合，而它报的错只说「码长集非法」，听
不出是树深了一点还是多了一片叶子。

四、怎么找到它的

    self/tree.hmyr   只建树不写流，打印三张表的码长分布、最大深、Kraft 和
    --字面 模式       编码器不做匹配，于是它与参照实现输出逐位可比的流
    ref-encoder.mjs  node 写的参照编码器，证明手写的动态块 zlib 一定接受

第一处差异的位号从「一万六千位里某处」缩到 50，再从 50 缩到一行代码。这三样东西
都是被那三轮失败逼出来的，而它们比修好的那一行更值钱。

五、剩下的

四件做过之后的样子：

    16/17/18 重复压缩     做了，动态流 1175 降到 1156 字节 —— 十九字节
    编码侧多块           做了，107 KB 输入切成两块，第一块 BFINAL=0
    找匹配改链           做了两遍：首字节分桶时 43 KB 要 72 秒，
                         换成三字节哈希、桶用可变数组之后 7.5 秒（固定）与 15.7 秒（动态）
    CRC 提速             做了其中一半：43 KB 从 1.15 秒降到 0.77 秒

关于第三行：首字节那一版能跑完，但慢在「改一个桶」上 —— 桶是元组，改一次要重建整个元组。
为它加的可变数组（数组/设，见 design/ARRAY.txt）把这件事变成 O(1)，桶也从 256 个变
成 4096 个（按三字节哈希）。同样四万三千字节，固定 Huffman 从 71.9 秒降到 7.5 秒，动态从
82.6 秒降到 15.7 秒，产物两版都被 zlib 解回原样。

关于最后一条，原本写的是「每字节两次异或降到一次查表」。那句话不成立：CRC 的标准
更新是 c = (c >> 8) 异或 表[(c 异或 b) 与 255]，两次异或里只有第一次能缩 —— 它只
用到低八位，不必拿三十二位去算。缩了之后 4 KB 从 0.15 秒到 0.08 秒、43 KB 从 1.15
秒到 0.77 秒。

真正还能大幅提速的地方是链：72 秒压 43 KB，瓶颈是按首字节分桶太粗。三字节哈希能把
候选压到几十个，但 4096 个桶的维护在 HMYR 里是每个字节 O(4096)，那要先把「桶的更新」
做成常量时间的数据结构，语言层面还没有。
