索引：一个按键查的东西
====================================================================

  2026-10-24 起草。这份只写约定，不写实现 —— 实现要动六处（宿主求值器、
  最小求值器、编译期内置名、字节码内置表、自举求值器、C 机器），
  tools/builtin-gap.mjs 会指出漏在哪一处。

一、为什么需要它
--------------------------------------------------------------------

  语料生成那三支（tools/ucd-case.mjs、ucd-nfc.mjs、ucd.mjs）都要按码点回头查，
  而 HMYR 现在只有两种能查的东西：

    记录      record_new 一次建好，键必须是「像名字」的字符串（首字符是字母或下划线）
              —— 码点键 "0041" 直接被拒
    元组      按下标取，没有「按键找」这一说

  拿记录凑合也不行，因为**没有增量置入**：record_new 只收一整份对表，而边扫边填就需要
  反复重建。拿元组收集再一次性建表，量过了：

    500 到 8000 个键的元组拼接，8000 那一段就撞步数上限（O(n²)：每一步都复制整个元组）

  所以这不是「写法不对」，是缺一件东西。

二、五条内置
--------------------------------------------------------------------

    index_new()                     建一个空索引
    index_set(索引, 键, 值) -> 索引  放一个；交回同一个索引
    index_get(索引, 键)              取；取不到报 HMYR-R0218
    index_has(索引, 键) -> Bool      有没有
    index_len(索引) -> Int           几项
    index_keys(索引) -> 元组         键的列表，按第一次放进去的顺序

  键是**任意字符串**，不像记录的字段名那样要「像名字」。这是它与记录最要紧的差别：
  码点键 "0041"、路径键 "data/ucd/UnicodeData.txt" 都得能直接放。

三、几条约定
--------------------------------------------------------------------

  一、index_set 交回同一个索引，于是可以链式写：`表 = index_set(表, k, v)`。
      不返回值会逼人写两条语句，而那在 HMYR 里没有就地修改的写法。

  二、index_get 取不到**报错**（R0218），与 field_get 取不到报 R0216 是同一条规矩：
      先问再取（index_has），或者接受「取不到就是错」。

  三、index_keys 交回的顺序是「第一次放进去的顺序」，不是排序后的顺序。
      理由是记录那边 field_names 就是这么定的；两边一致比「更好用的顺序」要紧。

  四、重复 index_set 同一个键是**覆盖**，不报错，键的位置保持第一次的样子。
      语料生成里这会遇到：同一个码点在两个文件里都出现时，后读到的说了算。

  五、索引是值，不是引用：它与记录一样靠传递，语言里没有「就地改动一个索引」的语法。
      所以 index_set 交回的那个才该继续用。

四、六处要动的地方
--------------------------------------------------------------------

    宿主求值器      src/eval.mjs 的 BUILTINS
    最小求值器      src/minimal-eval.mjs
    编译期内置名    src/bytecode.mjs 的 内置名
    字节码内置表    src/vm-builtins.mjs
    自举求值器      self/eval.hmyr 的分派
    C 机器          vm/hmyr.c 的 name_is 分支

  加完跑 node tools/builtin-gap.mjs，差集应当为 0 —— 那把工具就是为这件事写的。

五、实现的选择（留给实现者）
--------------------------------------------------------------------

  JS 那四处：用 Map 最省，键已经是字符串。
  C 那台：哈希表（开放寻址）或者排序数组加二分。哈希表更快，但要多一段内存管理；
  排序数组加二分更省内存，但每次 set 都要插入 —— 语料生成是「先全放、再全查」，
  所以可以在「第一次 get 之前」一次性排好，那就是排序数组的天下。
  这一条等到写 C 那边再定。

六、落地情况（2026-10-24）
--------------------------------------------------------------------

  六处都到了：宿主 72、最小 71、编译 72、字节码 72、自举 72、C 72
  （最小说少的那一个是 f64_bytes，与索引无关，是早就记着的账）。

  JS 那四处与自举那一处是真的实现了：宿主与最小求值器用一个 Map，字节码机用
  { tag: "index", m: Map }，自举求值器的六个分支照它旁边那些写。

  C 那台给的是**一句具体的拒绝**，不是实现：

      这台机器没有索引：这里的记录把字段名放在常量池里（编译期已知），
      而索引的键是运行时的字符串 —— 那要一张真正的哈希表。

  index_has 是例外，交回 0 —— 问「有没有」不是失败。

  为什么这算「到了」而不是「没做」：SELFRUN.txt 里那条判据说的就是这件事 ——
  每个名字在六处都有分支，而分支可以是「做了」，也可以是一句具体的「这台机器没有」。
  真要做，那是一件独立的活（一张哈希表 + 值的生命周期），不该混进「加一个内置」。

  验收：宿主 Runtime 打出「有0041 true 取 99 长 2」，字节码机与 CLI 打出
  「有 true 取 99 长 2 / 键 [0041, 0042]」；test/c-vm.test.mjs 八十项全过，
  说明那六条拒绝没有碰到别的东西。
七、第一个真实用户遇到的三个问题（2026-10-24）
--------------------------------------------------------------------

  self/ucd-nfc.hmyr 是索引的第一个真实用户。它现在**跑不完真语料**，三段问题按发现顺序：

  一、`v - (v / 16) * 16` 算出负的极小值。

      这一门语言的数字只有双精度，「除以 16 再乘回去」在浮点除法不精确时会得到 -2e-323 这种数，
      拿去当下标就是越界（报错里那句「a value of length 16」正好指十六进制字符表）。
      已改成 `v % 16` 加 `floor(v / 16)`。

  二、全分解只收了六条，而扫描收集到三百七十九条。

      扫描阶段的计数是对的（序数 379），全分解阶段却只落了六条 —— 中间那层出了问题，
      还没查。可能是递归里把「分解后仍是码点自己」的情形误判，也可能与栈的元组操作有关。

  三、排除表那一段报 HMYR-R0150（给一个没有 var 声明的名字赋值）。

      三行的小语料能跑到写出阶段，三千行就停在这里 —— 而改名（把「排除」换成「排掉」）之后
      停的位置又变了，说明它不是某一句固定的错，更像「同一个名字在多个循环里各自声明」这一类
      情形触发的。要查，得先把排除表那一段剥成独立小程序，而不是在大程序里猜。

  记在这里的理由不是「记一笔失败」，而是这三条各自都能独立复现：
  第一条已经修好并被小语料验证；第二条有明确的两个数字（379 与 6）；第三条有明确的错误码。
  下一轮从任何一个开头都能直接动手，不必重走这一遍。
  四、把范围缩到了「槽 38、pc 465」这一句。

      隔离测试先说清一件事：排除表那一段剥成独立小程序（223 行、81 条）在 vm 上跑得通，
      所以那几行本身没写错。回到主程序，把虚拟机那条报错改得带上槽号与程序计数器之后：

          HMYR-R0150  slot 38 at pc 465

      而且阶段打印显示它已经走到排除表的最后一行（G222），也就是循环收尾那几句之一。
      下一轮从这里开头：拿编译器给的槽表对一下 38 是哪个名字，就知道那句赋值为什么被当成
      「没有 var 声明」。带着槽号与 pc 的报错本身也留下了 —— 这类错以后都能这么查。

      顺带：三次连跑停在同一处，说明这是确定的程序问题，不是虚拟机的随机行为。
  五、槽表那一招奏效了，第三段已修好，第四段是新的。

      给编译器加了一个开关（HMYR_SLOTS=1，输出走 stderr、不碰产物）：分配槽的时候把
      「槽号 ← 名字（可写性）」打出来。于是「槽 38」当场对上：

          槽 38 ← 首类（let）· main

      而程序里那一句是 `let 首类 = 0` 之后又 `首类 = index_get(...)` —— let 的槽不可写，
      这正是 R0150 的意思。改成 var 就过去了。

      教训写在这里：**报错不带名字时，先给它补上能定位的东西，再查**。三轮回合的猜测，
      加起来不如给编译器加一个开关。

  六、现在停在写出阶段：HMYR-R0131（cannot compare "[" with 0）。

      排除表已通过，组合收集到 353 条。写出阶段某处把一个字符串（含 `[`）当数字比较了 ——
      `十六进制写法` 的第一个参数、或者某段表头文本被拿去比大小。下一轮照同一个办法：
      让 R0131 带上 pc，或者把写出阶段切成几段打印。
  七、最后缩到一句：`填[0]` 拿到的是 "["。

      实测的顺序（都是 vm 上的打印）：

          p1 cp=193
          p2 cp=194
          p3 cp=195
          HEX<832>       第一份分解的第一个码点，正常
          HEX<[>         紧接着的一次调用就收到了 "["

      也就是说 `序列[p]` 那一路是好的（193、194、195 都是数字），出问题的是拼 `填` 那三句：

          var 填 = (0, 0, 0, 0)
          填 = slice(填, 0, q) + (全[q],) + slice(填, q + 1, 4)

      而 "[" 恰好是这门语言把元组转成文字时的第一个字符（`[832, 0, 0, 0]` 的开头）。
      所以 `填` 在某一步**变成了字符串**，于是 `填[0]` 取下标的第一个码元就是 "["。

      下一轮从这一句开头：验证 `slice(元组, 0, 0)` 的返回类型，以及「元组 + 字符串」时
      `+` 走的是拼接还是别的。这大概是这一支最后一个问题。

  八、这一轮留下的两件工具（都是通用的）
      一、HMYR_SLOTS=1 —— 编译器把「槽号 ← 名字（可写性）」打到 stderr，产物不受影响。
      二、R0131 与 R0150 的报错带上了 pc、函数名（R0131 还有槽号），
          「不能比较」这一类错从此能指出位置，而不只是说「不能」。
