基础库的宿主形状：它不需要实现 JS 语义
====================================================================

这一份回答一个问题：用户点下的那个 C++ 基础库，长什么样。
它不写实现，只把形状定下来 —— 形状错了，写多少行 C++ 都是错的。

证据三件，都是现成的，不是推断
--------------------------------------------------------------------

  一、design/HOSTMIN.txt 第 78-121 行：那张「宿主至少要给什么」的表已经从
     上界收紧成实测下界。办法是 NODE_V8_COVERAGE 跑六条真实路径，结论是
     十项全局、八种构造，每一项都真的被走到过 —— 没有一项是虚的。
     而同一份文档第 102-104 行把这张表的用法改了一句：「十项全局与八种构造
     是『用另一种语言实现 JS 语义』这条路的需求表。C 这条路绕过了它，所以
     对这条路来说它不是待办。」

  二、design/SELFRUN.txt 第 90-92 行：vm/hmyr.c 不实现 JS 语义 —— 它直接
     执行字节码，值、栈、错误信息都是自己的。

  三、self/vm.hmoca 八百一十六行：HMYR 写的字节码机器，装载、执行、二十二
     个内置，同样不经过 JS 语义。它由 C 那台驮着，而它自己还在往「接 C 那台
     的位置」走。

所以宿主形状是：字节码机器的宿主
--------------------------------------------------------------------

  基础库要给的四样：

    ・分配       一块能领、能还的内存。第一代可以先只领不还，与 vm/hmyr.c
                 现在的口径一致 —— 那个口径写在它自己的头注里（一个 run 很短，
                 GC 是另一件活）。
    ・串         UTF-16 码元的那一种，因为字节码里的串就是它。
    ・文件读写    读一份 .hmoks 进来、把一份写出去。
    ・退出       带一个码，机器停下来。

  基础库不实现的：

    ・闭包、异常、Map、JSON、RegExp —— 那些是「JS 语义」那一层的，而这一条
      路不经过那一层。它们要的时候由语言自己给（self/ 那一族已经写着它们）。
    ・十项全局与八种构造那张表 —— 它继续有用，但用处在「换一个 JS 实现」
      的时候，不在这一条路上。

  这个形状与 Yunooka 那边那句「分配器、字符串、文件读写」是同一句话：
  那边写在 design/LANGS.txt，这边写在这里，两边说的是同一个库。

一个待定的问题，而它不拦路
--------------------------------------------------------------------

  谁在这个库上跑？vm/hmyr.c（第一代）还是 self/vm.hmoca 的第二版？
  两台机器的宿主需求是同一批（分配、串、文件、退出），差别只在「跑谁」
  那一刻才显出来。所以这个问题的答案可以等，形状不用等。

  判据也可以等形状定了再立。这一份先立判断，与 INDEPENDENCE、LANGS 那两次
  同一个顺序：先立判断，再立判据，判据落下之前这文件里的证据就是它自己。
