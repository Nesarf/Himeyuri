签名：为什么 Ed25519 不在 HMYR 里，以及三条替代
====================================================================

现状：这条链的签名是 Ed25519，格式是 OpenSSH 的分离签名（ssh-keygen -Y sign -n file），
验证靠 ssh-keygen -Y verify。也就是说，「与现有签名链互通」这件事绑在 Ed25519 上。

一、量出来的边界，不是估计
--------------------------------------------------------------------

这份语言的数字是 IEEE 双精度，能精确表示的整数上限是 2 的 53 次方。用 HMYR 自己跑一遍：

    2 的 53 次方        9007199254740992
    它加一              9007199254740992      ← 加一丢掉了
    它加二              9007199254740994
    32 位乘 32 位       18446744065119617000  ← 真值 18446744065119617025
    它的低八位          0                     ← 真值 225
    16 位乘 16 位       4294836225            ← 这个是对的

前四行说明一件事：32 位乘 32 位得 64 位这种乘法，在这门语言里从低位就是错的。
而 Ed25519 的域运算（mod 2 的 255 次方减 19）每一步都建立在这种乘积的累加之上。

所以「在 HMYR 里实现 Ed25519」不是难，是先缺一层地基：没有精确的 32×32→64 乘法，
就得先用 16 位字重造大整数算术（16×16→32 是精确的，这是唯一一条能走的路）。

二、那条路要付什么
--------------------------------------------------------------------

  一、大整数：255 位 = 16 个 16 位字；乘法 256 次部分积外加进位链。
  二、SHA-512：现有的是 SHA-256，而 Ed25519 用 SHA-512，要新写一份。
  三、曲线运算：点加、倍点、标量乘（255 轮条件加），每一步都在上面那层大整数上。
  四、OpenSSH 的签名格式：一份 base64 包着的二进制结构，要解析。

四样加起来是数百到上千行 HMYR。

但速度不构成障碍 —— 这一点也量过了，用 HMYR 自己跑：256 万次位加 1272 毫秒（每次约
0.5 微秒），20 万次「16 位乘加拆字」90 毫秒（每次约 0.45 微秒）。按这个折算，一次
255 位的域乘（16 个半字，256 次 16 位乘）约 115 微秒，而 Ed25519 一次签名约 2550 次
域乘 —— 亚秒级，验签同量级。

所以选项 C 的代价在代码量与正确性，不在速度：四样东西要一次写对，而错了只能对着
公开测试向量反推。

三、三条替代，各自的代价
--------------------------------------------------------------------

A. 换签名方案：用 HMYR 能精确实现的那一类（例如 HMAC-SHA256 加一把发布钥匙）。
   好处：全部在语言里，几百行，可验收。
   代价：与 OpenSSH 那条链不互通 —— 老验签器验不了新包。目标里「互通」这一条要改。

B. 验签留在 JS，HMYR 只做内容核验。
   好处：今天就能用；内容核验（每文件 sha256 加整份 digest）已经在 self/verify.hmyr 里。
   代价：发布链上仍有一处依赖 node —— 「完全独立」还差这一步。

C. 真的在 HMYR 里做 16 位大整数 + SHA-512 + 曲线。
   好处：互通成立，且是真正的全自举。
   代价：上面第二节那四样，以及它们带来的长期维护面。

四、现在停在这里的理由
--------------------------------------------------------------------

三条路没有一条是「显然对」的，而选哪一条取决于发布这件事要许什么承诺：
是要「任何人用 OpenSSH 就能验」，还是要「整条链一行 JS 都不碰」，还是两者都要。
这个取舍不该由写代码的人替人定，所以第四件停在测量与记录。

已经确定的部分：内容核验在 HMYR 里（self/verify.hmyr，逐项 sha256 加整份 digest），
说明书里那条「怎么自己验」写的也正是这条路 —— 它不需要签名，只需要 sha256。

验签本体（self/curve.hmyr 里的 验签）已经接起来，4 到 5 秒跑完，但对 node 生成的
合法签名仍然回答「不通过」。

最后一次测量的两条矛盾，就是下一轮的起点：

    一、压缩形式与坐标对不上。a·B 与解压出来的公钥点在坐标上相同，
        但把 a·B 压成 32 字节之后与公钥字节不同 —— 压缩函数本身可能就是错的，
        而它是我这一轮刚写的、还没被任何验收覆盖的五分钟代码。
    二、r·B 与签名里的 R 在坐标与压缩形式上都不同，两种 x 符号都试过。

第一条尤其值得先查：一个没被验收覆盖的新函数，出现在两条矛盾的正中间。
如果压缩函数错了，那么「坐标相同」这个判断也许是靠另一条路（解压）对上的，
而 r·B 的比较一直在一个不可靠的尺度上做。

接着做的最短路径：
    一、给 压缩 写验收（压缩再解压应当回到同一个点；基点的压缩形式是已知常量）。
    二、用压缩后的比较重跑 r·B 与 R。
    三、若 r 仍不对，再查 r 的输入 —— 但那时至少是在一个已经验证过的尺度上查。

不计入完成的部分：与 ssh-keygen 的双向互通（验旧包、旧验签器验新包）一步都没做。

七、更正：第一条矛盾是误读
--------------------------------------------------------------------

上面那两条里，第一条不成立。重跑时把输出存成文件再读，才发现那一行是
「压缩(a·B) 与公钥字节相同 是」—— 上一次是把 GBK 解出来的乱码看成了「否」。

压缩函数没有验收套件，但它是对的：压缩再解压往返一致（随机一对密钥上验过），
而 a·B 的压缩形式与公钥字节逐字节相同。所以压缩、解压、标量乘这三样一起被洗清了。

于是真矛盾只剩一条：r·B 与签名里的 R 不同，两种 x 符号都试过。
而这一条与验签本身没有关系 —— 验签只需要 S、k、R、A，不需要 r。
r 只在签名时用。所以 r 算错不影响验签，验签不通过的原因仍在 k 的输入或两边的系数上。

这一条更正的教训比它的内容更值钱：把控制台的乱码当成结论，等于用一个读错的刻度去
下判断。往后凡是「否」这种关键判断，输出先落成文件再读，不直接读终端的转码结果。


八、突破：理解是对的，错在 HMYR 的实现
--------------------------------------------------------------------

这一轮把签名过程手工走了一遍，与 node 的 crypto.sign 逐字节比：

    R（压缩形式）      相同
    S                  相同
    公钥与 a·B 的压缩  相同

于是 R、S、k、A 四样都被确认为自洽。再在同一份数据上算验签方程的两边：

    S·B 与 R + k·A     相等（左右 x 逐位相同）

这推翻了上一节的判断。验签方程按我的理解是成立的，两条边在 node 里也确实对上了 ——
所以「共有理解错了」这个说法不成立，错的是 self/curve.hmyr 里那份实现。

又一次栽在同一件事上：上一条「不等式成立」的结论来自控制台乱码，而这次把输出落成
文件再读，同一个脚本给出的答案是「相等」。

下一轮因此变成一次普通的逐段对照，不再需要推理：
    一、固定一组 (公钥, R, S, 消息)，用 node 算出 k 与左右两点的坐标。
    二、让 HMYR 的 验签 把同样的中间值打印出来（开关是 参全局()）。
    三、第一个对不上的那一段，就是 bug 的位置。

这条路的成本很低，因为两边都已有现成的打印。


九、定位到一个函数：k 算错了
--------------------------------------------------------------------

用同一组输入（公钥、签名、消息三样都打印出来逐字核对过）跑两边，第一个对不上的
中间值就是 k：

    node 的 k  = 0c3a58429fc872ad436af8165a2bf9712b3ef3fe67db54cd253b1c21036eb95d
    HMYR 的 k  = 0f28e6912a9f014dee6a80e78aab9dcb4500e256bf202b723dba6b0f6debf1c7

输入相同而结果不同，所以 k 的计算链（sha512字节 再接 模L长）里有一处错。
sha512字节 已经被四份样本验过（「abc」等四条，与 node 一致），所以嫌疑落在 模L长。

而两边算出左边 S·B 的 x 是相同的（7af7ef9c…），说明 S 与标量乘都对 ——
错的只有 k，于是右半边跟着错，等式自然不成立。

下一轮验 模L长 的办法也现成：拿一个已知的大整数（比如把某个 32 字节串当数），
用 node 算「它模 L」的值，与 模L长 的输出比。这一步只用一步就能判定，
因为 模L长 是最后一段还没被单独验过的代码。

十、收尾：根因是端序，而它瞒过了两个实现
--------------------------------------------------------------------

验签通过了（2026-10-24）。这一节只写最后那一跳，前面各节已经把走过的路写完。

一、这一次的顺序是「先审判据，再算等式」

    前几轮都从「哪一步算错了」入手，于是每轮都在改对的东西而不在改根因。这一轮换了
    顺序，四道检查各自给一个能说否的外部判据：

        判据可否定    node 对好签名说真、对改了一个字节的签名说假      通过
        基点对不对    基点满足曲线方程；[L]G 是单位元 (0, 1)           通过
        解压无损      decompress 再 compress 与原始 32 字节逐字节相同   通过
        标量乘对      [a]B 等于公钥、[r]B 等于签名里的 R               通过

    四道全过之后才去看 k —— 这时「左不等于右」只剩一个可能的成因：两边算出来的 k
    不是同一个数。问题于是从「算术」变成「读法」。

二、根因

    RFC 8032 的验签第一步是「把 SHA-512 摘要当作 little-endian 整数取模 L」。
    模L长 的实现从第一个字节读起、逐位累加 —— 那是大端。k 因此与每一份正确实现
    都不同，左右两边永不相等。

三、为什么这么久没抓到

    因为「两个独立实现给出同样的答案」被当成了证据。我在 node 里手写的仿射版与
    HMYR 版逐点相同，当时的结论是「错在共有的理解」—— 那句话本身没错，但它指向的
    方向错了：共有的理解若本身错，比对只能证明两边一致，不能证明一致的东西是对的。
    第二意见必须来自这份理解之外：RFC 的向量、node 的 crypto、以及「把签名改一个
    字节它敢不敢说否」。

    还有一次误读值得与第八节并排记：当时看到「压缩形式与公钥字节不同」，于是怀疑
    压缩函数，后来把输出落成文件再读，那一行其实是「相同」—— 控制台转码把「是」
    读成了「否」。同一个读法错误在这个文件里出现过两次。
