签名：为什么 Ed25519 不在 HMYR 里，以及三条替代
====================================================================

现状：这条链的签名是 Ed25519，格式是 OpenSSH 的分离签名（ssh-keygen -Y sign -n file），
验证靠 ssh-keygen -Y verify。也就是说，「与现有签名链互通」这件事绑在 Ed25519 上。

一、量出来的边界，不是估计
--------------------------------------------------------------------

这份语言的数字是 IEEE 双精度，能精确表示的整数上限是 2 的 53 次方。用 HMYR 自己跑一遍：

    2 的 53 次方        9007199254740992
    它加一              9007199254740992      ← 加一丢掉了
    它加二              9007199254740994
    32 位乘 32 位       18446744065119617000  ← 真值 18446744065119617025
    它的低八位          0                     ← 真值 225
    16 位乘 16 位       4294836225            ← 这个是对的

前四行说明一件事：32 位乘 32 位得 64 位这种乘法，在这门语言里从低位就是错的。
而 Ed25519 的域运算（mod 2 的 255 次方减 19）每一步都建立在这种乘积的累加之上。

所以「在 HMYR 里实现 Ed25519」不是难，是先缺一层地基：没有精确的 32×32→64 乘法，
就得先用 16 位字重造大整数算术（16×16→32 是精确的，这是唯一一条能走的路）。

二、那条路要付什么
--------------------------------------------------------------------

  一、大整数：255 位 = 16 个 16 位字；乘法 256 次部分积外加进位链。
  二、SHA-512：现有的是 SHA-256，而 Ed25519 用 SHA-512，要新写一份。
  三、曲线运算：点加、倍点、标量乘（255 轮条件加），每一步都在上面那层大整数上。
  四、OpenSSH 的签名格式：一份 base64 包着的二进制结构，要解析。

四样加起来是数百到上千行 HMYR。

但速度不构成障碍 —— 这一点也量过了，用 HMYR 自己跑：256 万次位加 1272 毫秒（每次约
0.5 微秒），20 万次「16 位乘加拆字」90 毫秒（每次约 0.45 微秒）。按这个折算，一次
255 位的域乘（16 个半字，256 次 16 位乘）约 115 微秒，而 Ed25519 一次签名约 2550 次
域乘 —— 亚秒级，验签同量级。

所以选项 C 的代价在代码量与正确性，不在速度：四样东西要一次写对，而错了只能对着
公开测试向量反推。

三、三条替代，各自的代价
--------------------------------------------------------------------

A. 换签名方案：用 HMYR 能精确实现的那一类（例如 HMAC-SHA256 加一把发布钥匙）。
   好处：全部在语言里，几百行，可验收。
   代价：与 OpenSSH 那条链不互通 —— 老验签器验不了新包。目标里「互通」这一条要改。

B. 验签留在 JS，HMYR 只做内容核验。
   好处：今天就能用；内容核验（每文件 sha256 加整份 digest）已经在 self/verify.hmyr 里。
   代价：发布链上仍有一处依赖 node —— 「完全独立」还差这一步。

C. 真的在 HMYR 里做 16 位大整数 + SHA-512 + 曲线。
   好处：互通成立，且是真正的全自举。
   代价：上面第二节那四样，以及它们带来的长期维护面。

四、现在停在这里的理由
--------------------------------------------------------------------

三条路没有一条是「显然对」的，而选哪一条取决于发布这件事要许什么承诺：
是要「任何人用 OpenSSH 就能验」，还是要「整条链一行 JS 都不碰」，还是两者都要。
这个取舍不该由写代码的人替人定，所以第四件停在测量与记录。

已经确定的部分：内容核验在 HMYR 里（self/verify.hmyr，逐项 sha256 加整份 digest），
说明书里那条「怎么自己验」写的也正是这条路 —— 它不需要签名，只需要 sha256。


五、进度：地基铺到哪了
--------------------------------------------------------------------

已经站住的三层，各有验收并挂进 check-all：

    大整数（self/bigint.hmyr）     16 位字组成 256 位值，加、减、乘、比、模乘、求逆，
                                   40 项与 node 的 BigInt 对照
    曲线（self/curve.hmyr）         twisted Edwards 上的点加、倍点、标量乘，
                                   18 项：0 与 1 的边界，加上 2 到 8 都落在曲线方程上
    速度                            一次标量乘基点 1.2 秒（扩展坐标；仿射那一版要几分钟）

还差三层：

    SHA-512      站住。六十四位字拆两个 32 位半，八十个轮常量由工具现算而不是手抄。
                 8 项与 node 的 crypto 对照：空串、三字节、112 字节（填充边界）、
                 200 字节（跨两块）。两个 bug 各留了一课：长度字段的高位零该在前，
                 以及十六进制串的「前八个字符是高 32 位」被我当成了低半。
    线格式       站住（只做「解出来」这一步）。self/ssh.hmyr 解 base64、按 SSHSIG 的
                 结构取段：魔数、版本、公钥 blob、命名空间、保留、哈希算法、签名 blob。
                 9 项对着一份真的签名（dist/manifest.json.sig 的正文）逐字节比。
    签与验       验签函数写好了，但还没通过 RFC 8032 的第一条测试向量。
                 这一轮修掉两个真 bug：
                   一、模 L 的字节序。sha512字节 交回的是大端，我却从最后一个字节开始扫。
                   二、模 L 的进位。逐字节乘 256 时 出 会到 2^261，十六个字装不下，
                      丢掉的正是 2^256 那一档。改成逐位乘二就不越界。
                 修完 k 与 node 算出的一致了，但左右两边仍不相等 —— 第三个 bug 是点加
                 公式里的 D：add-2008-hwcd-3 要的是 Z1*Z2，我写成了 2*Z1*Z2*Z2。
                 在单位元那种 Z1 = Z2 = 1 的场合它只是把分子分母同时放大，所以
                 「1 到 8 倍基点」那一组测试看不出问题；一到两个真点相加就错了。
                 改完仍不通过，说明还有第四个。中间值的打印留着，开关是 参全局()。

                 这一轮又往前推了两步，都没有让等式成立，但各排除一大片：

                 一、那条 RFC 8032 向量本身是错的。用私钥推出 a、再推出 r，算
                     (r + k*a) mod L，结果与签名里的 S 不相等 —— 一份合法签名不可能
                     这样。所以拿它当判据一直在冤枉验签。引用测试向量时，先验它自洽。
                 二、换一份现生成的签名（node 的 crypto 造密钥与签名，再喂进来）仍然
                     不通过。而用 BigInt 在 node 里写的仿射版（与 HMYR 不同的一套代码）
                     给出与 HMYR 完全相同的两个点 —— 于是这不是实现差异，是两边共有
                     的一个理解错误。

                 已经被排除的：解压（用私钥算 a·B，与解压出来的公钥点逐字节相同）、
                 标量乘、点加、模 L、SHA-512 字节出口。剩下最可疑的是 R 的解压符号
                 与等式两边各自的系数，下一轮从这两个地方入手。

                 再往前一步，这一轮拿到的是最硬的一条线索：对一份 node 生成的签名，
                 node 自己验签通过、a·B 也确实是公钥点，可是我算的
                 (r + k*a) mod L 与签名里的 S 不相等。既然签名合法，那不等就意味着
                 r 或 k 里有一处的输入与我以为的不同 —— 下一轮该拿 node 的签名过程
                 反推：用同一个 seed 手工算一遍 r，再与它的 S 对，看是从哪一步分岔。
