  不同：都是「有名字、但没有判据」的那一种。

  一、surface 的 POSIX 后端只做到 -NoShow。
      deps/surface/win.py 与 win.ps1 逐字段一致，四十九项在两个系统上全过 ——

      tkinter 起不来；sudo 要密码，所以装不了 tk。

      收掉了（2026-11-03 更晚）：判据先立，再写窗口。deps/surface/win.py 用 ctypes
      调 libX11 真开一个窗口，把窗口 id 打进回执；deps/surface/xprobe.py 拿那个 id

      只记下错误的；回执必须在「按住窗口」之前打出来并 flush，否则调用方拿不到 id。
      Windows 那一侧仍然是 WPF，它不交 id 也没有 X11 可问 —— 那一节在那里如实跳过。
  二、call_c 的混合形状。

      判据要先有形状，比如一个 take_int_then_str 的测试函数。

      收掉了（2026-11-03 更晚）：数与串各一个时，认「数在前」与「串在前」两种
      顺序；判据是 test/ffi.test.mjs 自己编的一份共用库（take_int_then_str 与

2026-11-03 更晚：inflate 的步数账
--------------------------------------------------------------------

  一、inflate 每输出一个字节走 272 步。
      现在是什么样（当时）：654370 字节（十份 bootstrap/pack.hmtn、zlib 的 Z_FIXED）走
      1.78 亿步，WSL 上 12.23 秒。输出块已经从元组逐字节拼改成定长数组加计数，而那一条
      只买到 14% —— 元组复制不算步，它藏在内置的 + 里面，复制一千个元素仍然记一步。
      为什么当时还没做：只知道慢在步数上，没有 272 步在各段之间的分布。三个候选各自值
      多少都没量过 —— 按码查 每次调用先重建长表 的 29 项元组再线性扫、取位 每读一位造
      两个记录、解规范 找「第几个同长度的符号」是 318 项全扫。

      怎么量的（同一天更晚）：不改一行代码，造三种等长输入，让它们只差「走了哪条路」——
      zlib level 0 的 stored 块（位流一位都不读）、deflate --固定 压随机数据（全字面量，
      zlib 压不可压数据会退回 stored，所以这一份必须用自家的编码器造）、deflate --固定
      压全重复（长回引）。三条路的 ops 相减，分布就出来了：

          输出路径                                      54.32 步/字节
          Huffman 解码（解符号 + 按码查(长表)）         506.23 步/字节
          回引（解距 + 查表 + 复制循环）                 24.72 步/字节

      那个 506 把三个候选的排序推翻了：解规范 根本不在这条路上（主测量走的是固定块），
      取位 的记录分配确实贵，而最贵的是「逐位读、再按三段分支判断」这件事本身。

      收掉了（同一天更晚，四步）：位读取摊进局部变量（取位 退休）；解符号 改成补位加一张
      五百一十二项的九位表；长表与距表按码直接下标（按码查 退休）；读lsb 改成一次取 n 位
      （位缓冲本来就是低位先出，取 n 位就是 当前 对 2 的 n 次方取余），并给距表建一份
      反序副本供它查。

          步/字节   时间（WSL，十倍种子）   提交
          272      14.23 秒              （元组版）
          250       9.39 秒              5ea667a
          212       8.61 秒              b97a0a1
          152       7.15 秒              （三表下标化）
          111       5.67 秒              1834e11

      收掉之后哪里会变：它是最慢五套之一，而这条路的账现在分层了 —— 输出路径 55.64 步
      每字节，在主测量里已经占到一半。下一段该量它，而不是继续在解码上找。

      又收掉一段（同一天再晚）：解规范。要造第四种样本才量得到它 —— 种子前六十四 KB
      走 zlib 的默认策略，那才写出 BTYPE=2。量出来是每输出一个字节七百五十步，固定块的
      六点七倍，而前面所有量测一次都没碰到它，因为种子的流是固定 Huffman。改法是同一个
      招式：造规范表 按块建一张九位表（码表在流里，所以不能建一次用到底），九位装不下的
      长码在表里留空、退回逐位读，而 补位 已经把九位留在缓冲里，状态不用回退。
      七百五十降到一百八十七 —— 与固定块的一百六十三只差一成。

      判据跟着来了（test/inflate.test.mjs 的三·七节）：整份种子与它的十倍走默认策略，
      六条，其中两条是步数上限。原来的动态流只有四 KB，一两块走不完建表，所以那三条
      判据在新路上几乎是空的。而上限是验过的 —— 把建表停掉，它红在七百六十三与
      七百三十八上，而往返判据仍然过。上限若没人见它红过，它就是个占位符。

       mapagree，六项判据全过；impact 十七项也跟着全过（它比的是「地图报的套件数」
       与「套件清单长度」，两边一起变，所以没被这个新套件撞红）。


  十六、字宽从 16 位换到 24 位。做完之后量到的是：乘 1.1272 到 0.5997 毫秒（减 47%），
       模乘 1.4868 到 0.7607（减 49%），模幂 421 到 218（减 48%），curve 单独跑
       69.6 到 36.1 秒（减 48%），sign 那套 129.5 到 46.5 秒。推算与实测差在一个
       百分点上下 —— 那条「少一条指令换一成二」的斜率不只解释了旧代码，也预测了新代码。
       撞到三处，都不是改常数就行的：低半与高半的交界落在字中间（256 不是 24 的倍数），
       折叠常数 38 变 9728 且第 255 位要一次算清减几次（264 位的余最多是 p 的五百多倍），
       以及从字节串的「两字节一个字」变「三字节一个字」。三处都是判据撞出来的，
       没有一处是读代码看出来的 —— 换表示的时候，判据比读更靠得住。
       分解与新字宽的账都在 design/SCALARS.txt 新一节。
  十七、Linux 上的线程。vm/hmyr.c 的线程结构体、线程表、线程起、找线程、
       清线程从「只在 _WIN32 里」扩成「桌面两支」：线程句柄收成一个类型
       （HANDLE 与 pthread_t），join 用 完 位轮询（POSIX 没有带超时的标准
       join，没有引 glibc 的扩展），cancel 的语义差写在代码里。
       判据：cvm 第二十三节在 Linux 上通过。
  十八、run_program 在 POSIX 上的实现。原来整块只在 _WIN32 里，else 一支
       只写一句 ENOPROC。补的是 fork 加两根管道加 execvp、非阻塞读、超时
       kill、退出码 waitpid，另加一支握手管道 —— exec 失败时子进程写一个字节，
       父进程据此给 -1，于是两边对「程序不存在」的答案一样（少了它 Linux 给 127）。
       判据：cvm 第二十二节在 Linux 上通过。
  十九、两处「包在 _WIN32 里但其实通用」的代码：字节串放 与 cvm 那套的编译
       参数（-Wl,--stack 按平台换成 -pthread），外加线程上下文的 话 从 256
       加宽到 512 —— gcc 15 把那个截断报成警告，而警告是真的（截掉的是一句
       错误信息）。
