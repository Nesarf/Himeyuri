不变式：SPEC §2.4 那三样里的第三样
====================================================================

SPEC §2.4 的第三只旋钮写的是三样：requires、ensures、invariant。
前两样在 design/CONTRACTS.txt 里立住了（五台全查）；这一页立第三样。

一、它写在哪
--------------------------------------------------------------------

与 requires 和 ensures 同一个位置：函数签名之后、函数体之前，各自一行。

    函数 取(n: Int) -> Int
      invariant n >= 0
    {
      返回 n
    }

为什么不在别处：

  一、不在类里。这门语言没有类，Eiffel 那种 class invariant 没有落点。
  二、挂在 当 上的那一处是同一套想法的另一个落点，而它自成一节：见第八节。

二、它什么时候查
--------------------------------------------------------------------

两头都查：入口一次（与 requires 同时机），每次返回之前一次（与 ensures 同时机）。

这就是「不变式」在这个语言里的意思：进入时成立，退出时也成立。
它不保证「中间每一步都成立」—— 那要逐语句检查，是另一件事，也更贵。

与另外两样的分工因此清楚：

    requires    调用者的义务：你给我的东西要对
    ensures     被调者的承诺：我交出去的东西对
    invariant   这个函数自己的前提：它跑之前与跑完之后，那件事都还在

三、失败报什么
--------------------------------------------------------------------

    HMYR-契-003   不变式不成立

与 001、002 同一条路：消息里有函数名与这是第几条。

四、顺序
--------------------------------------------------------------------

入口：先 requires，再 invariant。先查「调用者有没有守约」，再查「函数自己的前提」——
前者不成立时，后者往往也没有意义。

出口：先 ensures，再 invariant。「我交出去的东西对不对」比「我的前提还在不在」更近。

两个顺序都写在这里，因为它们是可观察的：两条同时不成立时，报的是先查的那一条。

五、开关
--------------------------------------------------------------------

与契约同一个：options.contracts（宿主求值器与 stage 0）、编译期那个开关（字节码）、
--contracts（自举那一层）、HMYR_CONTRACTS（启动器）。五台一致。

六、今天做到哪一步
--------------------------------------------------------------------

五台全查：src/eval.mjs、src/minimal-eval.mjs、src/vm.mjs（检查由 src/bytecode.mjs 编进
函数入口与每条 返回 之前）、vm/hmyr.c（它执行的就是那份字节码，所以只需要认 契约失败
这个名字）、以及 self/eval.hmoca（解释那一条路，开关是命令行的 --contracts）。

判据在 test/invariants.test.mjs：语法层（invariant 真的进 contracts.invariant，宿主与
子集两条路都认）、入口一条、出口一条、两个顺序各一条、硬条款一条；解释、字节码、
自举解释、子集编译器四台各跑一遍，第八节还让它们对循环不变式说同一句话。

曾经的两处边界，2026-11-02 都收掉了：

  一、解释那一路原来拒绝「函数里写模块级 var」（scope.assign 只沿作用域链走，不碰全局表），
      于是「出口不成立」那条只能在字节码那台验。现在两台求值器都收 顶层变 声明，
      并在作用域链上找不到名字时回退到全局表 —— 与读它走的是同一条回退，
      所以「读得到、写不上」那种不对称没有了。判据是第四节：出口不成立在解释这一台上也验。
  二、宿主解析器原来在「签名之后换行、再写 {」时不认那个体，除非前面有契约把换行吃掉。
      现在它与 if/else 那一处同一条规矩：先往前看，确认隔着若干换行真是 {，才吃那些换行。
      判据在 test/else-newline.test.mjs 第三节（两种写法同一棵树、跑出同一段）。

八、循环不变式：同一个词，挂在 当 上
--------------------------------------------------------------------

语法是写在条件与块之间。

    当 i < 4 invariant i >= 0 {
      i = i + 1
    }

    当 i < 4 invariant i >= 0
    {
      i = i + 1
    }

这两种写法从 2026-11-02 起是同一棵树。在那之前宿主解析器在换行上 atPunct("{") 为假、
体就丢了，于是不变式只能挤在同一行 —— 那让「怎么写」变成了语义。
现在声明的体、if 的 then、while 的体、else 之后的块四处共用一个判据
（src/parser.mjs 的 过换行看花括号），规矩是「先往前看，确认隔着若干换行真是 {，
才吃那些换行」；无条件过空行会把两条语句之间唯一的边界也吞掉。

它什么时候查：入口一次，每轮体末一次。

    查 I             进来时它成立
  头:
    条件为假就跳到尾
    体
    查 I             这一轮跑完，它仍然成立
    跳回头
  尾:

三件事因此各自有着落。0 轮时入口那一次仍然跑 —— 体一次都不进，而「进来时它成立」
不该因此免检。n 轮时每轮都把「保持」验一遍。退出那一刻正好落在最后一次体末上：
末轮体末之后只再求一次条件，而条件不该改循环里的名字。

不查「中间每一步都成立」：那要逐语句插桩，是另一件事，也更贵。

失败报 HMYR-契-004。消息与另外三样不同：带行号，不带函数名与「第几条」。
理由是位置。循环在同一个函数里可以有若干个，「第几条」对它没有意义；而带函数名
就要记住「当前在哪个函数里」，那项状态的恢复点有两处 —— 正常返回与抛出，
正是这类状态最容易漏的地方。行号取的是不变式表达式自己那一行：它可能与 当 分行，
而读的人要找的正是那一条条件。

开关与另外三样同一个。五台全查：解释那台入口一次、每轮体末一次；字节码那台
把两段编进循环的头与尾；C 那台执行的就是那份字节码，所以只需要认 契约失败；
自举解释那台在 执行反复 里用 次数 == 0 认出入口；自举编译器那台把两段编进同一处。
判据在 test/invariants.test.mjs 第八节，四台各说一句同一句话；
tools/self-vm-compile.mjs 另有一份带循环不变式的样本，两台编译器逐字节比。

一条要承认的边界：写在同一行是这一层的现状，不是设计上的偏好。若哪天 当 的语法
允许「条件与块分两行」，不变式那一段要跟着放宽。

一条来自现场的记录：自举那一层原来用空元组表示「没有不变式」，而两个空元组相比
在编译那条路上判假，于是 编循环不变 去读了 .line 并报「没有这个字段」。
今天用 假 表示「没有」—— 那一层现成的说法，而它的真值规矩正是「只有假才算假」。
空元组不承担这个角色，也写在这里，免得下一个人又试一次。
