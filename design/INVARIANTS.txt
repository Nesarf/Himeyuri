不变式：SPEC §2.4 那三样里的第三样
====================================================================

SPEC §2.4 的第三只旋钮写的是三样：requires、ensures、invariant。
前两样在 design/CONTRACTS.txt 里立住了（五台全查）；这一页立第三样。

一、它写在哪
--------------------------------------------------------------------

与 requires 和 ensures 同一个位置：函数签名之后、函数体之前，各自一行。

    函数 取(n: Int) -> Int
      invariant n >= 0
    {
      返回 n
    }

为什么不在别处：

  一、不在类里。这门语言没有类，Eiffel 那种 class invariant 没有落点。
  二、不在循环上。循环不变式是另一件事：它要改 当 的语法，而那是另一层。
      今天不做，理由写在这里，而不是让它看起来是被忘了。

二、它什么时候查
--------------------------------------------------------------------

两头都查：入口一次（与 requires 同时机），每次返回之前一次（与 ensures 同时机）。

这就是「不变式」在这个语言里的意思：进入时成立，退出时也成立。
它不保证「中间每一步都成立」—— 那要逐语句检查，是另一件事，也更贵。

与另外两样的分工因此清楚：

    requires    调用者的义务：你给我的东西要对
    ensures     被调者的承诺：我交出去的东西对
    invariant   这个函数自己的前提：它跑之前与跑完之后，那件事都还在

三、失败报什么
--------------------------------------------------------------------

    HMYR-契-003   不变式不成立

与 001、002 同一条路：消息里有函数名与这是第几条。

四、顺序
--------------------------------------------------------------------

入口：先 requires，再 invariant。先查「调用者有没有守约」，再查「函数自己的前提」——
前者不成立时，后者往往也没有意义。

出口：先 ensures，再 invariant。「我交出去的东西对不对」比「我的前提还在不在」更近。

两个顺序都写在这里，因为它们是可观察的：两条同时不成立时，报的是先查的那一条。

五、开关
--------------------------------------------------------------------

与契约同一个：options.contracts（宿主求值器与 stage 0）、编译期那个开关（字节码）、
--contracts（自举那一层）、HMYR_CONTRACTS（启动器）。五台一致。

六、今天做到哪一步
--------------------------------------------------------------------

五台全查：src/eval.mjs、src/minimal-eval.mjs、src/vm.mjs（检查由 src/bytecode.mjs 编进
函数入口与每条 返回 之前）、vm/hmyr.c（它执行的就是那份字节码，所以只需要认 契约失败
这个名字）、以及 self/eval.hmoca（解释那一条路，开关是命令行的 --contracts）。

判据在 test/invariants.test.mjs：语法层（invariant 真的进 contracts.invariant，宿主与
子集两条路都认）、入口一条、出口一条、两个顺序各一条、硬条款一条，三台各跑一遍。

两处边界写在这里，因为它们不在这一件该修的范围里：

  一、解释那一路拒绝「函数里写模块级 var」（scope.assign 只沿作用域链走，不碰全局表），
      所以「出口不成立」那条只能在字节码那台验 —— 它的编译器会把这种赋值编成 全域存。
      那是既有的不一致，属于「四台一致」的另一个话题。
  二、宿主解析器在「签名之后换行、再写 {」时不认那个体，除非前面有契约把换行吃掉。
      同样是既有行为，与不变式无关。

循环不变式（loop invariant）今天不做：它要改 当 的语法，而那是另一层。
