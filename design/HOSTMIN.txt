执行器要宿主给什么（SELFRUN 第三步的第一小格）
====================================================================

为什么量这一件事
--------------------------------------------------------------------

  SELFRUN 的第二步做完了：启动器读自己那一层用的是子集那两层，跑的是最小求值器，
  而 src/capabilities.mjs 是它们碰世界的唯一入口。于是「借了什么」第一次有了清单。

  但那张清单只覆盖「世界」——文件、进程、时间这些。还有一层东西一直在借，而且借得无声：
  宿主语言的语义本身。闭包、异常、Map、字符串方法、Unicode 归一化——这些不是能力，
  是「跑这段代码的那台机器」给的。第三步要把执行器搬到自己的机器层上，那要先知道
  那台机器至少要给什么。

  这一份就是那份需求，量出来的，不是猜的。

怎么量的
--------------------------------------------------------------------

  静态扫描 Stage 0 那五份（src/minimal-eval.mjs · src/loader.mjs · src/subset-lex.mjs ·
  src/subset-parse.mjs · src/diagnostics.mjs），共一千一百一十三行：

    一、剥掉行注释、块注释与字符串字面量。不剥的话，名字出现在注释或字符串里就会被算成依赖——
        第一次扫的时候 process 就是这样冒出来的：它只是 minimal-eval 里效果名的字符串值。
    二、再数宿主全局名与语言构造。

  这个办法证明的是「源码里出现了哪些名字」。它不证明「运行时真的调到」：
  某个只在一个走不到的分支里的名字也会被算进来。所以这份清单是上界，而不是实测用量。
  要量下界，得把全局包一层、记每次访问——那是第二小格的事。

量出来的（2026-10-20）
--------------------------------------------------------------------

  宿主全局，按出现次数：

    String 13 · Error 12 · Array 10 · Math 5 · JSON 5 · Map 5 · Set 4 · Object 3 ·
    Number 3 · TextDecoder 3

  十项。其中 TextDecoder 是唯一一项「有点份量」的：它负责按 BOM 与编码名解码字节，
  而那件事是最小机器层最难自己给自己的一件事——它要么有一条内置的解码表，
  要么把「解码」也当作一项能力交给宿主。

  没有出现的（这一半也是答案）：

    Boolean Date WeakMap WeakSet RegExp TypeError RangeError Symbol Promise Buffer
    URL TextEncoder Intl globalThis console require

  值得单说三项：没有 Promise（执行器是同步的，这一条从设计上就成立）、
  没有 RegExp（这是剥掉字符串之后的结果——正则只出现在字符串参数里）、
  没有 Symbol 与 Proxy，于是最小的机器层不必提供它们。

  语言构造，用到的八种：

    class · try/catch · throw · instanceof · new · spread · arrow · getter/setter

  没有 async/await，没有模板字面量，没有可选链与空值合并。于是这一层的语法面
  比「现代 JavaScript」窄得多。

这一份数字意味着什么
--------------------------------------------------------------------

  第一步不是「写一个 JS 引擎」。那份需求是：十个全局 + 八种构造 + 一个同步的执行模型。
  这比「一门语言的完整语义」小得多，而它仍然是真正的一层——闭包与异常不是能省的东西，
  它们是这个执行器的骨架：作用域链靠闭包，return 与尾调用靠异常。

  第二步才是想清楚「最小机器层」与它的关系。三种可能，而它们的代价差很远：

    一、把它当规格写下来，然后用别的东西实现（例如字节码 VM，或者用 Himeyuri 自己写）。
        代价最大，收获最大：那才是 SELFRUN 第三层说的那一层。
    二、把它当规格写下来，然后继续用 JS 实现，只是不再叫它「高级宿主」。
        代价最小，而那只是换个说法，不是第三步。
    三、只量下界：包一层记每次访问，把「上界」收紧成一份真实的用量。
        这一件最便宜，而它会让上面两种判断都更有底气。

  我倾向先做第三件，再做第一件。而在那之前，这一份文档与它钉着的套件已经有用：
  谁要往 Stage 0 里加一个 Promise，会先看到这份清单，知道那是一次扩张而不是顺手。

钉住它
--------------------------------------------------------------------

  test/host-deps.test.mjs 扫同样五份、用同样的剥法，把上面三张表逐个对上。
  它红了通常有两类原因：新增了一种宿主全局（要问该不该加，或者该不该自己实现），
  或者某种构造第一次出现（同理）。两件都不是坏事，但都要有人看一眼。
