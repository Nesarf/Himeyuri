包管理：第一步，清单与哈希
====================================================================

  2026-10-27 起草。这一页只定「一个包怎么说明自己」，不定「怎么装、怎么取、怎么发」——
  那三件归 design/DISTRO.txt 与包管理 kagaribi 那一套，而它们要等这一页先立住。

  为什么先立这一页：一个包能自己说明身份，是「不许运行时偷下载」这条规矩的前提。
  没有清单，语言就只能靠路径去找东西；而路径说不了版本、许可与哈希。

一、清单在哪、叫什么
--------------------------------------------------------------------

    包根/<包名>/hmyr.hmkit

  与套件清单同名，因为它是同一种东西：一份「这里有什么」的声明。一个包根下面
  既有一个包的清单，也可能有它自己的套件清单 —— 两者共用一个文件名，读的人
  不必记两个。

  格式是 JSON。理由：它是被工具读的，而工具已经有 JSON 的读写（json.hmoca 与
  宿主两侧都有）。用一门语言自己的记录语法写成配置文件更漂亮，但那要一个解析器
  与一套错误报告，而这一页的价值在四项字段，不在语法。

二、四项字段
--------------------------------------------------------------------

    {
      "名字": "甲包",
      "版本": 2,
      "许可": "CZGD-PL-1.1",
      "哈希": "sha256:9f86d0…",
      "依赖": { "乙包": 2, "丙包": 1 },
      "依赖哈希": { "乙包": "sha256:…", "丙包": "sha256:…" }
    }

  ・名字    必须与它所在的那一层目录名一致。不一致是错 —— 因为包名就是 import
            写的那个词，而两个地方各说一套会让「我引的是哪个包」变成猜测。
  ・版本    一个整数。它必须与入口文件顶部那句 rev N 一致；不一致是错。
            两处写同一件事看着冗余，但它们的读者不同：清单给包管理看，rev 给
            装载器看。让它们必须一致，是唯一能让两边都不说谎的办法。
  ・许可    非空字符串。内容不校验 —— 那是许可文本那件事，不是解析器的事。
  ・哈希    sha256:<64 位小写十六进制>，算的是入口文件 index.hmoca 的字节。
  ・依赖    名字 → 最低版本。可以省（没有依赖的包不写这一栏）。
  ・依赖哈希  名字 → 那个包入口文件的 sha256。与依赖同进同退：写了依赖就该写它，
            而它让「我用的那个包有没有被人换过」变成可判的，不需要签名。

三、版本范围：不做
--------------------------------------------------------------------

  依赖只写「最低版本」，不写区间、不写通配。理由与省事无关：

    这门语言只有整数 rev，而它已经在两处起作用（模块顶部声明、import 要第几版）。
    一个区间要一套自己的语法（大于等于与小于怎么写、多段怎么并），而那是第二套
    版本语言 —— 写在清单里的与写在源码里的会成为两种东西，而两边不一致时没有
    一条能判。「最低版本」是唯一一个能与 rev 的「向下兼容」语义对上的形状：
    模块提供到第 N 版就意味着它提供第 M 版（M 小于等于 N），所以「我要至少 M」可判。

  等真的需要上限那一天，它该是一套通用的版本语法，而不是清单里多一个字段。

四、校验发生在哪儿
--------------------------------------------------------------------

  装载器只做「形状」那一半：清单能读、几项齐、名字与目录一致、版本与 rev 一致、
  哈希的形状对、依赖的名字与版本是合法的。它不做哈希计算 —— 因为那要一个密码学库，
  而装载器至今只借文件与路径两样能力（见 design/HOSTMIN.txt）。

  哈希计算与依赖哈希的比对给它一个工具：tools/hmkit-check.mjs。它读清单、算文件、比。
  不符就退非零并说清哪一位不一样。这样「校验」这件事分成两层，而每层只借它真正
  需要的东西。

五、签名：清单说「谁担保它是」
--------------------------------------------------------------------

  哈希链挡得住「换了一个包」，挡不住「换的人同时改了清单」。签名挡的是后一件。

  一、签名在哪里

    清单里多一个字段：

      "签名": { "包": "甲包", "算法": "ed25519", "值": "<128 位小写十六进制>" }

    包名写在签名里，是因为它要被签进去 —— 否则同一个签名能被挪到另一个名字的清单上。

  二、签的是什么：规范化字节

    「把清单签一遍」这句话在实现上有无数种说法，而两个实现差一个空格就验不过。
    所以规范化只有四条：

      一、去掉 签名 字段本身。
      二、键按 UTF-8 字节序排序，嵌套的对象也照此。
      三、没有空格、没有换行。
      四、编码成 UTF-8 字节。

    它是 JSON 的一个子集，而不是「随便一个 JSON」—— 值里不许出现需要转义的字符
    （这门语言的包清单里本来也只有名字、整数、许可与十六进制串）。这条限制是
    为了让「规范化」不必实现一个完整的 JSON 序列化器：四类值，四条规则。

  三、公钥从哪儿来：包根的可信表

    包根下面一个 hmyr.hmtrust：

      { "甲包": "<64 位小写十六进制公钥>", "乙包": "…" }

    它不在包里，而在包根。理由是：包里那个签名若连同包一起被换，可信表也跟着换，
    签名就没有意义了 —— 信任的锚必须放在被信任的东西之外。这一条不是完备的信任
    模型（一个能改包根的人也能改可信表），它只是把「换一个包」与「换整个包根」
    分成两件事，而后者要动的是工作区本身。

  四、两层校验

    装载器验形状：写了签名就要求可信表里那个包有公钥、算法的名字认得、值的形状对。
    真伪由 tools/hmkit-check.mjs 验（node:crypto 有 Ed25519 的验签）。

    分两层与哈希那个理由相同：装载器只借文件与路径，密码学归工具。

  五、签名里仍然不做的

    ・密钥怎么产生、怎么保管、怎么轮换：那是一套工具与流程，不是清单格式。
    ・撤销：可信表里删掉一个公钥就是撤销，而「删掉之后已经装好的包怎么办」不在这一页。

六、仍然不做的
--------------------------------------------------------------------

  ・怎么取得：从哪儿下载、缓存放哪、怎么装。运行时不许偷下载这一条已经在规格里，
    而「显式步骤」长什么样还没有落点 —— 它是这一页之后最大的一件，因为它要回答
    「一次安装从哪儿开始、到哪儿结束」，而那不属于清单格式。
  ・可信表本身怎么分发：它现在是一个放在包根的文件，而「谁担保这张表」是同一个问题
    往上退一层。这一页只到「信任的锚在被信任的东西之外」，再往上不归它管。
