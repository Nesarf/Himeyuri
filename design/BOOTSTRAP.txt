引导：Stage 0 的账
====================================================================

  这一份说的是「完全自举」这四个字在实践上能做到哪儿。
  它不给愿望，给数字与路线。

一、为什么 Stage 0 不能为零
--------------------------------------------------------------------

  要跑 Himeyuri 写的程序，总得有一个能跑 Himeyuri 的东西。
  那个东西若是 Himeyuri 自己，它就得先被跑起来——于是要有一个更早的能跑它的。
  这就是引导（bootstrap），而它是递归的底，不是懒。

  编译器界的说法是 Stage 0 编译 Stage 1：Stage 0 是宿主写的那个，
  Stage 1 是产物，而两者在语言设计一致时应当产出同样的结果。
  这一份里的 Stage 0 就是宿主的三个文件。

二、Stage 0 现在有多大
--------------------------------------------------------------------

  实测（2026-10-20，能力内核收完之后）：

    src/loader.mjs          114 行    读文件、跟 import、去环、转发诊断（也走能力层）
    src/subset-lex.mjs      175 行    切词（含浮点与进制、位置、末尾的 eof）
    src/subset-parse.mjs    386 行    搭树，报与宿主同一批码，并按宿主的办法恢复
    src/diagnostics.mjs      20 行    诊断的形状（它不属于任何一个阶段）
    src/minimal-eval.mjs    413 行    执行 self/ 的代码，只认那张量出来的表
    ------
    合计                   1108 行

  宿主那三份（lexer 290 · parser 489 · eval 827）还在仓库里，
  而它们都不在 Stage 0 这条路上了：启动器用子集那两层读，用最小那份算。
  它们现在是对照与工具——格式化器、语言服务器、一致性检查要读比子集更宽的语法，
  而对照那一条是给「最小那份真的能顶替」做证据的。

  诊断原先住在 lexer.mjs 里，于是凡是要记错误的地方都得 import 宿主的切词器。
  那是一条假的依赖：加载器一次也没有调到宿主切词器，却写着它。
  把它搬到自己的文件里，那条例才真的成立。

  账写过四次，而每次都不是把数字往好看改：

    早先一笔   885 行，启动器与工具走同一条路（都是宿主那两层）
    中间两笔   启动器先换到子集（552 行那一侧），工具那一侧还是宿主（892 行）
    第三次     工具也换了子集，于是 693 行，而宿主那两层成了工具路线
    第四次     求值器也换了最小那份，于是 1102 行——账变大了，因为「怎么算」进来了
    现在       能力内核收完，loader 与 minimal-eval 各长了几行，于是 1108 行

  第四次这个数变大值得说一句：Stage 0 以前只回答「怎么读」，现在也回答「怎么算」，
  于是它的账从 693 涨到 1102。那不是退步，是把一件一直借宿主的活计到自己手里。

  而要说清的是「怎么算」有两个意思：
  算出来的意思对不对，由 self/eval.hmyr 定义；Stage 0 里那一份只负责照它执行。
  于是这一门语言的语义仍然全在 self/ 里，Stage 0 只多了「按那份语义跑起来」的能力。

三、已经成立的那一半
--------------------------------------------------------------------

  六份全对（见 design/SELFCOMPILE.txt）：把 self/ 里每一份交给自举的函数名们，
  它算出来的函数名与宿主算出来的完全一致，默认栈，三到五秒一份。

  于是「它能读自己」这一句是真的。而它读自己用的那两件事（切词与搭树），
  现在也换成了子集那一份——见第六节与第七节。

四、再缩的办法：子集到底要什么
--------------------------------------------------------------------

  目标是让 Stage 0 只支持「跑 self/ 里那六份所需」的子集。

  为了知道子集里必须有什么，把六份源码扫了一遍。结果（2026-10-20）：

    语句      六种：Block · Return · ExprStmt · Let · Assign · Var
    表达式    十一种：Ident · Literal · Binary · Call · Field · If ·
                     Record · Index · Tuple · Unary · While
    运算符    十四种：! != % && * + - / < <= == > >= ||
    字面量    三种：bool · int · string

  而 If 与 While 在这一门语言里也是表达式（if 有值），于是它们既算语句也算表达式。
  这一点值得单独说，因为第一次扫漏了它——那时数出来的运算符只有五种，
  而「只有五种」那个结果看起来很干净，差点被当成真的。

  有了这份清单，一个手写引导器的规模能估出来：单是这些构造的切词与求值，
  三四十行是不够的，三五百行更接近实际。那份文档原来写「三四十行」，
  在这里改正——一个偏小的估计比一个偏大的估计更容易骗人。

  而缩到零不在路线里。任何声称「零引导」的说法，底下都藏着一个没被说出来的 Stage 0。

五、这一份数字会变
--------------------------------------------------------------------

  test/bootstrap.test.mjs 钉着第二节与第三节的数字：
  Stage 0 的行数、六份文件数、声明数、以及六份全对这件事。
  数字变了它会红，红的时候先读这里。

六、第一步已经落了一格：切词层对得上了
--------------------------------------------------------------------

  src/subset-lex.mjs 是一个一百来行的子集切词器。它现在：

    六份一致   lex 1988 · chain 2137 · stmt 1252 · body 1285 · eval 2687 · run 2246
               token 的种类、值与顺序，与 src/lexer.mjs 逐个相同

  那处分歧（换行折叠的位置）查清了，而且它只有一个成因：ident 与 keyword 那一支
  用 出.push 而不是 记()，于是「这一行最后一个 token」停在更早的运算符上，
  续行() 把真实的行尾误判成续行，把那一个 newline 吞掉。

  一个笔误，六份里的四份各差几个 token，而症状看起来像「换行规则理解错了」。
  前一版这份文档写着「追踪过两次没查清」；查清它的办法不是再读一遍那段规则，
  而是把两个切词器并排喂同一份源码、逐 token 报出第一个分岔与它的行列。

  位置也跟着来了：行从 1、列从 1，每推进一个字符若不是换行就加一列，token 记的是
  它第一个字符的位置。那套算法是照 src/lexer.mjs 抄的，而 CRLF 里那个 \r 也占一列——
  照抄这一条是有代价的：不照抄，同一份用 CRLF 的源码在两边会差出一列。

  于是「六份一致」现在含位置，报错也带得上行号与列号了。

  还差的是范围而不是规则：转义表只认 \n \t \r \\ \"，以及它不认全角标点的别名
  （宿主有一张 ALIASES 表，而 self/ 那六份里没有用到全角标点）。

  它仍然不接线到任何地方。理由变了一点：以前是「半成品不该被套件钉住」，
  现在是「它还没有自己的立场」——它目前只证明能对齐，而 Stage 0 要的是能替代。
  test/subset-lex.test.mjs 钉着这件对齐的事（含位置），也钉着那个笔误的具体形状
  （行尾是一个 ident、而它前面是运算符时，那一个换行必须出得来）。

  这一步量到的东西也有用：把 Stage 0 的切词那一层（269 行）压到一百七十行上下，
  而压下去的办法是「只认用得到的东西，遇上不认的就报错而不是猜」（后来补了浮点与进制，
  所以比最初那一百出头多了一些——那些是量出来缺的，不是想加的）。
  那与这份文档第二节那些数字是同一件事的两端。

  离「能用」还差：转义表补全，以及全角标点别名。

七、第二层：搭树，六份的树已经一样了
--------------------------------------------------------------------

  src/subset-parse.mjs 是子集 parser 的第一格。它认的构造是先数出来的，不是照语法书抄的：

    声明   只有 fn，124 个；没有 type / const / effect / pub，没有类型参数，没有 requires/ensures
    参数   258 个，全部带类型，没有默认值，没有 own/borrow
    类型   只有三种：Int 189、String 65、Bool 4，全是单名
    语句   六种：let / var / assign / return / ExprStmt / Block
    表达式 十一种：Literal · Ident · Binary · Unary · Call · Index · Field · Tuple · Record · If · While
    运算符 十四种，五档优先级（与 src/parser.mjs 的 PRECEDENCE 同一张表）

  那份普查连带钉住了一件事：六个文件里一个 import 之外的顶层构造都没有，
  于是子集 parser 的规模不是「语法有多大」，而是「这六份用了多少」。
  而它照样会碰到别的写法，所以每一条不认的构造都各自报错，并说清是哪一行哪一列。

  验收是两棵树整棵深比较，连字段名与每个节点的行号列号一起比：六份全部相同，
  26 · 20 · 10 · 14 · 26 · 28 个函数，合计 124；节点合计 6635，位置逐个相同。

  位置起初是分开做的（先形状、后位置），理由是两者混在一起查，红了说不清是哪一边的事。
  而位置那一格只查出一种取法要照抄：Field 记的是「字段名之后那个 token」的位子。
  宿主如此，这里照办——照抄的理由是「两棵树一样」这句话要经得起逐节点核，
  而单方面改对一处，就等于把两棵树拆开。Block 只带行不带列，也照抄：
  缺一个字段与有一个错的字段不是一回事。

  错误路径也跟着对上了。宿主那五个解析码（E0101 到 E0105）在这一份里是同一批，
  位置取法相同，恢复办法也照抄：报一次，然后跳到下一个能开始语句的地方继续，
  遇到 } 就吃掉它再返回（停在 } 上不前进，一个多余的括号能生出成百条同样的错）。
  八种语法错逐个核过，码与位置全同，其中包括「块没关」那一例——它指的是文件尾，
  而文件尾的位置需要切词器产出 eof token 才有，于是切词器现在也产它。

  有一条边界明写着，并且由套件钉住：宿主读得动、而这一份还不认的构造（type / const /
  match / 泛型 / 可空 / 参数默认值 / own / 带参数的效果 / 无体函数）是抛，不是记诊断。
  那是这一份的边界，边界要大声说，不然会被当成语法错。options.strict 为真时连语法错也抛，
  那是给「只想问一句这棵树对不对」的调用方用的。

  消息写中文，码用与宿主相同的编号。验收只比码与位置，不比消息文本——
  措辞可以不同，而码是给人查的，位置是给人点过去的。

八、接线：这两层真能顶替宿主那两层
--------------------------------------------------------------------

  前两节钉的是「对得上」。对得上还不等于能顶替，于是这一节钉「顶替」：
  src/loader.mjs 的 options.reader 是一个可以换掉「怎么把源码变成树」的口子，
  默认仍是宿主的两层，而套件把子集的两层接进去并排跑。

  比的是加载器交出来的东西，不是树：

    模块顺序      六份相同（被引的在前，入口在后）
    声明序列      每个模块逐个相同
    函数表        跑起来之后名字逐个相同
    同一个答案    同一段源码，两路都给 7
    一个真工程    入口 import 另一件、调它的函数，两路都给 42

  同一份套件还钉了两条相反的：默认那一路遇上 type 声明会抛（它的立场是报错而不是猜），
  而宿主那一路读得动同一份文件。两条路都还在，只是默认换了人。

  默认换了两步，而两步都留着痕迹：先换启动器（bin/hmyr.mjs 用子集那两层读自举层），
  再换加载器（loadUnit 的默认 reader）。第二步之前先量了一件事：仓库里 37 份 .hmyr
  能不能全部被子集那两层读进来——36 份能，剩下那份用了小数，于是子集补了浮点与进制，
  补完 37 份全过。先量再换，换的时候心里有个数字。

  一句明写的代价：子集认得窄，遇上不认的构造会抛，而不是给一棵猜出来的树。
  将来谁往仓库里加一个子集还没认的写法，加载器会在那里失败——
  而在他跑到那里之前，subset-lex / subset-parse / subset-diag / subset-load 四套会先红，
  红在那个写法上。启动器把那个抛出接住，写成与「读不进来」同一种输出：
  一个会露出栈的启动器，对读它的人没有用处。

  launcher 那十三项在换主体之前与之后一样全过，subset-load 那十六项在换默认之后
  改成钉「两条路交出的东西仍然相同」。换主体不该悄悄改对外行为，
  而这一条比任何一句说明都硬。

九、求值器还剩多少：一张数出来的需求表
--------------------------------------------------------------------

  Stage 0 现在只剩「怎么读」，而「怎么算」全在 self/。可求值器本身仍在宿主里：
  src/eval.mjs 八百零二行。那它到底该有多大，这件事不该靠猜。

  量的办法：把宿主求值器的 evalExpr / evalCall / execBlock 包一层，跑六条真实路径
  （hello、带 while 与赋值、带函数与字符串、目标不存在、目标语法坏、目标 import 一件库），
  记下每一个节点种类与每一个内置名。六条合起来就是全集。

  结果（2026-10-20）：

    表达式  十一种：Binary · Call · Field · Ident · If · Index · Literal · Record ·
                    Tuple · Unary · While
    语句    五种：Assign · ExprStmt · Let · Return · Var
    内置    十七个：argv · chr · field_get · field_has · file_exists · is_letter ·
                    is_mark · len · nfc · print · print_err · read_text ·
                    record_new · slice · str · to_int

  值得单独说的一条：宿主求值器认得十八种节点，而跑自举层只用到这十一种。
  Match 一次都没被用到——它在这门语言里存在，而读 self/ 那六份用不上它。

  所以这张表不是「所以可以删掉 Match」。它是「想把求值器缩小的人该知道的硬要求」：
  这十一加五加十六是必须的，而其余的部分是选择。两句话差得很远，
  而把它们混成一句，就会有人在删掉 Match 之后发现某个迁移脚本坏了。

  这张表漏过一次，而把它抓出来的不是文档。第一版只跑了六条路径，里面没有一条用记录，
  于是表里少了 record_new / field_get / field_has 三个。启动器换到 stage0 模式之后
  跑那个造记录的程序，当场抛了「stage 0 does not need the builtin 'record_new'」。
  路径补上、表补齐、文档改成十六——这件事的顺序本身说明了一件事：
  一份写在纸上的需求表只能被人点头，一个会拦下来的求值器能把它证伪。

  于是启动器现在跑在 stage0 模式下（bin/hmyr.mjs 里 runUnit 的 options）。
  它不是把求值器缩小，而是把「它需要多少」变成可执行的约束：
  六份里哪天有人用上表外的东西，启动器会立刻抛，而不是等到某天有人真要换掉求值器时
  才发现「原来还用了这么多」。

  表由 test/stage0-eval.test.mjs 钉住。它红了通常有两类原因：self/ 用上了新的构造
  （表要扩），或者某条路径不再被走到（表要缩）。两件都不是坏事，但都要有人看一眼。

十、一份最小求值器：照那张表另写，能不能顶替
--------------------------------------------------------------------

  src/minimal-eval.mjs 是第二份求值器，而它只认第九节那张表：
  十一种表达式、五种语句、十七个内置。表外的节点与内置它不是「碰巧没实现」，
  而是抛并说清是哪一种——于是它自己就是那张表的执行体。

  规模：宿主 src/eval.mjs 八百三十四行，这一份四百零九行。

  三条语义是照宿主抄的，因为它们在 self/ 那六份里是活的：

    尾调用    return f(...) 不新压一帧。没有这一条，self/run.hmyr 的递归
              在默认栈下就撞深度（当年真的踩过）。
    效果      被调者做的不能比调用者声明的多（R0201）。内置也算：读文件属 file 组。
    闸        深度（R0108）与步数（R0102）是语言的，不该让宿主栈先崩；
              步数还兼管「换函数」——纯尾递归每层不做一次求值，不记步就是死循环。

  验收是逐条路径对照，而不是「跑得动」：

    正常八例      hello · while · 函数加字符串 · 记录 · import 一件库 ·
                  文本切片 · 元组串接 · 嵌套 if 表达式       两路同码同输出
    一万层尾递归  两路都算完，不撞深度                        TCO 是真的
    错误七例      除零 · 取余除零 · 索引越界 · 未知名字 ·
                  非尾递归撞深度 · 改一个 let · 没声明效果就读文件
                                                            两路同编号，且都不给值
    表外一例      match                                       这一份抛，宿主给 R0110
    自举自己十二个表达式  1 + 2 * 3 · 括号 · 取余 · 除法 · 一元负号 · 双负号 ·
                          比较 · 字符串相加 · len · str · 两个坏表达式
                                                             两路给同一个字符串

  最后那一组是最硬的一组：它跑的不是加法，而是 self/run.hmyr 里的 跑——
  那条路上要经过自举的切词、搭树与求值三层。两个宿主求值器在那条路上给出同一个字符串，
  才算「它们对这门语言的理解一致」，而不是「它们都会算加法」。

  最后那一组判据是「两边都没有给出一个值」，而不是「两边说话一样」。
  那样更贴要保的东西：一个求值器最容易被写错的地方不是算错加号，
  而是该拒绝时给了个值；而给出来的值会一路走到用户那里。

  它现在是启动器的默认求值器。开关反过来了一条：--host-eval 换回宿主那份跑，
  而那是给人对照用的——同一份程序两条路给出同一个答案，那才是「这一份能顶替」的证据。
  两个开关都从 argv 里剔掉，不然语言侧取 argv[1] 当目标文件会挪错位。

  于是 Stage 0 这条路上现在是：loader 112 行 + 子集切词 175 行 + 子集 parser 386 行 +
  诊断 20 行 + 最小求值器 409 行，合计 1102 行。宿主那两层（切词与 parser）与宿主求值器
  都还在仓库里，而它们都不在这条路上了——它们成了对照与工具。

  这几件加起来回答的是同一个问题：「跑 self/ 那六份，最少需要多少」。
  而答案分两层：怎么读（切词与搭树）与怎么算（那个只认表的执行器）。
  至于「算出来的意思对不对」，那仍由 self/eval.hmyr 定义——执行器只负责照它跑。

十一、这一份数字会变
