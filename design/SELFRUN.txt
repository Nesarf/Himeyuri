HMYR 全面自举：运行时、宿主依赖与启动

最终目标（2026-10-19 用户原话，写在最前面）
--------------------------------------------------------------------

  「hmyr 的最终目标是成为一个完全独立的计算机语言」

  这一句比「全面自举」重。全面自举说的是「能跑自己」，
  而完全独立说的是「不依赖任何宿主」——两者差着三层：

    第一层 语言侧不依赖宿主：.hmyr 文件只用内置，不 import 宿主的任何模块。
           这一层已经成立（2026-10-19 实测：语言侧对 node: 的依赖为零）。

    第二层 宿主缩成能力内核：文件、进程、终端、时间、环境各一组，
           而求值器换成自举那条线。这一层就是下面三步里的第二步。

    第三层 执行器不依赖高级宿主：一个最小的机器层，让「谁来跑求值器」
           这个问题的答案不再是 Node 或任何别的语言。

  第三层为什么绕不开：用 Himeyuri 自己写一个执行器，写出来仍要一个宿主来跑它——
  那是无限递归。所以「完全独立」只有一条路：自己提供那一层最小的机器接口。
  那是另一个量级的工作，而它是这个目标的定义的一部分，不是可选的装饰。

  在此之前，这个仓库的每一处「借能力」都要写明借的是谁、为什么能还——
  那正是 capabilities 那份契约与 tools/check-builtins.mjs 在做的事。


目标（用户原话）
--------------------------------------------------------------------

  往后所有部分都要用 HMYR 启动，包括运行时与宿主依赖本身。
  也就是说，不能长期停在「Node 起一个 .mjs 脚本」这一步。

现状（2026 年间实测，数字都来自当场检查）
--------------------------------------------------------------------

  ・启动方式：node bin/hmyr.mjs xxx.hmyr（启动器会把目标程序交给自举的求值器，而不是宿主的）
  ・宿主：纯 ESM 的 Node 脚本，Node 24。
  ・构建：没有。无 package.json、无 tsconfig、无打包器、无 node_modules。
  ・第三方依赖：零。
  ・宿主模块（七个，是这一条要收掉的东西）：
      node:fs            读写文件、同步读 stdin
      node:os            主目录、临时目录与平台信息
      node:path          路径拼接与解析
      node:readline      逐行输入（真终端那一格）
      node:url           取当前模块地址
      node:child_process  跑一个程序（run_program）
      node:worker_threads 真线程（thr_spawn；已登记为专有模块，见 tools/conformance.mjs）
  ・规模（2026-10-19 实测）：宿主 src/ 2290 行；.mjs 89 个 9306 行，.hmyr 30 个 3492 行。
  ・已经自制的那一半：self/ 那六件（lex · chain · stmt · body · eval · run）证明「Himeyuri 能跑 Himeyuri」。
    而「读它自己那一层」也交出去了：Stage 0 换成了 src/subset-lex.mjs 与 src/subset-parse.mjs，
    于是宿主的 src/lexer.mjs 与 src/parser.mjs 不在启动那一条路上了。
    它们留在仓库里，给要读更宽语法的工具用（格式化器、语言服务器、一致性检查）。
    Stage 0 现在是 693 行：loader 112 · 子集切词 175 · 子集 parser 386 · 诊断 20。
    还差的是求值器与能力内核——那两件就是下面第二步剩下的部分。

走到第几步（2026-10-19）
--------------------------------------------------------------------

  第一步 能力收敛：已做。九组能力写进了 design/CAPABILITIES.txt，
          而 tools/check-builtins.mjs 让「代码、规格第一圈、契约」三面对得上，
          并由 test/builtins.test.mjs 挂进每次全量。
  第二步 启动器还原：做完了。bin/hmyr.mjs 已经把目标程序交给自举的求值器，
          而「读它自己那一层」与「跑」都交出去了：默认的读法是子集那两层，
          默认的执行器是 src/minimal-eval.mjs（只认量出来的那张表，见 design/BOOTSTRAP.txt 第九、十节）。
          宿主那几份仍在仓库里，而它们成了对照（--host-eval）与工具路线。

          能力内核也收成了显式的一层（src/capabilities.mjs：文件、进程、时间、环境、路径、终端、线程）。
          而 src/eval.mjs 不再 import 任何 node: 模块——它只拿到一个能力对象，
          于是「这一门语言借了世界什么」变成一份可以问的清单，而不是要去读它的源码。
          验收在 test/capabilities-layer.test.mjs：换一份能力实现，同一段程序给出同一个答案。

  第三步 自举闭环：前提齐了，还没开始。它要的是「谁来跑求值器」那一层——
          一个最小的机器层，让执行器本身不依赖高级宿主。
  第三步 自举闭环：未开始。它要等第二步的求值器换过去。


三步（按顺序，前一步不成立就不走下一步）
--------------------------------------------------------------------

  一、能力收敛
      把散落的宿主内置按能力分组：文件、进程、终端、环境、路径。
      每一组在 SPEC 里写契约：函数名、语义、需要什么效果、拒绝时给哪个编号。
      做完这一件，「宿主是什么」就变成一份可替换的清单，而不是一堆隐形的内置。

  二、启动器还原
      把 node 那一步缩成最小能力内核：只留读文件、写终端、跑进程、取时间与环境。
      求值器逐步换成 self/eval.hmyr 那条线（先补语句层，再补记录）。
      输出与输入仍走可注入的通道——这两条优势不能为了自举而丢。

  三、自举闭环
      宿主只剩能力内核，而 hmyr xxx.hmyr 由 HMYR 写的启动器完成。
      到那时 Node 只是众多宿主之一，而不是唯一的那一个。

底线（比进度更要紧）
--------------------------------------------------------------------

  ・每条断言仍要可查。自举不换来任何「先跑起来再说」。
  ・能力边界写在明处：做不到的说做不到，不装作支持。
  ・效果声明与可注入这两条优势不许为自举让路：谁动世界谁声明，输入输出都要能被断言。
  ・换宿主时，同一份 .hmyr 的行为必须一致；不一致就是契约没写清，先补契约。

不做什么
--------------------------------------------------------------------

  ・不为了自举而放弃现有的套件。
  ・不在能力契约写清之前动启动器。
  ・不把「能跑了」当成「自举完成了」。
