HMYR 全面自举：运行时、宿主依赖与启动

最终目标（2026-10-19 用户原话，写在最前面）
--------------------------------------------------------------------

  「hmyr 的最终目标是成为一个完全独立的计算机语言」

  这一句比「全面自举」重。全面自举说的是「能跑自己」，
  而完全独立说的是「不依赖任何宿主」——两者差着三层：

    第一层 语言侧不依赖宿主：.hmyr 文件只用内置，不 import 宿主的任何模块。
           这一层已经成立（2026-10-19 实测：语言侧对 node: 的依赖为零）。

    第二层 宿主缩成能力内核：文件、进程、终端、时间、环境各一组，
           而求值器换成自举那条线。这一层就是下面三步里的第二步。

    第三层 执行器不依赖高级宿主：一个最小的机器层，让「谁来跑求值器」
           这个问题的答案不再是 Node 或任何别的语言。

  第三层为什么绕不开：用 Himeyuri 自己写一个执行器，写出来仍要一个宿主来跑它——
  那是无限递归。所以「完全独立」只有一条路：自己提供那一层最小的机器接口。
  那是另一个量级的工作，而它是这个目标的定义的一部分，不是可选的装饰。

  在此之前，这个仓库的每一处「借能力」都要写明借的是谁、为什么能还——
  那正是 capabilities 那份契约与 tools/check-builtins.mjs 在做的事。


目标（用户原话）
--------------------------------------------------------------------

  往后所有部分都要用 HMYR 启动，包括运行时与宿主依赖本身。
  也就是说，不能长期停在「Node 起一个 .mjs 脚本」这一步。

现状（2026 年间实测，数字都来自当场检查）
--------------------------------------------------------------------

  ・启动方式：node bin/hmyr.mjs xxx.hmyr（启动器会把目标程序交给自举的求值器，而不是宿主的）
  ・宿主：纯 ESM 的 Node 脚本，Node 24。
  ・构建：没有。无 package.json、无 tsconfig、无打包器、无 node_modules。
  ・第三方依赖：零。
  ・宿主模块：现在只剩这些（2026-10-20 实测）
      src/capabilities.mjs        node:fs · node:os · node:path · node:child_process · node:worker_threads
                                  ——能力内核自己，这是它该在的位置
      src/format.mjs src/lsp.mjs src/reflect.mjs src/embed.mjs
                                  工具路线：格式化器、语言服务器、反射、嵌入，
                                  fs / path / url / readline 各取所需
      bin/hmyr.mjs bin/run-eval.mjs   node:path · node:url，只为算模块自己的位置
      src/thr-worker.mjs          跑在另一个线程里的那一份
    启动那条路上一处都没有：Stage 0 的五份（loader · 子集切词 · 子集 parser · 诊断 ·
    最小求值器）全都不 import node:，它们只拿到能力对象。
  ・规模（2026-10-20 实测）：src/ 三千四百三十九行；.mjs 一百三十七个，.hmyr 三十七个。
  ・已经自制的那一半：self/ 那六件（lex · chain · stmt · body · eval · run）证明「Himeyuri 能跑 Himeyuri」。
    而「读它自己那一层」与「跑」都交出去了：Stage 0 现在是五份 1108 行
    （loader 114 · 子集切词 175 · 子集 parser 386 · 诊断 20 · 最小求值器 413）。
    宿主那几份（lexer · parser · eval）留在仓库里，而它们成了对照与工具路线——
    见 design/BOOTSTRAP.txt 第二节那五笔账。

走到第几步（2026-10-20）
--------------------------------------------------------------------

  第一步 能力收敛：已做。九组能力写进了 design/CAPABILITIES.txt，
          而 tools/check-builtins.mjs 让「代码、规格第一圈、契约」三面对得上，
          并由 test/builtins.test.mjs 挂进每次全量。
  第二步 启动器还原：做完了。bin/hmyr.mjs 已经把目标程序交给自举的求值器，
          而「读它自己那一层」与「跑」都交出去了：默认的读法是子集那两层，
          默认的执行器是 src/minimal-eval.mjs（只认量出来的那张表，见 design/BOOTSTRAP.txt 第九、十节）。
          宿主那几份仍在仓库里，而它们成了对照（--host-eval）与工具路线。

          能力内核也收成了显式的一层（src/capabilities.mjs：文件、进程、时间、环境、路径、终端、线程）。
          而 src/eval.mjs 不再 import 任何 node: 模块——它只拿到一个能力对象，
          于是「这一门语言借了世界什么」变成一份可以问的清单，而不是要去读它的源码。
          验收在 test/capabilities-layer.test.mjs：换一份能力实现，同一段程序给出同一个答案。

  第三步 自举闭环：前提齐了，第一格已经落地。它要的是「谁来跑求值器」那一层——
          一个最小的机器层，让执行器本身不依赖高级宿主。
          它的需求表已经量出来了：design/HOSTMIN.txt（十项全局、八种构造，没有 Promise），
          而覆盖率把那份「上界」收紧到「每一项都真的被走到过」。所以这一步要选的不是
          「减什么」，而是「由谁提供」——自己实现那一层，或者把规格写死继续用 JS。

          而第一格不是「由谁提供」，是「怎么跑」：AST 现在能编译成一串指令，
          一个循环能跑完它们，六条真实路径给出的答案与最小的那个求值器一样。
          见 design/VM.txt 与 src/bytecode.mjs + src/vm.mjs。它没有摆脱 JS——
          值仍是 JS 的数组与对象，错误仍是 JS 的 throw。那三样才是第三层剩下的部分。

  第三步落到了哪儿（2026 这一轮，实测）
  --------------------------------------------------------------------

  上面那句「三种可能」现在少了一种，而它是被做出来的，不是被选掉的。

  vm/hmyr.c 那台机器不实现 JS 语义：它直接执行字节码，值、栈、错误信息都是自己的。
  于是「谁来跑求值器」这个问题在这条路上已经有答案，而且答案不是任何语言。
  它现在带四张从仓库语料生成的字符表，is_letter、大小写、NFC 都不再借宿主的。

  这一轮又补上最后一块用户面的一格：vm/hmyr.c 自己就是启动器。

    hmyr 程序.hmyr  先用种子编成字节码，再跑那一份
    hmyr 程序.hmyrb 直接跑

  于是「hmyr xxx.hmyr」这一步不再需要 Node。验在 test/bootstrap-seed.test.mjs（九项，
  全程只有 gcc 与种子）与 test/cli.test.mjs（十九项）。

  这一格落地之后，design/HOSTMIN.txt 那张清单的用法要改一句：十项全局与八种构造
  是「用另一种语言实现 JS 语义」这条路的需求表。C 这条路绕过了它，所以对这条路来说
  它不是待办 —— 那份文档仍然有用，但用处在「换一个 JS 实现」的时候。

  还差什么，按代价排（数字都是当场数的）：

    一、世界面：每个名字在六处都有分支了（差 0）。账本做成工具：
       tools/builtin-gap.mjs 一次列出六处（宿主求值器、最小求值器、编译期内置名、
       字节码内置表、自举求值器、C 机器）各有哪些名字，差集就是这一项的待办。
       2026 实测：宿主 64、最小 63、编译 64、字节码 64、自举 64、C 64。
        最小求值器差的那一格是 f64_bytes（字节序诊断用，不是常用路）。
        自举那一侧的 arena 给的是「这台机器没有 arena」的一句拒绝，不是转发。

       已经搬完的一格：split（文本）。它在六处一起加，验收在
       test/c-vm.test.mjs 第十四节 —— 连续分隔留下空段、空分隔按码元切、
       末尾分隔留下尾空段，三种边界两台机器逐字相同。
       搬之前先撞了一次「两边都空」：编译期那张「内置名」表没有 split，
       于是同一段程序被编成「调用一个用户函数」，两台机器都报没有这个函数。
       这正是「加一个内置要动六处」的意思，而工具现在会指出漏在哪一处。

       缺的按组（0 个）：世界面齐了。

       判据写在这里：每个名字在四处都有分支，而分支可以是「做了」，
       也可以是一句具体的「这台机器没有」。最后补的两样正是后者：

       线程四条（thr_spawn thr_join thr_cancel thr_count）要一个独立的机器实例，
       而这台的执行状态还是文件级全局 —— 于是 spawn 交回 -1（无效句柄）、
       join 与 cancel 报 R0221、count 交回 0，与 JS 那侧「起不来」是同一条路。
       验收在 test/c-vm.test.mjs 第二十三节：两台机器给出 -1 0。

       arena 在语言里是关键字，自举那条 parser 不认它（写出来是 E0104），
       于是字节码路径上它编译就过不去；C 那台仍留一条 R0104 的分支，
       防的是宿主 parser 把 AST 直接交给字节码那一层。它的三个字段是函数值，
       而这门语言没有一等函数，所以那条分支的答案只能是「没有」。

       文本、终端、时间、环境、输入五组齐了，进程那一组也齐了。

       run_program 是进程那一组的后半，也是这一路最硬的一格：两条管道、
       一个截止时间、一份五个字段的记录（code stdout stderr timedOut error）。
       跑不起来的程序照实报告（error 是 ENOENT、退出码 -1），不抛 ——
       「程序没找到」是关于世界的结论，不是脚本的错。
       参数按 MSVCRT 的规矩加引号（宽拼参），与既有的命令行切分是同一套规矩的两面。
       完整实现只在 Windows 上；别的平台交回 ENOPROC，而不是装作跑成功。
       验收在 test/c-vm.test.mjs 第二十二节：两台机器给出 0 hi 3 -1 true。

       输入那四个（key_push key_available key_read key_start）共用一条键队列：
       套件塞键、真终端读键，于是「按一个键就停」这种程序没有终端也能被断言。
       三种情形要分清：队列有键就交回队首；队列空而 stdin 是终端才同步读一次
       并按码点拆开、多余的推进队列；队列空而没有终端就立即交回空串。
       C 那台的队列有界 16 项，JS 那侧无界 —— 这一条差异写进了契约，
       不是等以后才发现。验收在 test/c-vm.test.mjs 第二十节：
       两台机器给出同一串 1 true a false true false。

       环境那九个（cwd home_dir temp_path repo_path python_path locale_current
       locale_env locale_set console_codepage）里有两个是「如实说没有」的：
       repo_path 只认设了的 HMYR_REPO（没设就把相对路径原样交回），
       python_path 只认 HMYR_PYTHON（否则交回 python 这个名字）。
       locale 只认那四套档案的名字，别的报 R0205。
       验收在 test/c-vm.test.mjs 第十八与第十九节：程序只输出形状与 locale 名字，
       不输出路径本身 —— 两台机器给出不同的串本来就是对的。

       时间那两条（now_ms sleep_ms）的落点值得单说：桌面上用
       GetSystemTimeAsFileTime 与 timespec_get，而板子上两样都没有 ——
       于是 now_ms 给 0、sleep_ms 空转，文档写明这是「没有时钟」，
       不是「时钟恰好是零」。验收在 test/c-vm.test.mjs 第十七节，
       断言形状而不断言值：钟往前走、sleep_ms(5) 交回 5、负数归零。

       终端那六个（term_size term_clear term_escape term_color term_hide term_show）
       只交回「该写什么」，不写出去 —— 所以它们是最便宜的一组，也正是
       「板子没有终端也不怕」的那一组。验收在 test/c-vm.test.mjs 第十六节：
       两台机器给出同一串 4 27 11 4 2 false 3;7H。
       term_size 在桌面上问一次控制台，问不到就给 24 行 80 列，
       与 JS 那侧 capability 的缺省值一致。

       下一格要一起做的是线程四条与那台机器的 GC，因为它们是同一个前提：
       现在 g_stack / g_base / g_cur / steps / 键队列 / locale 都是文件级全局，
       于是「另一个线程跑一个 HMYR 函数」与「GC 扫描所有活动帧」都无从谈起。
       把状态收进一个 Hmyr机器 结构（操作栈、帧链、池子、键队列、locale），
       两件事就同时成立：线程是第二个实例，GC 的根是实例里那条帧链
       加上函数表里的常量。这是这一路唯一一次结构性改动，做完之后
       thr_* 与 GC 各有自己的验收；arena 那一项按 MEMORY.txt 的三区模型另算。

       这一格的价码量出来了（2026-10-25）：vm/hmyr.c 里有三十八项文件级可变状态，
       引用合计一百二十七处（static const 不计，函数里的 static 不算）。
       量具是 tools/machine-state.mjs —— 它只数，不判断哪些该进结构。

       于是切法建议按「改动集中在一处」排，而不是按功能大小排：

         一、GC 的根先收成一个 Hmyr根（操作栈、帧链、键队列、函数表、argv）。
             改动集中在 gc_收集 一处加它的几个赋值点，而验收现成：
             c-vm 第二十四节量峰值、第二十六节量索引在收集中活着。
             这一刀不改变行为，只是把「根在哪儿」从六处散着变成一个地方。

         二、线程那半要整台机器实例化，是最后一刀。它才是把 Hmyr根 变成
             Hmyr机器 的那一步，也是唯一要动函数签名的一步。

         三、arena 在 C 那台排在两项之后，而且它有一个前提不是工程量的问题：
             它的三个字段是函数值，而这门语言没有一等函数 ——
             要落地得先定一件事，是把那三个操作改成收块参数的内置，
             还是别的形状。那是语言面的决定，不是实现的活。

    二、工具链：LSP、格式化器、嵌入、打包发布、语料生成、测试框架都还是 JS。
       它们不在「跑程序」这条路上，可以一直是工具。

       这一句现在有可执行的证明：tools/runtime-path.mjs 从五个入口
       （启动器、只当命令用的那一份、三份执行器）顺着 import 走一遍，
       闭包里出现任何工具模块就红。验收是 test/runtime-path.test.mjs（九项，
       已挂进 check-all）。2026 实测的闭包大小：十六、十一、十、三、十二个文件，
       一个工具都没碰。

       「不在路径上」与「不用搬」是两件事，账在这里分开写：

        已搬：编译（self/compile.hmyr）、打包（self/pack.hmyr）、
              求值（self/eval.hmyr + self/run.hmyr）、读（self/lex.hmyr 那六件）、
              启动（vm/hmyr.c 自己就是启动器）。于是「跑程序」这条路上
              没有 JavaScript，运行时不依赖任何工具。
              测试框架也已经搬了：self/check.hmyr 读一份清单、一个一个跑、
              按退出码汇总。它只用两件世界面（读文本、跑程序），而清单由
              node tools/check-all.mjs --list 生成，只有这一个来源。
              验收是 test/check-hmyr.test.mjs（十一项，含「真的调度得动」：
              三个快套件、三个通过、没有一行不通过）。
              嵌入也搬了：self/embed.hmyr 把一份 .hmyrb 摊成 C 源码。
              为此世界面加了一格 read_bytes —— read_text 会按 UTF-8 解码，
              而字节码文件一过就坏。它同样六处对齐，验收是
              test/embed-hmyr.test.mjs（十六项，含「数组从 HMYRB 的魔数开始」）。
              搬的时候撞到的平方级也记在那儿：加号每拼一次就复制一次已经拼好的
              全部，四万三千字节摊成二十六万字符的 C 文本，逐字节拼会顶到四吉；
              所以它先入行、再折半拼接，与 self/compile.hmyr 的 拼两半 同一个形状。

        已搬，语料生成的第二支：self/ucd-nfc.hmyr 生成 vm/ucd-nfc.h（分解、组合类、
        组合对）。真语料上跑两秒半，产物 144299 字节、4060 行，与 tools/ucd-nfc.mjs
        的产物逐字节相同（test/ucd-nfc-hmyr.test.mjs，七项）。它是 design/INDEX.txt
        那五个内置的第一个真实用户 —— 全分解要按码点回头查，而记录一次建好、元组
        拼接是 O(n²)，实测八千个键就撞步数上限。
        这一支撞到「slice 对元组切的是它写成文字之后的字符串」，于是「弹出栈顶」把
        元组变成了 "["，全分解只收六条 —— 改成递归之后才对上。

        已搬，语料生成的第三支：self/ucd-case.hmyr 生成 vm/ucd-case.h（大小写映射
        与两个属性区间，读三份语料）。真语料上三秒，产物 137722 字节、4301 行，与
        tools/ucd-case.mjs 的产物逐字节相同（test/ucd-case-hmyr.test.mjs，七项）。
        这一支把排序写成了三次方（用「按位置重建元组」做插入排序，三千条要跑六分钟），
        换成可变数组之后三秒 —— 同一个排序在前一支已经写对过，说明「可变结构用数组」
        该当成默认，不该每次重新想。
        已搬，语料生成的第一支：self/ucd-c.hmyr 从 codepoints.txt 生成两张
        C 用的区间表（字母与记号）。验收是最结实的那种对拍：两份实现喂同一段
        两千行的小样本，产物逐字节相同（test/ucd-c-hmyr.test.mjs，十一项）。
        为此 tools/ucd-c.mjs 加了可选的输入与输出目录参数，缺省行为不变。

        已搬，格式化器的第一版：self/fmt.hmyr 排的是表达式 —— 括号按优先级与结合性加，
        打印两次与打印一次一样。验收是 test/fmt-hmyr.test.mjs（十六项：六个例子的
        期望排版，加上每一条再排一次不变）。整文件排版仍在 src/format.mjs，
        它要完整语句树，那是下一步。

        已搬，整文件排版：self/fmt.hmyr 的 整文件 现在排的是整个文件，而不只是表达式。
        验收是 test/fmt-whole-hmyr.test.mjs（八项），三件事分开验：
          没有注释的文件（examples 里的 arith、over、twice）与 src/format.mjs 逐字节相同；
          有注释的文件里自举那一份把注释留下，而宿主那一份按设计丢弃并报 W0100 ——
          去掉注释行之后两边一致，所以这不是缺陷，是自举那一份多做了一件事；
          行尾的 carriage return 不会漏进输出（那一份语料本身是 CRLF）。
        为此去首尾 补了 chr(9) 与 chr(13) —— 它原来只认空格，连 tab 都写成了两个字面字符。
        工具链：全部搬完（2026-10-25 逐件核对过的账）

        这一栏原来写着「LSP、格式化器、嵌入、打包发布、语料生成、测试框架都还是 JS」。
        今天核了一遍，一件不剩了。逐件与它的验收：

          格式化器    self/fmt.hmyr        表达式与整文件都在，验收 fmtwholehmyr（8 项）
          语料生成    self/ucd-c.hmyr      区间表，验收 ucdchmyr

        这张清单现在有一份可执行的替身：tools/tooling-ledger.mjs。
        每一项要么「搬了」（必须指一个真的在 check-all 里的验收套件），
        要么「不搬」（必须写理由，而且它的文件要落在 runtime-path 那五份入口的
        import 闭包之外 —— 那是「不在运行时路径上」的可执行证明）。
        验收是 test/tooling-ledger.test.mjs（四十七项）。于是「逐项结清」这句话
        有一条命令可以核，而不是一句自述。

        搬调度器时撞到一处看起来像分叉、其实不是的事，记在这里免得再被它绊一次：
        print 自己不添换行 —— 四台机器（宿主求值器、最小求值器、字节码执行器、C）
        在这一点上一致，自举层那一支也只是转发，同样不添。
        换行是调用方的事（想分行就写 chr(10)），而 CLI 按行显示是显示层的选择。
        调度器为了好看自己补了 chr(10)，那是工具自己的排版，不是语义。

       下一格先搬测试框架那一项：它只需要 run_program 与 argv，
       而两者都已经在 C 机器上验过了。

  于是「完全独立」现在有两种读法，两种都说得清：近的那一种的世界面已经齐了，
  而「跑程序」这条路已经与工具链分开（有可执行的证明）；远的那一种的差距
  就是上面那几项，按代价排在底下。

  一条命令看今天的状态：node tools/independence.mjs。
  它把种子、世界面、工具账本、运行时路径四份证据汇成一张表，并给一行结论 ——
  结论里会明说自举层还差几格，不藏。验收是 test/independence.test.mjs（十二项）。

  入口这一层（2026-10 补）：vm/pack_seed.h 把种子摊成 C 数组（43619 字节，3653 行，
  由 self/embed.hmyr 生成），vm/hmyr.c 在桌面那一支把它编进来。于是 hmyr 自带编译器：
  一份 .hmyr 进来，cli_main 用内置种子编成字节码、再跑那一段 —— 全程不经 node，
  也不需要旁边有 bootstrap/pack.hmyrb。找种子的顺序变成「内置优先」，然后才是
  HMYR_SEED、可执行文件旁边、当前目录（那三条留给「想换一份种子」的人）。
  板子那一支不编它：那台没有文件系统，也用不到 cli_main，而几百千字节的常量会塞满 flash。
  验收是 test/self-contained.test.mjs（十二项，含「编译到一个没有 bootstrap/ 的目录里，
  跑 examples/twice.hmyr，输出正好是 hi 42 琥珀音」）。


三步（按顺序，前一步不成立就不走下一步）
--------------------------------------------------------------------

  一、能力收敛
      把散落的宿主内置按能力分组：文件、进程、终端、环境、路径。
      每一组在 SPEC 里写契约：函数名、语义、需要什么效果、拒绝时给哪个编号。
      做完这一件，「宿主是什么」就变成一份可替换的清单，而不是一堆隐形的内置。

  二、启动器还原
      把 node 那一步缩成最小能力内核：只留读文件、写终端、跑进程、取时间与环境。
      求值器逐步换成 self/eval.hmyr 那条线（先补语句层，再补记录）。
      输出与输入仍走可注入的通道——这两条优势不能为了自举而丢。

  三、自举闭环
      宿主只剩能力内核，而 hmyr xxx.hmyr 由 HMYR 写的启动器完成。
      到那时 Node 只是众多宿主之一，而不是唯一的那一个。

底线（比进度更要紧）
--------------------------------------------------------------------

  ・每条断言仍要可查。自举不换来任何「先跑起来再说」。
  ・能力边界写在明处：做不到的说做不到，不装作支持。
  ・效果声明与可注入这两条优势不许为自举让路：谁动世界谁声明，输入输出都要能被断言。
  ・换宿主时，同一份 .hmyr 的行为必须一致；不一致就是契约没写清，先补契约。

不做什么
--------------------------------------------------------------------

  ・不为了自举而放弃现有的套件。
  ・不在能力契约写清之前动启动器。
  ・不把「能跑了」当成「自举完成了」。
