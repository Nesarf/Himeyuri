全自举：38% 到 100% 意味着什么，现在离它多远
====================================================================

目标已经明确：让 HMYR 自己写的代码占全部代码的百分之百。这份文件写三件事 ——
现在的口径、沿途的障碍、以及一条能一段一段验的路线。

一、口径
--------------------------------------------------------------------

按行数算，今天的比例是 8017 / 20965，约百分之三十八：

    self/*.hmoca     32 个文件   8017 行    HMYR 自己
    src/*.mjs       28 个文件   6450 行    求值器、编译器、加载器、词法、语法
    tools/*.mjs     25 个文件   2762 行    打包、清单、发布、检查器
    vm/*.c           1 个文件   3736 行    字节码机

test/*.mjs 那 14850 行不计入，因为验收是验收，不是产品的一部分 —— 但它们的语言
也要跟着换，否则「全自举」只是产品自举、验收还在别人的引擎上。这一条写在边界里。

二、百分之百的严格定义
--------------------------------------------------------------------

绝对的一百做不到，也不该假装做得到：程序要读文件、要分配内存、要退出，这些总得
落到某个宿主上。所以这里的定义是：

    除了「读文件、写文件、分配、退出」这几项宿主口之外，仓库里没有第二套实现。

今天的 src/ 与 vm/ 都超出了这个范围 —— 它们不只是宿主口，它们是求值器、
编译器与字节码机本身。所以它们要一段一段被 HMYR 的实现替掉，而不是被「迁移」。

三、沿途的障碍，按难度排
--------------------------------------------------------------------

    一、字句法（lexer/parser）。self/ 里已有能跑的那一份，且与 JS 版逐条对齐过
       （selflex、subsetlex、subsetparse 三套验收）。这一段最接近完成。

    二、求值器。self/eval.hmoca 已经能跑，但与 src/eval.mjs 比还缺内置与效果检查的
       一些分支。stage0eval 与 minimaleval 两套验收在量它到底需要多少。

    三、编译器。self/compile.hmoca 能编一部分，hmyrcompile 那套验收在量「两套编译器
       给出同一个答案」的边界。

    四、字节码机。vm/hmyr.c 是唯一没有 HMYR 版本的一层，也是最大的一块（3736 行 C）。
       要它自举，得先有一个用 HMYR 写的 VM —— 而那件事要求「HMYR 能表达内存与指令
       循环」，也就是要先把数组与指针那类东西在语言里做扎实。

    五、宿主口。最后剩下的是 file、process、time 那三组内置 —— 它们不是「还没搬」，
       是「本来就该在宿主上」。这一层不算欠账。

四、路线：四段，每段都要有验收
--------------------------------------------------------------------

    第一段  让 self/ 那一套跑通全部验收（不是跑通一部分）。判据：把 src/ 那一份
            换掉之后，156 套里有多少套还是绿的。今天这个数要量出来，作为起点。

    第二段  把「换掉之后还绿的」这一批一套一套扩到全部。每扩一套，src/ 里就少一段
            被用到 —— 用 --affects 看得到是谁还在用它。

    第三段  字节码机：先让 HMYR 写的 VM 跑通 test/bytecode.test.mjs，再接 C 那台的
            位置。这一段最长。

    第四段  收尾：src/ 与 vm/ 只剩宿主口。那时比例才是接近百分之百，
            而剩下的几千行要写清「为什么它们必须留在宿主上」。

五、现在就该做的两件小事
--------------------------------------------------------------------

    一、量第一个数。把 self/ 那一套（self/*.hmoca 的求值器与编译器）真的接到
       check-all 的一个开关后面，跑一次，数出「换掉之后还绿多少套」。没有这个数，
       后面四段都是空谈。

    二、别让比例悄悄退回去。可以在 design 里放一行、或者在账本里加一条，
       记录每次的比例。数字不动的时候，人不会注意到自己在往回走。

两个数都量了。它们各自是「换掉 src/ 之后还绿多少套」的下界，合起来把起点定得更窄。

第一件：求值这一层，十四段程序全部对上（14 / 14）。量具 tools/self-coverage.mjs，
挂进 check-all 叫 selfcov。这个数说的是「self/run.hmoca 那条全 HMYR 的链，在十四段
小程序上与 JS 版给出同样的值」，不是「换掉 src/ 之后还有多少套是绿的」。

第二件（2026-10-24）：加载这一层，二十七份真实源码全部认得下来（27 / 27）。
量具 tools/self-loader.mjs，挂进 check-all 叫 selfload —— 默认子集二十八秒，
加 --全部 跑五十四份（根目录二十一份加 self/ 三十三份），五十五秒。

判据只是形状：两边都说 ok，或两边都说错。它量的是「切词与搭树认不认得真实文件」，
比「值对不对」更早一步，也更容易在换 loader 的时候先坏掉 —— 所以它值得常驻。
样本里二十一份是根目录的库文件（pixel、surface、json、term …），六份是自举的核心
（lex、chain、stmt、body、eval、run）。全部五十四份的那一次实测也是 54 / 54。

仍然没量的是那个真正的起点数：换掉 src/loader.mjs 之后，一百五十八套里还有多少套是绿的。
它需要 loader 的实现本身，而今天 self/ 那一条链只到「认出源码」，还没到「按 import 递归、
把诊断装成宿主 loader 那个形状」。所以第一段还差一件事：把 self/ 的加载链包成一个与
src/loader.mjs 同形状的东西。那件事做完，这个数才量得出来。

起点数的一个上界（2026-11-01 量）

那个数还没量，而它的上界可以量，两行命令：

    node tools/impact.mjs --affects src/loader.mjs   → 直接一百零一套，无关七十六套
    而 test/ 与 tools/ 里同时用 loadUnit 与读 .ast 的只有三个文件
    （读 .ast 的共七个，其中 parser.test.mjs 是专门验宿主解析器形状的那一套）

所以：一百零一套里，最多九十八套不依赖 ast 的形状 —— 它们只要「加载顺序对、
程序能跑」，而这两件 self/ 那边已经对齐（selfload 的 27/27、selfmod 的 order 与错误码）。
真正要跟着形状走的是三套，加上 parser 那一套（它本来就该验宿主那一份）。

这个上界把第一段的工作量说小了：门槛不在「全面对齐 ast」，而在那三套。
而它仍然只是上界 —— 真正换掉之后会掉多少套，得先有那个适配层才量得出来。

而「形状敏感」到底几个，可以再量一层（2026-11-01，同日）

一百一十八个用 loadUnit 的文件里，只用 order 与 modules 的是一百一十五个，
还要读 .ast 的只有三个。

所以适配层的门槛比上一段说的还窄：把「加载顺序对、程序能跑」对齐，
一百一十五个文件就能走；真正要等 ast 形状的只有三个。

这条读数把第一段的形状从「一个适配层」改成了「一个只对齐顺序与错误码的适配层，
外加三处形状工作」—— 而 self/ 那边这两件都已经对齐（selfmod 的 order 与错误码、
selfloa 的 27/27）。

适配层的两条通道（2026-11-01 试过）

一、宿主启动器能跑自举层的模块。probe-load 里 import ../self/lex.hmoca 并调它的
    pub 函数，两侧都是「词数=13」—— 默认路径与 C 机器一字不差。

二、import 一个有 main 的自举模块时，后到的 main 赢。probe-load2 里 import
    ../self/run.hmoca 并写自己的 main，跑出来的是探针那一行。所以适配层可以借
    run.hmoca 并拥有自己的入口 —— 合并规矩是「后到者覆盖先到者」。

三、pub 包装也编得过：run.hmoca 加了 加载顺序公开 与 拼行从，函数数从五十九到
    六十一（selfcompile 那条期望跟着改了）。

四、而执行时卡在 call depth exceeded (500)。它连「没有 import 的文件」也一样，
    所以不是 import 递归。那两个函数里谁在递归还没缩出来 —— 这是下一步的第一件事。

五、三档读数（同日，缩了一步）

    不存在的文件               正常返回「错 E0302 路径」
    存在、无 import、一行       500 层
    存在、无 import、两百多行   超时（lex.hmoca，十秒不动）

    所以递归不在「找不到文件」那条路上，而在「真读到内容之后」那一段。而那一段里
    四个函数都已经读过：拆行的 while 两支都推进、去首 每层剥一个字符、引号里 的两个
    下标都有边界、slice 现在也截终点。也就是说，五个候选里没有一个是明显的死循环。

六、pub 是包内可见，而这一点先解释了一次假失败（同日）

    把 只解析 包成 只解析公开 之后，放在 examples/ 的探针仍然报「没有这个函数」；
    同一份探针挪进 self/ 就通了，打出「只解析 -> ok 1」与「只解析两函数 -> ok 2」。

    所以 pub 的作用域是包内，而 examples/ 与 self/ 是两个包 —— 适配层放在 self/ 里
    才叫得到 加载顺序公开（adapter.hmoca 就在那儿，所以它一直能调）。

    而这一条同时排掉了 只解析：它单独跑得好好的，一段两行源码与两段声明都认得下来。
    500 层因此在 加载走 的其余部分 —— 拼路径、目录部分、含路、拼行从 四者之一，
    或者 加载多 那一层的递归条件。这是下一步要读的地方。

七、读的时候撞见一处重复定义（同日）

    run.hmoca 里 是路径 出现了两次：

      127 行   ./  ../  盘符（第二字符是冒号）  /
      612 行   ./  ../  是绝对

    而合并的规矩是后到者覆盖先到者，所以 152 行 加载多 里那一句实际走的是 612 行
    那个版本 —— 判据比前一个窄（少一条「盘符」）。这不是 500 层的成因（board-spec
    一个 import 也没有，两版本对它给出同一个答案），但它是一处真隐患：
    同一份文件里两个同名函数，而先写的那个悄悄失效。

    要修的方向有两个：合并时把重复定义当成错（更安全，但会立刻暴露别处的重复），
    或者现在就把 127 行那个删掉（更小，但 612 行那个少了盘符那条判据）。

八、500 层的真凶是「宿主太浅」，而 C 机器也有它自己的门（同日）

    一、根因找到了，它不是加载器的 bug。

       只解析 对一份 62 行的真文件（board-spec）在最小求值器上直接超时；
       而在同一台机器上处理一两行的源码时，它立刻交回 ok。

       所以 加载走 对每个文件都要过的这一步，在最小求值器上根本跑不动：
       词法器与声明解析都是「每个 token 一层递归」，而宿主的上限是五百层递归
       与十秒。board-spec 六十二行、几百个 token，两层限制一起踩。

       于是「adapter 卡在 500 层」这件事的正确说法是：自举层的深递归撞上了
       最小求值器的浅栈。加载器本身没有错，selfload 那 27/27 之所以能过，
       是因为它跑在别的机器上（栈够深）。

    二、那就换机器跑，而换的时候撞到 C 机器的门。

       --host-eval 走不通：那条路缺 cwd 内置（stage 0 的边界）。
       于是改走 C 机器：把 adapter 编成字节码，hmyr.exe 直接跑。

       结果报 HMYR-R0211 cannot read 'D:/himeyuri'，而 print_err 那一行一行都没打出来
       —— 说明错误发生在 main 之前，不在 adapter 里。

       C 机器的命令行约定读过：hmyr.exe <目标文件> <参数…>，第一个参数是要跑的程序。
       而 probe-argv 用同样的调用方式跑通了，打印出 len=3、[0]=字节码路径、
       [1]=D:/himeyuri、[2]=examples/board-spec.hmoca —— 参数传递这一层是好的。

       所以还差的是一件：为什么一份带 file 效果的字节码，在 C 机器上会在 main 之前
       就去读一个目录。这一条还没验证，下一步用「最小字节码 + file 效果」单试一次。

    三、这一轮确定的与不确定的分开写在这里。

       确定：最小求值器跑不动真文件（超时，不是逻辑错）；C 机器的 argv 形状与
             最小求值器一致；--host-eval 缺 cwd。
       不确定：C 机器上那段 cannot read 的出处。

九、而 C 机器的 file 效果本身是好的（同日）

    最小的一问：一个只 read_text 一个确定存在的文件的程序，编成字节码交 C 机器跑。

      默认路径   长度=350
      C 机器     长度=350

    两侧一字不差。所以 adapter 那个 cannot read 不是 file 通道的问题，而 argv 的
    形状也验过是对的（[1] 目录、[2] 相对）。

    于是范围又窄了一格：问题在 adapter 的 main 与「读文件」之间那一段。
    下一步把它缩到最小 —— main 里只有一句 print，然后逐句加回来，每加一句编一次
    字节码（约十秒），四五次就能指到那一句。

第三件（2026-10-24）：模块加载的语义也量了。self/run.hmoca 的 加载走 照宿主 loader
文件头那三条承诺实现 —— import 真的加载、同一个文件只加载一次、环引用报 E0301；
另外引的文件不在就报 E0302（宿主也是这个码）。顺序取后序，于是 order 逐项相同。

判据是两件事：四棵真实 import 树（sign、release、package、verify）的 order 逐项一致；
以及两个构造出来的场景 —— 缺一个 import、两个文件互相 import —— 两边报同一个码。
量具 tools/self-load.mjs，挂进 check-all 叫 selfmod（约二十八秒）。

于是「加载」这一层有两半都对齐了：认不认得（selfload，27 / 27），以及按什么规矩加载
（selfmod，order 与错误码）。还差的一半是树的形状：
宿主 loader 交出的 ast 是 subset-parse 那一套（Module、Import、Fn、Block、Literal …，
带 line 与 column），而 self/chain.hmoca 交出的节点是另一套（num、str、name、bin、call、
field、index、tuple、record、unary —— 小写单字、不带位置、也没有声明与语句层）。
两套名字不同、字段不同、层次也不同。

所以「换掉 src/loader.mjs」真正的门槛在 ast，不在加载逻辑：要么让 self 那边产出
subset-parse 的形状，要么让宿主这一侧接受两种形状。在那之前，「多少套能换」这个数
只能算到「只用 loadUnit 的 ok」为止 —— 而验收里的套件几乎没有这样用的，它们都要
runUnit，也就都要树。这一段的工作量比上面两件加起来大，且它是一个形状问题，
不是一批 bug。

第四件（2026-10-24）：位置。self/lex.hmoca 的 scan 与 scan_lines 现在给每个 token 带上
line 与 column —— token 本来就带着字符偏移，所以这一遍只是一次线性扫描；位置在词法这一层
有了，后面的节点才有东西可抄。这一件不改任何现有语义，只多两个字段。

判据是逐项比：六段源码（一行赋值、多行函数、注释与空行、字符串与转义、中文标识符、
紧挨着的符号）在两边交出的 token，词形与位置逐项相同（4、15、10、4、4、14 个 token）。
量具 tools/self-positions.mjs，挂进 check-all 叫 selfpos。

三处还没对齐，一起记在这里，免得下次当成新发现：
  一、kind 的命名：宿主分 keyword 与 ident，self 一侧一律 ident（关键字也在 ident 里）；
  二、换行 token：宿主保留 newline（语句边界靠它），self 的 scan 不产，scan_lines 才产；
      eof 也一样只有宿主那一侧有；
  三、字段名：宿主的 token 用 type 与 value，self 用 kind 与 text。

位置之所以先做，是因为它只加字段、不改语义，而后面每一步都要它：一个说不出第几行的
诊断，没法与宿主的诊断对照。

第五件（2026-10-24）：节点位置。self/chain.hmoca 的表达式节点现在带 line 与 column ——
num、str、name、err、bin、unary、call、field、index 处各从它那个 token 抄一次。
这一件同样只加字段，不改语义。

一处照抄来的怪处值得记：宿主的 Field 记的是字段名之后那个 token 的位子（subset-parse 的
注释写着「照抄而不是改对」，为的是两棵树能逐节点核）。这一侧的 token 流不留换行，所以等价
写法是「名字的列 + 名字的长度」—— 名字后面紧跟的就是那个位子。不照抄，两棵树永远差一列；
照抄之后差得正好为零。

判据：四段样本（字面量与优先级、标识符与二元、一元负号、调用与字段）里，self 交出的每一个
节点位置，宿主树上都有对应位置的节点 —— 十八个节点，十八个都对上。量具 tools/self-nodes.mjs，
挂进 check-all 叫 selfnodes。

还没做的：语句层（let、var、return、assign、expr、if、while）还没有位置；声明层（Fn、
Block、Module、Import）在 self 这一侧还没有节点 —— 宿主的树里有，这边只是一组元组。
这两条是「形状」剩下的主要工作。
第六件（2026-10-24）：语句层也带位置。self/stmt.hmoca 的 let、var、return、assign、expr、
if、while 各从它该抄的那个 token 抄一次 —— 关键字节点抄关键字，赋值抄名字，表达式语句抄
语句起始那个 token，与宿主那边同一个规矩。

判据扩到六段样本（多了 if 与赋值、while 与赋值），五十个节点位置全部在宿主树上找得到。
selfnodes 从六项长到八项。

至此表达式层与语句层的位置都齐了。剩下的是声明层：宿主的树里有 Module、Import、Fn、Block
四个节点，self 这一侧还是元组 —— 那是「形状」最后也是最实的一块。它一动，两侧的节点数才
会真正相等；在此之前的比较都只能问「self 的位置宿主有没有」，还不能问「节点对不对得上」。
第七件（2026-10-24）：声明层。self/run.hmoca 的 造模块 把 parse_decls 的元组包成
Module → Fn → Block 三层 —— 宿主 loader 与 runUnit 认得的那三种东西。解析本身没动，
包一层是为了让两侧的节点数能对上。

为此 parse_decls 的元组从四件变成六件（末尾加行与列）。位置加在末尾，所以读 选[2] 与
选[3] 的老代码一行都不用改 —— 改形状的时候先想清楚谁在读它，这一条是故意的。

判据：六段样本，两边的声明逐项相同（名字、行、列、体的种类、体的语句数）。两边都是
一个 Module 加若干 Fn，每个 Fn 的 body 是 Block，语句数一样。selfnodes 从八项长到十四项。

到这里三层都齐了：表达式层、语句层、声明层。两侧现在能按节点逐一对，而不是只问
「这个位置你那边有没有」。下一件是把比较从「描述相同」推到「整棵树逐节点相同」——
那需要一张映射表（num 对 Literal、name 对 Ident、bin 对 Binary …）与一份沿树走一遍的量具。
第八件（2026-10-24）：整棵树并排走。tools/self-tree.mjs 把 造模块 交出的 Module 与宿主的
ast 放在一起走：先过一张映射表（num 对 Literal、name 对 Ident、bin 对 Binary、let 对 Let、
expr 对 ExprStmt …），然后每个节点比三样 —— 映射后的种类、位置、子节点怎么对。走到第一个
对不上的地方就停下，把两边的路径一起报出来：要修的是第一处，不是「有 N 个不同」。

为此补了一处形状：宿主的语句层把 if 与 while 包成 ExprStmt（它把 if 当表达式，语句层再包
一层）。这一侧在包装层跟着包，解析与求值两条路一个字都不动 —— 所以这处改动碰不到跑起来
的东西。

判据：六段样本整棵树逐节点相同，分别走了 9、11、8、8、16、12 个节点；种类、行、列、子节点
的对法都一致，if 与 while 内层语句数也对上（宿主那边是 Block，这边是元组，但两边必须数出
同一个数）。挂进 check-all 叫 selftree。

到这里两侧第一次做到「同一段源码，两棵树逐节点相同」。还没比的是值：Literal 的 value、
Ident 的 name 这些字段。今天比的是种类、位置与结构；载荷是下一件。
六、这条路线不算欠账的部分
--------------------------------------------------------------------

    test/*.mjs 的移植不在第一到第四段里。它跟着产品走：产品换成 HMYR 了，
    验收自然也该换成 HMYR 写的。但那是最后一步，不是第一步 —— 现在换，
    等于在没有尺子的地方量长度。


七、两个名字：Hiou Rengo 与 Yunooka
--------------------------------------------------------------------

路线的四段是工程顺序，但「百分之百」这个目标本身需要两件产品来承载 ——
否则它只是一串「把某段代码重写掉」的任务，没有形状。所以给它们名字：

    Hiou Rengo（緋凰·恋語）   完全态 SDK
        出自小一孁こはね那把等身大太刀的名字。它装的是「用 HMYR 写程序所需要的
        一切」：标准库、工具链（打包、清单、发布、检查）、以及给宿主留的那几道口
        的绑定。四段路线里的第一、二段主要落在这里。
        落点：D:\Hiou Rengo（2026-10-24 由用户建好，目前是空目录）。

    Yunooka（湯の岡）          完全态 OS
        出自她所属的学寮都市「カピラ」的寮名。它装的是「跑 HMYR 所需要的一切」：
        引导、内存、进程、文件、时间，以及那个还没有 HMYR 版本的字节码机。
        四段路线里的第三、四段主要落在这里。
        落点：D:\Yunooka（2026-10-24 由用户建好，目前是空目录）。

两件合起来，才是「百分之百」的完整说法：Hiou Rengo 负责「写」，Yunooka 负责「跑」。
只做到前者，是能自举但跑不动；只做到后者，是能跑但没有东西可写。

命名不只是装饰，它给了一个判据：当某段代码说不清该归 SDK 还是 OS 时，问一句
「它是给写程序的人用的，还是给跑程序的人用的」，答案通常就出来了。
宿主口归 OS，其余归 SDK —— 而宿主口本身永远要在某个真实的操作系统上落地，
Yunooka 能把它压到多薄，就是这条路线的最终刻度。
第九件（2026-10-24）：载荷。并排走除了种类、位置、子节点，现在也比每个节点带的那个字符串与
字面量的值：运算符（bin、unary）、名字（Ident、Let、Var、Assign、Fn）、字符串字面量
（两边都存解好的值）、以及数字字面量 —— 数字多一步，因为这一侧存的是源文本（"0x1f" 五个字符），
宿主存的是 31，所以走之前先做一次「源文本 → 数值」。

样本从六段扩到七段（加了带转义的字符串与十六进制数字）。七段全部整棵树对上，
走的节点数是 9、11、8、8、16、12、11。

到这里「两棵树一样」这句话的适用范围可以写清了：种类、位置、结构、运算符与名字、字面量的值。
还不能比的是宿主有而这一侧没有的节点（Import、TypeRef、合约三项）—— 它们要等对应的语法
在自举那一侧先被认出来。
第十件（2026-10-24）：Import。造模块 现在从 token 流里找出 import 行，包成 Import 节点
（path 加位置；alias 与 rev 留空，因为这一层的语法还不认它们 —— 所以量具只比 path 与位置，
注释里把这件事写明，而不是假装那两项也对得上）。

这里有一个真坑，值得单独记：去导入 把 import 行整行删掉，于是其后每一行的行号都往上移，
同一段源码在两边报出不同的位置（这一侧说 Fn 在 1:1，宿主说 3:1）。修法不是补偏移，而是换输入：
解析用原始 token 流，只有「行首是不是声明」那一个判断看剥过的文本。

判据：八段样本整棵树逐节点相同（走了 9、11、8、8、16、12、11、7 个节点）。
第十一件（2026-10-24）：门前的试推。把 造模块 交出的 Module 直接交给宿主的 Runtime：
registerModule 一次就收（它只读 decls 里的 kind 与 name），callFunction 则在第一句就停 ——
"cannot execute a statement of kind return"。

差的东西是一层形状适配，清单很短：

    kind 的大小写        let 对 Let、return 对 Return、expr 对 ExprStmt …
    Literal 的三件套     type/value/raw —— 这一侧只有 text，数字还要解析成值
    If 的 then/otherwise 要包成 Block（宿主的 execBlock 读 block.statements）
    Return 的空值       要用 null（这一侧是 nil 节点）
    params              要从名字变成 {name, fallback}

补上这层适配之后，五段程序（常数、let 与二元、if 分支、while 累加、十六进制）都由宿主的
求值器跑出正确的值。量具 tools/self-handoff.mjs，挂进 check-all 叫 selfhandoff。

要说明的是：这层适配写在工具里，是验证用的，不是产品代码。它证明的是「两边差一层翻译」，
而不是「已经换成功了」。真正的换法要么让 self 直接产出宿主那套名字，要么让宿主接受两种形状。
今天量到的是：翻译的清单就是上面那五条，没有隐蔽的第六类。
第十二件（2026-10-24）：名字统一。走的是「甲」那条路 —— 让 self 直接产出宿主那套名字，
而不是在工具里做一层翻译。改的是九个文件：chain、stmt、eval、compile、fmt、pipeline、sig、
run、parse。节点从 {kind: "let"} 变成 {kind: "Let"}、{kind: "bin"} 变成 {kind: "Binary"}，
num 与 str 合成 {kind: "Literal", type: "int" | "string"}（求值器按 type 分派）。

这一改，工具里那层适配退了一半：selfhandoff 的适配器从「改名字 + 改字段」缩成「只改字段」；
selftree 的映射表整个删掉（种类直接相等）。剩下没对齐的只有字段：Literal 的 value/raw、
If 的 then 包 Block、Return 的空值用 null、params 的形状。

顺带抓到两件：

  一、批量替换漏了 run.hmoca 里 n.kind == "if" || n.kind == "while" 那一处判断。症状是 Block
     的语句层不再包 ExprStmt，selftree 立刻红 —— 而它红得对，因为那时 self 与宿主的语句层
     确实差了这一层。
  二、selfcompile 期望的函数数过期了：lex 26 对 27、run 32 对 43。那不是改名气的，是这几轮
     新增的函数（补位置、加载语义四件、解析与形状七件）攒出来的。数字随规模走，那套件的
     注释里早就写着这一条。

九套自举与编译套件全绿：selfcov、selfload、selfmod、selfpos、selfnodes、selftree、
selfhandoff、selfcompile、hmyrcompile。
第十三件（2026-10-24）：字段对齐。名字统一之后，包装那一层（造模块）又翻了三处字段，
让 self 交出的树更接近宿主能直接吃下去的样子：

    params     名字字符串 → {name}（不写 fallback 就是「没有默认值」——不写比写一个假的干净）
    If         cond → condition，then 与 otherwise 包成 Block
    While      cond → condition，body 包成 Block

三处都做在包装层，解析与求值两条路仍然不动：求值器读的还是 cond 与语句元组。

工具的适配器因此只剩三件：Literal 的 value/raw（要把文本算成值）、Return 的空值（nil 对 null）、
以及 Ident 的 text → name 这一类字段改名。self-tree 除了改读新字段名之外无事可做 ——
一次对齐从外面看起来就该是这样。

又一次被 selfcompile 抓到：run.hmoca 从 43 个函数变成 44（新增 转参数们）。这套件的固定数字
今天第二次报红，两次都不是它错 —— 它报的正是「规模变了」。
第十四件（2026-10-24）：最后的翻译搬进 HMYR，适配器归零。

三件翻译从工具搬到包装层（造模块 与它的助手）：

    Literal 的 value/raw   解析字面量文本。十进制走 数到（它认得小数与指数），
                           0x/0b/0o 走新写的 按基读 —— 不能走 to_int，它只认整数的写法，
                           '0x1f' 会直接抛 R0208
    Ident 的 text → name
    ExprStmt 的 value → expr

另外空 return 不再带 value 字段：宿主读出来是 undefined，与它自己的 null 同效，
而这一侧本来就没有 null 可写。

搬的时候撞了两次：
  一、翻表达式 构造 Literal 时漏了 text，而两个工具还在读它 —— 一边报 NaN、一边跑出 null；
  二、ExprStmt 换了字段而 self-tree 与 self-handoff 都还读 value，一红一停。

现在 tools/self-handoff.mjs 只剩两个动作：registerModule，然后 callFunction。它问的问题也换了：
不问「适配之后能不能跑」，而问「不做任何适配，宿主一口吃下去能不能跑」。五段程序
（常数、let 与二元、if、while、十六进制）各自跑出期望值。

九套自举与编译套件全绿。
第十五件（2026-10-24）：整棵 import 树，一次造完。

加载走（递归、去重、环拒绝、后序）与 造模块（把一个文件的形状造出来）本来是两条链：
一条管「谁先被读到」，一条管「那一个文件长什么样」。宿主 loader 是把这两件合成一次的，
所以 造整棵 也合成一次 —— 交回一串 Module，按依赖顺序排。

判据做在一个临时工程上（lib.hmoca 提供 double，main.hmoca 引它并用 21 调它）：
造出两个 Module 且依赖在前；两个 Module 依次登记进同一个 Runtime 之后，main 跑出 42。
跨模块调用能成立，是因为宿主的函数表本来就是扁平的 —— 这一点在 loader 第一次写的时候就写清了。

selfhandoff 从 10 项长到 12 项。

到这里，「换掉 src/loader.mjs」缺的三件都齐了：形状（Module、Fn、Block、Import）、
规则（order 与错误码）、以及一次把整棵树造出来的入口。剩下的是把这三件接到真实的测试上 ——
那是下一件，也是「多少套能换」这个数第一次量得出来的时候。
第十六件（2026-10-24）：第一套真的换了 loader。

tools/self-bridge.mjs 是一座同形状的桥：loadUnit 与 runUnit 的签名不变，里面换成
self/run.hmoca 的 造整棵。引导那一层还得借宿主 —— 要跑 HMYR 写的加载器，总得先有个东西
跑它 —— 但从「读 .hmoca 文件、搭出树」这一步起，做主的已经是 HMYR 自己：递归、去重、
环拒绝、后序。

换了两套：

    selfpos    7 项，与宿主 loader 时一样全过
    selfcov   14 / 14，与宿主 loader 时一样

代价看得见：selfcov 从半秒变成四十多秒 —— 每次 loadUnit 都要先跑一遍 造整棵，而 造整棵 是
HMYR 代码、跑在宿主求值器上。那是一个数，不是一句结论：求值器也换过去之后它该降，加缓存则
能更早降下来。

换的过程中暴露了四处真正的差异，都是「这边没说清、那边只能猜」那一类：

    一、语法错的节点缺位置（越界时连 token 都没有）—— 包装层改成缺就填 0，而不是让一次
        缺字段把整棵树造失败；
    二、true 与 false 在这一侧是标识符，在宿主那边是字面量 —— 不转的话宿主会去找一个叫
        false 的名字，报 R0104，而那句话听起来像拼写错误；
    三、记录字面量里的字段值没有翻 —— 宿主于是去找一个叫 undefined 的名字；
    四、行首是声明 只看第一行，而 lex.hmoca 以注释开头，整份被当成裸语句包进 fn main。

四条都在包装层修好，解析与求值两条路仍然不动。
第十七件（2026-10-24）：扩面，以及代价。

把剩下四个自举工具也接到桥上，逐个跑：selfnodes 14 项通过、selftree 1 项通过、
selfhandoff 12 项通过。两套换不了 —— selfmod 与 selfload 本身就是「两边对照」：
它们拿宿主 loader 比 HMYR 的加载链，两边都成了 self 就没有对照了。换上去之后 selfmod 立刻
报「宿主报 E0301」失败，而它报得对。

代价也量出来了：走桥之后 selfnodes 从 0.8 秒变 71.8 秒，selfcov 从半秒变 72.5 秒 ——
每次 loadUnit 都要用 HMYR 写的加载器重走一遍整棵树，而它跑在宿主求值器上。五套各付一分多钟，
全量就从三分钟变七分钟。

所以做了取舍：

    selfpos      留在桥上 —— 它只加载 lex.hmoca（两百来行），六秒，成本可接受；
                 它是「真实套件真的走 HMYR 的 loader」这一条的常驻证据
    其余四个     恢复宿主 loader —— 它们的价值是比两边的产出，走桥不改变结论却要付一分多钟
    selfbridge   新加的桥专项验收（8 项，约 13 秒）：同一个文件两边都认得、函数名一模一样、
                 桥造的 Module 能跑、整棵 import 树的顺序一致、找不到的文件如实说

于是「换掉 src/loader.mjs」这条路今天的状态是：桥成立、有自己的验收、一处真实套件在用它。
还欠一件 —— 让 HMYR 写的加载器不再比 JS 写的慢七十倍。两个方向：把 造整棵 编成字节码跑
（vm 比解释器快一个量级），或者先把求值器换过去。
第十八件（2026-10-24）：甲路撞在一块更硬的地方 —— 尾调用。

把 self/run.hmoca 编成字节码：167 个函数、11135 条指令、67 KB，编得很干净。快也确实快：
造整棵 在字节码机上 0.33 秒，在解释器上要一到两秒。

但它跑不起来。深度一过 4000 就撞 JS 栈（3000 抛、4000 过、12000 抛，边界不干净），
而在桥这样的调用深度里 4000 也不稳。

原因不在字节码，在一条还没补的优化：解释器把尾递归吃掉（src/eval.mjs 的 TailCall），
字节码机老实压栈。而 tokenize 是「每读一个 token 递归一次」—— lex.hmoca 一千多个 token
就是一千多层。这一千层在解释器里是常数栈，在字节码机里是真栈。

于是这件事被重新定性了：它不是「换个配置就快七十倍」，而是「虚拟机缺尾调用」。
补上它要动 bytecode.mjs（编译时标出尾位置）与 vm.mjs（执行时复用帧），是一套独立的活。

今天的处置：桥走回解释器（慢但稳），字节码产物不入库 —— 一份用不上的产物摆在那里，
只会让人以为它已经在跑。生成命令留在注释里，等尾调用补上再用。

这一件没有变快，但它把一个「大概要优化」换成了一个「缺哪一条优化」。这种账要记清楚。
第十九件（2026-10-24）：补上尾调用，字节码那条路通了。

改动在 src/vm.mjs：CALLF 的下一条指令是 RET 时，换掉这一帧而不是压新的 —— 槽、效果集、
指令指针与栈都重来，深度不变。这就是解释器里那条规矩（TailCall）搬到显式栈上。

为什么非要它：tokenize 是「每读一个 token 递归一次」，lex.hmoca 一千多个 token 就是一千多层。
解释器把它吃成循环，字节码机老实压栈 —— 同一个程序在一边是常数栈，在另一边是真栈。

补上之后，造整棵 在字节码机上 0.13 秒跑出结果（深度 2000、4000、12000 都过），
桥（tools/self-bridge.mjs）现在默认走字节码：selfpos 从 6 秒变成 0.66 秒。

顺带修的两件：

    一、桥忘了拆 vm.调用 的返回包装（{ok, 值}），于是 树.模块们 永远是 undefined；
    二、字节码机交回的是它自己的类记录与类元组，宿主的 Runtime 只认普通对象与数组 ——
        桥里加了一层深转，量的是模块树，不随程序规模走。

也随之改了两处上限：test/bytecode.test.mjs 的函数数（151 到 173）与指令数上限（一万到一万二），
test/c-vm.test.mjs 的内存峰值界线（256 到 320 兆）。两处都不是宽容，是自举层确实长大了：
加载器那一串搬进 self/run.hmoca 之后，C 那台跑它的峰值从两百出头涨到两百九十上下。

runtime/run.hmoks 从此入库（67 KB）。它会过期，所以 selfbridge 里钉了一条：字节码不能比
self/run.hmoca 旧 —— 旧了桥会静默退回解释器，而套件该替人记住这件事。
第二十件（2026-10-24）：五套真实套件走 HMYR 的 loader。

字节码通了之后，把 selfcov、selfnodes、selftree、selfhandoff 也接到桥上 —— 它们之前走桥
各要七十秒上下，现在各 3.5 到 3.9 秒。加上一直留在桥上的 selfpos，一共五套。

三个数字放在一起，这件事的形状就清楚了：

    宿主 loader         各 0.5 到 0.8 秒
    桥（解释器）         各 70 秒上下
    桥（字节码）         各 3.5 到 3.9 秒

桥仍比宿主慢五倍上下 —— 它毕竟是「用 HMYR 写的加载器跑在宿主求值器上」，而那五倍里没有一处
是含糊的。但七十秒变成三秒半之后，「真实套件走自己的加载器」就不再需要特意挑一套来演示了：
它已经是默认形状（selfload 与 selfmod 除外，它们是对照本身）。
第二十一件（2026-10-24）：量「多少套能换」，顺手补上改名的漏网。

tools/loader-swap.mjs：把每个套件的 import 从 src/loader.mjs 换成桥，复制到 swap/ 跑一遍。
绿的就是换得动的。第一次跑出 103 处引用，十几分钟，一片红。

第二十六件（2026-10-24）：工程地图 —— 改一个文件，跑哪几套。

第二十八件（2026-10-24）：桥的代价 —— 为什么它现在不能做默认。

tools/bridge-cost.mjs 把两条路的同一份文件各卡一次表（中位数，三次）：

    样本                宿主 loader     桥          倍数
    locale.hmoca            1.1 ms     44.4 ms      38.7
    color.hmoca             1.3 ms     37.6 ms      28.0
    json.hmoca              3.5 ms    332.7 ms      95.0
    self/run.hmoca         16.4 ms   2986.8 ms     182.5
    examples/demo.hmoca     0.3 ms      7.4 ms      24.1

桥的引导（读 self/run.hmoca 那六份，一次性）是 3205 ms。

结论分两层。第一层：这个数量级不适合做默认 —— 一个普通程序加载要几十到几百毫秒，
而 self/run.hmoca 那种带整棵 import 树的要三秒。第二层：慢在哪里是很清楚的 ——
桥的每一毫秒都花在「造整棵」上，而那是 HMYR 代码跑在宿主求值器上。把它编成字节码交给
vm 跑，或者干脆交给 C 那台，这条线才谈得上做默认。

所以 92 / 95 这个数说的是「换得动」，不是「该换」。两件事要分开记账。
第二十九件（2026-10-24）：换执行器不解决慢 —— 一个被数据推翻的假设。

上一件里我写「把它编成字节码交给 vm，或者交给 C 那台，这条线才谈得上做默认」。尾调用补上之后，
把桥切成字节码路径，同一张表重量了一遍：

    样本                宿主 loader     桥（字节码）   倍数
    locale.hmoca            1.1 ms     49.2 ms       45.3
    color.hmoca             1.0 ms     37.6 ms       37.0
    json.hmoca              3.7 ms    343.2 ms       93.4
    self/run.hmoca         16.0 ms   3011.5 ms      188.5
    examples/demo.hmoca     0.3 ms      7.1 ms       27.9

与解释器那一路（44.4 / 37.6 / 332.7 / 2986.8 / 7.4）在同一个量级，有的还略慢。

所以慢的地方不在解释循环。字节码机把记录存在 Map 里、元组包成类，跨层交换要一次次搬；
而「造整棵」这份 workload 的绝大部分时间花在造记录、造元组、以及最后那次深转上，不在读指令。
换执行器省不下这些。

这个反证比原来那句推断值钱：它把「换个更快的执行器」从待办里划掉了，剩下的是数据形态本身 ——
要么让造整棵 直接产宿主形状（少一层深转），要么承认这条线只做可选路径、不做默认。
第三十件（2026-10-24）：深转也不是瓶颈 —— 第二个被推翻的假设。

第二十九件把「换执行器」划掉之后，剩下的话是「让造整棵 直接产宿主形状，少一层深转」。
tools/bridge-share.mjs 把这两段拆开量（三次取中位，毫秒）：

    文件             只调造整棵     走完整 loadUnit    包装部分
    locale.hmoca        53.2          54.4            1.2  （2%）
    json.hmoca         377.8         345.3          -32.5  （噪声）
    self/run.hmoca    3044.4        3055.0           10.7  （0%）

包装（深转、诊断、别名）几乎不占时间。慢的全部在「造整棵」里面 —— 也就是 self 的
lex/chain/stmt/body 那一串在造记录、造元组。

于是两条假设先后倒下：换执行器没用（第二十九），减少深转也没用（这一件）。
剩下的只有一条路：让解析器本身更快 —— 而那件事的代价不是改桥，是改语言实现的核心。

所以「桥做默认」这件事的答案已经清楚了：不是现在。92 / 95 说的是它能当一面镜子，
照出两边哪里不一致；当默认要的是另一个量级的东西。
第三十一件（2026-10-24）：求值器跑在字节码机上，并且给出同样的答案。

tools/self-vm-eval.mjs 把 runtime/run.hmoks 装进虚拟机 —— 也就是说自举那一层的 lexer、chain、
语句解析、body 解析与求值器全都是字节码在执行 —— 然后让它解释四段程序，与宿主求值器比答案：

    算术            7 · 7
    if 与 return     9 · 9
    while           4 · 4
    函数调用        42 · 42

5 项全过。这是与前面几轮不同的问题：那几轮问的是「换一个加载器行不行」，这一问问的是
「这台机器能不能跑自己的解释器」—— 对这一份语言来说，能。

它还不等于「自举完成」：能跑的四段是最小的一批，而工具链（编译、打包、签名）还没这样跑过。
但它把「求值器自举」从设想变成了一个可以继续加样本的量具。
第三十二件（2026-10-24）：工具链也在虚拟机上跑起来了。

tools/self-vm-compile.mjs 把 runtime/pack.hmoks（自举那一层的编译与打包）装进虚拟机，
让「编源码 → 打包」整条跑在字节码上，再与 JS 那位逐字节比：

    直接返回一个数        35 字节
    两个函数与一次调用     87 字节
    if 与字符串          104 字节
    while 与比较          96 字节
    元组与下标            86 字节

五段全部一致，6 项全过。已注册为 selfvmcompile（167 套）。

于是「自举」这条线的形状清楚了：

    selfvmeval      解释器在 vm 上跑 —— 运行
    selfvmcompile   编译与打包在 vm 上跑 —— 造字节

两件加起来，说的是同一句话：HMYR 写的工具，能由 HMYR 的机器执行，产出与宿主那边一样的东西。
它还不含「签名」那一段（那部分仍由 JS 侧的工具调用 HMYR 的验签），是这条线上剩下的最后一块。
第三十三件（2026-10-24）：签名也跑在虚拟机上 —— 自举这条线闭合了。

runtime/sign.hmoks 是 self/sign.hmoca 的字节码（92 个函数、4097 条指令、24443 字节）。
虚拟机加载它，让它验一次真实签名：

    真实签名（dist/manifest.json.sig）     验得过 true
    把 manifest 改一个字节                 验不过 false

8 项全过（五段字节对照 + 两条验签）。

顺带被静态核对抓到两处旧账：sha512.hmoca 里 一64 与 零64 声明 -> Int，实际交回 (1, 0) 与 (0, 0)。
那两个声明一直写着 Int，而检查以前看不见（因为返回类型根本没进树）。这一类错正是「收下返回类型」
之后才开始现形的 —— 声明与实情不符的地方，从此会当场说出来。

于是「自举」这条线现在是三段：

    selfvmeval      解释器在 vm 上跑 —— 运行
    selfvmcompile   编译与打包在 vm 上跑 —— 造字节
    （同一套件里的第三节）  验签在 vm 上跑 —— 收尾

三段合起来：发布链上的每一环，都能由 HMYR 的机器执行，而不借 JS 的运行时。

第三十五件（2026-10-24）：工具链的第一格 —— 格式化器上了虚拟机。

于是「工具链还是 JS」这句话，现在有一格不再成立。
第三十六件（2026-10-25）：测试框架值不值得搬到 HMYR 上 —— 量完之后的答案是不值得。

先量，再说。三组数都是当场跑的：

    空启动（node -e "0"）          60 毫秒/次
    启动并载入 loader             74.5 毫秒
    全量 171 套                   191.8 秒
    其中进程启动的总开销          约 10.3 秒（171 × 60 毫秒）

所以「启动」只占全量的百分之五左右。真正的时间在做活：最慢的一套 19 秒（selfbridge），
其次 docs 与 conform 也不便宜。搬一个「收集与比对」的外壳到 HMYR 上，省不下这五分之四——它
本来就不是启动贵。

反过来，搬过去要付的代价是清楚的：每跑一个套件都要「编译 + 虚拟机启动」，而这两个数在同一台
机器上是 0.2 到 3 秒（语料生成那三支量过）。171 套乘上去，只会比现在慢一到两个量级。

于是结论不是「以后再说」，而是这件事不该做：那五分之四的时间在模板里、在文件 IO 里、
在那几个 19 秒的套件里；换谁来当外壳都一样。要提速该提速的是那几套慢的，不是换框架。

这一条记在这里，好让下一次有人（包括我自己）想搬测试框架时先看到这两个数。

要补一句更正：写这一件之前我没先读 design/SELFRUN.txt 的账，而那里早就记着
「测试框架也已经搬了：self/check.hmoca 读一份清单、一个一个跑、按退出码汇总」，
验收在 test/check-hmyr.test.mjs（十一项）。所以「搬测试框架」根本不是待办 ——
我量的是 check-all 那层 JS 外壳（171 套的调度器），而 self/check.hmoca 是它旁边
另一条已经跑通的路。

两个数仍然有用（它们说明「换外壳省不下时间」），但结论要改一个字：
不是「不值得搬」，而是「已经搬了，而且留在 JS 里那一份也没必要再动」。
教训与上面那句「看下层实际产出」同族：动手前先读账，账可能已经结了。
第三十七件（2026-10-25）：工具链那一栏，清零了。

这件事不是「今天做完了最后一件」，而是「今天核账时发现早就没有待办了」。
design/SELFRUN.txt 里那一栏原来列着六件「都还是 JS」，下面还有两条「还没搬」：
语料生成剩两支、打包发布要等一个 deflate。逐件核过之后：

    十二件全在 self/ 下，每一件都有验收套件，而 deflate 早就在了 ——
    打包那五件正是用它写的。

于是「工具链就位」这四个字的含义变了。以前它指的是「跑程序这条路上没有 JavaScript」，
工具本身还是 JS 写的；现在连工具也不借 JS 的运行时了。这一栏的整栏清零，是这一路的终点，
而它是一次核账发现的，不是一次开发做出来的。

账为什么要核：今天有三个小时花在「照着过时的账做事」上 ——
先评估了一个已经搬完的测试框架，再评估了一个已经搬完的 LSP，
最后发现打包发布的前提（deflate）也早就满足了。三次都是读文件才纠正的。

所以这一件记的不是成果，是方法：开工前先核账，比先量一遍便宜，比先写一遍便宜得多。
第三十八件（2026-10-25）：账的总核 —— 现在它是干净的。

总核做了什么：把 design/SELFRUN.txt 与 design/C-VM.txt 里每一句「还没」「尚未」「仍是」
取出来，逐条对着树看。结果是：

    SELFRUN 三处   都是设计讨论（「谁提供值」那段），不是待办
    C-VM  七处     六处是边界与历史（板子上不编回收、UCD 版本、性能记录），
                   一处是「板子上还没跑过更大的真实程序」—— 那是硬件的事，没有可做的

加上今天前几轮核掉的：工具链十二件、LSP、格式化器、语料三支、deflate、GC，
以及 tools/tooling-ledger.mjs 的十九项（十八搬一不搬）——
这份账目现在是干净的：没有一条「说没做而其实做了」的。

第三十九件（同日）：给第一次来的人那一份也更新了。

design/TOUR.txt 是「看一眼 Himeyuri」那份导览，它有五处停在半年（或一个月）前：

    错误编号「五十七个」        → 六十个（索引那一组补了两个）
    发布「打包（tools/package.mjs）」 → 这一处当时没真的落到 TOUR 里，到第四十件才补上
    没有语言服务器              → 有骨架：initialize / documentSymbol / definition / hover
    没有在第二台机器上验过        → 桌面上的第二台已经逐字对拍八十项，板子上还没有
    中文人话「五十七句」          → 六十句

这一份比别的文档要紧：它是唯一一份写给「还没决定要不要读这个仓库」的人看的。
它过时的代价不是误导自己，是误导别人。

第四十件（同日）：端到端发布 —— 一条闭环，以及它照出来的一个缺口。

此前四件发布工具（manifest / package / verify / release）各有套件，但 releasehmyr 与
verifyhmyr 两套的「真跑」都挂在 HMYR_HEAVY 之后，而常规全量从不设那个变量。
于是「真发一次」这条路上，只有手动跑过的人知道它通不通。

先手动走了一遍：release.hmoca 造三样（清单 1212 行、包 312 个文件 4.78 MB、说明书），
再把那份清单交给 self/verify.hmoca 验 —— 250 项对得上、0 不对、0 缺，digest 也对得上。
194 秒。这条路成立。

于是把它固化成 tools/release-loop.mjs，一次三分钟上下，五节：

    一、HMYR 真发一次
    二、把包按中央目录解出来（成员一律 stored，按偏移切片即其内容）
    三、包内那份 manifest.json 与包外那份逐字节相同
    四、每个成员与仓库里的源文件逐字节相同
    五、拿解出来的包当根，用 HMYR 自己的 verifier 验包里那份清单
    六、从解出来的目录里起一次启动器，跑一个例子程序（字节对得上不等于跑得起来）

第五节照出一处缺口：清单报 [缺] runtime/text.hmoca。查下来是这样 ——

    manifest.hmoca   standardLibrary 递归 runtime/，列了 runtime/text.hmoca
                    与 runtime/ucd/blocks.hmoca 两条
    package.hmoca    目录表里根本没有 runtime/，注释写着「那里装着几 MB 的语料」

两件各自都对，合起来就是：包里的东西少了，而清单说它有。
在仓库根下验清单永远看不见这一处 —— 那些文件本来就在仓库里，要拿包当根才照得出来。

修法不是把语料收进包（codepoints.txt 45 MB、conformance 60 MB，读进来会撞内存上限），
而是按后缀筛：runtime/ 只收 .hmoca 与 .hmoks。改完成员从 313 涨到 319，第五节 14 项全过。

验收：

    tools/release-loop.mjs        17 项全过 · 成员 319 · 180 秒
    packagehmyr                   21 项全过（含 C 那台真打一次、整棵仓库、附加成员）
    releasehmyr（轻的一半）        10 项全过

这一条的意义不在修好一个目录表，在「单件全过、合起来不对」这一类 —— 四个套件各自盯自己
那一件，谁都不盯「发出去的东西拿回来还能不能验」。端到端不替代单件，它照的是单件之间
那条缝。

第六节是最后一层：清单只说明字节对得上，不说明那些字节能跑。从解出来的目录里起一次
启动器，它 import 的是包里的 src/、读的是包里的 runtime/，与仓库那份无关 ——
这才算「别人拿到这个包」。

还有一处跟着改的是说明书。它原来回答「怎么自己验」的三步，却没说包里少了什么 ——
拿到包的人跑 conformance 会撞在缺语料上，那不是他弄错了。现在第四节写着
conformance/ 与 runtime/ucd/codepoints.txt 不进包、为什么、去哪补，
releasehmyr 也跟着多一条断言，盯这句话还在不在。
