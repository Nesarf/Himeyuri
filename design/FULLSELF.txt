全自举：38% 到 100% 意味着什么，现在离它多远
====================================================================

目标已经明确：让 HMYR 自己写的代码占全部代码的百分之百。这份文件写三件事 ——
现在的口径、沿途的障碍、以及一条能一段一段验的路线。

一、口径
--------------------------------------------------------------------

按行数算，今天的比例是 8017 / 20965，约百分之三十八：

    self/*.hmyr     32 个文件   8017 行    HMYR 自己
    src/*.mjs       28 个文件   6450 行    求值器、编译器、加载器、词法、语法
    tools/*.mjs     25 个文件   2762 行    打包、清单、发布、检查器
    vm/*.c           1 个文件   3736 行    字节码机

test/*.mjs 那 14850 行不计入，因为验收是验收，不是产品的一部分 —— 但它们的语言
也要跟着换，否则「全自举」只是产品自举、验收还在别人的引擎上。这一条写在边界里。

二、百分之百的严格定义
--------------------------------------------------------------------

绝对的一百做不到，也不该假装做得到：程序要读文件、要分配内存、要退出，这些总得
落到某个宿主上。所以这里的定义是：

    除了「读文件、写文件、分配、退出」这几项宿主口之外，仓库里没有第二套实现。

今天的 src/ 与 vm/ 都超出了这个范围 —— 它们不只是宿主口，它们是求值器、
编译器与字节码机本身。所以它们要一段一段被 HMYR 的实现替掉，而不是被「迁移」。

三、沿途的障碍，按难度排
--------------------------------------------------------------------

    一、字句法（lexer/parser）。self/ 里已有能跑的那一份，且与 JS 版逐条对齐过
       （selflex、subsetlex、subsetparse 三套验收）。这一段最接近完成。

    二、求值器。self/eval.hmyr 已经能跑，但与 src/eval.mjs 比还缺内置与效果检查的
       一些分支。stage0eval 与 minimaleval 两套验收在量它到底需要多少。

    三、编译器。self/compile.hmyr 能编一部分，hmyrcompile 那套验收在量「两套编译器
       给出同一个答案」的边界。

    四、字节码机。vm/hmyr.c 是唯一没有 HMYR 版本的一层，也是最大的一块（3736 行 C）。
       要它自举，得先有一个用 HMYR 写的 VM —— 而那件事要求「HMYR 能表达内存与指令
       循环」，也就是要先把数组与指针那类东西在语言里做扎实。

    五、宿主口。最后剩下的是 file、process、time 那三组内置 —— 它们不是「还没搬」，
       是「本来就该在宿主上」。这一层不算欠账。

四、路线：四段，每段都要有验收
--------------------------------------------------------------------

    第一段  让 self/ 那一套跑通全部验收（不是跑通一部分）。判据：把 src/ 那一份
            换掉之后，156 套里有多少套还是绿的。今天这个数要量出来，作为起点。

    第二段  把「换掉之后还绿的」这一批一套一套扩到全部。每扩一套，src/ 里就少一段
            被用到 —— 用 --affects 看得到是谁还在用它。

    第三段  字节码机：先让 HMYR 写的 VM 跑通 test/bytecode.test.mjs，再接 C 那台的
            位置。这一段最长。

    第四段  收尾：src/ 与 vm/ 只剩宿主口。那时比例才是接近百分之百，
            而剩下的几千行要写清「为什么它们必须留在宿主上」。

五、现在就该做的两件小事
--------------------------------------------------------------------

    一、量第一个数。把 self/ 那一套（self/*.hmyr 的求值器与编译器）真的接到
       check-all 的一个开关后面，跑一次，数出「换掉之后还绿多少套」。没有这个数，
       后面四段都是空谈。

    二、别让比例悄悄退回去。可以在 design 里放一行、或者在账本里加一条，
       记录每次的比例。数字不动的时候，人不会注意到自己在往回走。

两个数都量了。它们各自是「换掉 src/ 之后还绿多少套」的下界，合起来把起点定得更窄。

第一件：求值这一层，十四段程序全部对上（14 / 14）。量具 tools/self-coverage.mjs，
挂进 check-all 叫 selfcov。这个数说的是「self/run.hmyr 那条全 HMYR 的链，在十四段
小程序上与 JS 版给出同样的值」，不是「换掉 src/ 之后还有多少套是绿的」。

第二件（2026-10-24）：加载这一层，二十七份真实源码全部认得下来（27 / 27）。
量具 tools/self-loader.mjs，挂进 check-all 叫 selfload —— 默认子集二十八秒，
加 --全部 跑五十四份（根目录二十一份加 self/ 三十三份），五十五秒。

判据只是形状：两边都说 ok，或两边都说错。它量的是「切词与搭树认不认得真实文件」，
比「值对不对」更早一步，也更容易在换 loader 的时候先坏掉 —— 所以它值得常驻。
样本里二十一份是根目录的库文件（pixel、surface、json、term …），六份是自举的核心
（lex、chain、stmt、body、eval、run）。全部五十四份的那一次实测也是 54 / 54。

仍然没量的是那个真正的起点数：换掉 src/loader.mjs 之后，一百五十八套里还有多少套是绿的。
它需要 loader 的实现本身，而今天 self/ 那一条链只到「认出源码」，还没到「按 import 递归、
把诊断装成宿主 loader 那个形状」。所以第一段还差一件事：把 self/ 的加载链包成一个与
src/loader.mjs 同形状的东西。那件事做完，这个数才量得出来。

第三件（2026-10-24）：模块加载的**语义**也量了。self/run.hmyr 的 加载走 照宿主 loader
文件头那三条承诺实现 —— import 真的加载、同一个文件只加载一次、环引用报 E0301；
另外引的文件不在就报 E0302（宿主也是这个码）。顺序取后序，于是 order 逐项相同。

判据是两件事：四棵真实 import 树（sign、release、package、verify）的 order 逐项一致；
以及两个构造出来的场景 —— 缺一个 import、两个文件互相 import —— 两边报同一个码。
量具 tools/self-load.mjs，挂进 check-all 叫 selfmod（约二十八秒）。

于是「加载」这一层有两半都对齐了：认不认得（selfload，27 / 27），以及按什么规矩加载
（selfmod，order 与错误码）。还差的一半是**树的形状**：
宿主 loader 交出的 ast 是 subset-parse 那一套（Module、Import、Fn、Block、Literal …，
带 line 与 column），而 self/chain.hmyr 交出的节点是另一套（num、str、name、bin、call、
field、index、tuple、record、unary —— 小写单字、不带位置、也没有声明与语句层）。
两套名字不同、字段不同、层次也不同。

所以「换掉 src/loader.mjs」真正的门槛在 ast，不在加载逻辑：要么让 self 那边产出
subset-parse 的形状，要么让宿主这一侧接受两种形状。在那之前，「多少套能换」这个数
只能算到「只用 loadUnit 的 ok」为止 —— 而验收里的套件几乎没有这样用的，它们都要
runUnit，也就都要树。这一段的工作量比上面两件加起来大，且它是一个形状问题，
不是一批 bug。

第四件（2026-10-24）：位置。self/lex.hmyr 的 scan 与 scan_lines 现在给每个 token 带上
line 与 column —— token 本来就带着字符偏移，所以这一遍只是一次线性扫描；位置在词法这一层
有了，后面的节点才有东西可抄。这一件不改任何现有语义，只多两个字段。

判据是逐项比：六段源码（一行赋值、多行函数、注释与空行、字符串与转义、中文标识符、
紧挨着的符号）在两边交出的 token，词形与位置逐项相同（4、15、10、4、4、14 个 token）。
量具 tools/self-positions.mjs，挂进 check-all 叫 selfpos。

三处还没对齐，一起记在这里，免得下次当成新发现：
  一、kind 的命名：宿主分 keyword 与 ident，self 一侧一律 ident（关键字也在 ident 里）；
  二、换行 token：宿主保留 newline（语句边界靠它），self 的 scan 不产，scan_lines 才产；
      eof 也一样只有宿主那一侧有；
  三、字段名：宿主的 token 用 type 与 value，self 用 kind 与 text。

位置之所以先做，是因为它只加字段、不改语义，而后面每一步都要它：一个说不出第几行的
诊断，没法与宿主的诊断对照。

六、这条路线不算欠账的部分
--------------------------------------------------------------------

    test/*.mjs 的移植不在第一到第四段里。它跟着产品走：产品换成 HMYR 了，
    验收自然也该换成 HMYR 写的。但那是最后一步，不是第一步 —— 现在换，
    等于在没有尺子的地方量长度。


七、两个名字：Hiou Rengo 与 Yunooka
--------------------------------------------------------------------

路线的四段是工程顺序，但「百分之百」这个目标本身需要两件产品来承载 ——
否则它只是一串「把某段代码重写掉」的任务，没有形状。所以给它们名字：

    Hiou Rengo（緋凰·恋語）   完全态 SDK
        出自小一孁こはね那把等身大太刀的名字。它装的是「用 HMYR 写程序所需要的
        一切」：标准库、工具链（打包、清单、发布、检查）、以及给宿主留的那几道口
        的绑定。四段路线里的第一、二段主要落在这里。

    Yunooka（湯の岡）          完全态 OS
        出自她所属的学寮都市「カピラ」的寮名。它装的是「跑 HMYR 所需要的一切」：
        引导、内存、进程、文件、时间，以及那个还没有 HMYR 版本的字节码机。
        四段路线里的第三、四段主要落在这里。

两件合起来，才是「百分之百」的完整说法：Hiou Rengo 负责「写」，Yunooka 负责「跑」。
只做到前者，是能自举但跑不动；只做到后者，是能跑但没有东西可写。

命名不只是装饰，它给了一个判据：当某段代码说不清该归 SDK 还是 OS 时，问一句
「它是给写程序的人用的，还是给跑程序的人用的」，答案通常就出来了。
宿主口归 OS，其余归 SDK —— 而宿主口本身永远要在某个真实的操作系统上落地，
Yunooka 能把它压到多薄，就是这条路线的最终刻度。
第五件（2026-10-24）：节点位置。self/chain.hmyr 的表达式节点现在带 line 与 column ——
num、str、name、err、bin、unary、call、field、index 处各从它那个 token 抄一次。
这一件同样只加字段，不改语义。

一处照抄来的怪处值得记：宿主的 Field 记的是**字段名之后**那个 token 的位子（subset-parse 的
注释写着「照抄而不是改对」，为的是两棵树能逐节点核）。这一侧的 token 流不留换行，所以等价
写法是「名字的列 + 名字的长度」—— 名字后面紧跟的就是那个位子。不照抄，两棵树永远差一列；
照抄之后差得正好为零。

判据：四段样本（字面量与优先级、标识符与二元、一元负号、调用与字段）里，self 交出的每一个
节点位置，宿主树上都有对应位置的节点 —— 十八个节点，十八个都对上。量具 tools/self-nodes.mjs，
挂进 check-all 叫 selfnodes。

还没做的：语句层（let、var、return、assign、expr、if、while）还没有位置；声明层（Fn、
Block、Module、Import）在 self 这一侧还没有节点 —— 宿主的树里有，这边只是一组元组。
这两条是「形状」剩下的主要工作。
