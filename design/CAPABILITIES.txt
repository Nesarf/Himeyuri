宿主能力契约（自举第一步）

为什么要有这一份
--------------------------------------------------------------------

  现在宿主提供了四十一个内置，它们散落在求值器里，只有源码知道各自做了什么。
  而「用 HMYR 启动」这件事的前提是：「宿主是什么」得先变成一份可替换的清单。
  所以下面按能力分组，每组写清四件事：成员、语义、要不要效果、拒绝时给哪个编号。

  换宿主时对着这一份逐组实现，同一份 .hmoca 的行为就该一致；
  不一致就是契约没写清，先补契约，不先改宿主。

分组
--------------------------------------------------------------------

  一、文本（纯函数，无副作用，不需要效果）
      slice ord chr to_upper to_lower to_int
      len str int abs min max
      nfc is_letter is_mark split
      语义：只从输入算出输出，不读也不写任何外部状态。
      拒绝：ord 空串给 R0206；chr 越界给 R0207；to_int 非整数写法给 R0208。

  二、输出
      print
      语义：写一行到一个可替换的出口（套件里换成缓冲，示例里换成 stdout）。
      一条要说清的边界：print 自己不添换行。换行是调用方的事 ——
      一份程序想分行，就自己写 chr(10)。四台机器（宿主求值器、最小求值器、
      字节码执行器、C 那台）在这一点上一致；而 CLI 按行显示，
      那是显示层的选择，不是 print 的语义。
      拒绝：无。它不失败，只会写不出去——而写不出去是宿主的事。
      效果：print 不需要效果。它写到一个可替换的出口（套件里换成缓冲），不算动世界。
            这条是设计决定，不是遗漏：谁要真的写文件或起进程，才需要 file 与 process。

  三、文件（需要 file 效果）
      read_text write_text file_exists
      read_bytes
      read_dir
      语义：读时编码要么显式写明，要么按 BOM 判——BOM 是事实，代码页是猜测，所以只认前者。
            写时只编得出 utf8、latin1、utf16le 与有表的那几个；写不出就拒绝。
      read_bytes 读的是原始字节（每个 0 到 255 的数）：嵌入与打包要它，
            而 read_text 会按 UTF-8 解码，二进制一过就坏。它不需要编码参数，
            也不猜；读不到与 read_text 同一条路（R0211）。
      read_dir 列一个目录，交回名字的元组（含目录名，不含路径）。排序由这一侧做，
            因为两台机器必须交回同一个顺序，而目录顺序是文件系统的习惯。空目录是
            零个名字而不是错；打不开与 read_text 同一条路（R0211）。
      is_dir   问一个路径是不是目录，交回 Bool。问不到交回 false —— 与 exists 同一个
            态度：调用者通常把「问不到」与「不是」当同一件事，多一个错误码只让人多
            写一段。递归要走下去，靠的就是这一条。
      校验和   CRC32：收字节元组，元素可以是一字节也可以是一块，交回一个 32 位的
            无符号数。纯算术，所以不需要效果 —— 多吉性与 ZIP 都要它，而它不碰世界。
            表第一次用时生成（多项式 0xEDB88320），与 src/vm-builtins.mjs 和 C 那台
            同一张：三处对同一串字节必须给出同一个值，否则 ZIP 不互通。
      拒绝：编码不认识给 E0008；表缺失给 R0203；字符编不了给 R0204。
      返回：写入的字符数（不是字节数）。
      编码名有别名：utf-8 与 utf8 同义，utf-16le 与 utf16le 同义；大小写不论。
      走表的那条路：逐字符查表，缺的字一次全报（前八个 + 还有多少个）；先查齐，再写，不写半个文件。

      打包用的三条（write_bytes f64_bytes pack_value）
      为什么在这里而不是在语言里：这门语言没有字节类型，也没有 typeof 与 try，
      所以「字节怎么落成文件」「双精度的位怎么排」「一个值是数还是串还是记录」
      这三件事在语言内部做不到 —— 试过，猜不准，而猜不准的编码器比没有更危险。
      所以它们和 read_text 一样留在世界这一侧，由 .hmoks 的打包者调用：
        write_bytes(路径, 字节元组)  → 写入的字节数
        f64_bytes(数)                → 8 个字节（小端）
        pack_value(值)               → .hmoks 里那一段（标签 + 内容）
      空元组编成 null：这门语言没有 null，「空元组就是它」，
      所以一个空元组在运行时的意思就是「没有值」，写成 null 的标签既短又与 JS 那侧一致。

      按行读的两条（read_line read_lines）
      为什么入口长这样：语言里没有文件句柄类型，也没有「用完要关」的机制，
      所以真正的流式读只能长成「给一个偏移，读一行，交回下一处从哪开始」——
         read_line(路径, 起点) → {行, 下一起点}；读完时 下一起点 是 -1
         read_lines(路径)      → 行的元组（末尾那个空段不算）
      每一次调用自己开、自己关、自己 seek：开销大一点，但语义封闭，
      而调用者可以按自己的节奏一段一段读，不必把整份文件塞进内存。
      CRLF 与 LF 读出来一样（行尾的 \r 去掉）。
      拒绝：读不到给 R0211。

  四、进程（需要 process 效果）
      run_program chdir argv print_err
      语义：跑一个程序（必须带超时，缺省十秒）或改变进程的工作目录。
      返回形状：run_program 交回一个记录，字段是 code（没有退出码时为 -1）、stdout、stderr、
                timedOut 与 error（跑不起来时带宿主的错误码，例如 ENOENT）。
                记录是对外的事实，不是异常：跑不起来也照实报告，不抛。
      两个细节：stdout 与 stderr 的尾部空白被去掉；而一次最多收 8 MB，超出时 spawnSync 报 ENOBUFS，
      那个码出现在 error 字段里，而不是另设编号。
      第四个参数是输出的编码：中文 Windows 的控制台多半是 GBK，写死 UTF-8 会让每个汉字变成替换字符。
      拒绝：进不去的目录给 R0209；程序名为空给 R0213。

  五、环境（只读，不需要效果）
      cwd home_dir locale_env locale_current locale_set console_codepage
      repo_path python_path temp_path
      （仓库根、解释器位置与临时目录：语言文件里不写死绝对路径，换机器也不用改）
      语义：读宿主的位置与语言环境；locale_set 只改「当前选的是哪一套」，不改任何文件。
      拒绝：没有那套语言档案给 R0205。

  六、时间（不需要效果，但破坏可复现性）
      now_ms sleep_ms floor
      语义：读时间、等一会儿、向下取整。
      注意：要可复现的程序不该用 now_ms。这一条写在第一圈里，不是事后提醒。

  七、终端（只返回字符串，一个字都不写出去）
      term_size term_clear term_escape term_color term_hide term_show
      语义：把终端控制序列当作值交回，由调用者决定写给谁。副作用留给 print。
      拒绝：无。它们不失败，只会给出一串没有用处的序列。

  八、输入（队列加真终端的同步读，不需要效果）
      key_push key_available key_read key_start
      read_stdin_line
      read_stdin_bytes
      bytes_to_text
      read_stdin_line 读的是标准输入的一行，交回一个记录 {行, 结束}：
      结束是 EOF，与「读到一个空行」是两件事 —— 「读到没有为止」的循环
      要能分清它们，所以两者不能都塞进空串里。行尾的 \r 去掉，别的空白不动。
      read_stdin_bytes 读的是 N 个字节（0 到 255），交回 {字节们, 结束}：
      结束表示没读满（EOF 先到了）。两格分开是因为 JSON-RPC 的请求体未必只有一行 ——
      先读头拿长度、再按长度读体，是两步。
      板子上没有标准输入，那里一律交回结束。
      bytes_to_text 把字节元组按 UTF-8 解码成文本：它是 read_stdin_bytes 的搭档 ——
      一个交回字节，一个把字节变回字。不猜编码，给的必须是 UTF-8；
      坏字节按替换字符走，与 read_text 同一条路。
      语义：真实终端与套件走同一个队列。而 key_read 有三种情形，三种都要说清：
            一、队列里有东西：立即交回一个键。
            二、队列空而 stdin 是终端：同步读一次 stdin，阻塞到有键为止，一次最多读 64 字节，
                读完把多出来的推进队列（于是 key_available 才有意义）。
            三、队列空而 stdin 不是终端：立即交回空串——不阻塞，也没有键。
      为什么用同步读而不是 data 事件：求值器是同步的，而 sleep_ms 是忙等，
      事件循环在那一刻堵着，事件永远送不进来。同步读绕开了这件事。
      队列有界：C 那台 16 项，满了不收、交回当前长度；JS 那侧无界。
      这一条差异明写在这里，而不是等板子在某个规模上悄悄变慢。
      拒绝：无。没有键就是空串；而 key_start 在非 TTY 下如实返回假，不装。

  九、记录（按名字造、按名字取、按名字列）
      record_new field_get field_has field_names
      语义：记录不是哈希表——record_new 只收「标识符能写的名字」，否则拒绝（R0214）。
            field_get 取不到会拒绝（R0216），而 field_has 只回答有没有（纯函数，不需要编号）。
            field_names 列出字段名（按造记录时的顺序），非记录给 R0217 ——
            交回空表会把「这不是记录」说成「这是一条空记录」。
      为什么它们在这一组：自举的求值器要按节点上的名字现场造记录，那时候
            名字是个变量，写成 .名字 写不出来。而 x[名字] 也不行——下标只收数字。

  九半、索引（按键查，键是任意字符串）
      index_new index_set index_get index_has index_len index_keys
      语义：与记录同一层（值，不是引用），但键不像记录的字段名那样要「像名字」——
            码点键 "0041"、路径键 "data/ucd/UnicodeData.txt" 都得能直接放。
            index_set 交回同一个索引，于是可以写 表 = index_set(表, k, v)；
            重复放同一个键是覆盖，而键的位置留在第一次那儿。
            index_get 取不到会拒绝（R0218），index_has 只回答有没有（纯函数，不带编号）。
      为什么它们在这一组：语料生成要按码点回头查（全分解、组合类、排除表），
            而记录只能一次建好、元组拼接是 O(n²)——实测八千个键就撞步数上限。
            约定与账目见 design/INDEX.txt；第一个真实用户是 self/ucd-nfc.hmoca。
      C 那台：也做了（2026-10-25）。用的是排序数组加二分，不是哈希 ——
            理由与摊还账写在 design/INDEX.txt 第六节。两块分配（表本身与项数组）
            都进了标记，验收专门有一节把回收阈值压到六十四千字节来盯着这一点。

  十、线程（需要 thread 效果）
      thr_spawn thr_join thr_cancel thr_count
      语义：worker 在另一个核上跑，结果经文件送达，共享内存只发「写完了」这一个信号。
            为什么不用 postMessage：那个回调也在主线程的事件循环里，而主线程正堵在
            Atomics.wait 上。隔离是硬的——worker 有自己的求值器实例。
      拒绝：句柄不存在给 R0221；等超时给 R0222。起不来就交回 -1（无效句柄），不另设编号。

  十一、内存（三区模型的记账那一半）
      arena
      实现现状（2026-10-25）：alloc(n)、close()、held()、freeze(b)、adopt(b) 五个。
      块带一个看得见的 zone 字段（"arena" 或 "managed"）：freeze 把它交给托管区，
      adopt 把它收回来，走错各有编号 —— R0302 是「不是这个区里活着的块」，
      R0303 是「一块的寿命被两处同时拥有」。验收在 test/zone.test.mjs，十六项。

      这一格做的是 MEMORY.txt 那条「不静默换区」里能检查的部分：记账与两条转换。
      而这一格的边界要说清，不然读的人会以为内存模型齐了：

        真内存            分配与释放仍是宿主的对象，块只是一个记录。
                          那块内存会不会被提前收走，这一层管不了。
        逃逸的编译期检查  MEMORY.txt 那条「不许逃逸」还是编译期的事，R0301 仍登记为
                          planned。今天写得出「返回一个 arena 里的块」这种程序，
                          而它要到运行时碰那个块才会出事。
        已关闭的区        收养它的块被拒绝而不是允许 —— 那块内存已经没了，
                          收回来只是把一块死内存记在账上，而记账错的地方比不记账更坏。

      一条边界值得写下来：arena 在语言里是关键字（lexer 的保留字，parser 有它自己的一支），
      而自举那条 subset parser 不认它 —— 于是「字节码路径上写 arena()」不是没有实现，
      是编译就过不去（E0104）。C 那台仍留了一条 R0104 的分支，防的是宿主 parser
      把 AST 直接交给字节码那一层的情形；而它的字段是函数值，
      这门语言没有一等函数，所以那条分支的答案只能是「没有」。
      freeze 与 adopt 走的是同一条门，所以它们今天也只在宿主那条路上成立。

这一份与实现的关系（2026-10-20 更新）
--------------------------------------------------------------------

  写完这一份的时候，「能力收敛」还差两件。现在它们的账是这样的：

  一、能力内核有了实现面：src/capabilities.mjs 的七个组
      （文件、进程、时间、环境、路径、终端、Unicode）。内置与最小求值器都从它取世界。
      验收在 test/capabilities-layer.test.mjs：换一份记账的实现，同一段程序给出同一个答案；
      而那份记账清单本身就是「这一趟借了什么」的答案。

      这一层被刻意写得无聊：read 一个不存在的文件就抛，而不是在这里编一个 R0211。
      「拒绝时给哪个编号」是上面那两层的事，放在这里会让它分散到两个地方去。

  一·五、Unicode 那一组是最后收进来的（2026-10-25）：normalize、isLetter、isMark。
      在那之前，两个求值器各自对宿主串调 normalize 与一条属性正则。那不只是「两处一样」的问题：
      它借的是一张随宿主来的字符表，而这件事从源码里看不出来。收进能力层之后，
      换一份表（或者换一个宿主）会影响哪些行为，答案在 capabilities.mjs 里。

  二、求值器的内置已经逐组对齐：文件、环境、进程、时间、终端、线程、Unicode 七组都走能力层。
      终端输入（isTTY / setRaw / readSync）与线程（spawn / signal / load / store / wait）也在其中——
      那两件原先最难搬，因为它们碰的是进程的输入流与另一个核。

      而现在求值器里一处直连都没有了（2026-10-20 收尾）：src/eval.mjs 不再 import 任何 node:
      模块。把最后三件收掉的办法各不相同，值得各说一句：

        编码表        走能力层读。它读的是一份文件，而「怎么读一个文件」只有一条路。
        模块位置      Node 自己给了 import.meta.dirname，于是 path 与 url 都不再需要。
        命令行那一面  搬到了 bin/run-eval.mjs。它一直不属于库，只是这个文件顺带当命令用的那一面。

      test/capabilities-layer.test.mjs 钉着这件事：求值器里出现一处直连就红。
      那条断言现在钉的是一个空集合，而空集合正是它的终点。

  三、一处教训值得留在这里：线程那一组的 spawn 把起不来的原因吞成了 null。
      「Worker 没 import」变成了一句安静的 null，而调用方只看到「交回 -1」。
      现在那一组留着一个上次错误，而注释里写着这件事——静默的失败比响亮的失败贵。

  于是换宿主时要对着做的东西，从「读求值器的源码」变成了两处：
  这一份契约（每组做什么、拒绝时给哪个编号），与 src/capabilities.mjs（现在是怎么做的）。
