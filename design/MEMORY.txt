内存模型（设计稿 1）

  对应 SPEC.txt 的 [悬] 1。本文给出倾向、理由与反例；定稿后这一页的内容并入规格。
  写法沿用 KID 的规矩：每条主张挂一个「谁来验它」，并把反例写在同一页上。

====================================================================
1. 这一页要解决什么
====================================================================

要求是「上下限都宽、软硬兼具」：同一门语言既要能写脚本（顺手），又要能进实时音频回调（不许有
不可预期的停顿）。这两头对内存的要求几乎相反：

  ・脚本（软）：不用想内存；分配随手；写起来像 Python
  ・实时（硬）：零分配、零 GC 停顿、释放时机可预测
  ・CAD／插画（长寿命）：对象活得久；与 C/C++ 共享缓冲区（不能移动）

如果为两头各造一套语义，语言就裂开了——那等于放弃「集百家之长」。
所以答案只能是：一套语义，多个「区」。

====================================================================
2. 倾向：以「区（zone）」为核心的三区模型
====================================================================

每个值都住在一个区里，区决定它如何被释放。值不会悄悄换区——换区必须显式转换。

  ・arena（竞技场）：分配者：arena.close() 一次释放全部：每帧、每个音频块、每次请求：[定]
  ・owned（所有权）：单一所有者：作用域结束：中长期对象、跨模块传递：[定]
  ・managed（托管）：运行时：不可预期（但不移动）：脚本档位、CAD 的长寿命对象：[定]

  [落地] owned 在 2026-10-27 有了第一版（src/eval.mjs · src/vm-builtins.mjs ·
  self/eval.hmoca · vm/hmyr.c，验收 test/owned.test.mjs）：

    owned() 交回一条持有格，它只装零个或一个值。四个动作：
      放(v)  只对空格 —— 已经有一个值时报 R0305
      取()   只对非空 —— 空的报 R0306；取走之后那条格子空了
      有()   报 0 或 1
      关()   清空并标记关闭；之后再放、取都报 R0305

    取出即转移。这不是形式化的所有权类型，而是「同一块内存有两处拥有」这件事
    能被挡住的最小形状：取出之后源那边就空了，于是「两个变量都声称拥有它」
    在运行期不成立。设计稿要的那一半（单一所有者）因此有了可执行的边界。

    仍然不做的，写在明处：作用域结束自动释放（那要作用域钩子，语言没有），
    以及编译期的转移检查（那要借用分析，是 Rust 那一级的工程）。
    今天它是「一个只能转移一次的格子」，由运行期看着，不由类型看着。

    [落地] 2026-10-27 补上了上面第一条的一半，而它的形状是被一次实测逼出来的：

      一条：一个帧退出时，把本帧登记的持有格一律关掉。
      另一条：放进去的若是一条持有格，那一条就从本帧的登记表里移走 ——
      这是「转移」的第二层意思，所有权连同「本帧退出时会关掉它」一起交了出去。

      少了第二条，把一个格子交出去之后它会被造它的那一帧关掉。实测的原话是
      「交出去之后 有=1，再取就吃 R0305」—— 而那正是「跨模块传递」这个用途要能做的事。
      两条一起才是对的形状；一条单独存在会把 owned 变成只能在原地用的东西。

      范围：四台都有了，而每台放登记表的地方不同 ——
        自举层      环境的纯传递让「往当前帧登记」只能落在那一张共享索引里
        宿主求值器  Runtime 上一个栈，每进一次调用压一层
        字节码机    帧对象上一个列表，帧退出时清
        C 那台      帧记录上一个固定数组（32 个），满了就不登记，因为这条路径
                    不该为登记表分配 —「不登记」的后果是那一格退回自己关，不是错

      还有一句必须写：「帧退出关掉没交出去的」那一半在语言里看不见 ——
      不交出去，外面就没有它的引用，于是没有观察点；交出去，它就不该被关。
      所以 test/owned.test.mjs 的判据只能覆盖转移那一侧。判据盖不住的那一半，
      在这里说，而不是让读的人以为「有判据就等于有保证」。

    [落地] 2026-10-27 的另半边：编译期的单次使用检查（src/owned-check.mjs，
    验收 test/owned-check.test.mjs，码 HMYR-E0321）。

      它做的是一份很小的状态追踪，不是借用分析：一个变量在一个函数体的直行序列里
      只有空、满、说不清三种状态。let X = owned() 是空；X.放 让它变满（而它已经满
      就是错）；X.取 让它变空（而它已经空就是错）。放进 let a = 格.取() 这种
      右值里的调用也算 —— 少了那一处，正例「放→取→放」会被误报成「放两次」。

      看不透就退回不判：分支与循环的体里一次也不追，只把外面那些变量的状态降级；
      从参数、返回值、字段来的持有格一律说不清；别的方法（关）也让后面说不清。
      这一份检查的失败模式必须是漏报 —— 一条误报就够让它被关掉。

      所以它盖住的是「直行里同一个格子被放两次或取两次」，而它明说什么不盖：
      分支两侧各放一次、循环里反复放、跨函数的转移、以及「关了之后还用」。
      那些今天只有运行期看着。

三条硬规则：

1. [定] 不静默换区。 arena.freeze(v) → 托管；arena.adopt(v) 要求 v 的生命周期不超出该 arena。
   没有转换就是编译错误，不是未定义行为。
   [落地] 记账与两条转换已经有了（2026-10-25，src/eval.mjs，验收 test/zone.test.mjs）：
   块带 zone 字段，freeze 交出、adopt 收回，走错给 R0302 / R0303。
   [落地] 「编译期」那一半在 2026-10-26 有了第一版（src/zone-check.mjs，验收
   test/zone-static.test.mjs）：装载一份模块时走一遍树，把没交出去就返回的 arena 内存
   报成 R0301，把循环里新建 arena 报成 W0310（§4.4 那条陷阱 —— 它是警告，不是错）。
   同一份检查还认三件事：在直行序列里 close 之后又碰到那块内存，报 R0301（4.1 的原例
   正是这一形态，而运行期对「读一个已关闭块的字段」是不吭声的）；把块存进一条记录，
   报 R0304（4.2 在今天写法里最近的形状 —— 记录能交出去、能返回，而区留在原地）；
   把块交给别的函数，报 W0311（见下面第三条缺口）。close 写在 if 或循环体里时不算数 ——
   它可能没执行过，漏报一种比误报一种好，误报会让这条检查被关掉。
   挂了两处：src/loader.mjs（所有走 loader 的路，含 --compile）与 bin/hmyr.mjs
   （默认那条解释路径，在交给自举层之前查一次；--no-zone-check 关掉）。
   R0301 这个码原来登记成 planned，现在它真的被 emit 了。
   还没做的：跨函数的逃逸、记录字段里存的块（要类型与跨函数分析），以及下面那三条缺口。
2. [定] 不许逃逸。 从 arena 作用域里返回该 arena 的值，编译期报错（反例见 §4.1）。
3. [定] 不移动。 托管对象永不移动（非移动式回收）。理由很实在：插画与 CAD 要把缓冲区交给
   C/C++ 与系统 API，移动式回收会让 FFI 变成一片补丁地。[验] FFI 用例：把托管缓冲区的指针交给
   一个 C 函数，长时间持有，回收后指针失效必须能被检测到（悬垂检测用例）。

   三条缺口，2026-10-26 同一天量到的。写在这里，免得下次把「检查做完了」读成「模型做完了」：

     一、（已补，2026-10-27）arena 原来在任何一条会跑的路径上都不存在：self/eval.hmoca
        对它的回答是「HMYR-R0104 这台机器没有 arena」。现在区在自举层是真的 ——
        self/eval.hmoca 里多了六个函数（新区 / 分配块 / 关区 / 交出去 / 收回来 / 求方法），
        区与块都用索引表示，因为记录不可变而 close 要改状态。
        验收 test/zone-self.test.mjs 十六项，其中两条最要紧：默认路径与 --host-eval
        的输出逐字相同；以及「放行之后块真的死了」—— 带检查时 R0301 拦住的那段，
        用 --no-zone-check 放过去之后读到 live=0，于是「拦的是真的」有了证据。
        仍然不做的：§4.2 的原例（下一条）。区现在四台都能跑，而它「存到哪儿」这件事
        语言里还没有地方 —— 那是语法与语义的事，不是机器的。
     二、（已补，2026-10-27）字节码编译器原来不认方法调用，于是区在 --compile 与
        C 那台上都跑不起来。现在四台都认：src/bytecode.mjs 发 CALLM，src/vm.mjs 执行它，
        self/compile.hmoca 发同一条，vm/hmyr.c 的 OP_CALLM 分派到 调区方法。
        值得记一笔的是 opcode 的号：它存成字节，而三处表要对齐（src/code-file.mjs 的
        操作码表、self/pack.hmoca 的操作码、vm/hmyr.c 的枚举与名字表）。第一版按字母序
        插在中间，症状是「文件在中途结束（offset 27185）」—— 后面每个号都错了一位。
        规矩写在 code-file.mjs 里：新号追加在末尾，旧号不动。
     三、（已补，2026-10-27）§4.2 的原例是「把块存到一个模块级变量里」。这一门语言
        没有顶层 var，但它有 const 持有索引 —— 索引可变，而 const 只约束名字不重新绑定。
        于是那个容器有了，而写法是 const 表 = index_new() 加 index_set(表, k, v)。
        四台机器都跑得动：默认、--host-eval、--compile、C 那台（验收 test/zone-self
        第九节四项）。为此补了四处：子集解析器认 const、字节码的 SETGLOBAL 与顶层段、
        自举层的声明扫描与常量装环境、C 那台的全局表。
        §4.2 今天写得出来的形态因此是三个，两条错一条警告：
          「把块存进一条记录」   R0304（记录能交出去、能返回，而区留在原地）
          「把块存进一条索引」   R0304（这一条最贴原例的 kept = b）
          「把块交给别的函数」   W0311（接收方的函数体不在这份源码里，判不了）
        仍然不做的：真正的模块级可变声明（顶层 var）。它是另一种语义 —— 初始化顺序、
        跨模块可见性、写全局算不算副作用、与线程的关系 —— 而「能存东西」这个需求
        已经由 const 索引满足了。

   那三条缺口到这里都补完了：静态检查拦得住逃逸，区在四台机器上都跑得动，
   而「活得比函数久的容器」也写得出。三区模型在语言里有了落脚处 —— 虽然它还没有
   一条真实的用途来证明自己值这些机器（仓库里用区的只有 examples/ 那一份）。

3. 实时档位的硬规矩
====================================================================

标记为 @realtime 的函数（音频回调、帧回调）受额外约束：

  ・禁分配：不许在托管区分配；只允许预先建好的 arena：[定]
  ・禁 panic：不许 panic（回调里不能展开栈）；失败必须走 Result：[定]
  ・禁阻塞：不许文件、网络、锁等待；效果声明里不得出现这些效果：[定]
  ・有界：所有循环必须可判定有界（不许以「等外部条件」为界）：[议]

[验] 三条：① 一个计数钩子在回调里断言分配次数为 0；② 符合性套件里「@realtime 里分配」必须
编译失败；③ 基准：回调的最坏耗时有上界（多次运行的最大值不超过阈值的 1.5 倍）。

[落地] 头两条的前半截在 2026-10-27 有了（src/realtime-check.mjs，验收 test/realtime.test.mjs）：
装载一份模块时，对每个实时档位上的函数走一遍，四条里能静态看的都拒 ——
调 arena()、碰文件/进程/线程那三类内置、以常量真值作循环条件、调一个没声明 realtime 的函数。
四条共用一个码 HMYR-E0320，消息里说清是哪一条。开关是 options.realtimeCheck === false。

它原来写在效果位上，2026-10-27 起有了自己的位置：

    fn 回调(n: Int) -> Int realtime { … }

  一条修饰符，位置在效果之后、函数体之前，两侧解析器（宿主与子集）都认，AST 上是
  Fn.realtime。旧的 effects(realtime) 仍然认 —— 仓库里还有按那个写法写的文档与程序，
  而两种写法喂进的是同一条检查。

  为什么曾经将就：效果说「这个函数能碰什么」（权限），档位说「它必须怎么跑」（约束）。
  借效果位写的代价是实打实付过的：效果检查要求调用者也声明 realtime，于是 main 只是
  调一个实时函数就吃 R0201；四处效果检查各加了「跳过 realtime」才算完。把约束写在
  权限位上一次，就要在每个检查权限的地方各解释一次 —— 那句话留着，比搬走它更值钱。

[验] 第三条（最坏耗时有上界）在 2026-10-27 有了一支标尺：bench/realtime.mjs 跑一份
实时回调若干次，报中位数、最大值与它们的比，超过 1.5 倍就点出来。一次实测（五次）：
中位数 0.923 秒、最大值 1.000 秒、比 1.08，堆账约 1.13 MB。工具自己在末尾写一句
「这只是一次测量，不是全称承诺」—— 那句话是它的一部分，不是客套。

[验] 第一条（回调里分配次数为 0）仍然做不到，而原因要说准：解释器与机器为目标程序
分配（帧、元组、字符串化），那份分配不经过语言的手。所以「零」这个数今天断言不出，
只能度量 —— 堆账那一列就是度量。它离「零」还有多远，那一列会说。

[补] 效果检查里的那四处「跳过 realtime」仍然留着：真语法不再把档位写进 effects，
但旧的写法还会那么写，而两种写法喂进来的是同一条检查。四处各一行，注释指向这一节。

4. 反例（写在这里，免得日后忘）
====================================================================

— 4.1 逃逸（必须编译失败）

fn make() -> Bytes {
  let a = arena()
  let b = a.alloc(16)
  a.close()
  return b            // 反例：b 在 a 关闭后失效
}

— 4.2 静默换区（必须编译失败）

var kept: Bytes? = nil
fn store(a: Arena, b: borrowed Bytes) {
  kept = b            // 反例：托管变量指向 arena 内存
}

— 4.3 回调里分配（必须编译失败）

@realtime fn on_audio(out: borrowed mut Buffer) {
  let tmp = managed_alloc(1024)   // 反例：实时回调里分配
  ...
}

— 4.4 会「看起来能跑」的坑（必须由工具警告）

fn warm() {
  let a = arena()
  let list = a.alloc_list()        // 每帧新建 arena
  ...
}                                  // 关闭正常，但分配量随帧数线性增长

这条不是错误，是性能陷阱——所以工具要给警告，而不是沉默。

5. 与其它设计的关系
====================================================================

  ・空安全（SPEC §2.3）：与内存无关；T? 管的是「有没有值」，区管的是「何时释放」
  ・错误处理：硬档位用 Result；panic 只在非实时档位允许
  ・所有权检查（SPEC §2.4）：borrow 是可选硬档；arena 模型承担了大部分安全，所以借用检查可以只开在需要的模块
  ・契约（SPEC §2.4）：可以是「这个函数不分配」这类断言，交给编译器核对
  ・单位与量纲（[议]）：无关，但 CAD 场景会与「不移动」这条一起受用

====================================================================
6. 为什么这样选（与其他路线比较）
====================================================================

  ・全 GC：实时档位直接出局（停顿不可预期）
  ・全手动（C 式）：脚本档位出局（下限太硬，写起来累）
  ・全所有权（Rust 式）：安全最强，但学习曲线把下限压死；与「简明扼要」这一端冲突
  ・ARC（引用计数）：介于两者之间，但循环引用与原子操作在实时档位仍是隐患
  ・三区模型（本稿）：两头都在：竞技场给实时，托管给脚本，所有权给中间地带；代价是要教用户何时用哪个区

最后这一条代价要认：它要求使用者理解「区」。所以语言的默认档位要能自动选对区
（脚本里不写区就进托管），只有进硬档位时才必须显式声明——这是「渐进披露」的落点。

8. 一次实测：区在自举层比直接的值操作慢
====================================================================

  [验] 2026-10-27。这一节是一个否定的结论，留着是因为「区能用了」与「区该用」
  是两句话，而这一节量的是后一句。

  做了什么：把 self/deflate.hmoca 的 压（stored 块）从「小块 = 小块 + (字节,)」
  改成「区里的块按下标写」—— 前者每加一个字节拷一遍整段（1024 字节的一块
  约五十万次拷贝），后者是 O(1)，每 1024 字节再读出来一次。

  怎么量的：test/deflate.test.mjs 整跑一遍（它含一次 gcc 编 C 那台与多次压缩，
  其中一节是 100 KB 输入）。同一台机器、同一份套件、连续两次。

      元组拼接（原样）    19.03 秒
      区里的块（改后）    20.23 秒

  结论：慢约 6%，退回。块按下标写在这台机器上一次是「方法调用 + 索引写」，
  而元组拼接是宿主数组的 spread —— 后者本身很便宜，于是前者的常数项压过了
  它省掉的那点二次项。100 KB 这个量级上，二次项还没有长到能翻回来。

  意义（三条，都不是安慰）：

    一、区的价值在「释放可预期」，不在「更快」。而释放可预期要等实时档位真的存在，
        今天没有那件事，所以区没有性能上的理由被选。
    二、块的内容存取是这一轮才有的，它让「把值放进区里」写得出来 ——
        但「写得出来」与「值得写」之间隔着一次测量，而这次测量说后者不成立。
    三、仓库里用区的仍然只有 examples/zone-ledger.hmoca 一份。它证明五台机器
        与静态检查都在工作，不证明这门语言需要区。

  所以「区有一条真实用途」这件事，今天的最好答案是：它有一条被量过的、
  变差了的用途，而那份改动已经退回。要让它变成好答案，先要有那件需要
  可预期释放的东西（实时回调），而那件东西还没有。
