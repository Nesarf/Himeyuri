内存模型（设计稿 1）

  对应 SPEC.txt 的 [悬] 1。本文给出倾向、理由与反例；定稿后这一页的内容并入规格。
  写法沿用 KID 的规矩：每条主张挂一个「谁来验它」，并把反例写在同一页上。

====================================================================
1. 这一页要解决什么
====================================================================

要求是「上下限都宽、软硬兼具」：同一门语言既要能写脚本（顺手），又要能进实时音频回调（不许有
不可预期的停顿）。这两头对内存的要求几乎相反：

  ・脚本（软）：不用想内存；分配随手；写起来像 Python
  ・实时（硬）：零分配、零 GC 停顿、释放时机可预测
  ・CAD／插画（长寿命）：对象活得久；与 C/C++ 共享缓冲区（不能移动）

如果为两头各造一套语义，语言就裂开了——那等于放弃「集百家之长」。
所以答案只能是：一套语义，多个「区」。

====================================================================
2. 倾向：以「区（zone）」为核心的三区模型
====================================================================

每个值都住在一个区里，区决定它如何被释放。值不会悄悄换区——换区必须显式转换。

  ・arena（竞技场）：分配者：arena.close() 一次释放全部：每帧、每个音频块、每次请求：[定]
  ・owned（所有权）：单一所有者：作用域结束：中长期对象、跨模块传递：[定]
  ・managed（托管）：运行时：不可预期（但不移动）：脚本档位、CAD 的长寿命对象：[定]

三条硬规则：

1. [定] 不静默换区。 arena.freeze(v) → 托管；arena.adopt(v) 要求 v 的生命周期不超出该 arena。
   没有转换就是编译错误，不是未定义行为。
   [落地] 记账与两条转换已经有了（2026-10-25，src/eval.mjs，验收 test/zone.test.mjs）：
   块带 zone 字段，freeze 交出、adopt 收回，走错给 R0302 / R0303。
   [落地] 「编译期」那一半在 2026-10-26 有了第一版（src/zone-check.mjs，验收
   test/zone-static.test.mjs）：装载一份模块时走一遍树，把没交出去就返回的 arena 内存
   报成 R0301，把循环里新建 arena 报成 W0310（§4.4 那条陷阱 —— 它是警告，不是错）。
   同一份检查还认三件事：在直行序列里 close 之后又碰到那块内存，报 R0301（4.1 的原例
   正是这一形态，而运行期对「读一个已关闭块的字段」是不吭声的）；把块存进一条记录，
   报 R0304（4.2 在今天写法里最近的形状 —— 记录能交出去、能返回，而区留在原地）；
   把块交给别的函数，报 W0311（见下面第三条缺口）。close 写在 if 或循环体里时不算数 ——
   它可能没执行过，漏报一种比误报一种好，误报会让这条检查被关掉。
   挂了两处：src/loader.mjs（所有走 loader 的路，含 --compile）与 bin/hmyr.mjs
   （默认那条解释路径，在交给自举层之前查一次；--no-zone-check 关掉）。
   R0301 这个码原来登记成 planned，现在它真的被 emit 了。
   还没做的：跨函数的逃逸、记录字段里存的块（要类型与跨函数分析），以及下面那三条缺口。
2. [定] 不许逃逸。 从 arena 作用域里返回该 arena 的值，编译期报错（反例见 §4.1）。
3. [定] 不移动。 托管对象永不移动（非移动式回收）。理由很实在：插画与 CAD 要把缓冲区交给
   C/C++ 与系统 API，移动式回收会让 FFI 变成一片补丁地。[验] FFI 用例：把托管缓冲区的指针交给
   一个 C 函数，长时间持有，回收后指针失效必须能被检测到（悬垂检测用例）。

   三条缺口，2026-10-26 同一天量到的。写在这里，免得下次把「检查做完了」读成「模型做完了」：

     一、（已补，2026-10-27）arena 原来在任何一条会跑的路径上都不存在：self/eval.hmoca
        对它的回答是「HMYR-R0104 这台机器没有 arena」。现在区在自举层是真的 ——
        self/eval.hmoca 里多了六个函数（新区 / 分配块 / 关区 / 交出去 / 收回来 / 求方法），
        区与块都用索引表示，因为记录不可变而 close 要改状态。
        验收 test/zone-self.test.mjs 十六项，其中两条最要紧：默认路径与 --host-eval
        的输出逐字相同；以及「放行之后块真的死了」—— 带检查时 R0301 拦住的那段，
        用 --no-zone-check 放过去之后读到 live=0，于是「拦的是真的」有了证据。
        仍然不做的：§4.2 的原例（下一条）。区现在四台都能跑，而它「存到哪儿」这件事
        语言里还没有地方 —— 那是语法与语义的事，不是机器的。
     二、（已补，2026-10-27）字节码编译器原来不认方法调用，于是区在 --compile 与
        C 那台上都跑不起来。现在四台都认：src/bytecode.mjs 发 CALLM，src/vm.mjs 执行它，
        self/compile.hmoca 发同一条，vm/hmyr.c 的 OP_CALLM 分派到 调区方法。
        值得记一笔的是 opcode 的号：它存成字节，而三处表要对齐（src/code-file.mjs 的
        操作码表、self/pack.hmoca 的操作码、vm/hmyr.c 的枚举与名字表）。第一版按字母序
        插在中间，症状是「文件在中途结束（offset 27185）」—— 后面每个号都错了一位。
        规矩写在 code-file.mjs 里：新号追加在末尾，旧号不动。
     三、§4.2 的原例（存到模块级变量）今天写不出来：模块顶层没有可变的声明
        （parser 的 parseDecl 只认 fn / type / const / effect / macro），记录也没有
        可写的字段（内置表里只有 field_get 与 field_has）。
        今天写得出来的是它的三个近形，两条错一条警告：
          「把块存进一条记录」   R0304（记录能交出去、能返回，而区留在原地）
          「把块存进一条索引」   R0304（2026-10-27 补的。索引可变，所以它活得比函数久，
                                 而区不会跟过去 —— 这一条比记录字面量更贴原例的 kept = b）
          「把块交给别的函数」   W0311（接收方的函数体不在这份源码里，判不了）
        原例本身要等语言有那个地方 —— 一条能言说的判据，不该替那个缺口说话。

   那三条里前两条都已补上：静态检查拦得住逃逸，而区在四台机器上都跑得动。
   剩下第三条是语言层的事 —— 它要的不是一条判据，是一个能存东西的地方。

====================================================================
3. 实时档位的硬规矩
====================================================================

标记为 @realtime 的函数（音频回调、帧回调）受额外约束：

  ・禁分配：不许在托管区分配；只允许预先建好的 arena：[定]
  ・禁 panic：不许 panic（回调里不能展开栈）；失败必须走 Result：[定]
  ・禁阻塞：不许文件、网络、锁等待；效果声明里不得出现这些效果：[定]
  ・有界：所有循环必须可判定有界（不许以「等外部条件」为界）：[议]

[验] 三条：① 一个计数钩子在回调里断言分配次数为 0；② 符合性套件里「@realtime 里分配」必须
编译失败；③ 基准：回调的最坏耗时有上界（多次运行的最大值不超过阈值的 1.5 倍）。

4. 反例（写在这里，免得日后忘）
====================================================================

— 4.1 逃逸（必须编译失败）

fn make() -> Bytes {
  let a = arena()
  let b = a.alloc(16)
  a.close()
  return b            // 反例：b 在 a 关闭后失效
}

— 4.2 静默换区（必须编译失败）

var kept: Bytes? = nil
fn store(a: Arena, b: borrowed Bytes) {
  kept = b            // 反例：托管变量指向 arena 内存
}

— 4.3 回调里分配（必须编译失败）

@realtime fn on_audio(out: borrowed mut Buffer) {
  let tmp = managed_alloc(1024)   // 反例：实时回调里分配
  ...
}

— 4.4 会「看起来能跑」的坑（必须由工具警告）

fn warm() {
  let a = arena()
  let list = a.alloc_list()        // 每帧新建 arena
  ...
}                                  // 关闭正常，但分配量随帧数线性增长

这条不是错误，是性能陷阱——所以工具要给警告，而不是沉默。

5. 与其它设计的关系
====================================================================

  ・空安全（SPEC §2.3）：与内存无关；T? 管的是「有没有值」，区管的是「何时释放」
  ・错误处理：硬档位用 Result；panic 只在非实时档位允许
  ・所有权检查（SPEC §2.4）：borrow 是可选硬档；arena 模型承担了大部分安全，所以借用检查可以只开在需要的模块
  ・契约（SPEC §2.4）：可以是「这个函数不分配」这类断言，交给编译器核对
  ・单位与量纲（[议]）：无关，但 CAD 场景会与「不移动」这条一起受用

====================================================================
6. 为什么这样选（与其他路线比较）
====================================================================

  ・全 GC：实时档位直接出局（停顿不可预期）
  ・全手动（C 式）：脚本档位出局（下限太硬，写起来累）
  ・全所有权（Rust 式）：安全最强，但学习曲线把下限压死；与「简明扼要」这一端冲突
  ・ARC（引用计数）：介于两者之间，但循环引用与原子操作在实时档位仍是隐患
  ・三区模型（本稿）：两头都在：竞技场给实时，托管给脚本，所有权给中间地带；代价是要教用户何时用哪个区

最后这一条代价要认：它要求使用者理解「区」。所以语言的默认档位要能自动选对区
（脚本里不写区就进托管），只有进硬档位时才必须显式声明——这是「渐进披露」的落点。
