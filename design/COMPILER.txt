编译器搬进 HMYR：现在到哪一步
====================================================================

  为什么要有这一份

  src/bytecode.mjs 是 JS 写的编译器，而它是「HMYR 不依赖宿主」最后一块借来的东西。
  self/compile.hmyr 是把它搬进语言自己的地方。这一份记的不是愿望，
  是「哪些已经搬过来了、哪些还借在那边、怎么看出来的」。

  已经搬过来的（都有断言）

    字面量      数、字符串
    名字        按名字取值（槽号在编译期定）
    运算        加减乘除余、六种比较
    调用        用户函数发 CALLF，内置发 CALLB
    容器        元组字面量、记录字面量、字段读取、下标
    语句        let、var、赋值、return、if 的两支、while、表达式语句
    跳转        if 与 while 的目标都事后回填（元组不可变，所以是重建）

  还借在 JS 那边的

    编译器的报错位置（行号列号）—— 自举 parser 的节点里还没有这个信息。
    .hmyrb 的落盘 —— 现在是 tools/compile-hmyr.mjs 用 src/code-file.mjs 写的；
      要彻底不借，这一层也得搬进 HMYR（写字节、拼文件头）。

  短路运算已经补上（第十轮）：&& 与 || 走 JMPF_KEEP / JMPT_KEEP，
  左操作数留在栈上由它决定跳不跳，两条路最后都用 BOOL 收成布尔。
  四条断言钉住它：两边都真、一边假、一边真、两边都假。

  自编译到哪一步了

  self/compile.hmyr 现在能编出整个自己加它的依赖：93 个函数、5131 条指令、31770 字节。
  那份产物也跑得起来了 —— 它执行自己的自测，输出「1 个函数，6 条指令，槽 2」，
  与原来那份编译器的自测一字不差。也就是说：HMYR 写的编译器，编出了 HMYR 写的编译器，
  而那个产物仍然能编东西。

  这一条在 test/hmyr-compiler.test.mjs 的第四节，两台机器都验过。

  卡了两轮的那个错，根因很小，而它教的东西不小

  症状    no field 'next' on that value
  根因    编译器的名字表从前往后找。同名变量第二次 let 之后，读的还是第一次那个槽 ——
          而那个槽里放的是上一轮的值（这里是空）。自编译把它放大到看得见了。
  修法    从后往前找：最近的绑定赢。

  这一类错之所以难查，是因为它在小程序里永远不出现 —— 只有「同一个名字被绑两次以上」
  才会撞上，而小例子恰恰都不重名。

  三、括号分组里的逻辑运算。paren_or_tuple 用 compare 读第一个元素，
      于是 (a && b) 在 && 上停住，报出来的是别处的错。改用最外层 logic 之后才对。
      同一处还有元组元素与记录字段值 —— 三处都要用最外层。

      它缺席的样子是「某个函数的体被读成 err」，而报出来的名字与 ! 毫无关系。

  怎么验的

  test/hmyr-compiler.test.mjs：
    一、十九段程序过两位编译者（HMYR 的与 JS 的），跑出的答案与手算一致；
    二、HMYR 编出的字节码交给 C 那台机器执行，其中包括 examples/twice.hmyr
        这么一个真东西 —— 它跑出 hi 42 琥珀音，与 JS 编译、JS 执行的一字不差；
    三、超出子集时明说「这一版还编不了」，而不是悄悄编错。

  搬这一份时掉出来的两件事，值得留着

  一、单行函数体。fn f() { return 7 } 写在一行，自举 parser 读出来的体是空的：
      each 遇到收尾的 } 就直接返回，把手上那一行丢了。多行时那行是空的（上一轮取过），
      单行时它就是全部。这不只影响编译器 —— 那一层的任何程序都受它影响。

  二、RECORD 的立即数。它在文件里是字符串数组，不是语言里的元组值。
      两位编译者都得照这个形状交出来，否则写盘那一步会写出一个空名字表，
      而症状是「没有那个字段」—— 看起来像字段名拼错了。

  下一步

  补短路运算，然后把 .hmyrb 的落盘也写进 HMYR。那之后 src/code-file.mjs
  只剩「读」的一半，而读那一半是给 JS 那台机器用的 —— 要不要留，由「谁还在这台机器上跑」
  回答，不由习惯回答。

  第十三轮：两位打包者逐字节相同了

  self/pack.hmyr 与 src/code-file.mjs 现在对同一份源码交出同样的字节，五个程序都验过：
  直接返回、两个函数带调用、带字符串比较与 print 的 if、带比较的 while、带下标的元组。
  四条格式修正与一条编译器修正把它凑齐，而那四条的症状是同一句：

    CALLF 与 CALLB 先写名字再写实参数（不是反过来）
    跳转目标是 u32，其他立即数多是 u16
    GLOBAL 带的是名字串，不是编号
    表达式语句只在「不是最后一条」时才丢值

  编译器那条是 while 要同时发空值与 POP：JS 那侧把 while 语句当表达式语句，
  循环编成一个什么也不产出的表达式，包着它的语句再把它丢掉。
  读到字节级才逼得出来 —— 两位编译者对「程序是什么意思」早就不吵架了。

  第十四轮：自举固定点，卡在累积

  想验的是「种子能重编自己」：先用 JS 编一次 self/pack.hmyr 存成种子，
  再让种子（在 C 上）编同一批源码，产物与种子逐字节相同 —— 那之后就不需要 src/ 了。

  pack.hmyr 现在能接多份源码（按给的顺序拼起来再编），这一步是对的。
  但整条链（lex、chain、stmt、body、compile、pack）一次编时内存不够：

      hmyr: out of memory

  原因在这一份自己身上：字节累加写成了 状态.b + (x,)，而元组不可变，
  于是每放一个字节都复制一次已有内容 —— O(n²) 的复制，几万字节就撑不住了。
  下一格是把它改成「按块累积」：每 256 个字节收成一块，最后交出块们的元组，
  由 write_bytes 一次写完。那既不改变字节，也不改变语义，只是不再平方。
