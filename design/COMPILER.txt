编译器搬进 HMYR：现在到哪一步
====================================================================

  为什么要有这一份

  src/bytecode.mjs 是 JS 写的编译器，而它是「HMYR 不依赖宿主」最后一块借来的东西。
  self/compile.hmoca 是把它搬进语言自己的地方。这一份记的不是愿望，
  是「哪些已经搬过来了、哪些还借在那边、怎么看出来的」。

  已经搬过来的（都有断言）

    字面量      数、字符串
    名字        按名字取值（槽号在编译期定）
    运算        加减乘除余、六种比较
    调用        用户函数发 CALLF，内置发 CALLB
    容器        元组字面量、记录字面量、字段读取、下标
    语句        let、var、赋值、return、if 的两支、while、表达式语句
    跳转        if 与 while 的目标都事后回填（元组不可变，所以是重建）

  还借在 JS 那边的

    编译器的报错位置（行号列号）—— 自举 parser 的节点里还没有这个信息。
    .hmoks 的落盘 —— 现在是 tools/compile-hmyr.mjs 用 src/code-file.mjs 写的；
      要彻底不借，这一层也得搬进 HMYR（写字节、拼文件头）。

  短路运算已经补上（第十轮）：&& 与 || 走 JMPF_KEEP / JMPT_KEEP，
  左操作数留在栈上由它决定跳不跳，两条路最后都用 BOOL 收成布尔。
  四条断言钉住它：两边都真、一边假、一边真、两边都假。

  自编译到哪一步了

  self/compile.hmoca 现在能编出整个自己加它的依赖：93 个函数、5131 条指令、31770 字节。
  那份产物也跑得起来了 —— 它执行自己的自测，输出「1 个函数，6 条指令，槽 2」，
  与原来那份编译器的自测一字不差。也就是说：HMYR 写的编译器，编出了 HMYR 写的编译器，
  而那个产物仍然能编东西。

  这一条在 test/hmyr-compiler.test.mjs 的第四节，两台机器都验过。

  指令累积是平方级的，而这件事在 2026 那天差点把机器拖垮
  --------------------------------------------------------------------

  量出来的：用种子编 self/ 六份（五千多条指令）时，C 那台机器一个进程吃到
  九千零八兆（采样到的工作集，第 171 秒）。整机内存被它一个人占满。

  原因是一行：发(状态, 指令) 写成 状态.码 + (指令,)。元组不可变，
  于是每发一条指令就复制一次已经发出的全部 —— 平方级。五千条指令意味着
  一千三百万次指令副本，而 C 那台分配了不回收，于是这个数就是它吃掉的量。

  这与打包器当年撞到的是同一个形状：状态.b + (x,) 每放一个字节复制一次全部，
  改法也一样 —— 按块收（打包器改完之后一百多秒变四秒、不再爆内存）。

  但这里比打包器难一处：跳转目标要事后回填，也就是要按位置改一条已经发出的指令，
  而块化之后按位置改要跨块定位。这是下一步要做的事，写下形状好让人接手：
  状态里存「已封的块 + 当前块」，长度是块数乘块长加小尾巴；回填时定位到块再重建那一块。
  块长取两百五十六条左右，回填跨不了几块。

  在那之前，有两道闸：

    一、C 那台现在有分配上限（默认四吉字节，HMYR_MEM_LIMIT 改，给 0 表示不限），
        超过了就打印一行并退 71 —— 「没有 GC」不等于「可以吃满」。
    二、test/bootstrap-seed.test.mjs 的第二、第三节默认跳过，设 HMYR_HEAVY=1 才跑。
        那两节正是这九千兆的来源。

  块化：第三次收尾（2026 这一轮）

  上面那两次的账到这里结清了一半：

    拼平 的顺序反了。上一次写成「小块 + 块们」，于是大于一块（256 条指令）
    的程序指令整段错位、小于一块的全对 —— 那正是「四份小程序逐字节相同、
    一百条 print 就不同」的来源。改成「块们 + 小块」，再改成折半拼接
    （从头往尾一块一块加，每一步都复制已拼好的全部，块一多又是一次平方级）。

    块号不能用除法。这门语言的除号是浮点除法，而 stage 0 那几份只许用
    白名单里的内置（int 不在里面 —— 宿主求值器会直接报
    「stage 0 does not need the builtin 'int'」）。块号改成减法循环算，
    块长是 256、块数不到五十，几轮就到了。

  验收：四份小程序与三百条 print 的大程序，新旧两位编译器逐字节相同；
  种子走到固定点 —— 块化版编自己得到 43680 字节，再编一遍还是 43680。

  块化：第四次收尾（同一天，从「第三节栈溢出」查进去）

  先量，不猜。给 C 机器加了调用深度探针（HMYR_DEPTH=1 每刷新一次峰值就打一行
  深度与函数名，HMYR_MAX_DEPTH=N 到 N 层就停下并说明）。拿它编 self/eval.hmoca，
  读出来的是两行字：

    拆行    一万六千层
    拼两半  三万层，然后退出码 0xC00000FD

  两件事，都不在内存那一头：

    一、拆行 是逐字符尾递归，深度就是字符数。一份五百多行的源码一万六千字符，
        就是一万六千层 C 栈。改成 while 循环（self/pack.hmoca 与 self/run.hmoca
        各一份，同样的写法）。

    二、拼两半 的中点找错了。它用「两头各收一步、差一步就停」，
        差一步时 左 + 1 正好等于 止，于是左半区间 [起, 中) 与整段 [起, 止)
        一样大 —— 同一段再交给自己，永远不缩小。块数一旦走到 2 就锁死。
        停的条件改成「差两步」，中点必然严格落在中间。

  修完之后 eval.hmoca 从「编不动」变成 14311 字节、零点九秒。

  种子跟着重来：JS 编出的编译器 A 编六份 self 得 B（43619 字节），
  B 再编一遍得 C —— B 与 C 逐字节相同，固定点站住了。
  bootstrap/pack.hmtn 换成这 43619 字节的一份；
  test/bootstrap-seed.test.mjs 第三节在 HMYR_HEAVY=1 下九项全过
  （它跑出了 hi 42 琥珀音）。

  还剩一个数：峰值 3.145 GB（HMYR_MEM=1 实测）。这一笔现在有了解释的方向：
  C 这台机器分配了不回收，而 self/pack.hmoca 是一份一份编 —— 每编一份，
  前面几份的堆都还在。单编 eval.hmoca 一份就要 1.61 GB；六份一路累积，
  就是这个数。真正该修的是「一份编完能不能把上一份放下」，
  那要 GC，或者按文件分段重启。




  卡了两轮的那个错，根因很小，而它教的东西不小

  症状    no field 'next' on that value
  根因    编译器的名字表从前往后找。同名变量第二次 let 之后，读的还是第一次那个槽 ——
          而那个槽里放的是上一轮的值（这里是空）。自编译把它放大到看得见了。
  修法    从后往前找：最近的绑定赢。

  这一类错之所以难查，是因为它在小程序里永远不出现 —— 只有「同一个名字被绑两次以上」
  才会撞上，而小例子恰恰都不重名。

  搬这一份时掉出来的三件事

  三、括号分组里的逻辑运算。paren_or_tuple 用 compare 读第一个元素，
      于是 (a && b) 在 && 上停住，报出来的是别处的错。改用最外层 logic 之后才对。
      同一处还有元组元素与记录字段值 —— 三处都要用最外层。
  四、逻辑非。chain 的一元层只认 -，于是 !keep_lines 解析不下去。
      它缺席的样子是「某个函数的体被读成 err」，而报出来的名字与 ! 毫无关系。

  怎么验的

  test/hmyr-compiler.test.mjs：
    一、十九段程序过两位编译者（HMYR 的与 JS 的），跑出的答案与手算一致；
    二、HMYR 编出的字节码交给 C 那台机器执行，其中包括 examples/twice.hmoca
        这么一个真东西 —— 它跑出 hi 42 琥珀音，与 JS 编译、JS 执行的一字不差；
    三、超出子集时明说「这一版还编不了」，而不是悄悄编错。

  搬这一份时掉出来的两件事，值得留着

  一、单行函数体。fn f() { return 7 } 写在一行，自举 parser 读出来的体是空的：
      each 遇到收尾的 } 就直接返回，把手上那一行丢了。多行时那行是空的（上一轮取过），
      单行时它就是全部。这不只影响编译器 —— 那一层的任何程序都受它影响。

  二、RECORD 的立即数。它在文件里是字符串数组，不是语言里的元组值。
      两位编译者都得照这个形状交出来，否则写盘那一步会写出一个空名字表，
      而症状是「没有那个字段」—— 看起来像字段名拼错了。

  下一步

  补短路运算，然后把 .hmoks 的落盘也写进 HMYR。那之后 src/code-file.mjs
  只剩「读」的一半，而读那一半是给 JS 那台机器用的 —— 要不要留，由「谁还在这台机器上跑」
  回答，不由习惯回答。

  第十三轮：两位打包者逐字节相同了

  self/pack.hmoca 与 src/code-file.mjs 现在对同一份源码交出同样的字节，五个程序都验过：
  直接返回、两个函数带调用、带字符串比较与 print 的 if、带比较的 while、带下标的元组。
  四条格式修正与一条编译器修正把它凑齐，而那四条的症状是同一句：

    CALLF 与 CALLB 先写名字再写实参数（不是反过来）
    跳转目标是 u32，其他立即数多是 u16
    GLOBAL 带的是名字串，不是编号
    表达式语句只在「不是最后一条」时才丢值

  编译器那条是 while 要同时发空值与 POP：JS 那侧把 while 语句当表达式语句，
  循环编成一个什么也不产出的表达式，包着它的语句再把它丢掉。
  读到字节级才逼得出来 —— 两位编译者对「程序是什么意思」早就不吵架了。

  第十四轮：自举固定点，先撞上平方复制

  想验的是「种子能重编自己」。pack.hmoca 先学会了接多份源码（按给的顺序拼起来再编），
  而整条链一次编时内存不够：

      hmyr: out of memory

  原因在 pack.hmoca 自己身上：字节累加写成了 状态.b + (x,)，而元组不可变，
  于是每放一个字节都复制一次已有内容 —— 平方级的复制，几万字节就撑不住。

  第十五轮：块化之后，固定点成立

  改成按块累积：攒够 512 个字节就封成一块，块们再拼成一个元组；
  交给 write_bytes 的是「块们的元组」，由世界那一侧一次拍平写出。
  块的数量只有总量的五百一十二分之一，复制量从平方掉到接近线性 ——
  同样的活从一百多秒、爆内存，变成四秒、稳稳跑完。

  于是「固定点」这一条立住了，而它的说法要精确：

      第一版  借一次 JS 编出来（种子）
      第二版  用第一版编同一条链（lex、chain、stmt、body、compile、pack）
      第三版  用第二版编同一条链
      验的是    第二版与第三版逐字节相同（40643 字节）

  为什么不拿第一版当基准：那是 JS 编译器编的，与 HMYR 编译器在「同名函数谁赢」
  这类合并规则上可以不同 —— 而那个差别与自举无关。自举需要的只有一条：
  自己编出来的东西，再编一次还是它自己。有了这一条，种子之后就不再需要 src/。

  这一节在 test/hmyr-pack.test.mjs 的第四节，前两版都由 C 那台执行。

  第二十轮之后：种子进仓库，src/ 不再是必需的

  bootstrap/pack.hmtn（40643 字节）现在躺在仓库里，而它是一版固定点：
  拿它当编译器，喂 self/ 的六份源码，出来的字节与它自己完全相同 —— 再编一遍还是相同。
  所以它一边是产物，一边是工具。

  一条要承认的事：种子第一次从哪来。它由「借一次 JS 编出 A，再用 A 编出 B」得到，
  而那一步只发生过一次，此后不需要 src/。这不是把借来的东西藏起来，
  而是把它缩到「一次」这个最小限度，并写在这里。

  test/bootstrap-seed.test.mjs 九项，而那条路里没有一次 node 调用：
    gcc 编出 C 那台 → 种子编 self/ 六份 → 字节与种子相同 → 再编一遍还是相同
  第三节还验了种子「不只是能重建自己」：它编出跑程序那一层，跑 examples/twice.hmoca
  得到 hi 42 琥珀音。一个只会自我复制的种子是个陷阱，能跑真东西的才是工具。

  还有一处仍要承认：源码里的 import 行要先拿掉，否则拼接起来的「多份文件」
  会被当成一堆不认识的语句。pack.hmoca 里补了与 self/run.hmoca 同形的 去导入
  （逐行看、只认行首的 import 与词界）—— 这不是语言的新能力，
  而是「读进来的东西要先整理」这一件搬运工的日常。
