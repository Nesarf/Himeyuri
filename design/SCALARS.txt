标量：这台机器此刻给的「意思」是什么
====================================================================

为什么要量这一件事
--------------------------------------------------------------------

  第三层剩下的全部，就是标量：数字、字符串、布尔、nil。它们现在是宿主的。
  要换掉它们，得先知道要保住的是哪些行为——否则换完只能靠手感判断「好像还一样」。

  test/scalars.test.mjs 就是那份清单，十九项，逐条可跑。它同时是未来的验收：
  谁把标量换掉，就得让这十九行继续通过。

数字
--------------------------------------------------------------------

  双精度浮点。整数与浮点是同一个类型，没有两个数字类型。

    0.1 + 0.2      等于 0.30000000000000004，不等于 0.3
    2 的 53 次方加一   存成 2 的 53 次方（精度按双精度走）
    7 / 2          3.5，除法不截断
    1 / 3          0.3333333333333333
    1e308 * 10     Infinity，溢出不报错
    0 - 0          0

  一条拒绝：除以零与对零取余都报 HMYR-行-012。那不是浮点的行为，是这门语言的选择——
  浮点本来会给 Infinity，而这里拦下它。

字符串
--------------------------------------------------------------------

  按 UTF-16 码元数，不按字符数。

    len("abc")        3
    len("😀")         2（一个代理对算两个码元）
    "abc"[1]          "b"
    slice("abcdef", 1, 3)   "bc"
    "a" < "b"         真（按码元序比较）

  这一条最容易被「看起来更合理」的写法改掉。按字符数更合乎人的直觉，
  而它会让每一处下标、切片与长度的含义同时改变。要改就得整体改，并先改这一份。

布尔与 nil
--------------------------------------------------------------------

    true + 1       2（布尔在算术里当一用）
    nil == 0       假（相等先看类型，跨类型走成串比较）
    1 == "1"       真（同上）
    len("")        0

  加法的三条重载：两个元组串接、任一边是字符串则拼接、否则按数字相加。
  于是 "abc" + 1 给 "abc1"。

要换掉标量意味着实现什么
--------------------------------------------------------------------

  对着上面那张表逐条实现，大致是这些：

    一、一个双精度数类型，连同它的十进制打印与解析（成串那一侧最麻烦）
    二、UTF-16 码元序列的字符串类型，连同长度、下标、切片、比较、拼接
    三、相等的跨类型规则（先看类型，再看成串）
    四、加法的三条重载
    五、除零与取余零的拒绝，带编号

  而这一份里没有的是：NaN 与负零的行为、非常大的整数与字符串的性能、
  Unicode 归一化（nfc 那一件现在走宿主）。它们要么还没量，要么本来就算在能力那一侧。

  于是「换标量」不是一件收尾的小事。它是第三层真正的墙：前面几格把「怎么跑」与
  「谁提供世界」换了，而这一格要换的是「数是什么、字是什么」。

一个地址（2026-10-21）
--------------------------------------------------------------------

  上面这些行为现在有了两个定义处：src/numbers.mjs 与 src/text.mjs。

  numbers.mjs 管解析、成串、加减乘除、取整、比较、判零、以及位模式（双精度 ↔ 六十四位）。
  text.mjs 管码元：长度、界内、取一个码元、切片、拼接、比较、码点。执行器与两个切词器
  都读它们，于是「1e308 是什么」与「一个表情有多长」不会因为读它的是哪一份实现而不同。

  它没有换来独立：实现仍是宿主的双精度与 UTF-16 串，这两层只是把标量的意思各收成一处。
  改变的是「换掉的时候只有一个落点」这件事第一次成立。

  收的过程中抓到一处安静算错的数：宿主切词器给进制字面量少填了 numeric，
  parser 于是退回 t.value，0x10 是字符串 "0x10"，0x10 + 0 给 "0x100"。
  子集那条路一直是对的 —— 两条路的分叉，只在有人写下进制时才现形，
  而仓库里 37 份 .hmoca 一份都没用进制。四处各自定义数，这就是它的代价。

  验收在 test/numbers.test.mjs（五十七条）与 test/text.test.mjs（二十条）：
  都跑在三条执行路上（宿主求值器、最小求值器、字节码），逐条比答案与错误编号；
  各自再加一层静态判据，说清那几份文件里不再自己写 Math.floor、Number()、
  typeof 判数、typeof 判串、.slice 与 String.fromCodePoint。
  缺了第二层，行为全同也可能只是几处各自写对了。

换到哪儿了（2026-10-24）
--------------------------------------------------------------------

  数的入口与出口不再借宿主：

    成文  numbers.mjs 的 成文 现在走 src/decimal.mjs —— 最短的、还能读回来的那一串，
          从一位试到十七位，判据只有「读回来是原来那个双精度」。
    解析  十进制的字面量走同一份；进制那一支自己逐字符累加，不再调 parseInt。
    位模式  那一对搬到 src/bits.mjs，它是三份实现里唯一需要知道宿主双精度长相的地方。

  算术与比较也接上了（2026-10-25）：加、减、乘、除、余、比、下整都走 src/f64.mjs，
  默认就是它。安全整数走一条快路，其余用位运算自己算双精度；比较对不可比交回 null，
  调用处按 IEEE 处理（见「还没量的」里那一条）。三条执行路读同一份 numbers，
  所以换实现只有一个落点。
  代价是量出来的：整数 1.5 倍、浮点 4.1 倍、最重的 curve 那套 3.1 倍。
  这三个是端到端 —— 整段程序跑下来慢多少。纯算术循环另有一笔账，见 design/F64.txt：
  二十万次加乘，浮点那条路三百倍上下，整数快路之后整数密集那半降到四倍多。
  两个数差得远，因为算术在程序总时间里只占一小块。混在一起说，两个都会说错。
  退回宿主那一条的开关是 HMYR_ARITH=0 或 bin/hmyr.mjs --host-arithmetic。

  所以此刻的账是：数的意思、算术、比较、成文、解析都在自家，借宿主的只剩
  「双精度类型本身」这一件事 —— 而那是第三层（自己的机器层）的事，不归这一层。

  字的那一半（2026-10-25）：src/units.mjs 把同一套规矩落在了码元序列上 ——
  长度、界内、取一个码元、切片、拼接、比较、码点拆代理对，全用一块十六位整数的
  内存自己写。它借的只有那样一块内存与两个转换原语（charCodeAt 与 fromCharCode）。

  两条执行路都接上了：最小求值器与字节码里的每一个字符串值都是码元序列，
  宿主串只在字面量进来与输出出去这两处出现。默认就是码元序列（2026-10-25 翻的），
  退回宿主串用 --host-scalars 或 HMYR_UNITS=0。

  验收在 test/units.test.mjs（二十四项）：一千个随机串逐项对照宿主的串、
  二十项边界（空、半边、落单代理、星平面、超出范围的码点），以及打开开关之后
  三条执行路在十五条文本程序上给出同一个答案。

  一句话说清位置：字符串的规矩早就在 text.mjs 里，而它的底现在是码元序列
  （src/units.mjs 那一份，经 src/text-impl.mjs 摆成同一个接口）。宿主串退成退路：
  --host-scalars 或 HMYR_UNITS=0。翻默认之前量到 5 个红，4 个是验收判据没跟上、
  1 个是真的（selfvmcompile 的「if 与字符串」多 44 字节）—— 根在 capabilities.mjs
  的 packValue 把码元序列当成记录编。修好之后带着开关跑满整轮全量，才翻的默认。

大整数的成本分解（2026-11-02）
--------------------------------------------------------------------

  curve 一直是全量里最慢的一套，而它的钱几乎全花在 self/bigint.hmoca 上。
  「慢在算术」这句话没有回答任何问题：一次模乘里，钱到底花在乘、在进位、
  还是在分配上？tools/bigint-bench.mjs 就是为了回答它写的。它不是套件 ——
  快慢没有通过与否，只有数字，与 tools/bench.mjs 同一条规矩。

  一次加载之后逐项计时的结果（下面这张是 16 位字那一版的；24 位之后的数字在本节后半）：

    零组(32) 分配            0.020 ms      占一次模乘的 1%
    加（16 个字）            0.065 ms
    减（16 个字）            0.028 ms
    比（16 个字）            0.002 ms
    乘（256 次内层小乘）     1.285 ms      占 78%
    模约简                   0.296 ms      占 18%
    模乘（乘 + 模约简）      1.655 ms
    一次完整的模幂           445 ms        255 轮，每轮一到两次模乘

  三句话把这张表读完：分配不是账上的东西（1%）；进位不贵（18%）；
  而乘那 78% 由 256 次内层小乘组成，一次约 5 微秒。

  那 5 微秒是这笔账里最值得看的一个数。两个 16 位数相乘再取余整除，
  在原生浮点里只要几纳秒 —— 所以这 5 微秒买的不是算术，是解释执行：
  一次内层循环是六条语句、二十来条字节码，每条约 250 纳秒。
  于是「想变快」在这个表示下的意思只剩一个：少跑几条指令。

  这个推论当场验过一次。乘的内层原来把 和 % 65536 算了两次（一次给字、
  一次给进位），改成取一次余、两处都用：

    乘      1.2853 → 1.1272 ms    减 12%
    模乘    1.6546 → 1.4868 ms    减 10%
    curve   端到端 83.3 秒 → 69.6 秒（两次都单独跑，同一套判据、同一台机器）

  同一条改动铺到了加、模约简的三段进位、乘的尾巴进位，以及 curve.hmoca
  自己的 规约 与 模加 上 —— 都是「取一次余，两处都用」，语义一个字没改。
  判据没动：bigint 四十项、curve 二十八项、sha512 八项、ssh 九项全过。
  一次内层少一条指令，换回 12%；这就是后面所有推演的斜率。

  字宽：从 16 位换到 24 位（2026-11-02 当晚做的）

  上一段写着「这一步不做」，理由是改动面；它后来还是做了，因为账已经量到
  可以照着推：乘占 78%，而内层小乘的次数由字数决定。字数从 16 降到 11，
  内层小乘从 256 降到 121 —— 乘那一半应当减 53%。

  实际量到的是：

    乘          1.1272 → 0.5997 ms     减 47%
    模乘        1.4868 → 0.7607 ms     减 49%
    模幂         421.2 → 217.6 ms      减 48%
    加          0.0640 → 0.0406 ms     减 37%
    curve 单独跑    69.6 → 36.1 秒     减 48%
    sign 那套      129.5 → 46.5 秒（它跑两次验签，每次一个标量乘）

  推算与实测的差在一个百分点上下，所以「少一条指令换一成二」那条斜率不只
  解释了旧代码，也预测了新代码 —— 这是这一轮最值得记的一件事。

  换的时候撞到三处，都不是「改个常数」就行的：

  一、低半与高半的交界。16 位字时 256 位正好是十六个字，交界落在字的边界上；
      24 位字之后，256 不是 24 的倍数，交界落在一个字的中间。低半那边碰巧被
      「成十六进制 只写最高字的十六位」救住了，高半差了整整八个二进制位。
      bigint 那四十项里的两条不通过就出在这里，而它对着 Node 的 BigInt 比 ——
      判据若只比「模乘对不对」，这个错会被模约简吃掉，永远看不出来。
  二、折叠常数。2 的 264 次方对 p 的余是 9728，不是 38。而 264 位的余最多是
      p 的五百多倍，所以第 255 位那一支不能再「减一次」或「循环几百次」，
      要一次算清要减几次（最多 511 次）。
  三、字节串的拼装。32 字节在 16 位字里是「两字节一个字」，在 24 位字里是
      「三字节一个字」，于是从字节串 的取模与位移都要换。SHA-512 那边只靠
      成数32 里一个乘数摸到字宽，改一个数就对。

  三处都是在判据上撞出来的，没有一处是「读代码看出来的」—— 这件事本身值得记：
  换表示的时候，判据比读得更靠得住。

  还没量的：一次求逆里模幂的分布（218 ms 里有多少花在最后一轮）；
  curve 的 36.1 秒里 bigint 占几成 —— 这一轮仍然只有间接的账。

还没量的
--------------------------------------------------------------------

  写作这一份时的边界，记下来免得后来的人以为量全了：

    NaN 能造出来（Infinity 减 Infinity），而它的比较不合 IEEE：
      == 给假、< 给假、> 给假 —— 这三条对；<= 与 >= 给真 —— 这两条不对。
      成因在「比」这个函数：它把「不可比」压成 0，于是调用处的 <= 与 >= 就成立。
      （已修 2026-10-25：numbers.mjs 加了 有序(a, b)，三个执行器与 C 那台在 <= 与 >=
      之前先问它，四条路径一起对；numbers 套件里加了四条非数比较盯着这一处。）
    负零：位模式与正零不同，而两者相等（IEEE 如此），成串都給 "0"。
    非整数下标："abc"[1.5] 原来三条路都给一个「未定义」的值，而那不是这门语言的值。
      （已定 2026-10-25：下标先取下整，与 slice 的起止、设()、chr() 同一条规矩 ——
      于是 "abc"[1.5] 给 "b"，-0.5 取整成 -1 之后算越界。四台机器一起改，
      scalars 套件钉住语义，numbers 那张表盯着三条路一致。）
    字符串的极端情形没有量（未配对代理、长度超过内存）。

  量到的照实写，没量的也照实写 —— 后者不是「大概没问题」。
