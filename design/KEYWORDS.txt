关键字：源码层的那二十五个词该叫什么
====================================================================

  这一页定一件事：源码里那二十五个保留词的汉字写法，以及改它的顺序。
  它服务的判据是「语法逻辑独立」—— 内部构成那一层（错误码七层、三十二种
  节点名、三十四条指令名）先换过，然后才轮到这一层：写程序的人敲的那个词。

  现状（2026-11-02）：二十五个词全部落地。三张词法器表各收二十五条
  （src/lexer.mjs、src/subset-lex.mjs、self/lex.hmoca），源码里一个英文
  关键字都不剩。剩下的英文只出现在两个地方：字符串里的 token 规范名
  （is_word(t, "if") 里的那个 "if"），以及注释里讲历史时的旧名 —— 两处都
  不该跟着换，理由见第三节。

  为什么先定表而不是先改代码：这批词出现在每一份 .hmoca 里，
  改一次要动全部源码、全部例子、以及文档里的代码块。
  表定下来之后那些替换是机械的；表没定就动手，同一批文件要改两遍。

一、这些名字从哪来
--------------------------------------------------------------------

  三个来源，按优先次序：

    一、已经落地的节点名。三十二种 kind 换名时定过一批汉字
        （字 名 二元 一元 调用 组 记录 索引 字段 类型名 组类型 记录类型
         函数类型 返回 表达式语句 赋值 当 若 定 变 类型别名 声明语句
         顶层变 函数 模块 常量 引入 宏 效果 块 误）。关键字优先沿用它们，
        于是「编译器内部叫什么」与「写程序的人叫什么」是同一套词。
    二、已经落地的指令名。三十四条操作码里有几个与关键字同名
        （布尔 常量 返回 存储 取 组 记录），同样沿用。
    三、既没有节点名也没有指令名的，才新定。这一批只有四个词：
        真 假 空 判（对应 true false nil match）。

三、实际走过的三步，与撞到的六个坑
--------------------------------------------------------------------

  做法与 design/FILETYPE.txt 第七节那一次改名相同，顺序也不能反：

    一、工具同时认两套。三张词法器表里收汉字，源码一个字不动。
        这一步做完，仓库里两种写法都能跑 —— 而它是能被单独验收的。
    二、批量换成汉字。只换代码位置：字符串里的是 token 的规范名，换了就坏。
    三、每一批一次全量验收，绿了才提交。

  反过来做（先换源码后改工具）会留下半个仓库两种写法，而那种状态最难查：
  工具认一半，剩下那一半安静地不被认出。

  实际撞到的坑，比原先猜的五条具体：

    一、字符串里的规范名不能换。is_word(t, "if") 的那个 "if" 是 token 归一之后
        的样子，换掉之后永远匹配不上 —— 那一轮三十五套一起红。
    二、记录字面量的字段名位置只接受声明层关键字。{pub: ...} 一直能跑，而
        {真: 1} 会炸：true 是表达式里的值，parser 在字段名位置没放宽那一类。
        所以真 假 空 三个词要先给那些字段名改名（真值 假值 空值）。
    三、关键字不能当函数名。self/pack.hmoca 有个函数就叫 空，它成了 nil 的
        汉字之后，parser 读函数名拿到 keyword，报「函数必须有函数体：?」。
    四、同一个词可能在同一个文件里既是变量名又是值。self/compile.hmoca 的
        编如果 里 假 既是 var 假 = s2 又是 c.ok == 假 —— 改的时候只动前者。
    五、replace 的范围要按「所有出现处」扫，不能按「核心文件」扫。第一遍
        改了六份核心文件，而 test/ 与 tools/ 里那两处 i.op === "RECORD" 漏了。
    六、import 有两个读法。词法器归一之外，模块加载器还按源码原文判断
        （self/run.hmoca 的 引号里 与 self/pack.hmoca 的是导入行），两处要成对修。

  还有一件事不在这一页的范围里，但每一步都踩它：改了 self/*.hmoca 就要重编
  runtime/ 四份产物、bootstrap/pack.hmtn、vm/pack_seed.h 与 C 机器。漏一份的
  症状是「按新字段名取，拿到 undefined」，看上去像改名改坏了。

四、怎么验收，以及验收的读数
--------------------------------------------------------------------

  可核的三条：

    一、三张词法器表各有二十五条，而 lexer 套件里有一条判据盯着三边相等 ——
        加一个词要么三处一起加，要么一处都不加，不允许漂移。
    二、src/lexer.mjs 的 KEYWORDS 集合仍然是那二十五个英文名。汉字是别名，
        归一发生在词法层，所以 KEYWORDS 不必动，动的是它旁边那张 关键字别名。
    三、全仓搜那二十五个旧名，命中只剩字符串里的规范名与注释里的历史名。

  读数（2026-11-02 这一段结束时）：docs 五十份全过；全量一百九十五套里
  一百九十四套绿，唯一的 arm 是三层与这一页无关的旧账（缺链接工具链九条、
  一条原有的 gc_收集 警告、五幺零二字节的 RAM 漂移）。

五、仍然不确定的几处
--------------------------------------------------------------------

  一、true 与 false 是否该做成内置而不是关键字。现在它们在关键字表里，
     而自举层的切词器把关键字一律当标识符（self/lex.hmoca 开头那段写着），
     于是「关键字」在两条路上的行为本来就不完全一样。它们落地了，而这一条
     没有因此变清楚 —— 只是不再挡路。
  二、nil 与空元组的关系。语言里没有 null，空元组就是它；而 nil 是关键字，
     汉字写成 空。落地之后实际读到的是：{空: 1} 那种字段名要改叫 空值，
     语言里那个「空」与「空元组」仍是两件事。这条设计上的张力没解开。
  三、运算符与标点的规范形式。ALIASES 现在让中文标点能进来，而出的一侧
     仍是 ASCII。关键字换完之后这一条要不要跟着换，是下一步的事 ——
     而格式化器的立场已经定了：它从 AST 重建，所以它印 ASCII。
