C 版虚拟机：那台不是 JS 的机器
====================================================================

  为什么要它

  HMYR 已经能解释 HMYR，但最底下那台是 JS 写的虚拟机。要让这门语言不依赖宿主，
  得有一台不是 JS 的机器执行同一份字节码。vm/hmyr.c 就是那一台：
  它读 .hmyrb，执行它，不懂 HMYR 的语法 —— 只知道指令流。那正是正确的分工：
  它是机器，不是语言。

  编译：gcc -std=c11 -O2 -Wall -o hmyr-vm vm/hmyr.c
  运行：./hmyr-vm 程序.hmyrb

  文件格式

  全部约定在 src/code-file.mjs 一个文件里，这一份照它读：

    文件头   "HMYRB" 五个字节 + 版本 u16（当前 1）
    函数数   u16
    每个函数 名字、参数量、槽数、效果名们、指令数、指令流
    全局数   u16，每个只是名字（值还没有落盘）

    串 = u16 长度 + 每字符 u16（UTF-16 码元，与语言里字符串的底一致）
    值 = 一字节标记：0 空、1 数（f64 小端）、2 串、3 布尔、4 元组、5 记录

  操作码按名字排序编号（src/code-file.mjs 的操作码表就是权威）。
  排序的理由是稳定：加一条指令时新号追加在末尾，旧号不动，于是旧文件仍然读得进来。

  这一台现在能做到什么

    指令   全部三十二条都实现了
    内置   十二个：print、print_err、str、len、chr、ord、to_int、slice、
           is_letter、is_mark、nfc、to_upper、to_lower、record_new、
           field_get、field_has、field_names、file_exists
    其它   报 HMYR-R0104 并把缺的那个名字说出来

  字符表随机器一起搬过去了：tools/ucd-c.mjs 从 runtime/ucd/codepoints.txt
  生成 vm/ucd-letter.h（677 段）与 vm/ucd-mark.h（321 段），C 里二分查找。
  于是 is_letter 不借任何人的表。

  归一化不做，明说：真表是 17 MB 语料，这台机器把文本原样交回。
  那对已经归一化的文本是恒等函数，对没归一化的就不对 —— 所以它记在这里。

  入口的那一条规矩

  self/run.hmyr 编译成字节码时，合并程序的规矩是「重名先到者赢」，
  而 import 顺序是依赖在前 —— 于是 main 会是 self/lex.hmyr 自己那个自测。
  症状是「跑起来没输出、退出码 19」：19 是 lex 自测算出的词数，与入口毫无关系。
  现在 tools/emit-code.mjs 在合并之后用入口文件的 main 覆盖，
  规则写在注释里：谁是入口，谁的 main 说了算。

  三处差异，写在明处而不是藏着

  一、数字写成文字用 %.15g，与 JS 那侧的最短往返写法在整数与短小数上一致，
      但不是每个值都一致。真正的那一份是 src/decimal.mjs，搬过来是另一格的事。

  二、值分配了不回收。一次运行很短，GC 是另一件工作。

  三、这台机器不查效果。效果是语言那一层的事，而 C 这一层只看指令流 ——
      要查的话，得把函数表里的效果名也读进栈帧，那是下一步。

  验收

  test/c-vm.test.mjs：找一个 C 编译器（没有就明说跳过），把它编起来
  （并且要求零警告，链接时把栈放大到 64 MB —— 解析器是深递归，默认那一兆不够），
  然后对同一份源码，JS 那台与 C 那台各跑一遍比输出。
  六组：算数与递归、比较与分支、字符串（含中文与码点）、坏文件被拒、
  自举层本身，以及最后 —— 用这台机器跑一个 .hmyr 文件。

  第五组是这一份存在的理由：self/run.hmyr 编成 40963 字节字节码，
  由 C 机器执行，跑出它自己的四行自测（1 + 2 * 3 → 7 等）。
  那四行是 HMYR 写的解释器在做真实解析与求值，而下面那台不是 JS。

  下一步

  已经做到：read_text、write_text、argv 都补上了，于是这台机器能跑一个 .hmyr 文件 ——
  hmyr-vm self.hmyrb 目标.hmyr 这一行里，读文件、解析、求值全是 C 与 HMYR 在做，
  中间没有 JavaScript。

  出口的规矩：带参数时用 命令行入口，不带参数时用 main（自举层自己的四行自测）。
  那是用户看到的样子：给它一个文件就跑，什么也不给就自测。

  已知缺口，实测撞到的：带 import 的目标程序在自举层这条路上还没跑通 ——
  conformance/lib-numbers.hmyr 报「不认识的运算符」。小文件（examples/twice.hmyr）
  是通的，所以问题落在「自举层读 import 的那条路」上，多半在 拼路径 与 ../ 的组合。
  JS 那张机器跑同一个 .hmyrb 会先撞「call depth exceeded (500)」——
  自举层套目标程序比直接跑深一倍，深限要放宽。两处都记在这里。
