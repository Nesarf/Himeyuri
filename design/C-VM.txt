C 版虚拟机：那台不是 JS 的机器
====================================================================

  为什么要它

  HMYR 已经能解释 HMYR，但最底下那台是 JS 写的虚拟机。要让这门语言不依赖宿主，
  得有一台不是 JS 的机器执行同一份字节码。vm/hmyr.c 就是那一台：
  它读 .hmyrb，执行它，不懂 HMYR 的语法 —— 只知道指令流。那正是正确的分工：
  它是机器，不是语言。

  编译：gcc -std=c11 -O2 -Wall -o hmyr-vm vm/hmyr.c
  运行：./hmyr-vm 程序.hmyrb

  文件格式

  全部约定在 src/code-file.mjs 一个文件里，这一份照它读：

    文件头   "HMYRB" 五个字节 + 版本 u16（当前 1）
    函数数   u16
    每个函数 名字、参数量、槽数、效果名们、指令数、指令流
    全局数   u16，每个只是名字（值还没有落盘）

    串 = u16 长度 + 每字符 u16（UTF-16 码元，与语言里字符串的底一致）
    值 = 一字节标记：0 空、1 数（f64 小端）、2 串、3 布尔、4 元组、5 记录

  操作码按名字排序编号（src/code-file.mjs 的操作码表就是权威）。
  排序的理由是稳定：加一条指令时新号追加在末尾，旧号不动，于是旧文件仍然读得进来。

  这一台现在能做到什么

    指令   全部三十二条都实现了
    内置   以 vm/hmyr.c 里 name_is 串起来的那些为准：print、print_err、str、len、
           chr、ord、to_int、slice、to_upper、to_lower、nfc、is_letter、is_mark、
           abs、floor、int、min、max、
           record_new、field_get、field_has、field_names、file_exists、
           read_text、read_lines、write_text、write_bytes、f64_bytes、pack_value、argv
    其它   报 HMYR-R0104 并把缺的那个名字说出来

  字符表随机器一起搬过去了，四张：

    vm/ucd-letter.h  677 段    tools/ucd-c.mjs 从 runtime/ucd/codepoints.txt 生成
    vm/ucd-mark.h    321 段    同上
    vm/ucd-case.h    1552 + 1460 条映射，加两组属性区间
                              tools/ucd-case.mjs 从 data/ucd 生成
    vm/ucd-nfc.h     2081 条分解、934 个组合类、961 个组合对
                              tools/ucd-nfc.mjs 从 data/ucd 生成

  前两张管「这个码元是不是字母、是不是记号」，于是 is_letter 不借任何人的表。
  第三张管大小写：UnicodeData 的简单映射打底，SpecialCasing 里无条件的那几条覆盖上去
  （德语那个字母会摊成两个单元），再加上 Cased 与 Case_Ignorable 两个属性区间——
  后者只有一处用途，就是词尾那一条规则：同一个字母在词里与在词尾形状不同。
  那一条不是表的事，是位置的事，所以写在代码里（hmyr.c 的 final_sigma）。

  第四张管归一化，NFC 就三步：分解到底、按组合类排好、再尽量组合回去。
  组合类大的记号要往前拱，遇到起头就停，类相同的不换位；组合时若中间隔着类不小于
  自己的记号就不试（阻塞），合成成功之后那个记号就没了，于是「中间什么都没有」重新成立 ——
  三个韩文字母能一路拼成一个音节，靠的就是这一条。
  分解与组合各有一处不走表：韩文音节是一段算术（初、中、终三个字母拼出来那一万多个），
  写成表只会是同一条算式抄一万遍，所以它在代码里。

  于是 nfc 也真的做了。以前它把文本原样交回，理由是「真表是十七兆语料」——
  那句话说的是测试语料（每个码点归一之后是什么），而生成一张表只需要三样小东西。

  这里记一件量出来的事：语料是 Unicode 16.0，而这台机器上的 Node 是 17.0。
  于是有 56 个码点是「宿主认得、语料里还没有」的（17.0 新加的那些字母，以及
  16.0 里已经有、但那时还没配对上大小写的几个）。C 那台按语料走，对那些码点一个字也不动；
  JS 那台问宿主，于是会动。这条缝不藏，验收里把它数出来（test/c-vm.test.mjs 第十节）：
  改动之后如果 Node 又升了一版，那个数字会变，而它会自己说话。

  入口的那一条规矩

  self/run.hmyr 编译成字节码时，合并程序的规矩是「重名先到者赢」，
  而 import 顺序是依赖在前 —— 于是 main 会是 self/lex.hmyr 自己那个自测。
  症状是「跑起来没输出、退出码 19」：19 是 lex 自测算出的词数，与入口毫无关系。
  现在 tools/emit-code.mjs 在合并之后用入口文件的 main 覆盖，
  规则写在注释里：谁是入口，谁的 main 说了算。

  启动器：一个可执行文件，两个入口

    hmyr 程序.hmyr  [参数]   先用种子把它编成字节码，再跑那一份。
    hmyr 程序.hmyrb [参数]   装载就绪的字节码，直接跑。

  第一条是这一份文档最后落下的那一块。它做到的事很具体：从源码到运行，
  路上没有 JavaScript —— 种子是自己编出来的字节码，编出来的那一份也由这台机器跑。
  判据是后缀，不是文件内容：猜错的时候症状比报错难查得多。

  种子的三种找法，按离用户近排：环境变量 HMYR_SEED、可执行文件旁边的
  bootstrap/ 与 ../bootstrap/、当前目录的 bootstrap/。都找不到就报 E0009 并退 2，
  并且把「怎么告诉它」写在那句消息里。

  两趟之间要卸下第一份（unload_program）。不卸的话第二份的槽位与名字池会接在
  第一份后面，症状是「程序跑起来了，但用的是别人的常数」—— 那种错比崩溃难查。

  编译那一段的 print 改道到标准错误：种子成功时会打印「N 个块」，
  那不该落在用户程序的输出里。改道而不是丢弃，因为编译失败时那几行正是诊断。

  步限分两档：编译那一段按两亿步直接给（编一份源码本来就不是小活），
  运行那一段照 HMYR_STEPS，默认五百万。

  Windows 上还有一件事要自己做：main 拿到的参数是按系统代码页解出来的，
  中文路径在那一步就已经坏了 —— 症状是「文件明明在，它说没有」。
  原始命令行还以宽字符留着，所以自己按 MSVCRT 那套规则再切一次，交成 UTF-8。
  这一条是验收逼出来的：测试里用中文当参数，第一次就没过。

  验收在 test/cli.test.mjs（十九项）：跑通一份真实源码、参数照顺序到达、
  返回值就是退出码、编不过时报 E0009 且不跑半成品、找不到种子时说得出话、
  字节码那条老路没变、以及 HMYR_KEEP 留下的那份文件确实是个 .hmyrb。

  ARM：这台机器编得进一块没有操作系统的板子

  2026 实测，用的是本机 Keil MDK 5.37 里的 Arm Compiler for Embedded 6.18：

    armclang --target=arm-arm-none-eabi -mcpu=cortex-m4 -O2 -Wall -c vm/hmyr.c

  编过，零警告，产出一个十九万字节上下的对象文件。验收在 test/arm.test.mjs：
  找得到 armclang 就编，找不到就明说跳过。

  编过之前要修两处，都是桌面假设漏在裸机那一条上：

    一、unistd.h 只为 getpid 进来，而裸机的 C 库没有它。
       现在它只在非 ARM 的 POSIX 上进来。
    二、临时路径里的 pid。裸机上没有 pid，也没有并发，名字就是固定的那个。

  这两处很小，而它们是这件事的全部意义：同一个 vm/hmyr.c，除了这两行，
  没有别的地方假设自己跑在 Windows 或 POSIX 上。四张 Unicode 表、字节码装载、
  解释器、启动器、分配上限与让路，全都在里面，一个字节都没改成条件编译。

  尺寸（实测，tools/arm-size.mjs）

    这台机器    code 39140 · ro 122426 · rw 12 · zi 1146
    移植骨架    code 378   · ro 48     · rw 0  · zi 4108

    Flash 常住 161992 字节（158.2 KB），RAM 常住 5266 字节（5.1 KB）。

    那个一百二十千字节的只读段几乎全是四张 Unicode 表 —— 于是「带不带表」
    直接决定这台机器装不装得进一块小 Flash 的芯片。移植骨架那四 KB 是示例的
    出口缓冲；真实项目里换成 UART，那四 KB 就没了。

    这一份不含 C 库、启动文件与运行时的堆与栈；真上板子时那几项要另算。

  堆：跑一个程序要多少（实测，HMYR_MEM=1）

    两函数、二十六条指令的小程序      峰值 29674 字节
    二百次循环、一条累加的程序        峰值 30105 字节

    第二个只比第一个多四百三十一个字节，因为循环里每一轮的值都被丢掉了 ——
    涨的主要是「装字节码、建函数表」这一笔固定开销，不是每轮泄漏。

    于是板子上那笔账是：静态 5.1 KB + 堆 30 KB 起 + 栈几 KB。
    一颗 128 KB RAM 的芯片跑得动小程序；而这一台不回收，所以「跑一个上午」
    那种用法在板子上不成立 —— 这与桌面上的选择同源，只是那边内存不心疼。

  接下来还要什么，按顺序：

    一、链接 —— 这一件做完了。port/startup_cm4.s 是向量表与复位入口，
       port/link.sct 是分散加载（512 KB Flash 从 0x08000000、128 KB RAM 从
       0x20000000、栈 8 KB、堆 32 KB），armlink 用的是 microlib。
       链出来的映像：ROM 168840 字节（164.9 KB），RAM 里 rw 40 + zi 42120。

       路上撞到的三件事都记在这里，因为它们各自都会伪装成别的问题：

         一、段名对不上。向量表在 GNU 语法的 .isr_vector 里，而 scatter 写的是
            Keil 惯用的 RESET —— armlink 报「没有段匹配这个挑选器」。
         二、__initial_sp 未定义。它由启动文件与链接脚本共同决定，两边都要给。
         三、atexit、exit、getenv 在 microlib 里没有。它们各自在 hmyr.c 的哪条
            路径上：atexit 只在 HMYR_MEM 那条诊断里；getenv 在所有诊断开关上；
            exit 在「不行了」的每一处。port/arm-port.c 给了三个桩，注释里写着
            为什么 exit 选择死循环而不是复位。
         还有一条警告：向量表是 ~PRES8 段而在存 REQ8 函数的地址。回答它的方式
         是在汇编里声明 .eabi_attribute 25, 1 —— 我们确实保留 8 字节对齐。
    二、读字节与写字节 —— 这一件也抽出来了。原来它们是桌面假设：read_file 走
       fopen，print 走 stdout。现在它们成了两个函数指针（Hmyr平台），
       默认是空的两格，空的时候走桌面那两份实现，于是桌面行为一个字节没变。
       板子开机时调一次 hmyr_装平台，把「从串口收」「往串口发」装进去即可。
       验收在 test/arm.test.mjs 第三节：入口存在、读与写都走它、桌面那份实现仍在。

       而且这条路在桌面上走得通：port/board-check.c 用 -DHMYR_LIB 编
       （去掉 main，留下 hmyr_运行），把一份字节码读进内存，交给 板子装上，
       再调 hmyr_运行，最后把出口缓冲打出来。验收是 test/board.test.mjs 七项：
       输出里有「hi 42 琥珀音」、退出码是程序的返回值、出口是那块缓冲。
       没有硬件也能验的那一半，到这里就没有缺口了。
    三、内存。默认四吉的上限与「分配了不回收」在一颗几十千字节 RAM 的芯片上
       立刻 OOM；四张 Unicode 表也占几十千字节的只读段。要上板子，
       得先有一版按需装载的表，或者干脆不带表。

  换句话说：这一轮证明的是「这台机器不属于桌面」，还没证明「它能在板子上跑」。
  两件事已经办到：桌面假设只有两处（都在给临时文件起名），以及读与写成了
  显式的两个口。剩下的都在板子那一侧：启动文件、内存布局、装那两个函数。
  这台机器与 src/capabilities.mjs 说的是同一件事 —— 语言只认动作，谁兑现由机器定。


  差异，写在明处而不是藏着

  一、数字写成文字。这一条本来在这里，现在没有了（第六轮）：C 那台以前用 %.15g，
      于是 0.1 写成 0.100000000000000006，而 JS 那台写 0.1。现在 C 也走
      「从一位有效数字试到十七位，第一个能读回原值的就留下」这一条，
      排版照 ECMAScript 那套（定点与指数形式的分界），与 src/decimal.mjs 一字不差。
      test/c-vm.test.mjs 第八节拿八个数对着比，包括 0.1、一除以三、与一个大整数。

  二、值分配了不回收。一次运行很短，GC 是另一件工作。
      这一条仍然是设计选择，而选择现在有个数字跟着：这台机器每次分配都记账
      （四个入口都换过，多要八个字节把块的大小记在自己头上），打开 HMYR_MEM
      就在退出时打印活着多少、峰到多少。最重的那一份自带工作 —— 自举层解释
      lib-strings 的三十二个断言 —— 峰值一百七十兆上下，而那三十二个断言照样全过。
      于是这句话现在是可验收的：test/c-vm.test.mjs 第十二节把那个数字读出来，
      要求它大于一兆（记账没坏）且小于二百五十六兆（这条界线还站得住）。
      要往下压就得做 GC；在那之前，至少这一条不再只是一句话。

  三、不查效果 —— 这一条也没有了（第七轮）。函数表里本来就带着每个函数声明的
      效果名，只是从来没人用。现在 CALLF 时往下核：被调者声明了什么，
      调用者就得先声明什么，缺一个就在调用处报 R0201，并且不执行。
      五个标准库仍然全过 —— 也就是说 self/ 六份文件自己的效果声明是完整的。
      反向也验了：一个没声明 file 的 main 去调要 file 的函数，被拒且文件没写出来。

  四、大小写只做 ASCII —— 这一条也没有了（第二十一轮）。表按全码点从语料生成，
      词尾那一条规则按位置算。两台机器对同一串文字现在交出同一串单元，
      取样是全码点扫过来的那三千多个「换了会变」的码点加一段等距抽样。

  五、归一化把文本原样交回 —— 这一条也没有了（第二十二轮）。见上面第四张表：
      分解、组合类、组合对都在仓库里，韩文走算术。两台机器对一万五千多行样本
      逐行一致，其中一万三千五百多个单码点与 conformance/unicode-nfc.txt 一字不差。

  两处静默的差异，是这一轮补大小写时撞出来的

  它们都不在差异清单上，因为没有人量过 —— 而两台机器各自跑各自的程序时都不会出声。

  ord 在 C 上读的是第一个单元，在 JS 那三台上读的是第一个码点。
  基本平面里的字符两者一样，于是这个差别只在增补面的字符上现形：
  同一个字，一边给 66560，一边给 55396（那个字的高位代理）。
  现在 C 也按码点读。

  chr 在 C 上把那枚码点一刀截成一个单元，于是增补面的字符只剩半个，
  而「只差一个字节」这种症状看起来像别处的错。现在按需要写出两个单元。

  还有一件事不在语言里，但它会让「两台机器一样」这句话对不上：
  Windows 的文本模式把每个换行翻成两个字节。现在这台机器开跑时把标准输出与
  标准错误按字节打开（_setmode 与 _O_BINARY），于是两边交出去的是同一串字节。

  验收

  test/c-vm.test.mjs：找一个 C 编译器（没有就明说跳过），把它编起来
  （并且要求零警告，链接时把栈放大到 64 MB —— 调用是 C 递归，默认那一兆不够），
  然后对同一份源码，JS 那台与 C 那台各跑一遍比输出。
  十二组：算数与递归、比较与分支、字符串（含中文与码点）、坏文件被拒、
  自举层本身、用这台机器跑一个 .hmyr 文件、五个标准库、数字写成文字、
  效果声明、大小写、归一化、堆账，以及第十四组的调用深度。

  第十组是三方的：C 那台跑一遍，JS 那台跑一遍，语料那一侧再独立读一遍
  （data/ucd 的 UnicodeData 与 SpecialCasing），于是「表有没有按语料生成」
  与「两台机器一不一样」是两条分开的断言。差出来的那 56 个码点另算一条，
  它该小的正好是「宿主认得而语料没有」那些。

  第十一组的样本从三张表里长出来：每个有规范分解的码点、每个组合对、
  一段等距抽样（拿 conformance/unicode-nfc.txt 当另一侧的答案，它是一百一十一万行）、
  两个组合类不同的记号按两种先后排、以及韩文字母拼音节。

  第五组是这一份存在的理由：self/run.hmyr 编成 40963 字节字节码，
  由 C 机器执行，跑出它自己的四行自测（1 + 2 * 3 → 7 等）。
  那四行是 HMYR 写的解释器在做真实解析与求值，而下面那台不是 JS。

  下一步

  已经做到：read_text、write_text、argv 都补上了，于是这台机器能跑一个 .hmyr 文件 ——
  hmyr-vm self.hmyrb 目标.hmyr 这一行里，读文件、解析、求值全是 C 与 HMYR 在做，
  中间没有 JavaScript。

  出口的规矩：带参数时用 命令行入口，不带参数时用 main（自举层自己的四行自测）。
  那是用户看到的样子：给它一个文件就跑，什么也不给就自测。

  已经验过的形状（都是 C 机器 + 自举层 + 目标文件）：
    算数与递归、while、字符串拼接、slice、chr(92) 这类反斜杠、记录与字段、
    import "./b.hmyr"、import "../b.hmyr"、中文字符串。

  还没通的一处，诚实记在这里

  规模上去之后会报「不认识的运算符：[object Object]」——
  conformance/lib-strings.hmyr（二十二个函数、三百行）与 conformance/lib-tuples.hmyr
  都复现，而上面那几种小形状都通。那句错来自 self/eval.hmyr 的 求二元，
  它收到的 op 不是字符串。

  定位时的两条事实：
    一、自举层不再把 import 行当语句解析了（合并从 里加了 去导入）——
        那是一个真修复，但它没能解决这个错。
    二、JS 那台跑同一份 .hmyrb 会先撞「调用深度」或 JS 栈，所以这一处只能在 C 上查 ——
        C 是唯一跑得到那里的机器。

  下一步的定位办法（写在明处，省下一次重走）：让 C 在 fail 时带上当前函数名与 pc，
  再用二分把它缩小到某一条指令。规模相关的错多半在某个数组的长度或索引上，
  而现在的报错只说「运算符不对」，离现场太远。

  已经走了一步（2026-10-26）：self/eval.hmyr 的 求二元 在收尾处加了四支辨认 ——
  若 op 是节点记录就说出它的 kind，若它自己带 op、带 name、带 value 也各说一句。
  于是消息从「[object Object]」变成了「一个带 value 的记录」。

  那一条很重要：带 value 的记录正是求值器自己的返回值形状 {ok: true, value: …}。
  所以 求二元 收到的第一个实参不是一个运算符，而是一次求值的结果 ——
  也就是「实参在栈上错位」这一类错。

  又走了一步（同一天）：给 C 加了三道守卫与一条轨迹。

    槽越界    LOAD / STORE / ASSIGN 若下标超出这个函数的槽数，报 R0110
    调用不足  CALLF / CALLB 若要的实参比本帧压着的值多，报 R0110
    轨迹      HMYR_TRACE=1 时留最近四十条指令（pc、操作码、当时的栈深）
    深度      HMYR_DEPTH=1 时每刷新一次峰值打一行（深度、函数名、调用者）；
              HMYR_MAX_DEPTH=N 到 N 层就停下，退出码 72，并说出是哪一层哪个函数

  第一道没响，第二道响了一次，而那次是误报。

    calling arg_list wants 3 argument(s), the frame has 2 (pc=62)

  那句话后来证明是守卫自己的错：C 这一侧的栈是所有帧共用的一条，
  拿 base 去比「本帧压了几个」在跨帧时会误判。收窄成「栈深不足」之后，
  examples/twice.hmyr 立刻恢复正常（hi 42 琥珀音），所以那一次报的是假的。

  lib-strings.hmyr 的错因此仍然在，而且不是栈深不足 —— 否则会报 R0110。
  现在能确定的是：求二元 收到的第一个实参是一个带 value 的字段值，
  所以在 节点.op 这条字段读取上，取到的不是 op。

  追它的时候抓到了一件真事（2026-10-26）：自举的表达式解析里没有逻辑那两级。

    症状   目标程序里写 if a && b { 时，条件解析停在 &&，于是 parse_if 看到的下一个
           记号不是花括号，报「语法层报的错：if」—— 错的文字是 if，与 && 毫无关系。
    修法   self/chain.hmyr 加 or_op、and_op、logic、logic_tail、and_level、and_tail 六件，
           并把 stmt.hmyr 的 from_here 从 compare 改成 logic。
    顺带   self/eval.hmyr 的 求二元 也要认 && 与 ||（不短路，这一点写在注释里）。

  修完之后 if a == 1 && b == 2 与 if a == 9 || b == 2 在 C 机器上都算对了，
  test/c-vm.test.mjs 第二节加了这两条。

  但 lib-strings.hmyr 的错没变。所以它是第三件事，不是这一个。

  第三件事追到的地方（2026-10-26）：错消息现在会把那个记录的字段名说出来，
  而它说的是 ok,value —— 正是求值器自己的返回值 {ok: true, value: …}。
  也就是说 求二元 的第一个实参是一次求值的结果，实参整体错位了一格。

  最小复现做不出来：外(1, 内(2), 3) 与 外(内(0), 2, 3) 在 C 机器上分别得 133 与 123，
  与 JS 那台一致。所以错位不在「嵌套调用」这件事本身，而在 lib-strings 那个规模上
  才出现的某个构造。

  下一步该做的是二分：把 lib/strings.hmyr 与 conformance/lib-strings.hmyr 各删一半函数，
  直到某一次删掉之后错消失 —— 那一段就是复现。

  二分做完了，复现缩到四行（2026-10-26）：

    fn id(n: Int) -> Int { return n }
    fn main() -> Int {
      if id(1) == 1 { print("eq") }
      return 0
    }

  这一份在 C 机器上报「不认识的运算符：一个带 value 的记录」。对照三条：

    let x = id(1)  然后 x == 1        通过
    1 == id(1)                        通过
    id(1) == 1                        出错

  所以触发条件是「一个调用的结果当二元运算的左操作数」。
  二分是这么走到的：conformance/lib-strings.hmyr 的第一个断言块就复现，
  再剥掉 import 与中文标识符，只剩上面四行。

  下一格从这条出发看 self/chain.hmyr 的 compare 与 add 对
  「左操作数是调用」这件事的处理 —— 那是自举 parser 的一条路径，
  与 C 的字节码执行无关（同一份目标代码在 JS 那台上也走同一条自举 parser，
  只是 JS 那台跑不到那么深就先撞调用深度了）。

  又缩了一层（2026-10-26）：写了一个探针，import self/lex.hmyr 与 self/body.hmyr，
  然后让自举层去解析 self/chain.hmyr，数它认出几个函数。探针报的是
  「语法层报的错：if」—— 而那探针自己一行 if 都没有。

  但那个结论后来被推翻了，而推翻它的方式值得写下来：直接在宿主上量。
  用 loadUnit + runUnit 把自举层跑起来，调它的 函数名们 依次解析 self/ 的六份文件，
  结果是 26、26、10、16、38、33 —— 与文件里的 fn 数完全一致，一个不缺。

  探针当时报错是因为步数不够（那一次是宿主那边的 500 万步上限），
  而「跑得太久」被我看成了「解析失败」。这类误读的代价是两格。

  同一批探针还确认了另一件事：那条四行程序在宿主上跑是对的 ——
  id(1) == 1 为真、print 也照常输出。

  所以最后剩下的事实是：同一份字节码，JS 那台机器跑得对，C 这台机器把实参错位了一格。
  这不是解析器的问题，也不是库的问题，是两台机器之间的分歧。

  下一格该做的是逐指令对比：给 vm.mjs 也加一条 trace（它现在没有），
  然后让同一份自举层字节码在两台上跑同一条目标程序，比最后几十条指令的 pc 与栈深。
  分歧的那一条就是答案。

  逐指令对比做了（同一天），而且它给出的答案比预期更具体。

  两件工具：
    tools/run-bytecode.mjs   用 JS 那台执行一份 .hmyrb（这是它的第一次正式入口）
    HMYR_TRACE=1             两边都留最近四十条指令（pc、操作码、栈深）
    HMYR_CALLS=1             两边都打调用序列，只打「第几个函数」

  调用序列比指令轨迹有效得多：四十条轨迹在两千条之后，一屏看不出先后；
  而调用序列一行一条，直接 diff 就定位到第 2076 行不同。

    第 2076 行之前的 2075 条完全相同。
    C 在那之后调 78（名字们）、75（坏）、100（坏执行）
    JS 在那之后调 74（好）、104（执行块）、103（执行块从）

  79 是 求二元。所以两台机器在同一个 求二元 调用上走了不同的分支：
  C 认为 op 不是运算符（于是去拼那句错话），JS 认为它是。

  前面 2075 条完全一致，说明这不是某一类指令的系统性错误，
  而是某一个具体的值在某一次读取时错了一位。下一步该查 RECORD：
  求二元 的 op 来自 节点.op 这条字段读取，而字段值来自造记录时压栈的顺序。

  再往下（同一轮）：把内置调用也记进序列，分歧就露出来了。

    第 4316 行之前一致。CALL 79（求二元）之后：
      C  : CALLB field_has n=2  （三次）
      JS : CALL 74（好）

  那三条 field_has 是 求二元 收尾处的诊断分支 —— 它们只在 op 不是任何已知运算符时
  才被问。所以结论很硬：同一次 求二元 调用，第一个实参在 C 上是记录，在 JS 上是字符串。

  三件对账工具因此齐了，两台机器都认：
    HMYR_CALLS=1   调用与内置调用的序列（函数打位置，内置打名字）
    HMYR_FIELDS=1  每次字段读取：pc、记录字段数、命中第几个、名字的码元、值的种类
    HMYR_POOL=1    （只 C 有）名字池按索引 dump，与 JS 侧模拟出来的并排比

  名字池比过了：1269 项逐行一致。字段读比过了：前 600 次一致。
  所以不是池、不是名字匹配 —— 是压进 求二元 第一个形参的那一个值本身。

  再往下（第三轮）：把字段与调用并成一条带全局序号的事件流，并给那一次调用加了实参种类。
  结果比上一句更硬，而且推翻了它的一半：

    EV 4804  FIELD pc=109 n=4 i=1 name=op val=str      ← 两台机器完全一致
    ARGS79   C  base=0 stackn=3 n=3 tags= 5 5 5
    ARGS79   JS base=0 stackn=3 n=3 tags= 2 5 5

  5 是记录，2 是字符串。所以「op 不是字符串」这句是错的 —— op 在两边都是字符串，
  而且读它的那条 FIELD 在同一个事件号上给出同样的结果。

  真的发生的是：求二元 被调用时，C 的栈顶三个值全是记录，op 那个字符串被挤下去了。
  也就是在 op 压栈之后、求二元 调用之前，有一步多压了一个值。

  下一格的方向因此是「找那一步」：给 CALL 事件加上当时的栈深（JS 那侧栈是局部的，
  一定等于实参数；C 那侧是共享的一条，多出来的那个值会在栈深上现形）。
  哪一次调用的栈深在两边第一次不同，那一次就是多压的那个。

  找到了，而且它是这一整串错误的根（第四轮）：

  C 的弹栈不认帧基线。

  两台机器的栈模型不同，而这一点一直没说透：JS 那台的栈是每帧一条数组，
  弹空只是拿到 undefined，帧外的东西碰不到；C 这台所有帧共用一条栈，
  pop 若不认基线，帧内弹空就会真的吃掉调用者的值 —— 少一个，后面所有实参
  整体错位一格。装函数从、跑模块们 里那种「if 的一支弹一次、另一支也弹一次」
  的写法，正是撞它的地方：真支里 ASSIGN 已经弹掉结果，随后的 POP 又弹一次。

  修法是小改：run_func 进帧时把 base 交给一个全局 g_base，pop 在 g_stack_n <= g_base
  时交回空值而不弹；RET 时还原外层的 g_base。

  修完立刻见效：
    examples/twice.hmyr                  hi 42 琥珀音
    conformance/lib-strings.hmyr         0
    conformance/lib-tuples.hmyr          0
    conformance/lib-json.hmyr            0
    conformance/lib-protocol.hmyr        0
    conformance/lib-tables.hmyr          16（还有一条，另一件事）

  也就是说：追了三轮的那条「实参错位」，是两台机器的栈语义差了一点点。
  而它只在「自举层替目标程序执行」这种深嵌套下才显形，所以小例子一直跑得对。

  同一轮里还有第二处，是 lib-tables 的第 16 条：合并两条同名字段的记录，
  件数算出四个而不是两个。差在 record_new —— C 那版按顺序塞，同名键不覆盖；
  而 JS 那侧记录是 Map 或普通对象，两者都是「后者赢」。改成覆盖之后五个库全通。

  于是现在的对账表是：
    examples/twice.hmyr                  hi 42 琥珀音
    conformance/lib-strings.hmyr         0
    conformance/lib-tuples.hmyr          0
    conformance/lib-tables.hmyr          0
    conformance/lib-json.hmyr            0
    conformance/lib-protocol.hmyr        0
  六条都在 test/c-vm.test.mjs 的第六、七节里，编不出 C 那台时明说跳过。

  事件流这个形式的代价要说一句：它每步写一行 stderr，跑一次几万行。
  所以三个开关都默认关着，只在对着查的时候开。

  下一步该查 FIELD 的名字匹配，以及 RECORD 指令里字段名与值的对应顺序 ——
  这两处都在「名字与值的配对」上，而错位的表现正是「取到了另一个字段的值」。

  怎么复现（省下一次重走）：
    gcc -std=c11 -O2 '-Wl,--stack,67108864' -o hmyr-vm.exe vm/hmyr.c
    node tools/emit-code.mjs self/run.hmyr self.hmyrb
    HMYR_TRACE=1 ./hmyr-vm.exe self.hmyrb conformance/lib-strings.hmyr

  一次栈溢出的查法（2026 这一轮）

  症状    hmyr bootstrap/pack.hmyrb 出 self.hmyrb self/eval.hmyr ... 退出码
          0xC00000FD，零输出。那个数字是 Windows 的 STATUS_STACK_OVERFLOW，
          它只说「栈没了」，不说谁挖的。

  量法    加两个开关。HMYR_DEPTH=1 时每刷新一次峰值就往 stderr 打一行：
          深度、函数索引、函数名（UTF-8），以及它从谁那里被调用。
          HMYR_MAX_DEPTH=N 时到 N 层就停，退出码 72，并说出停在哪一层哪个函数 ——
          比等到栈真的见底好，因为栈见底时连打印的机会都没有。

  读到的  拆行      一万六千七百零四层（逐字符尾递归，深度等于字符数）
          拼两半    三万零三百三十六层，然后崩

  根因    拆行：每个字符一层 C 栈。self/pack.hmyr 与 self/run.hmyr 各一份。
          拼两半：找中点时「两头各收一步、差一步就停」，差一步时 左 + 1 等于 止，
          左半区间与整段一样大，于是同一段再交给自己 —— 不收敛。
          块数一走到 2 就锁死。

  修法    拆行改成 while 循环；拼两半 的停条件从「差一步」改成「差两步」。
          修完 eval.hmyr 从编不动变成 14311 字节、零点九秒，
          自举固定点重来一遍是 43619 字节，B 与 C 逐字节相同。

  教训    深递归在这里有两个来源：源码写法（逐字符、折半算错）与机器模型
          （每层调用一层 C 栈）。所以「编不动」的第一问不是「内存够不够」，
          而是「深度有多大」；深度现在有开关能量。

  回收：三吉字节降到一吉字节（同一轮的后半）

  这台机器一直分配不回收，「一份一份编」时前面几份的堆全留着 ——
  自编译峰值 3.145 GB 就是这么来的。

  现在有一层标记清扫，收两样：Value 数组（元组的元素、记录的 vals、
  调用帧的槽）与字符串。

  字符串能收的前提是「交给 Value 的每一段都从一个入口来」：
  单编 串存 那一支走回收，其余照旧走堆。为此 slice 改成拷贝 ——
  子串指针落在块中间时地址表查不到它，而「查不到」就等于「不是我的块」，
  父串一被收掉它就悬空。文件镜像里的字符串不在这条链上（它们指向装载缓冲区），
  标记时查不到，也就永远不收 —— 那正是它们该有的待遇。

  四件事要说清：

    一、帧链。run_func 入口把 slots 指针压进一条链，出口还原；
        GC 靠它看见递归中的槽。以前所有帧共用一条操作栈，GC 看不见
        每个帧自己的槽数组 —— 而把正在用的槽收掉，是这类事故最常见的形状
        （第一次实测就是这么崩的：只标了槽里的值，没标槽数组本身）。
    二、显式标记栈。标记走的是数据的形状，递归版在自编译那种规模上
        会把机器栈吃掉（实测退出码 0xC00000FD）。
    三、字符串块是叶子。它的载荷是码元，不是 Value，标记循环要按种类跳过 ——
        否则会把码元当 Value 去读，那是一种「看起来像指针的整数」。
    四、自适应阈值。活数据不肯降到阈值以下时，把阈值抬到活数据的一点二倍 ——
        否则每次函数调用都会收一次，程序以收集为主（实测 29 秒还没编完）。
        两倍那一版太松，峰值会被「多一份活数据」顶起来；
        而再收紧也没有用：剩下的峰值就是真实的活数据。

  默认不开：HMYR_GC=1 打开，阈值默认 32 MB（HMYR_GC_BYTES 改），
  HMYR_GC_LOG=1 每次收集打一行（开始、结束、放掉多少、新阈值）。

  实测（同一份自编译，六份源码，同一台机器）：
    不开回收  3000 MB  1.7 秒
    开回收     967 MB  2.1 秒
  开回收结束时活数据 150 MB —— 收不掉的九百兆里，活的只有一百五十兆，
  其余是「六份产物同时在手」那一刻的真实占用。
  再往下压要动编译器的数据结构（编完一份就写盘、或者分段重启），
  那不是回收的事。

  产物都是 43619 字节，与种子逐字节相同 —— 回收不改变答案，只改变账。

  板子上不编这一块：地址表在桌面要几兆，而板子的堆只有几十千字节；
  那一台本来也遇不到三吉字节级的自编译。ARM 那一支给的是空实现。
